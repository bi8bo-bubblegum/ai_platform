# 21 · 底座能力全景与裁定

> 前提：**契约强度已定 —— 弱契约**（2026-10-10 用户拍板）。
> 底座给 Bean，业务自己装配；底座不代劳装配，也不长成框架。
>
> 这一篇回答：**除了已知的三个缺口，还有哪些能力该进底座、哪些不该。**

---

## 0. 弱契约已定，意味着底座的验收标准变了

| | 强契约的验收标准 | **弱契约的验收标准** |
|---|---|---|
| 底座交付什么 | 框架 + 注解 | **Bean + 文档** |
| 质量体现在 | 封装得多严实 | **接入时要知道的东西有多收敛** |
| 防漏靠什么 | 框架替你挂 | **结构测试 + 清单文档** |

**一句话**：弱契约下，"底座搭好"= 一个新助手接入时，**要写的代码和要踩的坑，都收敛到一份清单里**。

三个直接后果：

1. **文档是底座的一部分，不是副产品。** 交付单 10（新助手接入清单）在弱契约下的地位，等同于强契约里的自动装配类。
2. **每个装配点都必须有结构测试兜底。** 这是弱契约的**安全带** —— 没有它，弱契约从"灵活"变成"危险"。
3. **`AssistantWiringTest` 不是测试，是契约的一部分。** 它和文档一起，构成"漏挂会怎样"的答案。

## 1. 扫描框架：一次 AI 调用要回答的 12 个问题

用"问题清单"而不是"能力清单"来扫，是为了**保证不遗漏** —— 每个问题都对应一个必须处理的东西。

| # | 问题 | 现状 | 裁定 |
|---|---|---|---|
| 1 | 谁在调？ | `AiUserContext` 1 维（只有 userId） | **底座 · 现在做** |
| 2 | 用什么模型？ | chat / streaming / embedding 三类注册器 | 底座 · 已完成 |
| 3 | 说什么？ | 写死在 `@SystemMessage` | **不进底座** |
| 4 | 记得什么？ | 会话记忆 + 长期记忆 | 底座 · 已完成 |
| 5 | 能做什么？ | MCP 客户端与装配就绪，未接到助手 | **底座 · 现在做** |
| 6 | 知道什么？ | 无 | **底座 · 时机未到** |
| 7 | 花了多少？ | token 有，成本没有 | 底座 · **补字段现在做**，成本计算时机未到 |
| 8 | 好不好？ | 无 | **不进底座** |
| 9 | 能不能用？ | 网关限流 | **不进底座**（网关负责） |
| 10 | 安不安全？ | 无 | **底座（接入点）· 时机未到** |
| 11 | 怎么配？ | 六组配置各自 Properties | **底座（约定）· 时机未到** |
| 12 | 怎么找问题？ | 只**接收** traceId，不产生 | **底座 · 现在做** |

## 2. 逐项裁定的理由

### 2.1 进底座 · 现在做

#### ① 上下文五维（见交付单 20 的 §3）

`AiUserContext` → `AiCallContext`，从 1 维扩到 5 维。

**并且把"traceId 的产生"一起做掉** —— 见 §3.1。

#### ② 依赖边界（见交付单 20 的 §2）

pom 标 `<optional>`。10 分钟，零风险。

#### ③ 台账补四字段（见交付单 20 的 §4）

`success` / `latencyMs` / `traceId` / `errorType`。

#### ④ 工具闭环

现状是"装配了 `McpToolProvider` Bean，但零消费者"。底座该做的是**把"取工具"这件事标准化**：

```java
public interface ToolProvider {
    /** 供 AiServices.builder().toolProvider(...) 用；没工具时返回空实现（不该返回 null） */
    dev.langchain4j.service.tool.ToolProvider asLangChain4j();
    /** 当前挂了哪些 MCP 服务，给健康检查和运维页 */
    java.util.Set<String> connectedServers();
}
```

**关键设计：不要返回 null。** 现在业务侧要写 `ObjectProvider<McpToolProvider>` + `getIfAvailable()` + null 判断——这是"配置化能力"的通用痛点。门面里用空实现（`ToolProvider` 返回一个不含工具的实例），业务侧就永远是"直接挂"，不用判空。

#### ⑤ traceId 的产生与注入（并入 ①）

见 §3.1。

### 2.2 进底座 · 时机未到

| 候选 | 为什么算底座 | 为什么现在不做 | **触发条件** |
|---|---|---|---|
| **通用知识库检索** | 普遍（所有助手都可能要"问文档"）+ 无业务语义 + 有复杂度（切分/索引/召回） | 没有文档数据，做了无法验证 | 出现第一个"问文档"场景 |
| **token → 成本计算** | 普遍 + 无业务语义 + 中等复杂度（价格表 + 聚合） | 没有被问过"花了多少" | **第一次被问"这个月花了多少"** |
| **用户配额** | 普遍 + 无业务语义（技术上是计数+判断）+ 有复杂度（并发/窗口） | 没有真实用户量，阈值只能拍脑袋 | 接真实用户且有超额风险 |
| **审核接入点** | 机制通用（和工具同类，见 §3.4） | 没有合规要求 | 有合规要求 / 内容对外 |
| **配置分层约定** | 平台级约定，影响所有服务 | 还没上共享配置 | **上 Nacos 共享 dataId 之前**（必做） |

### 2.3 不进底座 —— 已由网关负责（写在这里，避免以后重议）

| 能力 | 为什么 |
|---|---|
| **限流** | `ai-gateway` 已在做。MEMORY 里已明确"AI-Common 不做限流" |
| **模型降级与切换** | 依赖"路由"，而"不做路由"是既有决定。降级是网关的事 |
| **凭证托管** | 同上。AI-Common 是"零基础设施依赖"的 |

> **判断依据**：这三件事的**共同特征是"需要看到全部调用"** —— 只有网关在那个位置。
> 底座是进程内的，看不到别的服务在干什么。

### 2.4 不进底座 —— 不是技术能力（同样写下来，避免重议）

| 能力 | 为什么 | 它该在哪 |
|---|---|---|
| **提示词内容** | 难点在"写什么"，那是业务知识；"怎么存"（模板+变量+版本）复杂度不足以成模块 | 助手的 `@SystemMessage`，或用配置项 |
| **评测基准** | "什么算好"是业务判断；且没有真实问答就没有基准 | 将来单独的评测工程，不是底座 |
| **内容策略** | 同提示词 —— 是策略问题不是技术问题 | 审核服务 / 业务配置 |

> **提示词的边界**：如果出现**第二个助手开始复制第一份的提示词片段**（比如"回答不要空话"），
> 那说明出现了"共用片段"的需求 —— **那时再考虑抽，且大概率是一个配置项而不是一个模块。**

## 3. 四个之前没讨论过的发现

### 3.1 `traceId` 只有"接收"，没有"产生"

现状：`AiCallContext`（将来）会从 header 和 MDC 读 `traceId`，但**没有任何组件生成它**。

后果：上游不给 → 永远是 null → 台账里的 `trace_id` 列全空 → **"和日志串起来"这个目的完全落空**。

**底座该做的**：

```java
/** 入口处：没有就生成，并且写进 MDC —— 写进 MDC 之后日志框架自动带上，一行 log 代码都不用改 */
private String resolveTraceId(HttpServletRequest request) {
    String traceId = MDC.get("traceId");
    if (traceId == null || traceId.isBlank()) {
        traceId = request.getHeader(traceHeader);
    }
    if (traceId == null || traceId.isBlank()) {
        traceId = generateTraceId();          // 入口没有就自己造
    }
    MDC.put("traceId", traceId);              // ← 关键：这一步让日志自动带链路 id
    return traceId;
}
```

**为什么"写进 MDC"是重点**：不写进去，你只能在台账里看到 traceId；写进去之后，**那一次请求打的所有日志都自动带上它** —— 排查时直接从台账复制 traceId，去日志里搜。

配套：`logback` 的 pattern 里加 `[%X{traceId}]`。

> 这也顺带解释了为什么"现在日志里链路全是 null" —— 不是忘了传，是**没人产生它**。

### 3.2 token ≠ 钱：底座缺一张单价表

`ai_token_usage` 有 token，但**算不出成本** —— 缺"哪个模型、什么时候、多少钱/千 token"这份数据。

而"这个月 AI 花了多少"**一定会被问**。现在是你好奇，接真实业务后是财务好奇。

**最小实现**：一张表 + 一个聚合查询。

```sql
CREATE TABLE ai_model_price (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    model_name      VARCHAR(128)  NOT NULL COMMENT '物理模型名，对应 token 台账的 model_name',
    input_price     DECIMAL(12,6) NOT NULL COMMENT '每千 token 输入单价',
    output_price    DECIMAL(12,6) NOT NULL COMMENT '每千 token 输出单价',
    currency        VARCHAR(8)    NOT NULL DEFAULT 'CNY',
    effective_from  DATETIME      NOT NULL COMMENT '生效起始',
    effective_to    DATETIME      NULL     COMMENT 'NULL = 至今',
    UNIQUE KEY uk_model_period (model_name, effective_from)
) ENGINE=InnoDB COMMENT='模型单价，按时间版本化';
```

**`effective_from` / `effective_to` 不是洁癖**：

> 模型调价了，**历史账单不能跟着变**。没有时间维度的价格表，
> 每次调价都会让历史账目被重算 —— 而账单是会被对账的。

**聚合查询（按月）**：

```sql
SELECT u.service_name,
       SUM(u.input_tokens  * p.input_price  / 1000) AS input_cost,
       SUM(u.output_tokens * p.output_price / 1000) AS output_cost
FROM ai_token_usage u
JOIN ai_model_price p
  ON p.model_name = u.model_name
 AND u.occurred_at >= p.effective_from
 AND (p.effective_to IS NULL OR u.occurred_at < p.effective_to)
WHERE u.occurred_at >= ? AND u.occurred_at < ?
  AND u.success = 1
GROUP BY u.service_name;
```

> **注意 `AND u.success = 1`** —— 失败的调用不该计费（或者该按实际用量计，取决于网关口径）。
> 这条**依赖于 §2.1 ③ 那个 `success` 字段** —— 没有它这个查询都写不出来。

### 3.3 配置的分层约定现在没有，而它必须在"共享配置"之前定

现状：六组配置散在各自 `@ConfigurationProperties` 里，**没有任何"哪些该共享、哪些该私有"的约定**。

一旦上 Nacos 共享 dataId，**必须先回答这个问题**。举例：

| 配置项 | 该共享还是私有？ | 理由 |
|---|---|---|
| `ai.chat.endpoints`（模型地址与凭证） | **平台级共享** | 所有服务连同一个网关 |
| `ai.embed.dimensions` | **平台级共享** | 向量空间必须全局一致，否则跨服务检索不可用 |
| `ai.memory.user.min-score` | **平台级共享** | 用户在不同助手的记忆体验要一致 |
| `ai.memory.assistant-id` | 服务级私有 | 每个助手不同 |
| `ai.metrics.service-name` | 服务级私有 | 同上 |
| `server.port` | 服务级私有 | 明显 |

**这个约定定错了，后面改要动所有服务的配置文件。** 而且它是**文档级产出，不是代码** —— 现在写一页，比以后改十个 yml 便宜。

**建议的判据**（一行）：

> **问"这条配置不同步会导致跨服务行为不一致吗？" —— 会，就是平台级。**

### 3.4 审核和工具是同一类东西

LangChain4j 的 `.contentModerator(...)` 和 `.toolProvider(...)` 都是 `AiServices` 的装配点。

**底座该做的是提供统一的接入方式，不是实现审核**（用什么审核服务、什么阈值，是合规决定不是技术决定）。

所以它俩可以共用同一个抽象思路：

```
机制进底座，策略归业务。
底座管"怎么接进来"，业务管"接哪个、什么阈值"。
```

**这条也是弱契约下的通用模式**：底座的每个"接入点"都长这样 ——

| 接入点 | 底座提供 | 业务提供 |
|---|---|---|
| 记忆 | `ChatMemoryProvider` Bean | 要不要挂 |
| 检索 | `RetrievalAugmentor` Bean | 挂哪些 retriever |
| 工具 | `ToolProvider` 门面 | 挂哪些工具 |
| 审核 | `ContentModerator` 门面（将来） | 用什么审核服务、阈值 |

**看到规律了吗**：底座的活是**"把可选项变成可注入的 Bean，并且保证不挂也不会炸"**。

## 4. 一个刻意不做的事，以及它的代价

**留痕**：`ai_token_usage` 只记 token，**不记 prompt / response 内容**。

这意味着你**无法事后回放** "这个回答为什么不好" —— 也做不了事后评测。

**判定：不做。** 理由两条：内容落库有隐私问题（用户对话可能含敏感信息）；存储成本远高于 token 数（一次对话几 KB vs 几十字节）。

**但要知道代价**：出问题时你只能看"当时花了多少 token"，看不到"当时问了什么"。
将来真需要时的做法是**采样留痕**（比如 1% + 全部失败请求），而不是全量。

**时机未到的五项不进这个列表** —— 它们的触发条件都写在上面的表里了。

**特别注意"配置分层约定"**：它没有代码，但**上 Nacos 之前必须做**。建议现在就先写一页，
因为它不需要等任何前置条件。

## 6. 一句话总结

> **底座的活是"把可选项变成可注入的 Bean，并保证不挂也不会炸"** ——
> 机制进底座，策略归业务。
>
> 按这个标准，剩下要做的是四件事：**依赖边界、上下文（含 traceId 产生）、台账补字段、工具闭环**。
> 其余的不是"不该做"，是"没有触发条件" —— 每个都写了明确的触发时机。

**弱契约下，还有一样东西和代码同等重要**：那份接入清单，以及钉住三个静默失效开关的结构测试。
**它们是"底座不替你做装配"这个选择的代价，也是这个选择能成立的前提。**
