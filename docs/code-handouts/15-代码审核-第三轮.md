# 二、🔴 P0-5 流式调用的台账，`user_id` 必然是 `anonymous`

**这条是修好上一轮 P0-2（给流式挂 listener）之后才会浮现的下一个坑。换句话说：
你现在就算把 listener 挂上，流式记录还是会以 `anonymous` 入库。**

`TokenUsageListener` 取用户是这么取的：

```java
public void onResponse(ChatModelResponseContext responseContext) {
    ...
    String userId = AiUserContext.get();      // ← ThreadLocal
```

而 `AiUserContext` 是 `ThreadLocal`，唯一写它的地方是 `AiUserContextInterceptor.preHandle()`。
问题出在**线程**上：

| 场景 | `onResponse` 在哪个线程执行 | 读得到 userId 吗 |
|---|---|---|
| 同步调用（`ask()` / 阻塞版 `chat()`） | **调用线程**（就是处理请求的线程） | ✅ 读得到 |
| **流式调用**（`TokenStream`，也就是主场景） | **模型自己的 I/O 线程**（OkHttp 回调线程） | ❌ **必然为 null** |

**决定性的一条是「线程不同」，不是 `afterCompletion` 的时机。** 哪怕 ThreadLocal 一直没清，
流式回调跑在 OkHttp 的线程上，也读不到请求线程里的那个值。所以：

```
流式对话 → 台账 user_id = anonymous
```

而流式是你唯一的主场景，所以实际结果是：**这张台账表里的用户维度基本是废的**，
只能按 `service_name` + `profile` 统计。

### 为什么这个坑很难自己发现

如果你先测一次**同步**调用（`assistant.ask(...)`），台账里 `user_id` 是对的 —— 于是你会认为"计量没问题"。
只有流式才会露馅，而流式的失败表现是"这一列的值为 anonymous"，不报错、不告警。

### 修法：三个选项，我推荐第二个

**选项 A：把 userId 通过 `customHeaders` 带在模型请求头上，让 ai-gateway 记录。**
这是 04 号交付单里就得出过的结论（"网关才是 token 计量的天然位置"）。但需要网关配合记录这个头。

**选项 B（推荐）：接受 SDK 层拿不到用户维度，明确分工。**

| 谁 | 记什么 |
|---|---|
| **ai-gateway** | token 数、模型耗时、成功率 —— **权威数据**，并支持按 `X-User-Id` 头维度 |
| **AI-Common 的 listener** | `service_name` / `profile` / `model_name` / 失败原因 |

然后把 `TokenUsageListener` 里那句 `AiUserContext.get()` **删掉**，`user_id` 一律写 `anonymous`，
并在类注释里写明"流式场景下 ThreadLocal 不可达，用户维度请查网关"。

> **为什么要删而不是留着**：留着它会产生"有时对、有时 anonymous"的混合数据 ——
> 比"全是 anonymous"更糟，因为你不知道该信哪些行。**一致地缺失，好过随机地正确。**

**选项 C：给 `ChatModel` 套一层装饰器，在 `doChat` 里把 userId 转存到别处。**
**不可行** —— listener 的回调在别的线程上，任何 ThreadLocal 都传不过去；
而 `ChatRequest` 没有 `attributes()` 之类的透传通道。这条路是死的，不用试。

### 顺带一个发现

`AiUserContext` 里其实**已经写了跨线程的包装器**：

```java
public static Runnable wrap(Runnable task){ ... }
public static <T> Callable<T> wrap(Callable<T> task){ ... }
```

说明当初就意识到过跨线程问题。但**全项目零调用者** —— 而且它救不了这个场景：
`wrap` 只能把上下文传给"从当前线程 fork 出去的任务"（比如往线程池丢任务），
**传不到模型内部的 I/O 线程**。

> 也就是说：这两个方法是**为另一类问题准备的**（比如 `UserMemoryRecorder.recordAsync` 那种
> "丢进 TaskExecutor"的场景 —— 而那个场景恰好不需要它，因为它从 memoryId 里解析 userId）。
> 所以它们现在是死代码。留着无害，但别指望它们能救 P0-5。

# 三、🟠 P1

## P1-7 `RedisSessionMemoryStore.getMessages` 反序列化失败没有降级

```java
@Override
public List<ChatMessage> getMessages(Object memoryId) {
    String json = redis.opsForValue().get(keyOf(memoryId));
    if(json == null || json.isBlank()){
        return new ArrayList<>();
    }
    return new ArrayList<>(ChatMessageDeserializer.messagesFromJson(json));   // ← 脏 JSON 会抛
}
```

`messagesFromJson` 是纯 JSON 反序列化，**脏数据一律抛异常**。什么情况会脏：

- 上次改 Redis key 格式 / 序列化格式之后残留的旧值
- 有人手工往 Redis 里写过东西（排查问题时很常见）
- 将来升级 LangChain4j，序列化格式变了

**后果特别难看**：`getMessages` 在**每一轮对话**都会被调（`SummarizingChatMemory.messages()`）。
一旦某个 key 脏了，那个会话的用户**每一轮都抛异常、完全无法对话**，而且没法自愈 ——
除非人工去 Redis 删 key。

这和 P1-3（维度过滤）是同一类风险的另一个实例：**脏数据不该让主流程失败。**

### 修法

```java
@Override
public List<ChatMessage> getMessages(Object memoryId) {
    String key = keyOf(memoryId);
    String json = redis.opsForValue().get(key);
    if(json == null || json.isBlank()){
        return new ArrayList<>();
    }
    try {
        return new ArrayList<>(ChatMessageDeserializer.messagesFromJson(json));
    } catch (Exception e) {
        // 脏数据（格式变过 / 手工写入 / 版本不兼容）不能让它把整轮对话打死 ——
        // 这个方法每轮都会被调用，抛出去等于这个会话永久不可用，且无法自愈。
        // 清掉这个 key，让会话从"空历史"重新开始：丢一次上下文，比彻底不能用好。
        log.error("会话历史反序列化失败，已清空该会话: key={}", key, e);
        redis.delete(key);
        return new ArrayList<>();
    }
}
```

> 这类"反序列化 + 清掉脏 key"的模式在缓存里是标准做法。
> 配上 `@Slf4j`（类上已经有，只是现在没在用日志）。

## P1-8 `ai.embed.timeout: 60s` 对请求路径上的检索来说太长

这个值是从**对话模型**那边抄过来的，但 embedding 的用途完全不同：

| 用途 | 在哪条路径上 | 超时设 60s 的后果 |
|---|---|---|
| 写入（抽取后算向量） | 异步线程 | 无影响 |
| **检索（每轮对话召回事实）** | **请求路径，同步** | **embedding 服务 hang 住 → 用户干等 60 秒** |

`MemoryRecallService.recall()` 是在 `AiServices` **调主模型之前**同步执行的：

```
用户提问
  → UserMemoryContentRetriever.retrieve()
    → embeddingModel.embed(query)          ← 这里可能卡 60 秒
    → 全量向量比对
  → 主模型开始生成
```

`MemoryRecallService` 对**抛异常**做了降级（catch 住、返回空列表）✓ 但**对"不响应"没有保护** ——
连接建立了但不返回数据，只会一直等到 60 秒超时。

**embedding 调用正常在 1–2 秒内返回。** 把超时设成 60 秒，等于"出了故障就陪用户等一分钟"。

### 修法（两步，都很便宜）

**第一步（现在就做）**：把配置调小，并在注释里写清理由。

```yaml
ai:
  embed:
    # ⚠️ 这个值同时管【写入】和【检索】。检索在对话的请求路径上同步执行，
    #    所以它不该按"能容忍多久"来定，而该按"超过多久就不值得等"来定。
    #    embedding 正常 1-2 秒返回；5 秒还没回来，直接放弃长期记忆、正常回答更好。
    timeout: 5s
```

**第二步（可选，等真需要区分时再做）**：给检索单独一个短超时的 `EmbeddingModel`
（多一个 `ai.embed.endpoints` 档位，`MemoryRecallService` 用 `get("recall")`）。
**现在不要做** —— 两套超时的复杂度换不来多少收益，除非你观测到 embedding 经常慢。

## P1-9 `userId` 由调用方任意指定 → 越权读取他人记忆

```java
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestParam String userId,
                         @RequestParam String sessionId,
                         @RequestParam String message) {
```

`userId` 是**请求参数**，没有任何校验。所以：

```bash
# 换个 userId 就能读到别人的会话历史和长期记忆
curl -N "http://host:8081/chat/stream?userId=别人&sessionId=任意&message=你还记得我是谁吗"
```

而长期记忆的设计是**用户级**的（跨助手共享），所以拿到 userId 就等于拿到那个人的全部画像。

**现在只有一个内部服务、自己调自己，风险可控。** 但这是**上生产前必须解决**的一项，
而且它和交付单 10 里那个「`userId` 两套来源」是同一族问题 —— 如果采纳了那条建议的
**选项 B**（在 Controller 里 `AiUserContext.set(userId)` 让台账和记忆用同一个来源），
**不会**解决这个安全问题：它只是让两处一致，`userId` 本身仍然是请求参数。

### 修法方向

`userId` 必须来自**认证后的上下文**，而不是请求参数：

```java
// 从认证信息里取，取不到就拒绝 —— 而不是信任调用方传的值
String userId = AiUserContext.get();       // 由网关注入 X-User-Id，或 Spring Security 的 SecurityContext
if (userId == null || AiUserContext.ANONYMOUS.equals(userId)) {
    throw new ResponseStatusException(HttpStatus.UNAUTHORIZED, "未认证");
}
```

> 前提是**网关层做了鉴权并覆写 `X-User-Id`**（不能让客户端自己传这个头）。
> 这条要和阿特（网关侧）对齐 —— 属于跨团队的约定，不是代码能单方面解决的。
> 所以我把它列成 P1 而不是 P0：**风险真实，但需要架构层面的配合。**

# 四、🟡 P2

## 4.1 `UserMemoryRecorder` 逐条算向量 —— 5 条事实 = 5 次 HTTP

```java
for(String fact: facts){
    float[] vector = embed(fact);          // ← 每条一次 embedding 调用
    if(isDuplicate(vector, existing)) continue;
    ...
}
```

抽 5 条事实就是 **5 次串行的 embedding HTTP 请求**。每次 100–300 ms，加起来 **0.5–1.5 秒**
（在异步线程上，不阻塞用户，但占着线程、吃 5 倍的 API 调用次数）。

LangChain4j 的 `EmbeddingModel` 支持批量：

```java
// 一次 HTTP 拿回全部向量
List<TextSegment> segments = facts.stream().map(TextSegment::from).toList();
List<Embedding> embeddings = embeddingModel.embedAll(segments).content();
```

> **为什么是 5 倍而不是"省一点"**：embedding API 通常按**请求数**计费和限流，
> 不是按 token。所以这不是"快一点"的问题，是"调用次数差 5 倍"的问题。
>
> **要不要现在改**：如果你打算给 `ai.embed` 配限流配额，那**值得现在改**；
> 否则可以等有真实压力再做。改动本身不大（循环里换个取向量的来源）。

## 4.2 抽取只传了本轮的两条消息

```java
// ChatStreamController
recorder.recordAsync(memoryId, List.of(
        UserMessage.from(message),
        AiMessage.from(response.aiMessage().text())));
```

而 `UserMemoryRecorder.recordAsync(String memoryId, List<ChatMessage> recentTurns)` 的参数名叫
**`recentTurns`（最近几轮）**，实际只给了**一轮**。

对"我是财务部的"这类**自包含**的事实没影响 ✓ 但抽不出**依赖上下文**的：

```
用户：上周那个报表再发我一份
助手：好的，已经按你上次说的格式发了
用户：就按这个来，以后都这样
```

单看最后一句，抽不出任何东西。带着前三句，才可能抽出"用户偏好每周报表用固定格式"。

**修法**：传最近 4–6 条而不是 2 条。数据源可以是
`chatMemoryProvider.get(memoryId).messages()`（注意它会把摘要作为第一条 `SystemMessage` 带上，
抽取提示词里得说明"忽略系统消息"）。

> **权衡**：传得越多，提示词越长、抽取越慢。**别超过 6 条** —— 事实抽取是"这一轮说了什么"，
> 不是"整段对话在讲什么"。

## 4.3 `RedisSessionSummaryStore.save` 不判空

```java
public void save(Object memoryId, String summary) {
    redis.opsForValue().set(keyOf(memoryId), summary, ttl);   // summary 为 null 时抛 IllegalArgumentException
}
```

Spring Data Redis 不允许 `null` value。当前调用方（`LlmConversationSummarizer`）判了空白 ✓
所以不会触发。但契约上应该有守卫 —— 这是个**会在别人手里炸**的方法：

```java
public void save(Object memoryId, String summary) {
    if (summary == null || summary.isBlank()) {
        // 空摘要没有意义，且会被 Redis 拒绝。直接删掉旧值，
        // 让语义变成"这个会话没有摘要"，而不是留一个过期摘要挂着
        delete(memoryId);
        return;
    }
    redis.opsForValue().set(keyOf(memoryId), summary, ttl);
}
```

> 注意这里是"删掉旧值"而不是"直接 return" —— 后者会留下上一轮的摘要，
> 而调用方以为已经写入了新的。

## 4.4 三个 pom 的依赖声明问题

| 模块 | 问题 | 修法 |
|---|---|---|
| `ai-common` | `spring-boot-starter-web` **没标 optional** | 加 `<optional>true</optional>` |
| `ai-common` | `spring-boot-configuration-processor` 没标 optional | 加 `<optional>true</optional>`（惯例，它只在编译期用） |
| `ai-memory` | **缺** `spring-boot-configuration-processor` | 加上 |

**第一条**为什么重要：`ai-common` 需要 web 来编译 `AiUserContextInterceptor`（`HandlerInterceptor`），
所以依赖本身不能删 —— 但**标上 optional 之后，它不再传递给使用者**。
区别是：

- 现在：一个**非 web** 的服务引 `ai-memory` → 被拖上整个 Tomcat + Spring MVC
- 标了之后：只有自己引 web starter 的服务才有 web 栈

**第三条**影响的是开发体验：`ai-common` 有 configuration-processor，所以写 `ai.chat.*` 时 IDE 有补全
和校验；而 `ai-memory` 没有，所以 `ai.memory.*` 全是**没有提示的裸字符串** ——
`extract-profile` 写错成 `extract-profiles` 时 IDE 一言不发。

> 一个具体的收益：加了处理器之后，`ai.memory.session.summary-ttl` 这类名字在 IDE 里可补全，
> 配合 `@DefaultValue` 还能看到默认值。这是配置项一多就回不去的体验。

## 4.5 `AiUserContextInterceptor` 一个类干两件事

```java
public class AiUserContextInterceptor implements HandlerInterceptor, WebMvcConfigurer {

    @Override public void addInterceptors(InterceptorRegistry registry){
        registry.addInterceptor(this).addPathPatterns("/**");   // 把自己注册进自己
    }
}
```

拦截器逻辑和 MVC 配置合在一个类里。能工作（Spring 会自动收集所有 `WebMvcConfigurer` Bean），
但读代码的人要在同一个文件里切换两种角色，而且**将来加第二个拦截器时无处可放**。

建议拆成两个类（`AiUserContextInterceptor` 只管拦截，`AiWebConfig implements WebMvcConfigurer` 负责注册）。
**不是必须** —— 属于"顺手改"级别。

## 4.6 `AiUserContext.wrap` / `open` 是死代码

```java
public static Runnable wrap(Runnable task){ ... }
public static <T> Callable<T> wrap(Callable<T> task){ ... }
public static Scope open(String userId) { ... }
```

实测**全项目零调用者**。它们是为"把上下文传给线程池任务"准备的，但当前唯一往线程池丢任务的
地方（`UserMemoryRecorder.recordAsync`）不需要它 —— 因为它从 `memoryId` 里解析 userId，
而不是从 ThreadLocal 读。

**留着无害**（是正确的工具，只是还没到用它的时候），但要知道**它救不了 P0-5**：
模型 I/O 线程不是从请求线程 fork 出来的，`wrap` 传不过去。

## 4.7 `MemoryRecallService` 每轮都对全量向量做余弦计算

```java
List<UserMemory> all = store.findByUserId(userId, config.maxFactsPerUser());
return all.stream()
        .filter(m -> isValid(m, queryVector))
        .map(m -> Map.entry(m, CosineSimilarity.between(queryVector, m.getEmbedding())))
        ...
```

500 条 × 1536 维 ≈ 77 万次乘加，几十毫秒量级 —— **可以接受**。
但它在**请求路径**上（每轮都跑），和 4.8 的 `embed` 调用加起来是首字延迟的一部分。

**现在不用改**，只是提醒它和 P1-8 是同一个"请求路径成本"议题。

## 4.8 `MemoryRecallService` 的降级是"静默"的

```java
} catch (Exception e){
    log.error("查询向量化失败，本次跳过长期记忆检索, userId={}", userId, e);
    return List.of();
}
```

降级本身是对的（没有长期记忆也要能回答）✓ 但**用户和调用方都感知不到"这轮没有长期记忆"**。

如果 `ai.embed` 服务挂了三天，你会看到三天的 error 日志，但**助手会用"失忆"的方式回答**，

方便告警规则匹配）—— 现在日志里是"查询向量化失败"，和真正的调用失败混在一起。

# 五、⚪ 两个观察

## 5.1 `SummarizingChatMemory.add()` 的 read-modify-write 竞态

```java
List<ChatMessage> all = new ArrayList<>(store.getMessages(id));   // ① 读
all.addAll(incoming);
int overflow = all.size() - maxMessages;
if(overflow > 0){
    List<ChatMessage> evicted = new ArrayList<>(all.subList(0, overflow));
    summarizer.append(id, evicted);        // ② 一次 LLM 调用，几秒
    all = new ArrayList<>(all.subList(overflow, all.size()));
}
store.updateMessages(id, all);             // ③ 写回
```

**读和写之间没有任何锁，而且中间夹着一次几秒的 LLM 调用（摘要生成）。**
如果同一个 `memoryId` 有两个并发请求，后写的会覆盖前写的 —— 丢消息。

触发条件（都不罕见）：
- 用户快速双击发送
- 前端网络重试 / 双发
- 同一个会话开了两个浏览器标签

**为什么一期建议不改**：
- 正常前端一次只能发一条，单实例部署下不会触发
- 真要修需要**分布式锁**（多实例下进程内锁无效），而 AI-Memory 还没拆成服务
- 而且 LangChain4j 的 `ChatMemory` 契约本身**不承诺并发安全** —— 这不是我们的实现缺陷，
  是没人为这个契约提供并发保证

**建议动作：加一段注释**，把这个已知竞态和触发条件写清楚，让后来人知道"丢掉一条消息"
可能是这里而不是别处：

```java
// ⚠️ 已知竞态：这里是 read-modify-write，且 ② 处有一次几秒的 LLM 调用。
//    同一 memoryId 的并发请求会互相覆盖（后写的丢掉前一条）。
//    触发条件：同一 sessionId 并发提交（双击、重试、多标签页）。
//    为什么没修：多实例部署下进程内锁无效，需要分布式锁；
//    而 LangChain4j 的 ChatMemory 契约本身不承诺并发安全。
//    真要修的话，落点在 SessionMemoryStore 层做 per-key 的原子追加。
```

## 5.2 `SessionRedisKey` 的 sha256 是无盐、截断到 8 字节

交付单 10 里已经记过「上生产前要补盐」，这里补上**量化**：

- 输入如果是**手机号**（约 10¹¹ 个候选），攻击者拿到 Redis key 后可以暴力枚举 → 反推 userId
- 8 字节截断让碰撞空间只有 2⁶⁴，但**对枚举攻击没有帮助**（枚举不需要碰撞）

**缓解**：盐放在配置里（不进 key），`sha256(salt + userId)`。
**但它只提高枚举成本，不能根本解决** —— 真要防，得让 userId 本身在进入 Redis 前就不可逆
（比如用内部代理 ID 而不是手机号）。

> 这一条的优先级取决于：**谁会看到 Redis key**。运维能看到、RDB 备份能被下载 ——
> 所以它是"内部人员可见性"问题，不是"外网可攻破"问题。按合规要求评估。
