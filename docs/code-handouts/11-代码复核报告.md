## 二、P0 · 两条不改就跑不对

### P0-1 `SessionKey` 少了紧凑构造器 → 校验逻辑**从未被执行**

**现状**：`requireNoSeparator(...)` 方法写了，但 record 里**没有紧凑构造器**去调它。

**实测证据**（用你编译好的 class 直接跑的）：

```
parse("u1")             => 抛 IllegalArgumentException      ← 这个是对的
of("a::b","u1","s1")    => SessionKey[assistantId=a::b, userId=u1, sessionId=s1]   ← 不该通过
of("a","u1", null)      => SessionKey[assistantId=a, userId=u1, sessionId=null]    ← 不该通过
```

**后果**：
- `assistantId` 里带 `::` 时不报错 → `toMemoryId()` 拼出 `a::b::u1::s1` → `parse` 时把 `a` 当助手、`b` 当用户 —— **静默错位，比抛异常难查十倍**
- `sessionId` 为 null 时拼出 `a::u1::null` → 看着正常、**永远查不到东西**
- `requireNoSeparator` 是死方法（IDE 会标灰，但容易以为是"预留的"）

**改法**（在 `SessionKey` 里加这一段）：

```java
public record SessionKey(String assistantId, String userId, String sessionId) {

    private static final String SEPARATOR = "::";

    /**
     * 紧凑构造器 —— 没有它，下面那个 requireNoSeparator 就是死方法。
     * 把"格式约定"从注释变成"构造时就炸"。
     */
    public SessionKey {
        requireNoSeparator(assistantId, "assistantId");
        requireNoSeparator(userId, "userId");
        // sessionId 允许含 ::（它是最后一段，解析时不歧义），但不能为空
        if (sessionId == null || sessionId.isBlank()) {
            throw new IllegalArgumentException("sessionId 不能为空");
        }
    }

    // ... 其余不动
}
```

### P0-2 `ChatAssistantTest` 的 memoryId 是裸的 `"u1"` → 必抛异常

**现状**：

```java
@SpringBootTest
class ChatAssistantTest {
    @Resource private ChatAssistant chatAssistant;

    @Test void chat() { System.out.println(chatAssistant.chat("u1", "我是小明，你记住")); }
    @Test void ask()  { System.out.println(chatAssistant.ask("u1", "我是谁")); }
}
```

**三个问题**：

1. **`memoryId = "u1"` 会直接抛异常。** 调用链我完整走了一遍：
   `chat("u1", ...)` → `ChatMemoryProvider.get("u1")` → `SummarizingChatMemory` →
   `store.getMessages("u1")` → `RedisSessionMemoryStore.keyOf("u1")` → `SessionRedisKey.of(...)` →
   `SessionKey.parse("u1")` → **`first = -1` → 抛 `IllegalArgumentException`**。上面那条实测已经证明了。
2. **两个测试都用 `"u1"`，且 `ask` 依赖 `chat` 先跑。** JUnit 不保证方法顺序 —— 就算格式改对了，这个测试也是"有时过有时不过"。
3. **`@SpringBootTest` 不是单测**：它要真 MySQL + Redis + AI 网关。CI 里必然失败。而且两个方法只有 `println`，**零断言** —— 跑过等于没跑。

**改法 A（推荐）：拆成两半。**

**(1) 单元测试**——不联网、不启 Spring，断言"记忆真的接上了"：

## 三、P1 · 五条，成本低收益明确

### P1-1 `UserMemoryRecorder` 每条事实算**两次**向量

**现状**：

```java
for (String fact : facts) {
    if (isDuplicate(fact, existing)) {   // ← 里面 embed(fact) 一次
        continue;
    }
    float[] vector = embed(fact);        // ← 又 embed 一次
```

`isDuplicate(String fact, ...)` 内部自己调了一次 embedding。**抽取 5 条事实 = 10 次 embedding 调用**，
翻倍的是接口延迟和钱，而且这个开销在一个本来就要"快"的异步路径上。

**改法**——把向量算一次、传进去：

```java
for (String fact : facts) {
    float[] vector = embed(fact);              // 只算这一次
    if (isDuplicate(vector, existing)) {       // 传向量，不传字符串
        log.debug("事实重复，跳过: {}", fact);
        continue;
    }
    UserMemory memory = UserMemory.of(userId, fact, sessionId);
    memory.setEmbedding(vector);
    userMemoryStore.insert(memory);
    existing.add(0, memory);
    inserted++;
}

private boolean isDuplicate(float[] candidate, List<UserMemory> existing) {
    if (existing.isEmpty()) {
        return false;
    }
    return existing.stream()
            .filter(m -> m.getEmbedding() != null && m.getEmbedding().length > 0)
            .anyMatch(m -> CosineSimilarity.between(candidate, m.getEmbedding())
                    >= config.dedupThreshold());
}
```

### P1-2 `source_assistant` 整条链都没落地

**现状**：`UserMemory` 没这个字段、`of(...)` 还是 4 参、`UserMemoryMapper.xml` 没这列、
`recordAsync` 拿不到 assistantId。

**后果**：用户事实是**跨助手共享**的（这是刻意的），但现在**出了事你查不到"这条是谁写进来的"**。

**改法**（四处）：

```java
// 1) UserMemory 加字段
private String sourceAssistant;

// 2) of() 多一个参数
public static UserMemory of(String assistantId, String userId,
                            String content, String sourceSession) {
    UserMemory m = new UserMemory();
    m.setSourceAssistant(assistantId);
    m.setUserId(userId);
    m.setContent(content);
    m.setSourceSession(sourceSession);
    m.setCreatedAt(Instant.now());
    return m;
}

// 3) UserMemoryMapper.xml
<result property="sourceAssistant" column="source_assistant"/>
<sql id="cols">id, user_id, content, embedding, source_session, source_assistant, created_at</sql>

// 4) UserMemoryRecorder：改成只收 memoryId，三段自己解析
public void recordAsync(String memoryId, List<ChatMessage> recentTurns) {
    ...
    SessionKey key = SessionKey.parse(memoryId);
    taskExecutor.execute(() -> record(key.assistantId(), key.userId(), key.sessionId(), recentTurns));
}
```

调用处（`ChatStreamController`）同步改成 `userMemoryRecorder.recordAsync(memoryId, List.of(...))`
—— **少传两个参数，就少一处"userId / sessionId 传反"的可能**。

DDL 的 `source_assistant VARCHAR(64) NOT NULL` 见交付单 05 的 1.1。

## 五、一个需要你确认的配置疑点

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mcp_gateway?...
```

库名是 **`mcp_gateway`**。所以：

- `ai_user_memory`（长期记忆）建在这个库里？
- `ai_token_usage`（ai-common 的 token 台账）也在？
- 这个库是复用现有的，还是给 AI 平台单开一个更合适？

如果三个助手将来都要连同一份 `ai_user_memory`，库名最好带平台语义（`ai_platform`），
否则半年后没人知道 `mcp_gateway` 里为什么躺着一张记忆表。

## 六、另：`ai.embed.dimensions: 1536`

现在是 1536，交付单里写的是 1024。**这个值没有问题，但记住它的性质**：
它和已有的向量绑死，一旦库里有数据就**不能改** —— 改了之后新老向量维度不一致，
`MemoryRecallService.isValid` 会把老的全部跳过（它会打一条 error 日志，这是设计好的降级）。

所以建议在 `application.yml` 里给它写一行注释说明这件事：

```yaml
  embed:
    # ⚠️ 改这个值 = 已存的向量全部失效（只能重建）。它和索引是一体的，不是调优参数。
    dimensions: 1536
```
