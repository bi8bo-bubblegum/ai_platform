# 第零节 · 前置：依赖与配置

## 0.0 存储选型：MyBatis-Plus，以及两个必须先满足的条件

**用 MyBatis-Plus，不手写 JDBC。** 理由不是"ORM 更高级"，是三条具体的：

1. **你项目里已经有了。** `ai-common/pom.xml` 里是 `mybatis-plus-spring-boot3-starter:3.5.17`，`AiTokenUsageEntity` + `AiTokenUsageMapper` + `TokenUsageDbAutoConfiguration` 已经跑通了一整套。**同一个工程里两套数据访问方式，是纯负担。**
2. **`BaseMapper` 覆盖了这里 5 个方法里的 3 个**（查、计数、条件删），剩下的只有"带 LIMIT 的两条"要写 SQL。
3. **`@Data` 实体 + `LambdaQueryWrapper` 是编译期类型安全的**，列名写错编译不过；手写 JDBC 的字符串 SQL 写错要等运行时。

### 实体必须是 class，不能是 record

这条是硬约束，我把验证过程也说清楚，免得你以后又想去试：

MyBatis 3.5.19 的 `Reflector` 里**确实有 record 支持**（`isRecord` / `addRecordGetMethods`），所以 record 的**读**是通的。实测（`SystemMetaObject.forObject(...)`）：

```
[record] getValue(id)   = 1          ← 读得到
[record] hasSetter(id)  = false      ← 没有 setter
[record] setValue(id)   = 抛 ReflectionException   ← 写不了
[class ] hasSetter(id)  = true
[class ] setValue(id)   = 99         ← 正常
```

而 MyBatis-Plus 有**两处必须往实体里写**：

- `@TableId(type = IdType.AUTO)` —— insert 之后要把自增主键**回填**到实体
- `updateById(entity)` —— 本来就要求实体可变

所以实体用 `class` + `@Data`，和 `AiTokenUsageEntity` 完全一致。

> 顺带解决一个坑：record 自动生成的 `equals`/`hashCode` 对 `float[]` 用**引用比较**，两条内容相同的事实会判不相等。
> 换成 `@Data` **这个问题依然存在**（Lombok 对数组同样用引用比较），所以：**测试里不要断言 `UserMemory` 的相等性，断言它的字段。**
> 等价的收益：`LambdaQueryWrapper` 的方法引用要写成 `UserMemory::getUserId` —— 这只有 class 才写得出。

### 条件一：`ai-memory/pom.xml` 要显式声明 MyBatis-Plus

它能从 `ai-common` 传递过来，**不加也能编译**。但代码里直接 `import com.baomidou...` 的模块应该显式声明自己用的东西（否则就是幽灵依赖：哪天 `ai-common` 去掉它，你会收到一个看不懂的编译错误）。

```xml
        <!-- MyBatis-Plus：版本跟 ai-common 保持一致。
             想彻底不重复版本号，就把这个 dependencyManagement 提到父 pom 里去 -->
        <dependency>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
            <version>3.5.17</version>
        </dependency>
```

### 条件二：`assistant-demo` 必须先配好数据源

**这一条不做，应用直接起不来。**

`mybatis-plus-spring-boot3-starter` 会带进 `spring-boot-starter-jdbc`，于是 `DataSourceAutoConfiguration` 被激活。而你现在的 `application.yml` **没有任何 `spring.datasource` 配置** —— Boot 会尝试自动判定驱动并失败：

```
Failed to configure a DataSource: 'url' attribute is not specified and
no embedded datasource could be configured.
```

完整的配置（MySQL 和 H2 两套方案、建表 DDL、连接池）在**交付单 07 的第一节**，这里只给最小可用的一份：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/ai_platform?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
```

> `characterEncoding` 要写 **`UTF-8`**，不是 `utf8mb4` —— 后者是 MySQL 的 charset 名，不是合法的
> **Java** charset 名，Connector/J 会直接报 `Unsupported character encoding`。

同时确认 `assistant-demo/pom.xml` 里有 `mysql-connector-j`（你已经有 ✓）。

```java
import com.best.ai_common.properties.EmbeddingModelProperties;
import dev.langchain4j.model.embedding.EmbeddingModel;
import dev.langchain4j.model.openai.OpenAiEmbeddingModel;

/**
 * 向量模型注册器。
 *
 * <p>和 ChatModelRegister 是同一个模子 —— ModelRegister&lt;M&gt; 的骨架一行没改。

    public EmbeddingModelRegister(EmbeddingModelProperties properties) {
        this.properties = properties;
    }

    @Override
    public String DefaultProfile() {
        return properties.profile();
    }

    @Override
    protected EmbeddingModel create(String profile) {
        EmbeddingModelProperties.Endpoint endpoint = properties.getEndpoint(profile);

        return OpenAiEmbeddingModel.builder()
                .baseUrl(endpoint.baseUrl())
                .apiKey(endpoint.apiKey())
                .modelName(endpoint.modelName())
                .dimensions(endpoint.dimensions() != null
                        ? endpoint.dimensions() : properties.dimensions())
                .timeout(endpoint.timeout() != null
                        ? endpoint.timeout() : properties.timeout())
                .maxRetries(endpoint.maxRetries() != null
                        ? endpoint.maxRetries() : properties.maxRetries())
                .build();
    }
}
```

# 第一节 · 数据模型

## 1.1 建表

这份 DDL 有两个去处：**存成 `assistant-demo/src/main/resources/schema.sql`**（H2 方案靠它自动建表，
方案见交付单 07），以及**手动在你的 MySQL 库里执行一次**。

```sql
CREATE TABLE ai_user_memory (
    id               BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id          VARCHAR(64)   NOT NULL             COMMENT '用户标识',
    content          VARCHAR(1000) NOT NULL             COMMENT '一条事实，一句话',
    source_assistant VARCHAR(64)   NOT NULL             COMMENT '哪个助手抽出来的 —— 事实是跨助手共享的，这一列是唯一的追溯线索',
    embedding        BLOB          NULL                 COMMENT 'float32 大端（Big Endian）序列，长度 = 维度 × 4',
    source_session   VARCHAR(128)  NULL                 COMMENT '在哪次会话里抽出来的',
    created_at       DATETIME(3)   NOT NULL             COMMENT '毫秒精度：同一批插入要靠它排序',
    INDEX idx_user_time (user_id, created_at)
) ENGINE = InnoDB COMMENT '用户长期记忆：一句一条';
```

**三个设计点，每一个都有理由**：

| 决定 | 理由 |
|---|---|
| `embedding` 存 BLOB 而不是 TEXT/JSON | 1024 维用 JSON 存约 12KB，BLOB 只要 4KB。检索时要把某个用户的**全部**事实读出来算相似度，读放大三倍 |
| `created_at` 用毫秒精度 | 一轮对话可能一次插入好几条事实，秒精度会导致它们的顺序不确定。而"冲突时以最新为准"这条规则依赖顺序 |
| 索引是 `(user_id, created_at)` 而不是只 `user_id` | 查询永远是"某用户的事实，按时间倒序"，复合索引能直接命中 |
| 多一个 `source_assistant` | 事实是**跨助手共享**的 —— 客服里抽出的事实，运筹眼也会检索到。这是刻意的，但**必须能追溯**：出了问题你要能回答"这条是谁写进来的"。它同时是将来做"按助手过滤事实"的落点 |

> **为什么不上向量库？** 单个用户的记忆量是几十到几百条量级。全捞出来在应用内算余弦，一次 SQL + 几百次点积，耗时在毫秒级。为这个规模引入 Milvus/pgvector 是纯成本。等单用户记忆过千再换——那时候只动 `UserMemoryStore` 的实现，接口不变。

## 1.2 `ai-memory/.../user/UserMemory.java`

```java
package com.best.ai_memory.user;

import com.baomidou.mybatisplus.annotation.IdType;
import com.baomidou.mybatisplus.annotation.TableField;
import com.baomidou.mybatisplus.annotation.TableId;
import com.baomidou.mybatisplus.annotation.TableName;
import com.best.ai_memory.user.db.FloatArrayTypeHandler;
import lombok.Data;

import java.time.Instant;

/**
 * 一条用户事实 —— MyBatis-Plus 的实体。
 *
 * <p><b>为什么是 class 而不是 record：</b>record 没有 setter，
 * MyBatis 的 {@code MetaObject.setValue} 在它上面会抛 ReflectionException（实测过），
 * 而 MyBatis-Plus 的 {@code IdType.AUTO} 要在 insert 之后回填自增主键、
 * {@code updateById} 也要求实体可变。详见 0.0 节。
 *
 * <p><b>equals / hashCode 的坑换成 class 也没消失：</b>Lombok 的 @Data
 * 对 float[] 生成的 equals 用的是【引用比较】，两条内容相同的事实判等会得到 false。
 * 所以：测试里不要断言 UserMemory 的相等性，断言它的字段。
 */
@Data
@TableName(value = "ai_user_memory", autoResultMap = true)
public class UserMemory {

    @TableId(type = IdType.AUTO)
    private Long id;

    /** 用户标识 */
    private String userId;

    /** 一句话的事实，例如"用户是财务部的，负责月度经营分析" */
    private String content;

    /**
     * 向量。新抽取出来、还没算过的时候为 null。
     *
     * <p>库里是 BLOB（float32 大端序列，即网络字节序），应用里是 float[]，中间的编解码
     * 交给 FloatArrayTypeHandler —— 所以这里能直接写 float[]，
     * 调用方（检索、抽取）完全不用关心 VectorCodec。
     */
    @TableField(typeHandler = FloatArrayTypeHandler.class)
    private float[] embedding;

    /** 从哪次会话抽出来的 */
    private String sourceSession;

    /**
     * 哪个助手抽出来的。
     *
     * <p>为什么要存：用户事实是**跨助手共享**的（这是刻意的设计），
     * 所以"这条事实从哪来"必须有记录 —— 否则一旦发现某条事实在别的助手那里
     * 产生了误导，你根本无从查起。
     * 它也是将来做"按助手过滤/加权"的落点：现在的策略是全量共享。
     */
    private String sourceAssistant;

    /** 毫秒精度：同一批插入要靠它 + id 排序 */
    private Instant createdAt;

    /** 新抽出来的事实：还没有 id */
    public static UserMemory of(String assistantId, String userId,
                                String content, String sourceSession) {
        UserMemory memory = new UserMemory();
        memory.setSourceAssistant(assistantId);
        memory.setUserId(userId);
        memory.setContent(content);
        memory.setSourceSession(sourceSession);
        memory.setCreatedAt(Instant.now());
        return memory;
    }
}
```

> **`autoResultMap = true` 这一个字不能省。**
>
> MyBatis-Plus 在**查询**时用的是它自动生成的 resultMap。如果 `@TableField(typeHandler = ...)`
> 只写在字段上、类上没加 `autoResultMap = true`，MP 生成的 resultMap **不会带上这个 typeHandler** ——
> 于是 `embedding` 列会被当成 `byte[]` 往 `float[]` 字段里塞，报类型不匹配。
>
> 写入（insert）那条路是通的，**只有查询会炸**。所以症状是"能存进去、读不出来"。
> 这是 MP 里最经典的一个坑。

## 1.3 `ai-memory/.../user/VectorCodec.java`

```java
package com.best.ai_memory.user;

import java.nio.ByteBuffer;
import java.nio.FloatBuffer;

/**
 * float[] 和 byte[] 之间的互转。
 *
 * <p>为什么不用 Java 原生的 ObjectOutputStream 序列化 float[]？
 * 那个格式带类名、带流头，1KB 的向量会膨胀到 1KB 以上，而且跨语言读不了。
 *
 * <p>为什么不用 JSON 文本？
 * 1024 维的 JSON 大约 12KB，而 float32 二进制只要 4KB ——
 * 差三倍的读放大，在"每次对话都要读全部向量"的场景下是实打实的开销。
 */
public final class VectorCodec {

    private VectorCodec() {}

    /**
     * float[] → byte[]（每个 float 4 字节，大端）。
     *
     * <p>⚠️ 字节序必须和 decode 严格一致。ByteBuffer.allocate() 默认是大端，
     * 两端都用默认值就是一致的。如果哪天有人给其中一边加了
     * .order(ByteOrder.LITTLE_ENDIAN)，读出来的向量会变成一堆乱数 ——
     * 而且不会报错，只会表现为"检索结果莫名其妙"。
     */
    public static byte[] encode(float[] vector) {
        if (vector == null) {
            return null;
        }
        ByteBuffer buffer = ByteBuffer.allocate(vector.length * Float.BYTES);
        buffer.asFloatBuffer().put(vector);
        return buffer.array();
    }

    public static float[] decode(byte[] bytes) {
        if (bytes == null || bytes.length == 0) {
            return new float[0];
        }
        // 长度不是 4 的倍数说明数据坏了（被截断、或者有人写了非本编码的内容）。
        // 这里不抛异常也不静默修正，直接把长度截到整数个 float ——
        // 因为一条坏数据不该让整次检索失败。
        FloatBuffer floatBuffer = ByteBuffer.wrap(bytes).asFloatBuffer();
        float[] vector = new float[floatBuffer.remaining()];
        floatBuffer.get(vector);
        return vector;
    }
}
```

## 1.4 `ai-memory/.../user/CosineSimilarity.java`

```java
package com.best.ai_memory.user;

/**
 * 余弦相似度。
 *
 * <p>为什么用余弦而不是欧氏距离？
 * 余弦只看【方向】，不看【长度】。文本向量里，长度通常和文本长度相关，
 * 而语义相似度和文本长度无关 —— 一句长话和一句短话表达同一个意思时，
 * 我们希望它们相似。
 */
public final class CosineSimilarity {

    private CosineSimilarity() {}

    /**
     * @return 0.0 ~ 1.0。任意一边是空向量时返回 0
     */
    public static double between(float[] a, float[] b) {
        if (a == null || b == null || a.length == 0 || b.length == 0) {
            return 0.0;
        }
        if (a.length != b.length) {
            // 维度不一致 = 两次用的 embedding 模型不同（或者 dimensions 改了）。
            // 这是个严重的配置错误，不能静默返回 0（那会表现为"检索永远没结果"）。
            throw new IllegalArgumentException(
                    "向量维度不一致: " + a.length + " vs " + b.length
                            + "，检查 ai.embed.dimensions 是否被改过");
        }

        double dot = 0.0;
        double normA = 0.0;
        double normB = 0.0;
        for (int i = 0; i < a.length; i++) {
            dot += a[i] * b[i];
            normA += a[i] * a[i];
            normB += b[i] * b[i];
        }
        if (normA == 0.0 || normB == 0.0) {
            return 0.0;
        }
        return dot / (Math.sqrt(normA) * Math.sqrt(normB));
    }
}
```

> **性能提示**：OpenAI 系的 embedding 输出已经是单位向量（模长=1），所以实际算的时候 `dot` 就等于余弦。上面的通用公式多算两次开方，但换来的是"换成不归一化的模型也不会错"。这点开销在几百条的量级下可以忽略。

## 2.1 `ai-memory/.../user/UserMemoryStore.java`

```java
package com.best.ai_memory.user;

import java.util.List;

/**
 * 用户事实的存储。
 *
 * <p>注意接口里【没有】searchByVector 这类方法。
 * 检索逻辑放在上层（MemoryRecallService），因为它是"业务策略"
 * （取多少条、阈值多少、怎么排序），而这里是"数据访问"。
 * 把这个界限划清楚，换成向量库时只改实现，检索策略不用动。
 */
public interface UserMemoryStore {

    /** 新增一条事实 */
    void insert(UserMemory memory);

    /**
     * 取某个用户的全部事实，按创建时间【倒序】。
     *
     * <p>倒序是刻意的：调用方拿到之后可以直接按顺序遍历，
     * 遇到冲突的事实先看到的就是最新的那条。
     *
```

```java
import com.best.ai_memory.user.db.VectorCodec;
import org.apache.ibatis.type.BaseTypeHandler;
import org.apache.ibatis.type.JdbcType;
import org.apache.ibatis.type.MappedTypes;

import java.sql.CallableStatement;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

/**
 * float[] ←→ BLOB 的编解码。
 *
 * <p>为什么值得单独一个类，而不是在每个调用点手写 VectorCodec.encode/decode：
 * 那样的话"float[] 存成什么格式"这件事会散落到 insert、查询映射、测试桩三处。
 * 收进 TypeHandler 之后它只出现在一个地方，
 * 而且 UserMemory 的字段类型可以是干净的 float[]。
 */
@MappedTypes(float[].class)
public class FloatArrayTypeHandler extends BaseTypeHandler<float[]> {

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    float[] parameter, JdbcType jdbcType) throws SQLException {
        ps.setBytes(i, VectorCodec.encode(parameter));
    }

    @Override
    public float[] getNullableResult(ResultSet rs, String columnName) throws SQLException {
        return VectorCodec.decode(rs.getBytes(columnName));
    }

    @Override
    public float[] getNullableResult(ResultSet rs, int columnIndex) throws SQLException {
        return VectorCodec.decode(rs.getBytes(columnIndex));
    }

    @Override
    public float[] getNullableResult(CallableStatement cs, int columnIndex) throws SQLException {
        return VectorCodec.decode(cs.getBytes(columnIndex));
    }
}
```

> 注意 `decode` 对 `null` 返回的是 **`new float[0]` 而不是 `null`**（见 1.3）。
> 也就是库里 `embedding` 为 NULL 时，实体上拿到的是空数组。
> 这在检索侧是被处理过的（`isValid` 里判了 `length == 0`），但你自己写测试时要知道这一点。

## 2.5 `ai-memory/.../user/db/MybatisUserMemoryStore.java`

```java
package com.best.ai_memory.user.db;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.best.ai_memory.user.UserMemory;
import com.best.ai_memory.user.UserMemoryStore;
import lombok.RequiredArgsConstructor;

import java.util.List;

/**
 * UserMemoryStore 的 MyBatis-Plus 实现。
 *
 * <p>注意它 implements 了 2.1 那个接口 —— 所以将来换成向量库时只换这一个文件，
 * UserMemoryRecorder 和 MemoryRecallService 一行都不用改。
 * 这就是接口存在的全部理由，和换 ORM 无关。
 */
@RequiredArgsConstructor
public class MybatisUserMemoryStore implements UserMemoryStore {

    private final UserMemoryMapper mapper;

    @Override
    public void insert(UserMemory memory) {
        // IdType.AUTO：insert 之后自增主键会【回填】到 memory.getId()。
        // 这正是实体必须是 class、不能是 record 的直接原因（见 0.0）。
        mapper.insert(memory);
    }

    @Override
    public List<UserMemory> findByUserId(String userId, int limit) {
        return mapper.selectByUserId(userId, limit);
    }

    @Override
    public int countByUserId(String userId) {
        // 方法引用 UserMemory::getUserId 是【编译期】校验的：
        // 字段名改错编译不过。字符串列名的写法要等运行时才发现。
        Long count = mapper.selectCount(
                new LambdaQueryWrapper<UserMemory>().eq(UserMemory::getUserId, userId));
        return count == null ? 0 : count.intValue();
    }

    /**
     * 删掉最老的几条。
     *
     * <p>刻意拆成"先查 id 再按 id 删"两步，而不是写
     * {@code DELETE ... ORDER BY ... LIMIT ?} —— 后者是 MySQL 专有语法，
     * 在 H2 / PostgreSQL 上会直接报错。分两步之后这个实现是【跨库可移植】的，
     * 本地用 H2 跑测试、生产用 MySQL 都不用改代码。
     *
     * <p>代价是多一次查询。但这个方法只在用户记忆超上限时才被调到，频率极低。
     */
    @Override
    public void deleteOldest(String userId, int count) {
        if (count <= 0) {
            return;
        }
        List<Long> ids = mapper.selectOldestIds(userId, count);
        if (ids.isEmpty()) {
            // 必须挡这一下：ids 为空时 Wrapper 会生成 IN ()，
            // 而 MySQL 的 IN () 是语法错误，不是"匹配零行"。
            return;
        }
        mapper.delete(new LambdaQueryWrapper<UserMemory>().in(UserMemory::getId, ids));
    }

    @Override
    public void deleteAll(String userId) {
        mapper.delete(new LambdaQueryWrapper<UserMemory>().eq(UserMemory::getUserId, userId));
    }
}
```

```java
package com.best.ai_memory.user;

import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.data.message.UserMessage;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.service.AiServices;
import dev.langchain4j.service.SystemMessage;
import lombok.extern.slf4j.Slf4j;

import java.util.List;

// ⚠️ 关于命名冲突的说明（不是错误，是这一行必须这么写）：
//
// 这个文件里出现了两个叫 UserMessage 的东西：
//   dev.langchain4j.data.message.UserMessage  —— 消息对象，render() 里要判类型
//   dev.langchain4j.service.UserMessage       —— 注解，标在 extract() 方法参数上
//
// Java 不能让两个同名类型同时 import。取舍是：
// 导入【数据包的那个】（用得更多），把【注解】在方法参数上写全限定名。
// 所以下面 extract() 的签名是 @dev.langchain4j.service.UserMessage String conversation。
// 如果你觉得难看，也可以反过来导注解、把 render() 里的类型判断写全限定名。

@Slf4j
public class LlmUserMemoryExtractor implements UserMemoryExtractor {

    /**
     * 抽取结果的载体。
     *
     * <p>为什么用一个包装 record 而不是直接返回 {@code List<String>}？
     * LangChain4j 的结构化输出是把返回类型转成 JSON Schema 让模型填的。
     * 顶层就是一个 List 时，模型有时会返回一个裸字符串而不是数组。
     * 包一层对象之后，"必须有一个 memories 字段"这件事在 schema 层面就固定了。
     */
    public record ExtractionResult(List<Fact> memories) {
        public record Fact(String content) {}
    }

    /**
     * 真正干活的那个接口。LangChain4j 动态代理生成实现，
     * 自动做"拼提示词 → 调模型 → 按 ExtractionResult 解析 JSON"。
     */
    interface ExtractorAssistant {
        @SystemMessage("""
                你从对话里抽取【关于用户本人的、值得长期记住的】信息。

                该抽的：
                - 身份与角色（部门、岗位、职责范围）
                - 稳定的偏好（喜欢什么形式的输出、习惯用什么工具）
                - 明确说过的长期目标、约束、决策
                - 用户自己确认过的事实

                注意：抽出来的事实是【跨助手共享】的 —— 用户在客服里说的话，
                运筹眼助手也会看到。所以判断标准里多一条：
                换个场景、换个助手，这句话还成立吗？不成立就别抽。

                不该抽的：
                - 一次性的问题（"帮我查一下上周的数据"）
                - 只对本次任务成立的上下文（"这次用表格"、"这个订单"、"刚才那个报表"）
                - 助手说的话（只抽用户的信息）
                - 寒暄、客套、情绪
                - 临时的状态（"我现在有点忙"）
                - 从对话里推断出来的、用户没说过的结论

                每条写成一句话，以「用户」开头，不要分点、不要编号。

                示例一
                对话：
                用户：我们部门是做经营分析的，我负责月度报表这块
                助手：好的，那我以后…
                输出：{"memories":[{"content":"用户在经营分析部门，负责月度报表"}]}

                示例二
                对话：
                用户：帮我查一下昨天的 GMV
                助手：昨天 GMV 是…
                输出：{"memories":[]}

                示例三
                对话：
                用户：以后给我结果都直接上表格，别写大段文字
                助手：明白
                输出：{"memories":[{"content":"用户偏好表格形式的输出，不喜欢大段文字"}]}

                如果没有任何值得记的，返回 {"memories":[]}。
                """)
        ExtractionResult extract(@dev.langchain4j.service.UserMessage String conversation);
    }

    private final ExtractorAssistant assistant;

    /**
     * @param chatModel 建议传一个便宜的档位（配置里的 ai.memory.user.extract-profile）
     */
    public LlmUserMemoryExtractor(ChatModel chatModel) {
        this.assistant = AiServices.builder(ExtractorAssistant.class)
                .chatModel(chatModel)
                .build();
    }

    @Override
    public List<String> extract(List<ChatMessage> recentTurns) {
        if (recentTurns == null || recentTurns.isEmpty()) {
            return List.of();
        }
        try {
            ExtractionResult result = assistant.extract(render(recentTurns));
            if (result == null || result.memories() == null) {
                return List.of();
            }
            return result.memories().stream()
                    .map(ExtractionResult.Fact::content)
                    .filter(c -> c != null && !c.isBlank())
                    .map(String::trim)
                    .toList();

        } catch (Exception e) {
            // 抽取失败不能影响对话 —— 这和摘要是同一个取舍。
            // 漏记一条事实，用户下次再说一遍就补上了；
            // 而抛异常出去会把已经成功的对话变成失败。
            log.error("抽取用户事实失败，本次跳过", e);
            return List.of();
        }
    }

    private static String render(List<ChatMessage> turns) {
        StringBuilder sb = new StringBuilder();
        for (ChatMessage m : turns) {
            if (m instanceof UserMessage um) {
                sb.append("用户：").append(um.singleText()).append('\n');
            } else if (m instanceof AiMessage am && am.text() != null) {
                sb.append("助手：").append(am.text()).append('\n');
            }
        }
        return sb.toString();
    }
}
```

# 第四节 · 异步写入

## 4.1 `ai-memory/.../user/UserMemoryRecorder.java`

```java
package com.best.ai_memory.user;

import com.best.ai_memory.config.AiMemoryProperties;
import com.best.ai_memory.session.SessionKey;
import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.model.embedding.EmbeddingModel;
import lombok.extern.slf4j.Slf4j;
import org.springframework.core.task.TaskExecutor;

import java.util.Comparator;
import java.util.List;

/**
 * 把「刚刚聊完的这一轮」变成长期记忆。
 *
 * <p>整条流程：
 * 1. LLM 抽取候选事实
 * 2. 每条事实算向量
 * 3. 和该用户已有的事实比相似度，太像的丢掉（去重）
 * 4. 写入
 * 5. 超容量的话删掉最老的
 *
 * <p>为什么整个流程是异步的？
 * 因为它要在【响应已经发给用户之后】才做，用户在等流式输出的最后一个字时，
 * 不该再为"记一笔"多等一秒钟。所以入口方法立刻返回，真正的活在别的线程上跑。
 */
@Slf4j
public class UserMemoryRecorder {

    private final UserMemoryExtractor extractor;
    private final EmbeddingModel embeddingModel;
    private final UserMemoryStore store;
    private final AiMemoryProperties.User config;
    private final TaskExecutor taskExecutor;

    public UserMemoryRecorder(UserMemoryExtractor extractor,
                              EmbeddingModel embeddingModel,
                              UserMemoryStore store,
                              AiMemoryProperties.User config,
                              TaskExecutor taskExecutor) {
        this.extractor = extractor;
        this.embeddingModel = embeddingModel;
        this.store = store;
        this.config = config;
        this.taskExecutor = taskExecutor;
    }

    /**
     * 异步记录。方法立刻返回，不阻塞调用线程。
     *
     * <p>用 Spring 自动配好的 applicationTaskExecutor，不自己 new 线程池：
     * ① 它是 Spring Boot 管理的，应用关闭时会优雅收尾；
     * ② 复用同一个池，不会出现"每个模块各自开一堆线程"的失控局面。
     *
     * <p>⚠️ 和摘要不同，这里【不需要按会话串行】。
     * 摘要需要串行是因为它是"读旧摘要 → 生成新摘要 → 覆盖"，
     * 两个并发请求会互相覆盖。而事实写入是纯追加，每条独立，
     * 并发写不会互相破坏。这个区别决定了它们用不同的执行器 ——
     * 摘要是单线程池（保证串行），事实是多线程池（追求吞吐）。
     */
    public void recordAsync(String memoryId, List<ChatMessage> recentTurns) {
        if (!Boolean.TRUE.equals(config.enabled())) {
            return;
        }

        // 三段都从 memoryId 解析出来 —— 调用方只传它手上那一个 id。
        // 少传两个参数，就少一处"userId / sessionId 传反了"的可能。
        SessionKey key = SessionKey.parse(memoryId);
        String assistantId = key.assistantId();
        String userId = key.userId();
        String sessionId = key.sessionId();
        if (userId == null || userId.isBlank() || recentTurns == null || recentTurns.isEmpty()) {
            return;
        }

        taskExecutor.execute(() -> {
            try {
                record(userId, sessionId, recentTurns);
            } catch (Exception e) {
                // execute 里抛异常会被线程池吞掉（默认策略只是打日志），
                // 所以我们自己兜住，至少保证日志里有完整的堆栈
                log.error("记录用户记忆失败, userId={}", userId, e);
            }
        });
    }

    /** 同步版本，方便测试和手动补偿 */
    public void record(String userId, String sessionId, List<ChatMessage> recentTurns) {
        List<String> facts = extractor.extract(recentTurns);
        if (facts.isEmpty()) {
            return;
        }

        // 把该用户已有的事实一次性读出来，用于去重。
        // 读一次而不是每条新事实读一次：这个量级下（几百条）一次读更划算。
        List<UserMemory> existing = store.findByUserId(userId, config.maxFactsPerUser());

        int inserted = 0;
        for (String fact : facts) {
            if (isDuplicate(fact, existing)) {
                log.debug("事实重复，跳过: {}", fact);
                continue;
            }
            float[] vector = embed(fact);
            UserMemory memory = UserMemory.of(assistantId, userId, fact, sessionId);
            // 实体是可变 class，向量直接 set 进去 —— 不再是 record 那种"造副本"
            memory.setEmbedding(vector);
            store.insert(memory);
            existing.add(0, memory);   // 加进内存列表，避免同一批里的重复
            inserted++;
        }

        if (inserted > 0) {
            enforceCapacity(userId);
            log.info("为用户 {} 新增 {} 条长期记忆", userId, inserted);
        }
    }

    /**
     * 去重判断。
     *
     * <p>⚠️ 这里【只判断"太像了"就跳过】，不做 UPDATE / DELETE。
     * 这是交付单里说过的降级决策，理由：
     * 误删一条用户事实比漏记一条严重得多（漏记用户下轮再说一遍就补上了，
     * 误删是永久丢失）。而且 Mem0 在 2026 版也把自己的自动路径改成了 ADD-only。
     *
     * <p>代价：用户说"我搬到西雅图了"时，库里会同时留着"住在奥斯汀"和
     * "搬到西雅图"。缓解办法在检索侧 —— 按时间倒序，并在注入的文本里
     * 明确告诉模型"若有冲突以靠前的为准"。见交付单 06。
     */
    private boolean isDuplicate(String fact, List<UserMemory> existing) {
        if (existing.isEmpty()) {
            return false;
        }
        float[] candidate = embed(fact);
        return existing.stream()
                .filter(m -> m.getEmbedding() != null && m.getEmbedding().length > 0)
                .anyMatch(m -> CosineSimilarity.between(candidate, m.getEmbedding())
                        >= config.dedupThreshold());
    }

    private float[] embed(String text) {
        return embeddingModel.embed(text).content().vector();
    }

    /** 超容量就删最老的。注意是"删到刚好不超"，不是一次删一大堆 */
    private void enforceCapacity(String userId) {
        int count = store.countByUserId(userId);
        int overflow = count - config.maxFactsPerUser();
        if (overflow > 0) {
            store.deleteOldest(userId, overflow);
            log.warn("用户 {} 的长期记忆已达上限 {}，清理了最老的 {} 条",
                    userId, config.maxFactsPerUser(), overflow);
        }
    }
}
```

```java
package com.best.ai_memory.user;

import com.best.ai_memory.config.AiMemoryProperties;
import dev.langchain4j.data.embedding.Embedding;
import dev.langchain4j.data.message.UserMessage;
import dev.langchain4j.data.segment.TextSegment;
import dev.langchain4j.model.embedding.EmbeddingModel;
import dev.langchain4j.model.output.Response;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.core.task.SyncTaskExecutor;

import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

import static org.assertj.core.api.Assertions.assertThat;

class UserMemoryRecorderTest {

    /** 假抽取器：返回预先设定的结果 */
    static class StubExtractor implements UserMemoryExtractor {
        List<String> result = List.of();

        @Override
        public List<String> extract(List<dev.langchain4j.data.message.ChatMessage> turns) {
            return result;
        }
    }

    /**
     * 假 EmbeddingModel：把文本映射成一个固定的 2 维向量。
     * 内容里含"表格" → (1, 0)，否则 → (0, 1)。
     * 这样我们就能精确控制相似度，测去重逻辑。
     */
    static class StubEmbeddingModel implements EmbeddingModel {
        @Override
        public Response<Embedding> embed(String text) {
            float[] v = text.contains("表格") ? new float[]{1f, 0f} : new float[]{0f, 1f};
            return Response.from(Embedding.from(v));
        }

        @Override
        public Response<Embedding> embed(TextSegment textSegment) {
            return embed(textSegment.text());
        }

        @Override
        public Response<List<Embedding>> embedAll(List<TextSegment> textSegments) {
            return Response.from(textSegments.stream().map(s -> embed(s).content()).toList());
        }
    }

    /** 内存 Store 替身 */
    static class InMemoryUserMemoryStore implements UserMemoryStore {
        final Map<String, List<UserMemory>> data = new ConcurrentHashMap<>();

        @Override
        public void insert(UserMemory memory) {
            data.computeIfAbsent(memory.getUserId(), k -> new ArrayList<>()).add(0, memory);
        }

        @Override
        public List<UserMemory> findByUserId(String userId, int limit) {
            return List.copyOf(data.getOrDefault(userId, List.of()));
        }

        @Override
        public int countByUserId(String userId) {
            return data.getOrDefault(userId, List.of()).size();
        }

        @Override
        public void deleteOldest(String userId, int count) {
            List<UserMemory> list = data.get(userId);
            if (list == null) return;
            // 列表是倒序的，最老的排在最后
            for (int i = 0; i < count && !list.isEmpty(); i++) {
                list.remove(list.size() - 1);
            }
        }

        @Override
        public void deleteAll(String userId) {
            data.remove(userId);
        }
    }

    private StubExtractor extractor;
    private InMemoryUserMemoryStore store;
    private UserMemoryRecorder recorder;

    @BeforeEach
    void setUp() {
        extractor = new StubExtractor();
        store = new InMemoryUserMemoryStore();
        AiMemoryProperties.User config = new AiMemoryProperties.User(
                true, 5, 0.6, "fast", 0.95, 3);   // maxFactsPerUser = 3，方便测容量
        recorder = new UserMemoryRecorder(extractor, new StubEmbeddingModel(), store,
                config, new SyncTaskExecutor());
    }

    @Test
    @DisplayName("抽到事实就写进去")
    void insertsExtractedFacts() {
        extractor.result = List.of("用户在财务部");

        recorder.record("u1", "s1", List.of(UserMessage.from("我在财务部")));

        assertThat(store.findByUserId("u1", 10)).hasSize(1);
        assertThat(store.findByUserId("u1", 10).get(0).getContent()).isEqualTo("用户在财务部");
    }

    @Test
    @DisplayName("抽不到事实就什么都不写")
    void emptyExtractionWritesNothing() {
        extractor.result = List.of();

        recorder.record("u1", "s1", List.of(UserMessage.from("你好")));

        assertThat(store.findByUserId("u1", 10)).isEmpty();
    }

    @Test
    @DisplayName("太像的重复事实被丢掉 —— 这是唯一的"写时治理"")
    void duplicatesAreSkipped() {
        extractor.result = List.of("用户偏好表格输出");
        recorder.record("u1", "s1", List.of(UserMessage.from("x")));

        // 再抽一条向量几乎相同的（都含"表格"）
        extractor.result = List.of("用户喜欢表格形式的输出");
        recorder.record("u1", "s1", List.of(UserMessage.from("y")));

        assertThat(store.findByUserId("u1", 10)).hasSize(1);
    }

    @Test
    @DisplayName("不像的事实会都留下")
    void differentFactsAreBothKept() {
        extractor.result = List.of("用户偏好表格输出");
        recorder.record("u1", "s1", List.of(UserMessage.from("x")));

        extractor.result = List.of("用户在财务部");
        recorder.record("u1", "s1", List.of(UserMessage.from("y")));

        assertThat(store.findByUserId("u1", 10)).hasSize(2);
    }

    @Test
    @DisplayName("超过上限时删掉最老的")
    void capacityIsEnforced() {
        // 上限是 3，依次插入 4 条互不相似的
        recorder.record("u1", "s1", List.of(UserMessage.from("a")));
        extractor.result = List.of("事实A"); recorder.record("u1", "s1", List.of(UserMessage.from("a")));
        extractor.result = List.of("事实B"); recorder.record("u1", "s1", List.of(UserMessage.from("b")));
        extractor.result = List.of("事实C"); recorder.record("u1", "s1", List.of(UserMessage.from("c")));

        assertThat(store.countByUserId("u1")).isLessThanOrEqualTo(3);
    }

    @Test
    @DisplayName("不同用户的事实互不干扰")
    void usersAreIsolated() {
        extractor.result = List.of("用户在财务部");
        recorder.record("u1", "s1", List.of(UserMessage.from("x")));
        recorder.record("u2", "s1", List.of(UserMessage.from("x")));

        assertThat(store.findByUserId("u1", 10)).hasSize(1);
        assertThat(store.findByUserId("u2", 10)).hasSize(1);
    }
}
```
