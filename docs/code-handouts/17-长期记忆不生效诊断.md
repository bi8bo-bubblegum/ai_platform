# 长期记忆不生效 · 诊断手册

> 现象：**换了 `sessionId` 之后助手就不知道我是谁了**（同一会话内正常）。
> 这个现象说明「会话记忆」是好的（同一 session 能读到历史），问题出在**长期记忆**这条线上。

---

## 一、先说结论：五个候选原因，以及一个必须先修的障碍

长期记忆的完整链路是：

```
写：Controller.onCompleteResponse → recordAsync(memoryId, ...)
      → 抽取事实 → 算向量 → 去重 → INSERT ai_user_memory

读：UserMemoryContentRetriever.retrieve(query)
      → 从 query.metadata().chatMemoryId() 解析 userId
      → MemoryRecallService.recall(userId, 问题文本)
        → 算问题向量 → 取该用户全部事实 → 逐条算余弦 → 【阈值过滤】→ TopK
```

**按可能性排序的五个原因：**

| # | 原因 | 特征 | 有没有日志 |
|---|---|---|---|
| **A** | **`min-score: 0.60` 门槛太高** ✅ **已确认** | 库里有数据，但**没有一条**超过阈值 → 静默返回空。实测改成 0.3 才查到 | ❌ **完全静默** |
| B | 写入侧没成功 | `ai_user_memory` 表里**没有**这个 userId 的数据 | 部分有 |
| C | `RetrievalAugmentor` Bean 不存在 | 检索**压根没被调用过** | ❌ 静默（`getIfAvailable()` 返回 null 直接跳过） |
| D | embedding 维度不一致 | 老向量维度 ≠ 当前维度 → 全部被 `isValid` 过滤 | ✅ 有一行 error |
| E | 检索链路抛异常被吞 | 只留一行"失败" | 「有」，但**没堆栈** |

**而 `MemoryRecallService` 里这一行，让 A/C/E 全都变成不可见的：**

```java
} catch (Exception e){
    log.error("失败");      // ← 没传 e，堆栈丢了；文案也没任何上下文
    return List.of();
}
```

**所以第一步不是查根因，是先把这行修掉**（见第五节）。否则你会在日志里看到"失败"两个字，
然后不知道该往哪查。

---

## 二、最快的分叉点：先查表

这一步花 30 秒，能把五个原因**砍掉一半**。

```sql
SELECT id, user_id, source_assistant, content,
       LENGTH(embedding) AS embed_bytes, created_at
FROM ai_user_memory
ORDER BY id DESC
LIMIT 20;
```

**看 `user_id` 那一列，找你的测试用户：**

| 结果 | 说明 | 往哪查 |
|---|---|---|
| **一条都没有** | 写入侧就断了 | 第 4.2 节（B） |
| **有数据，`embed_bytes` 是 0 或 NULL** | 向量没存进去 | 第 4.2 节（B） |
| **有数据，`embed_bytes` 是一个固定值** | 写入正常 ✓ | **读侧问题** → 第 4.1 节（A/C/D/E） |

> `embed_bytes` 应该等于 `维度 × 4`。你的 `dimensions: 1536` → **6144 字节**。
> 如果看到的值不是这个，说明写入时的维度配置和现在不一样 → 那就是原因 **D**。

## 三、一次看清全部：诊断端点

如果不想一步步猜，把这个端点加到 `assistant-demo` 里，**一次请求就能看到全部五个原因的状态**。

路径：`assistant-demo/src/main/java/com/best/assistant_demo/controller/MemoryDebugController.java`

```java
package com.best.assistant_demo.controller;

import com.best.ai_common.register.EmbeddingModelRegister;
import com.best.ai_memory.config.AiMemoryProperties;
import com.best.ai_memory.user.CosineSimilarity;
import com.best.ai_memory.user.MemoryRecallService;
import com.best.ai_memory.user.UserMemory;
import com.best.ai_memory.user.UserMemoryStore;
import dev.langchain4j.model.embedding.EmbeddingModel;
import dev.langchain4j.rag.RetrievalAugmentor;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

/**
 * ⚠️ 临时诊断端点 —— 排查完请删掉，不要带到生产。
 *
 * <p>用法：
 * <pre>
 * curl "http://localhost:8080/debug/memory/status?userId=u1&query=你还记得我是谁吗"
 * </pre>
 */
@RestController
@RequestMapping("/debug/memory")
@RequiredArgsConstructor
public class MemoryDebugController {

    private final ObjectProvider<RetrievalAugmentor> augmentorProvider;
    private final UserMemoryStore store;
    private final MemoryRecallService recallService;
    private final EmbeddingModelRegister embeddingModelRegister;
    private final AiMemoryProperties properties;

    @GetMapping("/status")
    public Map<String, Object> status(@RequestParam String userId,
                                      @RequestParam String query) {
        Map<String, Object> result = new LinkedHashMap<>();

        // ① 排除原因 C：检索到底有没有被挂上
        result.put("retrievalAugmentorPresent", augmentorProvider.getIfAvailable() != null);

        // ② 排除原因 B：这个用户库里有几条事实
        List<UserMemory> all = store.findByUserId(userId, properties.user().maxFactsPerUser());
        result.put("factCount", all.size());

        // ③ 排除原因 D：向量维度的分布（key = 维度，value = 条数；-1 表示没有向量）
        Map<Integer, Long> dims = new TreeMap<>();
        all.forEach(m -> {
            int d = (m.getEmbedding() == null || m.getEmbedding().length == 0)
                    ? -1 : m.getEmbedding().length;
            dims.merge(d, 1L, Long::sum);
        });
        result.put("embeddingDimensions", dims);

        EmbeddingModel model = embeddingModelRegister.getDefault();
        result.put("currentDimension", model.dimension());
        result.put("configuredMinScore", properties.user().minScore());
        result.put("configuredTopK", properties.user().topK());

        // ④ 排除原因 A：实跑一次打分，看分数分布 —— 这是最关键的一段
        if (!all.isEmpty()) {
            float[] qv = model.embed(query).content().vector();
            List<Map<String, Object>> scores = all.stream()
                    .filter(m -> m.getEmbedding() != null && m.getEmbedding().length == qv.length)
                    .map(m -> {
                        Map<String, Object> e = new LinkedHashMap<>();
                        double s = CosineSimilarity.between(qv, m.getEmbedding());
                        e.put("score", Math.round(s * 1000) / 1000.0);
                        e.put("content", m.getContent());
                        return e;
                    })
                    .sorted(Comparator.comparingDouble((Map<String, Object> e) -> (Double) e.get("score")).reversed())
                    .limit(5)
                    .toList();
            result.put("top5Scores", scores);
            result.put("passedThreshold", recallService.recall(userId, query).size());
        }

        return result;
    }
}
```

### 输出怎么读

```json
{
  "retrievalAugmentorPresent": true,       ← false 就是原因 C
  "factCount": 3,                          ← 0 就是原因 B
  "embeddingDimensions": { "1536": 3 },    ← 有多个 key 或者不是 1536，就是原因 D
  "currentDimension": 1536,
  "configuredMinScore": 0.6,               ← 记下这个值，和下面的分数比
  "configuredTopK": 5,
  "top5Scores": [
    { "score": 0.412, "content": "用户在经营分析部门，负责月度报表" },
    { "score": 0.338, "content": "用户偏好表格形式的输出" }
  ],
  "passedThreshold": 0                     ← 0 就说明【检索到了但全被阈值挡了】
}
```

**这张输出直接把五个原因全区分开了：**

| 看到什么 | 结论 |
|---|---|
| `retrievalAugmentorPresent: false` | **原因 C** —— 检索根本没挂上，去看 `ai.memory.user.enabled` 和 Bean 装配 |
| `factCount: 0` | **原因 B** —— 写入侧断了 |
| `embeddingDimensions` 里有非 1536 的项 | **原因 D** —— 老向量维度不符，全被过滤 |
| `top5Scores` 里最高分 **低于** `configuredMinScore` | **原因 A** —— **阈值太高**（我赌这个） |
| `top5Scores` 里最高分 **高于** 阈值，但 `passedThreshold: 0` | 逻辑出问题了，或者检索链路抛异常被吞（**原因 E**） |

> **注意 `passedThreshold` 和最上面的分数对照着看** —— 这两个数一对比，
> "是阈值问题"还是"是链路问题"立刻分晓。

## 四、逐个原因的处理

### 4.1 原因 A：`min-score: 0.60` 门槛太高 —— ✅ **已实测确认（2026-10-10）**

**实测数据**：库里存「用户叫小明」，问「你知道我是谁吗」

| 阈值 | 结果 |
|---|---|
| `0.60` | 查不到 ❌ |
| **`0.30`** | **查到了** ✅ |

**你的第一反应是"0.6 也不算高啊"** —— 这个直觉需要纠正，见 4.1.1。

**事情的经过是这样**：你问的和库里存的是**两种不同的表述**：

| 用户的问题 | 库里的事实 | 大概的余弦相似度 |
|---|---|---|
| "你还记得我是谁吗" | "用户在经营分析部门，负责月度报表" | **0.3 ~ 0.5** |
| "我是谁" | "用户在经营分析部门，负责月度报表" | 0.3 ~ 0.5 |
| "我在哪个部门" | "用户在经营分析部门，负责月度报表" | 0.6 ~ 0.75 |

**只有第三种问法能过 0.60 的门槛。** 而用户最常问的恰恰是第一种 —— "你还记得我吗"、
"我是谁来着"、"我跟你说过什么" —— 这些都和事实本身**主题不重合**，分数天然偏低。

**这就是为什么感觉"完全没生效"**：不是没检索，是检索出来被挡掉了。而且是**静默的**。

**修法**：把阈值降下来。改配置就行，不用改代码：

```yaml
ai:
  memory:
    user:
      min-score: 0.35      # 原来 0.60
      top-k: 5
```

**为什么敢降到 0.35**：召回的目的**不是精确匹配**，而是"给模型一批线索让它自己判断"。
多给两条不相关的，代价是 prompt 长一点；一条都不给，代价是"失忆"。
而且 `UserMemoryContentRetriever` 拼的 header 里本来就写着
「若其中互相冲突，以靠前的为准」—— 说明这套设计**本来就预期给多条、让模型自己挑**。

**降完要观察**：如果开始出现"答非所问地引用无关事实"，再往上调一点。
建议在 0.35 / 0.45 / 0.55 各跑几次，用实际问法看召回质量。

> **一个更彻底的改法（现在别做）**：把"问句"和"事实"的表达形式对齐 —— 检索时不要直接用
> 用户原话，而是先用一次轻量 LLM 把问句改写成陈述（"你还记得我是谁吗" → "用户的身份"），
> 再算相似度。LangChain4j 里有 `CompressingQueryTransformer` 就是干这个的。
> **但那要多一次模型调用**，而且 0.3 的阈值已经够用了。先改阈值，别上这个。

#### 4.1.1 为什么 0.6 在这个场景**真的**算高

你的直觉是"0.6/1.0 才刚过一半，不算高"。这个直觉来自**长文档 RAG** 的常规经验 ——
那里 chunk 和 query 有大量词汇与主题重叠，0.6~0.7 是常见的合理阈值。

**但这里的情况完全不同**：事实是**极短的陈述句**（"用户叫小明"），问句是**极短的疑问句**。
在这类文本上，embedding 模型的分数分布**整体下移、而且很窄**：

| 组别 | 实测分数段 |
|---|---|
| 无关问句（"今天天气怎么样"） | 0.05 ~ 0.25 |
| 相关问句（"我叫什么"、"你还记得我是谁吗"） | 0.28 ~ 0.50 |

**0.6 落在这两段之外** —— 所以不是"刚好卡住"，是**任何问法都够不到**。
这也解释了为什么感觉是"完全失忆"而不是"偶尔想不起来"。

**根本原因：余弦相似度衡量的是「表述相似」，不是「语义相关」。**

"你还记得我是谁吗" 和 "用户叫小明" 在人的判断里强相关，但在向量空间里隔得远，因为：

1. **一个是疑问句、一个是陈述句** —— 句式、语序、语气都不同
2. **人称错位**（最具体的一条）：问句用第一人称"**我**"，而事实被强制写成第三人称
   "**用户**" —— 抽取提示词里明确要求"每条写成一句话，以「用户」开头"。
   这两个词的向量差异很大，直接压低分数
3. **文本太短** —— "用户叫小明"只有 6 个字，没有上下文可以借力

第 2 条是可以验证的，见 4.1.2。

#### 4.1.2 自己验证分数分布

给第三节那个 `MemoryDebugController` 再加一个方法：

```java
    /**
     * 对比多个问法对同一条事实的打分 —— 用来判断"阈值该定多少"。
     *
     * <p>这是定阈值唯一靠谱的方法：不要凭感觉，要看这个模型在你这类文本上的真实分布。
     *
     * <p>用法：
     * <pre>
     * curl "http://localhost:8080/debug/memory/compare?fact=用户叫小明&queries=我叫什么,我是谁,用户叫什么,今天天气怎么样"
     * </pre>
     */
    @GetMapping("/compare")
    public Map<String, Object> compare(@RequestParam String fact,
                                       @RequestParam List<String> queries) {
        EmbeddingModel model = embeddingModelRegister.getDefault();
        float[] factVector = model.embed(fact).content().vector();

        Map<String, Object> result = new LinkedHashMap<>();
        result.put("fact", fact);
        result.put("currentMinScore", properties.user().minScore());

        // LinkedHashMap 保序，输出顺序和传入的 queries 一致
        Map<String, Double> scores = new LinkedHashMap<>();
        for (String q : queries) {
            float[] qv = model.embed(q).content().vector();
            scores.put(q, Math.round(CosineSimilarity.between(qv, factVector) * 1000) / 1000.0);
        }
        result.put("scores", scores);
        return result;
    }
```

```bash
curl "http://localhost:8080/debug/memory/compare?fact=用户叫小明&queries=我叫什么,我是谁,你知道我是谁吗,用户叫什么,今天天气怎么样"
```

**看两件事**：

1. **相关问法的分数段落在哪** → 那就是阈值的上界
2. **人称一致 vs 人称错位**（"用户叫什么" vs "我叫什么"）→ 验证上面第 2 条

> 如果结果显示"用户叫什么"明显高于"我叫什么"，那就证实了**人称错位**在拉低分数。
> 但**先别急着改抽取提示词**（比如改成第一人称），因为：
> ① 改人称会和已有数据不一致（老数据是第三人称）；
> ② 第三人称在跨助手/跨会话场景下更清晰。
> **正确的顺序是：先降阈值把功能跑通 → 积累真实数据 → 再决定要不要动人称。**

#### 4.1.3 阈值怎么定（校准方法）

不要凭感觉。三步：

1. 准备 **5 条你认为是相关**的问法 + **5 条明确无关**的
2. 跑 `/compare`
3. 看两组有没有干净的分界：
   - **有分界** → 取分界的中点
   - **重叠严重** → 说明单靠向量相似度分不开这两组，得换方案（见 4.1.4）

对「用户叫小明」这类短事实，实测的合理区间是 **0.25 ~ 0.35**。

#### 4.1.4 如果分数分不开（备选方向）

**方向 1：降低阈值 + 靠 top-k 截断**（一期就够）

单用户的事实量很小（十几到几十条）。`min-score` 设 0.25~0.3，再靠 `top-k: 5` 截断 ——
多给两条不相关的，代价是 prompt 长一点；一条都不给，代价是"失忆"。
而且 header 里本来就写了「若其中冲突，以靠前的为准」，说明设计上预期给多条让模型挑。

**方向 2：查句改写**（效果好，但多一次模型调用）

检索前先用一次轻量 LLM 把问句改写成陈述（"你还记得我是谁吗" → "用户的身份信息"），
让问句和事实的表述形式对齐。LangChain4j 有 `CompressingQueryTransformer`。
**代价是每轮对话多一次模型调用**，一期不做。

**方向 3：混合检索（向量 + 关键词）**

对"用户叫小明"这种**关键词在事实里但不在问句里**的情况帮助有限 ——
用户问"我是谁"时并不包含"小明"。**所以这条对当前场景收益不大。**

**方向 4：rerank 模型**（cross-encoder）

比向量检索准得多，但要额外部署一个模型。**规模不划算。**

**我的建议：一期只做方向 1**（降阈值），把功能跑通。等事实量涨到几百条、
或者出现明显的"召回不准"投诉时，再考虑方向 2。

### 4.2 原因 B：写入侧断了

先看日志里这几行（**它们的文案都是可搜的**）：

| 日志 | 说明 | 下一步 |
|---|---|---|
| `抽取用户事实失败，本次跳过` | LLM 抽取调用失败 | 看堆栈里的根因（网关？鉴权？） |
| `批量向量化失败` / `查询向量化失败` | embedding 调用失败 | 查 `ai.embed` 的 base-url / key |
| `未找到指定的模型配置: xxx` | `extract-profile` 指向了不存在的档位 | 对齐 `ai.chat.endpoints` 的 key |
| `记录用户记忆失败, userId=...` | `record()` 内部抛了异常 | — |
| `事实重复,跳过` | 正常去重（debug 级，默认看不到） | 不是问题 |

**如果这些日志一条都没有** —— 那说明 `recordAsync` 压根没被调到，或者被提前 return 了：

```java
public void recordAsync(String memoryId, List<ChatMessage> recentTurns) {
    if (!Boolean.TRUE.equals(config.enabled())) {
        return;                              // ← ai.memory.user.enabled 是 false 就在这里静默返回
    }
    if (memoryId == null || memoryId.isBlank() || recentTurns == null || recentTurns.isEmpty()) {
        return;                              // ← 参数为空也静默返回
    }
    ...
}
```

**检查 `ai.memory.user.enabled` 是不是真的 `true`**（`@DefaultValue("true")` 兜底，
但如果 yml 里写成了别的值，或者缩进串位了，可能没绑上）。

### 4.3 原因 C：`RetrievalAugmentor` Bean 不存在

症状是**静默**的，因为 `AssistantConfig` 里是这么写的：

```java
RetrievalAugmentor augmentor = augmentorProvider.getIfAvailable();
if (augmentor != null) {          // ← null 就什么都不做，一行日志都不打
    builder.retrievalAugmentor(augmentor);
}
```

**这个 `null` 检查本身是对的**（长期记忆是可选能力，不该拖垮启动）。但它**不该静默** ——
建议加一行日志：

```java
RetrievalAugmentor augmentor = augmentorProvider.getIfAvailable();
if (augmentor != null) {
    builder.retrievalAugmentor(augmentor);
    log.info("已挂载长期记忆检索（RetrievalAugmentor）");
} else {
    // 长期记忆是可选能力，没有它也要能启动。但必须能看见 ——
    // 否则"长期记忆不生效"会被误判成"模型不记得"，白白排查半天。
    log.warn("未找到 RetrievalAugmentor，长期记忆不会注入。"
            + "检查 ai.memory.user.enabled 是否为 true、DataSource 是否就绪");
}
```

（需要给 `AssistantConfig` 加 `@Slf4j`。）

**Bean 为什么不存在的三个原因**：

1. `ai.memory.user.enabled: false`（或没绑上）
2. `UserMemoryConfig` 那个嵌套配置类整体没装载 —— 它的条件是
   `@ConditionalOnClass({BaseMapper.class, DataSource.class})` + `@ConditionalOnBean(DataSource.class)`。
   而 `@ConditionalOnBean` 依赖 `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`
   **必须写在外层类上**（你写了 ✓）
3. `@Qualifier("userMemoryContentRetriever")` 找不到那个 Bean（它也是条件 Bean，同一个配置类里）

### 4.4 原因 D：embedding 维度不一致

日志里搜 `发现向量维度不一致的记忆`。有的话说明库里有**旧维度**的向量：

```sql
-- 直接看维度的分布（每个维度的字节数 = 维度 × 4）
SELECT LENGTH(embedding) / 4 AS dimension, COUNT(*)
FROM ai_user_memory
GROUP BY LENGTH(embedding) / 4;
```

如果出现两个不同的维度值 —— 说明 `ai.embed.dimensions` 被改过。
**旧向量无法与新查询向量比较，必须重建**：

```sql
-- 维度不符的那些，向量置空（它们还能作为"事实"存在，只是不参与检索）
-- ⚠️ 或者直接删掉，看你是否还需要那些事实文本
UPDATE ai_user_memory SET embedding = NULL WHERE LENGTH(embedding) / 4 <> 1536;
```

> 更好的做法是**让应用重新算一遍**：把旧向量置空 → 走一次容量/补算流程。
> 但目前没有"补算向量"的功能，所以一期最简单是**删掉重建**（用户在下一轮对话里会重新说出来）。

### 4.5 原因 E：检索链路抛异常被吞

**这就是第五节要修的那一行。** 修完再看日志。

## 五、正式改动：修掉吞异常的 catch + 加分数日志

这两处**不是临时诊断，是应该长期留着的** —— 因为"检索返回空"是这个功能最常见的故障形态，

### 5.1 `MemoryRecallService` 完整代码（替换整个文件）

路径：`ai-memory/src/main/java/com/best/ai_memory/user/MemoryRecallService.java`

```java
package com.best.ai_memory.user;

import com.best.ai_common.register.EmbeddingModelRegister;
import com.best.ai_memory.config.AiMemoryProperties;
import dev.langchain4j.model.embedding.EmbeddingModel;
import lombok.extern.slf4j.Slf4j;

import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

@Slf4j
public class MemoryRecallService {

    private final UserMemoryStore store;
    private final EmbeddingModel embeddingModel;
    private final AiMemoryProperties.User config;

    private volatile boolean dimensionMismatchReported = false;

    public MemoryRecallService(UserMemoryStore store, EmbeddingModel embeddingModel, AiMemoryProperties.User config) {
        this.store = store;
        this.embeddingModel = embeddingModel;
        this.config = config;
    }

    public List<UserMemory> recall(String userId, String query) {
        if (userId == null || userId.isBlank() || query == null || query.isBlank()) {
            return List.of();
        }

        float[] queryVector;
        try {
            queryVector = embeddingModel.embed(query).content().vector();
        } catch (Exception e) {
            log.error("查询向量化失败，本次跳过长期记忆检索, userId={}", userId, e);
            return List.of();
        }

        try {
            List<UserMemory> all = store.findByUserId(userId, config.maxFactsPerUser());
            if (all.isEmpty()) {
                return List.of();
            }

            // 先算完所有可比较项的分数（含维度过滤），再排序 ——
            // 这样"最高分是多少"可以直接打出来，用于判断阈值是不是设高了。
            List<Map.Entry<UserMemory, Double>> scored = all.stream()
                    .filter(m -> isValid(m, queryVector))
                    .map(m -> Map.entry(m, CosineSimilarity.between(queryVector, m.getEmbedding())))
                    .sorted(Comparator.comparingDouble((Map.Entry<UserMemory, Double> e) -> e.getValue()).reversed())
                    .toList();

            // ★ 这一段是排查"长期记忆不生效"的关键。
            //   阈值过滤是【静默】的，不把分数打出来，你永远不知道
            //   是"没检索到"还是"检索到了但被门槛挡了"。
            if (log.isDebugEnabled()) {
                log.debug("长期记忆召回: userId={}, 候选={} 条, 可比较={} 条, 阈值={}, 结果={} 条",
                        userId, all.size(), scored.size(), config.minScore(),
                        scored.stream().takeWhile(e -> e.getValue() >= config.minScore())
                                .limit(config.topK()).count());
                if (!scored.isEmpty()) {
                    log.debug("打分 Top3: {}", scored.stream().limit(3)
                            .map(e -> String.format("%.3f | %s", e.getValue(), e.getKey().getContent()))
                            .collect(Collectors.joining("\n    ")));
                }
            }

            return scored.stream()
                    .filter(e -> e.getValue() >= config.minScore())
                    .limit(config.topK())
                    .map(Map.Entry::getKey)
                    // 召回之后【重新按时间倒序】：
                    // 相关度排序帮不上"互相矛盾的事实"这个忙 ——
                    // 库里可能同时有"住奥斯汀"和"搬到西雅图"，两条对"我住哪"的相关度一样，
                    // 只有时间线索能让模型选对。
                    .sorted(Comparator.comparing(UserMemory::getCreatedAt).reversed())
                    .toList();

        } catch (Exception e) {
            // ⚠️ 这里原来是 log.error("失败") —— 没有传 e，堆栈全丢，文案也没有任何上下文。
            //    结果是"长期记忆突然不生效"时，日志里只有两个字，无从排查。
            //    降级本身是对的（没有长期记忆也要能回答），但必须留下能查的线索。
            log.error("长期记忆检索失败，本次跳过（对话继续，但这一轮没有长期记忆）, userId={}, query={}",
                    userId, query, e);
            return List.of();
        }
    }

    private boolean isValid(UserMemory memory, float[] queryVector) {
        if (memory.getEmbedding() == null || memory.getEmbedding().length == 0) {
            return false;
        }
        if (memory.getEmbedding().length != queryVector.length) {
            // 维度对不上 = 两次用的 embedding 模型不同（多半是 dimensions 被改过）。
            // 这类数据没法比较，直接跳过；但要报出来，否则会表现为
            // "明明库里有几百条，检索永远只返回几条"。
            if (!dimensionMismatchReported) {
                dimensionMismatchReported = true;
                log.error("发现向量维度不一致的记忆（{} vs {}），已跳过。"
                                + "通常是 ai.embed.dimensions 被改过，需要重建历史向量",
                        memory.getEmbedding().length, queryVector.length);
            }
            return false;
        }
        return true;
    }
}
```

> 变化三处：① `catch` 补上异常和上下文（**这是修 bug**）；
> ② 新增 debug 级打分日志（**这是加可观测性**）；
> ③ 补注释（顺带把"召回后按时间倒序"的理由写清）。

## 六、结论与后续

### 已经确认的

**原因 A 成立** —— `min-score: 0.60` 太高，改成 `0.30` 后长期记忆恢复工作。
这不是参数没调好，而是**这个模型的分数分布本来就落不到 0.6**（见 4.1.1）。

**但原因 A 只是让你"查到"，不代表整条链路的健康度已经达标。** 还有三件事值得做：

| 顺序 | 做什么 | 为什么 | 耗时 |
|---|---|---|---|
| **1** | **修 `MemoryRecallService` 的 catch**（5.1 节） | 现在 `log.error("失败")` 不传 `e`，堆栈全丢。这次是阈值问题（静默），下次如果是异常，你连"哪里抛的"都看不到 | 2 分钟 |
| **2** | **加 debug 打分日志**（5.1 节，同一处改动） | 把"阈值过滤"从静默变可见。以后再出现类似现象，一条日志就能判断 | 同上 |
| **3** | 跑一次 `/compare`（4.1.2），把分数分布记下来 | 你现在的 0.3 是"试出来的"。有分布数据之后，它能变成"算出来的" | 5 分钟 |
| 4 | 给 `AssistantConfig` 的 `getIfAvailable()` 补 warn 分支（5.3 节） | 另外两个静默点之一 | 1 分钟 |
| 5 | 排查完删掉临时诊断端点 | 别带进生产 | — |

### 暂时不做的

| 项 | 为什么不做 |
|---|---|
| 改抽取提示词的人称（第三人称 → 第一人称） | 先积累真实数据再定。改了会与老数据不一致（见 4.1.2 的说明） |
| query 改写（`CompressingQueryTransformer`） | 每轮多一次模型调用，0.3 的阈值已经够用 |
| 混合检索 / rerank | 对当前场景收益不明显（见 4.1.4） |

### 留一个观察点

`min-score: 0.3` 是个**宽松**的值。宽松的代价是"可能召回不相关的事实"。
跑一段时间后回来看：**有没有出现"助手答非所问地引用了一条无关的用户信息"**。

- 没有 → 0.3 合适，甚至可以考虑再往上调到 0.35
- 有 → 说明需要更精确的召回（这时候才轮到 query 改写）

> **别一开始就追求精确。** 这个功能的故障代价是不对称的：
> 召回不准 → 模型多一句废话；召回不到 → 用户认为"你什么都记不住"。
> **后者严重得多**，所以阈值宁可偏低。

## 七、为什么这个故障特别值得记一笔

它暴露的不是某一个 bug，而是**一类设计问题**：

> 这条链路上有 **5 个静默的降级点**（`getIfAvailable()` 返回 null、`return List.of()` × 3、
> 阈值过滤、`isValid` 过滤），而它们的**共同表现都是"检索结果为空"**。
>
> 结果就是：**五种完全不同的故障，在用户和日志看来长得一模一样** —— 助手"想不起来"。

**降级本身都是对的**（没有长期记忆也要能回答，不能把对话变成 500）。但每个降级点
**都应该留下"我降级了、因为什么"的痕迹**。这就是为什么第五节那两处改动
（修 catch + 加分数日志）不是可选的 —— 它们是把五个静默点变成可区分的最小代价。

> 这条经验可以推广到整个 AI-Memory：**凡是"返回空"的地方，都要能回答"为什么是空的"。**
