# 22 · 配置分层与共享：让重复物理消失

> 触发点（2026-10-10 用户提出）：
> **"每新建一个业务都要新建一份配置文件，且大部分相同（`ai.*` 基本全相同）。"**
>
> 这一篇解决它。不是靠"约定"，是靠**让重复的文件内容物理上不存在**。

---

## 1. 现状：一个数字

`assistant-demo/src/main/resources/application.yml` 有 **64 行**。

| 类别 | 行数 | 内容 |
|---|---|---|
| **服务级私有** | **2 行** | `server.port`、`spring.application.name` |
| **平台级共享** | **62 行** | `spring.datasource` / `spring.data.redis` / `spring.mvc.async` / `ai.chat` / `ai.embed` / `ai.memory` / `ai.mcp` |

**62 / 64 = 97% 是会被原样复制的内容。**

这个数字本身就是答案：**问题不是"该不该共享"，是"重复量已经到了必须消灭的程度"。**

---

## 2. 三层配置模型

先把概念理清，否则会纠结"某个配置放哪"。

| 层 | 特征 | 变化频率 | 现在放哪 |
|---|---|---|---|
| **平台级** | 所有服务相同；不一致会导致跨服务行为不一致 | 低（跟着 ai-common 版本走） | **→ 模块 jar 内的 `xxx-defaults.yml`** |
| **服务级** | 每个服务不同 | 建服务时定一次 | `application.yml` |
| **环境级** | 同一服务在不同环境影响（连接串、凭据、外部地址） | 部署时定 | `application-{env}.yml` 或环境变量 |

**判据一行**：

> **"这条配置不同步会导致跨服务行为不一致吗？"** —— 会，就是平台级。

举几个用这条判据过一遍的例子：

| 配置 | 判据结果 | 归属 |
|---|---|---|
| `ai.embed.dimensions` | **会** —— 向量空间不一致则跨服务检索直接失效 | 平台级 |
| `ai.chat.endpoints` | **会** —— 不同服务连不同网关，行为不可预期 | 平台级 |
| `ai.memory.user.min-score` | **会** —— 用户在不同助手的"记忆好坏"不一致 | 平台级 |
| `spring.datasource.url` | **不会**（但**必须**一致，见 §5.2） | 环境级 |
| `server.port` | 不会 | 服务级 |
| `spring.application.name` | 不会 | 服务级 |

---

## 3. 方案：模块自带默认值 + 服务侧 import

### 3.1 三个文件

```
ai-common/src/main/resources/
    ai-common-defaults.yml          ← 新建。模型 / 工具 / web / 基础设施连接

ai-memory/src/main/resources/
    ai-memory-defaults.yml          ← 新建。记忆策略

assistant-demo/src/main/resources/
    application.yml                 ← 精简：64 行 → 8 行
```

### 3.2 `ai-common/src/main/resources/ai-common-defaults.yml`（新建）

```yaml
# AI 平台 · 模型与工具层的默认配置
#
# 这是【平台级】默认值：所有服务相同，不同步会导致跨服务行为不一致。
# 服务侧通过 spring.config.import 引入，本地 application.yml 可以覆盖任何一项。
#
# 改这里的任何内容都要重新打包 ai-common —— 这是它的代价，也是它的保证：
# 配置和它服务的代码版本永远一致。

spring:
  mvc:
    async:
      # SSE 流式必须配。默认 30s 会让长回答被截断。
      # 注意：这个值必须 >= 各 SSE 端点的 SseEmitter 超时，两侧不一致会静默掐断。
      request-timeout: 120s

  # 基础设施连接串 —— 严格说是【环境级】配置，
  # 这里给的是【本地开发的默认值】。生产环境应由环境变量或 application-prod.yml 覆盖。
  datasource:
    url: jdbc:mysql://localhost:3306/mcp_gateway?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: ${DB_USER:root}
    password: ${DB_PASSWORD:root}
    driver-class-name: com.mysql.cj.jdbc.Driver
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}

ai:
  chat:
    profile: free
    temperature: 0.7
    max-tokens: 2000
    timeout: 60s
    endpoints:
      free:
        base-url: ${GATEWAY_BASE_URL}
        api-key: ${GATEWAY_API_KEY}
        model-name: best-1-nothinking

  embed:
    profile: default
    # ⚠️ 改这个 = 向量库里的历史向量全部失效，必须全量重建。
    #    它不是一个"随手调"的参数，和索引一起版本化。
    dimensions: 1536
    timeout: 5s
    max-retries: 3
    endpoints:
      default:
        base-url: ${CLOSEAI_BASE_URL}
        api-key: ${CLOSEAI_API_KEY}
        model-name: text-embedding-3-small

  mcp:
    enabled: true
    tool-timeout: 60s
    servers:
      mcp_gateway:
        transport: http
        url: ${MCP_GATEWAY_URL:http://127.0.0.1:8800/mcp/}
        headers:
          # ⚠️ 原来这里是明文 token，见 §5.1 —— 共享配置会被分发到每个服务，
          #    明文凭据绝不能进去。
          Authorization: Bearer ${MCP_GATEWAY_TOKEN}
        timeout: 30s
```

> **`spring.mvc.async.request-timeout` 为什么放这里**：它服务的是"流式输出"这件事，
> 而流式是所有助手的标配。放平台级能保证**所有助手的超时一致** —— 不一致会导致
> "A 助手的回答能写完、B 助手被截断"这种极难排查的现象。

### 3.3 `ai-memory/src/main/resources/ai-memory-defaults.yml`（新建）

```yaml
# AI 平台 · 记忆层的默认配置
#
# 单独一份，不并进 ai-common-defaults.yml —— 理由：
#   1. 谁的能力，谁的默认值。ai-memory 的默认值不该受 ai-common 版本影响
#   2. ai-memory 将来若独立部署，这份默认值跟着它走
#   3. import 顺序决定优先级：后 import 的胜出，所以更具体的模块放后面

ai:
  memory:
    session:
      store: redis
      max-messages: 20
      summary-enabled: true
      # summary-ttl 必须 >= ttl，否则会出现"摘要还在、消息已过期"的空摘要
      summary-ttl: 96h
      ttl: 48h
    user:
      enabled: true
      top-k: 5
      # ⚠️ 0.30 是实测值，不是拍脑袋。余弦相似度的分布很窄：
      #    无关问句约 0.05~0.25、相关问句约 0.28~0.50，0.60 会导致"怎么问都检索不到"。
      #    详见 docs/code-handouts/17-长期记忆不生效诊断.md
      min-score: 0.30
      extract-profile: free
      dedup-threshold: 0.95
      max-facts-per-user: 500
```

**注意这里没有 `assistant-id` 和 `service-name`** —— 它们默认取 `spring.application.name`（服务级），
所以在平台级里配反而是错的。

### 3.4 `assistant-demo/src/main/resources/application.yml`（精简）

```yaml
server:
  port: 8080

spring:
  application:
    # 这一个值同时充当三个身份：assistantId（记忆隔离）、serviceName（token 台账）、服务发现名。
    # 必须全局唯一 —— 两个服务同名会让它们的会话记忆混在一起。
    name: assistant-demo
  config:
    import:
      # 被 import 的配置优先级【低于】本文件 → 下面可以覆盖上面任何一项
      - classpath:ai-common-defaults.yml
      - classpath:ai-memory-defaults.yml

# ====================================================================
# 需要覆盖平台默认值时，就写在这里。例如：
#
# ai:
#   memory:
#     user:
#       min-score: 0.5     # 只有这个服务收紧阈值
#   chat:
#     endpoints:
#       reason:            # 追加一个只有本服务用得到的模型档位
#         base-url: ${GATEWAY_BASE_URL}
#         api-key: ${GATEWAY_API_KEY}
#         model-name: best-1-thinking
# ====================================================================
```

**64 行 → 15 行（含注释），有效的只有 11 行。**

## 4. 关键机制：优先级规则

**按 Spring Boot config data 的规则，`spring.config.import` 引入的配置优先级【低于】声明它的文件。**

这就是我们要的语义：**平台级 = 默认值，服务级 = 覆盖**。

```
优先级从低到高：

  ai-common-defaults.yml    (平台级默认值)
  ai-memory-defaults.yml    (平台级默认值，后 import → 胜出前者)
  application.yml           (服务级)
  application-{profile}.yml (环境级)
  环境变量 / 命令行参数       (最高)
```

**多个 import 之间：后声明的胜出。** 所以顺序是"更基础的在前、更具体的在后"。

### ⚠️ 这是行为性知识，请实测一次再信

在 `assistant-demo/application.yml` 里加一行覆盖，然后确认覆盖生效：

```yaml
ai:
  memory:
    user:
      min-score: 0.99        # 一个明显不合理的值，便于观察
```

**验证方法**（二选一）：

```bash
# 方法一：通过环境端点看生效值（需要 actuator，没有就用方法二）
curl -s http://localhost:8080/actuator/env | grep -A2 min-score

# 方法二：起服务，观察行为 —— 0.99 会让长期记忆完全检索不到
#         （如果仍然能检索到，说明覆盖没生效，优先级理解反了）
```

**如果覆盖没生效**（即平台级反过来覆盖了服务级），那说明规则和我说的相反 —— 那时把
`ai-platform-defaults.yml` 改成"服务级 import 平台级"之外的另一种写法即可，但**概率很低**：

> 从设计意图看，import 的唯一天然用途就是"引入额外数据源，且允许被本地定制"。
> 如果它的优先级更高，本地配置永远会被覆盖，import 这个功能就没有存在意义了。

## 5. 四个必须知道的坑

### 5.1 【安全】共享配置会被分发到每个服务 —— 明文凭据绝不能进去

**现在代码里的问题**：`ai.mcp.servers.mcp_gateway.headers.Authorization` 是**明文 token**：

```yaml
Authorization: Bearer gw_KFSjH007EjqYW4S5CmsCoCzigeMpnPM0h3KMrnO_2jM   # ← 明文
```

而 `ai.chat` / `ai.embed` 用的是占位符（`${GATEWAY_API_KEY}`）—— **同一个文件里两种做法，不一致。**

**共享之后这个风险会被放大**：这份文件会进每个服务的仓库、每个构建产物。
所以搬进 `ai-common-defaults.yml` 时**必须改成占位符**：

```yaml
Authorization: Bearer ${MCP_GATEWAY_TOKEN}
```

**两个配套动作**：

1. **本地开发**：设环境变量，或用 IDE 的 Run Configuration（IntelliJ 支持直接配 env）
2. **⚠️ 如果这个仓库将来推到远程，先把那个已经写进文件的 token 轮换掉** ——
   它已经存在于本地文件和 git 历史之外的地方（比如你贴给我的对话里）。
   现在项目还不是 git 仓库（所以还没有历史包袱），这是个好时机。

**一条通用纪律**：**共享配置里的每一项，都按"它会被复制到 N 个地方"来对待。**

### 5.2 【判断】连接串该共享吗？—— 要，但归属是"环境级"

`spring.datasource.url` 用判据一测是"不会导致跨服务行为不一致" → 技术上不是平台级。

**但它【必须】一致**：长期记忆是用户级、跨助手共享的（这是既有决定），
**三个助手连不同的库 = 用户画像碎成三份**。

所以它属于**环境级** —— 同一个环境里所有服务必须连同一份。做法：

- **本地开发**：`ai-common-defaults.yml` 里给 `localhost` 默认值（省事）
- **生产**：由环境变量或 `application-prod.yml` 覆盖（**绝不能靠 defaults 里的值上生产**）

> 判断"某配置是环境级还是平台级"的一个问法：
> **"我希望它在测试环境能改、生产环境能改，但同一个环境里所有服务必须一样吗？"**
> 是 → 环境级。

### 5.3 【陷阱】不要在 jar 里放 `application.yml`

Spring Boot 的默认配置位置包含 `classpath:/application.yml` —— 而 classpath 包含 jar。
所以如果你把文件命名成 `application.yml` 放进 `ai-common/src/main/resources/`，**它确实会被加载**。

**但不要这么做**，两个原因：

1. **优先级不确定** —— 取决于 classpath 扫描顺序，不同环境可能不同
2. **这是 Spring Boot 官方不建议 starter 做的事**（starter 不该有"我是应用"的语义）

**用 `spring.config.import` 显式引入** —— 顺序确定、意图明确、可被覆盖。

（文件名也不要叫 `application-*.yml`，那会被当成 profile 特定配置。）

### 5.4 【细节】import 的文件找不到会怎样

```yaml
# 不带 optional：找不到就启动失败（推荐）
- classpath:ai-common-defaults.yml
```

**推荐不带 `optional:`** —— 因为一份缺失的平台配置意味着"这个服务缺一堆配置"，
**明确失败好过静默缺配置**。

（将来接 Nacos 时反过来：`optional:nacos:...`，因为配置中心暂时不可用不该阻止服务启动。）
这个差别本身就说明了静态配置和动态配置的不同定位。

## 6. 新建服务的模板（这就是最终产出）

以后新建一个助手服务，`application.yml` **全文就这些**：

```yaml
server:
  port: 8081                    # ← 改这个

spring:
  application:
    name: assistant-yunchou     # ← 改这个（必须全局唯一）
  config:
    import:
      - classpath:ai-common-defaults.yml
      - classpath:ai-memory-defaults.yml
```

**两处改动，零复制。**

需要差异化时，往下追加：

```yaml
ai:
  chat:
    profile: reason             # 这个服务的默认档位不同
```

## 7. 什么时候该换成 Nacos

**不是现在。** 静态 import 已经解决了 97% 的问题，而且它有个 Nacos 没有的优点：
**配置和代码版本绑定** —— `ai-common` 升到 2.0，它的默认值跟着变，不会出现
"代码是新版、配置还是旧版"的错配。

**该换的信号**（出现任一）：

| 信号 | 因为静态配置做不到 |
|---|---|
| 需要**改配置不重启**（比如调 `min-score` 要立即生效） | 要重新打包 + 重启 |
| 服务数量到 **5+**，改一次要发 N 个版本 | 改一处要重建 N 个镜像 |
| 需要**多环境统一管理**（dev / test / prod 的配置要能对比） | 三份文件各自维护 |
| 需要**配置变更审计**（谁在什么时候改了阈值） | 无记录 |

**迁移成本极低** —— 改 import 的一个字符串：

```yaml
  config:
    import:
      - optional:nacos:ai-common-defaults.yml     # classpath: → optional:nacos:
      - optional:nacos:ai-memory-defaults.yml
```

**服务侧其他部分一行都不用改。** 这就是把方案选成"import"而不是"jar 内 application.yml"
的回报 —— 它留了这条迁移路径。

## 9. 一句话总结

> **不要靠"约定"维持分层，靠"文件位置"固化分层。**
>
> `xxx-defaults.yml` 里的就是平台级，`application.yml` 里的就是服务级 ——
> 谁都不会搞错，因为写错位置会立刻表现为"这个值没生效"。
>
> 而选 `spring.config.import` 而不是"jar 内 application.yml"，是因为它
> **顺序确定、可被覆盖、并且留了一条通向 Nacos 的直路**（改一个字符串）。
