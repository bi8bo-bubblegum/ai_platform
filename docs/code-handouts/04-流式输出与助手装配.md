# 第零节 · 前置：给 AI-Common 补流式注册器

## 为什么要补

你现在的 `ChatModelRegister` 造出来的是 `OpenAiChatModel`——**阻塞式**的。流式需要的是 `OpenAiStreamingChatModel`，是另一个类、另一套 builder。

好消息是：**它俩能共用同一份 `ChatModelProperties`。** 这正是你那个泛型骨架的价值——同一个 `profile`、同一套 `ai.chat.endpoints` 配置，只是造出来的东西不同。

## 0.1 `ai-common/.../register/StreamingChatModelRegister.java`

```java
package com.best.ai_common.register;

import com.best.ai_common.properties.ChatModelProperties;
import dev.langchain4j.model.chat.StreamingChatModel;
import dev.langchain4j.model.openai.OpenAiStreamingChatModel;

/**
 * 流式对话模型注册器。
 *
 * <p>它和 ChatModelRegister 共用同一份 ChatModelProperties —— 这是刻意的。
 * profile 描述的是"用哪一档模型"，而不是"用哪种调用方式"，
 * 所以同一个 profile 既能造阻塞版也能造流式版，配置只写一份。
 *
 * <p><b>关于这个 builder 的观测性：</b>它也支持
 * {@code .listeners(List.of(new ChatTokenUsageListener(profile, recorder)))}，
 * 接口就是给阻塞式用的那个 ChatModelListener，没有单独的版本。
 *
 * <p>但"挂上 listener"不等于"能拿到 token 数" —— 流式下 usage 取不取得到，
 * 取决于请求有没有带 stream_options.include_usage 以及网关透不透传。
 * <b>这一点必须实测，别假定。</b>完整说明见下面的 0.2 节。
 */
public class StreamingChatModelRegister extends ModelRegister<StreamingChatModel> {

    private final ChatModelProperties properties;

    public StreamingChatModelRegister(ChatModelProperties properties) {
        this.properties = properties;
    }

    @Override
    public String DefaultProfile() {
        return properties.profile();
    }

    @Override
    protected StreamingChatModel create(String profile) {
        ChatModelProperties.Endpoint endpoint = properties.getEndpoint(profile);

        return OpenAiStreamingChatModel.builder()
                .baseUrl(endpoint.baseUrl())
                .apiKey(endpoint.apiKey())
                .modelName(endpoint.modelName())
                .temperature(endpoint.temperature() != null
                        ? endpoint.temperature() : properties.temperature())
                // 注意这里的方法名是 maxTokens 而不是 maxOutputTokens，
                // 和 OpenAiChatModel 的 builder 略有出入，别照抄
                .maxTokens(endpoint.maxTokens() != null
                        ? endpoint.maxTokens() : properties.maxTokens())
                .timeout(endpoint.timeout() != null
                        ? endpoint.timeout() : properties.timeout())
                .build();
    }
}
```

## 0.2 一个必须提前说清的问题：流式的 token 统计

这里有个坑，比它看起来深。分三层说。

### 第一层：类型上——能

`StreamingChatModel` **支持 `ChatModelListener`**（就是给阻塞式用的那个接口，没有单独的版本）：

```java
OpenAiStreamingChatModel.builder()
        .listeners(List.of(new ChatTokenUsageListener(profile, recorder)))
        .build();
```

而且 `onCompleteResponse(ChatResponse)` 里的 `ChatResponse` 是**完整响应**，带 `ChatResponseMetadata`。所以 `metadata().tokenUsage()` 这个取值路径是通的。

### 第二层：数据上——不一定

**OpenAI 协议的流式响应，默认不返回 `usage`。**

非流式：响应体里直接有 `usage: {prompt_tokens, completion_tokens, total_tokens}`。

流式：所有 chunk 的 `usage` 都是 `null`。想要它，必须在请求里加：

```json
{ "stream": true, "stream_options": { "include_usage": true } }
```

加上之后，服务端会在**最后一个 chunk** 里带 `usage`（同时 `choices` 为空数组）。

所以你的实际情况取决于两件事，**都必须实测**：

1. LangChain4j 1.20.0 的 `OpenAiStreamingChatModel` 有没有帮你带上 `stream_options.include_usage`
2. 你的 `ai-gateway` 收到这个参数后，会不会原样透传给上游、再把 usage 带回来

**怎么实测**（三行就够）：

```java
var model = streamingRegister.getDefault();
model.chat("说三个字", new StreamingChatResponseHandler() {
    @Override public void onPartialResponse(String t) { }
    @Override public void onCompleteResponse(ChatResponse r) {
        System.out.println("tokenUsage = " + r.metadata().tokenUsage());   // 关键就看这里
    }
    @Override public void onError(Throwable t) { t.printStackTrace(); }
});
```

**输出是 `null` 还是数字，直接决定后面怎么做。** 不要猜。

> 顺带说：即使拿到 `null`，我们写的那份 `ChatTokenUsageListener` 也不会炸 —— 它里面是
> `usage == null ? null : usage.inputTokenCount()`，会把 `null` 如实记下来。
> **所以症状是"统计里 token 全是空"，而不是报错。** 这个失败方式很隐蔽，要主动去查。

### 第三层（更重要）：就算能拿到，也未必该在这儿做

**你已经有 `ai-gateway` 了。它才是 token 计量的天然位置。**

想想看：

- 它是**所有**模型调用的必经之路 —— 不管调用方是 Java 助手、脚本、还是别的语言写的服务
- 它能看到**完整的响应体**，包括流式的最后一帧 —— 拿 usage 不依赖 SDK 的参数拼装
- 它做一次，覆盖全部，不用在每个助手服务里汇总

而 SDK 层挂 listener 的局限：

- 只覆盖**用了 AI-Common 的 Java 助手**，别的调用方统计不到
- 受第二层制约 —— 网关不配合就可能拿不到数
- 每个助手各自统计，要额外做汇总

**那 listener 这一层还有什么用？** 有，它管的是**网关看不到的那部分**：

- **哪个助手**在调（`assistantId`）
- **哪个用户、哪个会话**（`traceId` / `sessionId`）
- 业务侧的耗时（包含排队、序列化，比网关看到的纯模型耗时更贴近用户感受）

网关知道"某次调用花了 1200 token"，但不知道"这是熊鑫在运筹眼的第 3 轮对话"。

### 所以建议的分工

| 谁 | 统计什么 | 什么时候做 |
|---|---|---|
| **ai-gateway** | token 用量、模型耗时、成功率 —— **权威数据** | 现在就去做（找网关的负责人） |
| **AI-Common 的 listener** | assistantId / traceId / 业务耗时 / 失败原因 | 按之前的观测性交付单做，但要给请求带上业务标识 |

**怎么让网关知道"是哪个助手"**：`OpenAiChatModel` / `OpenAiStreamingChatModel` 的 builder 都支持 `customHeaders(...)`，把 `X-Assistant-Id` / `X-Trace-Id` 带上，让网关记下来。

```java
.customHeaders(Map.of(
        "X-Assistant-Id", assistantId,     // 从 spring.application.name 来
        "X-Trace-Id", traceId))
```

**这一步比在 SDK 里挂 listener 更值得先做** —— 因为它一次解决所有语言、所有调用方的统计问题。

### 如果决定就在这一层做：完整方案

行，这条路能走通。但要先处理两件事，不然做出来是个对不了账的报表。

#### 前提一：先花 10 分钟把「能不能拿到 usage」测出来

不用写代码，三个 case 各试一次就行：

| case | 怎么试 | 看什么 |
|---|---|---|
| 直连厂商 | `base-url` 指向厂商官方地址 | `metadata().tokenUsage()` 是不是 null |
| 经你的网关 | `base-url` 指向 `ai-gateway` | 同上 |
| 带参数 | 手动往请求里塞 `stream_options.include_usage` | 同上 |

**三种结果对应三条路**：

- 直连有、经网关没有 → 网关把 usage 吞了，去找网关的人加个透传（**一行的事，比估算准得多**）
- 带参数才有 → LangChain4j 没自动带，需要想办法透传这个参数
- 全都没有 → 走下面的估算兜底

#### 前提二：`ModelUsage` 加一个 `estimated` 字段

这条不是可选的。**报表里混着"准确值"和"估算值"是最坏的情况** —— 你会拿估算值去对账，发现对不上，而且不知道该信哪些行。

```java
public record ModelUsage(
        // ...原有字段不动...
        Integer inputTokens,
        Integer outputTokens,
        /** true 表示这两个数是本地估算的，不是 provider 给的 */
        boolean estimated          // ← 新增
) {}
```

#### 路 A：usage 拿得到 —— 什么都不用改

前面那份 `ChatTokenUsageListener` 直接用，`estimated` 恒为 `false`。

#### 路 B：拿不到 —— 加估算兜底

`OpenAiTokenCountEstimator` 在 `dev.langchain4j.model.openai` 包里，用的是 **jtokkit**（OpenAI 真实的 BPE 分词），而 `langchain4j-open-ai` 你已经引了，不用加新依赖。

改 listener（只列改动部分）：

```java
import dev.langchain4j.model.TokenCountEstimator;

    private final String profile;
    private final ModelUsageRecorder recorder;
    /** 可为 null —— 为 null 时不做估算兜底，token 直接记 null */
    private final TokenCountEstimator estimator;

    public ChatTokenUsageListener(String profile,
                                  ModelUsageRecorder recorder,
                                  TokenCountEstimator estimator) {
        this.profile = profile;
        this.recorder = recorder;
        this.estimator = estimator;
    }

    @Override
    public void onResponse(ChatModelResponseContext ctx) {
        AiCallContext.Snapshot snap = snapshotOf(ctx.attributes());
        ChatResponse resp = ctx.chatResponse();
        TokenUsage usage = resp.metadata().tokenUsage();

        Integer input;
        Integer output;
        boolean estimated;

        if (usage != null) {
            // 正常路径：provider 给了准确值
            input = usage.inputTokenCount();
            output = usage.outputTokenCount();
            estimated = false;
        } else if (estimator != null) {
            // 兜底路径：自己数
            input = estimator.estimateTokenCountInMessages(ctx.chatRequest().messages());
            // 流式中若模型返回的是工具调用而不是文本，text() 会为 null
            String text = resp.aiMessage().text();
            output = estimator.estimateTokenCountInText(text == null ? "" : text);
            estimated = true;
        } else {
            input = null;
            output = null;
            estimated = false;
        }

        recorder.record(ModelUsage.builder()
                .assistantId(snap.assistantId())
                .tenantId(snap.tenantId())
                .traceId(snap.traceId())
                .profile(profile)
                .physicalModel(resp.metadata().modelName())
                .inputTokens(input)
                .outputTokens(output)
                .estimated(estimated)          // ← 别忘了这个
                .latencyMs(elapsedMs(ctx.attributes()))
                .success(true)
                .build());
    }
```

装配处（在 `ChatModelRegister.create` 里挂 listener 的那一行）：

```java
// ⚠️ 关于模型名：OpenAiTokenCountEstimator 只影响选哪套 BPE 词表。
// 你的网关后面挂的是 best-1-xxx（自研/代理模型），没有对应词表，
// 传 "gpt-4o" 是借 OpenAI 的词表来估。
//
// 英文偏差很小；中文通常偏大（同一个词中文被切成更多 token）。
// 所以这个值只能用来做【相对比较】和【告警阈值】，不能用来对账计费。
TokenCountEstimator estimator = new OpenAiTokenCountEstimator("gpt-4o");

.listeners(List.of(new ChatTokenUsageListener(profile, recorder, estimator)))
```

> 如果 `new OpenAiTokenCountEstimator("best-1-nothinking")` 这种未知模型名会抛异常，就传枚举 `OpenAiChatModelName.GPT_4_O` 或者 `"gpt-4o"` —— 反正词表是借的，名字只影响选词表。

#### 这一层独有的一个硬限制：拿不到 TTFT

`ChatModelListener` 只有三个回调：`onRequest` / `onResponse` / `onError`，**没有 token 级回调**。

流式下 `onResponse` 只在**流结束时**触发一次。所以你在这层能拿到"总耗时"，**拿不到"用户多久看到第一个字"**（TTFT, time to first token）。

这条为什么重要：你会盯着"总耗时 3.2 秒"发愁，但用户可能 0.4 秒就看到第一个字了，体感完全没问题。**TTFT 才是流式体验的真实指标。**

要统计它，只能在业务侧自己做 —— 在 `TokenStream.onPartialResponse` 的**第一次**回调里记时刻：

```java
AtomicLong firstTokenAt = new AtomicLong(0);
long startedAt = System.currentTimeMillis();

assistant.chat(memoryId, message)
        .onPartialResponse(token -> {
            // compareAndSet 保证只记第一次
            if (firstTokenAt.compareAndSet(0, System.currentTimeMillis())) {
                log.info("TTFT = {}ms", firstTokenAt.get() - startedAt);
            }
            emitter.send(token);
        })
        ...
```

**这是在这一层做监控时最容易漏的指标**，而且它恰好是流式体验最该看的那个。

## 2.2 为什么这里**不放**装配器

一个很自然的想法是：既然每个助手都要写 `AiServices.builder(...)`，那就把它封进 AI-Memory，提供一个 `AssistantFactory`。**本交付单不做这件事**，理由有三条：

**一、AI-Memory 的产出是「能力」，不是「装好的助手」。**

看它给 LangChain4j 提供的东西，全都是在**扩展点**上插桩：

| 能力 | LangChain4j 的扩展点 |
|---|---|
| 会话记忆 | `ChatMemoryProvider`（02/03 已给） |
| 长期记忆检索 | `ContentRetriever` + `RetrievalAugmentor`（06 会给） |

这就是它和框架的全部契约。而 `AiServices.builder()` 是**调用方**的入口 —— 框架把它设计成 fluent builder，本来就是给使用者自己配的。

**二、装配器会长成 `AiServices.Builder` 的影子。**

装配器目前只拼 3 样（chatModel / streamingChatModel / memoryProvider）。而 `AiServices` 还有 `.tools()`、`.contentModerator()`、`.hallucinationStrategy()`、`.chatRequestParameters()`……

每加一样，你要改的都是 **AI-Memory 的公共 API**，然后所有助手跟着改。**你没有消除复杂度，你把它从 LangChain4j 搬进了 AI-Memory，还多付一层版本同步成本。**

**三、算总账，它没省多少。**

它唯一的收益是"防止忘记挂 `chatMemoryProvider`"。但代价是：**一个不需要记忆的助手（比如纯分类、纯翻译）也被迫依赖 AI-Memory**，还得给它塞一个用不上的 provider。

> 至于"忘记挂会静默失效"这个担心是真实的 —— 我们在 `AssistantConfig` 里用一个单元测试把它钉住（见 4.3 末尾）。**测试比封装便宜，而且不会限制你加工具。**

# 第三节 · 自动装配

### 一条规则：只有装配类碰 `ChatModelRegister` / `EmbeddingModelRegister`

后面你会看到很多 `ChatModel chatModel`、`EmbeddingModel embeddingModel` 这样的字段。
**它们的解析全部发生在装配处，业务类只拿实例、不拿注册器。**

| 谁 | 持有什么 | 例子 |
|---|---|---|
| 自动装配类、助手装配类 | `XxxRegister`，在 `@Bean` 方法里解析 | `AiMemoryAutoConfiguration`、`AssistantConfig` |
| 其它一切业务类 | 解析好的实例 | `LlmConversationSummarizer`、`MemoryRecallService`、`LlmUserMemoryExtractor` |

**四条理由，按实际影响排：**

1. **可测。** `ChatModelRegister` 是**具体类**（`ModelRegister<M>` 的 `create` 是 protected abstract，
   构造器还要 `ChatModelProperties`），测试里造一个假的很别扭；而 `ChatModel` 是 LangChain4j 的**接口**，
   `new FakeChatModel()` 一行就够。业务类依赖得越"接口化"，单测越省事。
2. **类的真实需求是"一个 ChatModel"，不是"一个按档取模型的工厂"。** 声明 register 等于把
   "用哪一档"的决定权交给了这个类 —— 而那个决定权属于装配层。
3. **`profile` 这个词被挡在装配层。** 全项目搜 `profile` 只会命中配置类和装配类，
   排查"这个模型到底走哪一档"时不用满工程翻。
4. **与 05/06 的写法一致**（`MemoryRecallService`、`UserMemoryRecorder`、`LlmUserMemoryExtractor`
   都是收实例），不用维护两套。

**那"模型热更新"怎么办？** 这一条要说清楚，因为它是这个问题真正的难点：

> **`AiServices` 是在 `.build()` 那一刻绑定模型的。** 所以即使把所有下游都改成"调用时从 register 取"，
> `chatAssistant` 那个 Bean 也换不了模型 —— 除非**整个重建 `AiServices`**。

也就是说，"让业务类延迟取模型"**解决不了热更新**，它只能让下游跟着换；真正的瓶颈在 `AiServices` 那一层。

所以一期的结论是：**`ModelRegister.refresh()` 不接线**（它清了缓存，但没有任何 Bean 会重新去取）。
等真要接 Nacos 时，正确做法是发一个模型变更事件、由 `AssistantConfig` **重建 `AiServices` Bean** ——
那时候再统一改，而不是现在给每个业务类都塞一个 register 备用。

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.core.StringRedisTemplate;

@AutoConfiguration
@EnableConfigurationProperties(AiMemoryProperties.class)
public class AiMemoryAutoConfiguration {

    // ================================================ 摘要器

    @Bean
    @ConditionalOnMissingBean
    public ConversationSummarizer conversationSummarizer(
            AiMemoryProperties properties,

    @Bean
    @ConditionalOnMissingBean

                                                 SessionMemoryStore memoryStore,
                                                 SessionSummaryStore summaryStore,

                memoryStore, summaryStore, summarizer,
                properties.session().maxMessages());
    }

    // ================================================ 存储：内存版

     * 后者两个分支之间会有"谁先注册"的顺序依赖，而 @ConditionalOnMissingBean
     * 在同一个类里是按声明顺序求值的，很容易踩坑。
     * 拆成两个互斥的嵌套类，是靠属性切换，没有顺序问题。

    @Configuration(proxyBeanMethods = false)
    @ConditionalOnProperty(prefix = "ai.memory.session", name = "store",

    static class InMemoryStoreConfig {

        @ConditionalOnMissingBean
        public SessionMemoryStore sessionMemoryStore() {
            return new InMemorySessionMemoryStore();
        }

        @Bean
        @ConditionalOnMissingBean

> 全部是「能力」。装配的工作交给助手自己 —— 见 4.3。

> 💡 **顺手记一个小陷阱**：`SummarizingChatMemoryProvider` 的构造器里有三个同类型的引用参数
> （`SessionMemoryStore` / `SessionSummaryStore` / `ConversationSummarizer`）加一个 `int`。

> 写完扫一眼参数列表，成本很低，换来的是避开一个很难查的静默错误。

```java
package com.best.assistant_demo.assistant;

import dev.langchain4j.service.MemoryId;
import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.TokenStream;
import dev.langchain4j.service.UserMessage;

/**
 * 助手接口 —— 没有实现类。
 *
 * <p>LangChain4j 用动态代理在执行期生成实现：
 * 它会把 @SystemMessage 的内容、历史消息、当前用户消息拼成一次模型调用，
 * 再把返回值按方法签名转换（String / TokenStream / 结构化对象）。
 *
 * <p>参数上的 @MemoryId 是"哪个会话"的标记，框架据此去问
 * ChatMemoryProvider 要对应的 ChatMemory。
 * 注意它的值不是 sessionId 本身，而是 SessionKey 拼出来的 memoryId —— 见控制器。
 */
@SystemMessage("你是运筹眼助手。回答只讲事实和数字，不要寒暄，不要用'赋能''抓手'这类词。")
public interface ChatAssistant {

    /**
     * 流式：返回 TokenStream，控制器逐字推给前端。
     * 用 streamingChatModel 执行。
     */
    TokenStream chat(@MemoryId String memoryId, @UserMessage String message);

    /**
     * 阻塞：直接拿完整字符串。
     * 用 chatModel 执行（就是装配里另外传的那个）。
     *
     * <p>同一个接口给两个方法是有意的 —— 它顺带证明了
     * "同一个助手、同一份历史，既能流式调也能同步调"。
     * 而且它让 AssistantWiringTest 能写成普通单测，
     * 不用去接 TokenStream 的回调。
     */
    String ask(@MemoryId String memoryId, @UserMessage String message);
}
```

> `@SystemMessage` 放在**接口上**表示对这个接口的所有方法生效（LangChain4j 支持接口级和方法级两种写法）。
> 如果你的版本对接口级不生效，把它挪到两个方法上各写一遍即可 —— 唯一要保证的是**两处一致**，否则同一个助手会有两套人设。

### 为什么是 `TokenStream`，不是 `Flux`

`Flux` 是能用的（加 `langchain4j-reactor` 就行），但这里**选 `TokenStream`**。把依据摆出来，你以后想翻也知道代价在哪。

**LangChain4j 1.20 把流式拆成四种返回类型，选哪个只由方法签名决定：**

| 返回类型 | 语义 | 稳定性 |
|---|---|---|
| `String` / POJO | 同步阻塞 | 稳定 |
| `TokenStream` | 回调式流 | **稳定** |
| `CompletableFuture` / `CompletionStage` | 单次响应、非阻塞 | `@Experimental` |
| `Flow.Publisher` | 事件流、非阻塞 | `@Experimental` |

`Flux` 是第四种的 Reactor 适配形式 —— 加 `langchain4j-reactor` 依赖即可，适配器通过 ServiceLoader 自动注册，不用写配置。

官方文档对稳定性说得很直白：**「异步与响应式支持是实验性的；同步与 `TokenStream` API 不受影响。」**
这句话本身就是一条决策依据 —— 你要的是能稳定跑的东西。

**Flux 能给的，你现在一个都用不上：**

| Flux 的能力 | 你现在的形态 |
|---|---|
| 背压（`limitRate` / `onBackpressureBuffer`） | 消费端是 `emitter.send(token)`，比模型产 token 快几个数量级 |
| 算子（`timeout` / `retry` / `buffer`） | 流处理逻辑是"原样转发"，零算子 |
| 与 WebFlux 天然集成 | 你用 **Spring MVC** |
| 多路流合并（`merge` / `zip`） | 没有这个需求 |

**切过去的四条成本：**

1. **引入 `@Experimental` API** —— 升级 LangChain4j 时它可能变。
2. **`SummarizingChatMemory` 必须补 `addAsync` / `setAsync` / `messagesAsync`。** 这三个默认实现是抛 `AsyncNotSupportedException` 的。现在返回 `TokenStream` 走同步路径，用不到；一旦返回 `Flux`，`AiServices` 就会走异步路径去要记忆 —— 不补的症状是**"能流式输出，但记不住任何东西"，而且不报错**（异常被吞进 future）。交付单 02 提过的预警，这里会变成真要写的活。
3. **要加 `langchain4j-reactor`。** 好消息是 `reactor-core` 你不用引 —— 它已经跟着 `spring-boot-starter-data-redis` → lettuce 进来了（实测 `reactor-core:3.7.19`）。所以这条成本最低。
4. **冷流陷阱（最阴的一条）。** 官方对 `Flow.Publisher` 返回值的原话是：*publisher 是冷的，什么都不订阅就不会发生，**而且每一次订阅都会开启一次新的交互***。
   `TokenStream` 是显式 `.start()` —— **调一次就是一次请求**；`Flux` 是**订阅几次就是几次请求**。在 MVC 里 Spring 会替你订阅一次，如果你（或某段调试代码）再 `subscribe()` 一次，**用户点一次、模型被调两次、钱花两遍**，而第二次的结果没人看。

**为什么把接口固定成 `TokenStream`：**

它是信息最全的那个句柄。除了 `onPartialResponse`，还有：

- `onPartialThinking` —— 推理模型的思考过程
- `beforeToolExecution` / `onToolExecuted` —— 工具调用前后
- `onRetrieved` —— RAG 检索到的内容

你项目里已经有 `ai-common/mcp/McpClientRegister`。**一旦接上工具，`onToolExecuted` 就是你唯一能看到"模型调了哪个工具、参数是什么"的地方。** 换成 `Flux<String>`，这些全丢。

而且接口定成 `TokenStream`，将来真要转 WebFlux，**改的是控制器，不是契约** —— 反过来定成 `Flux`，想拿回工具事件就得改接口，那才是真返工。

**顺带记一个运维参数**（万一以后真走 `Flow.Publisher`）：官方说事件走**有界缓冲，默认 16384 条**，订阅者落后太多会被 `IllegalStateException` 终止，而不是无限缓冲。可以调：

```java
AiServices.builder(ChatAssistant.class)
        .streamingBufferSize(1024)   // 默认 16384
        .build();
```

设计含义和我们在 AI-Common 给 `AsyncModelUsageRecorder` 定有界队列是同一个取舍：**宁可让流报错，也不让你 OOM。**

**什么时候该翻成 Flux？** 两种情况，而且都是**全项目的决定**，不是"流式输出"这一个点能单独决定的：

- 整个应用切到 WebFlux（全链路非阻塞才成立，背压才有意义）
- 要做"多个助手并发回答、结果合并成一个流"（比如运筹眼同时问三个模型）—— 那才是 `Flux.merge` 真正的主场


## 4.3 `assistant-demo/.../config/AssistantConfig.java` ← 本篇的重点

**这个文件就是"AI-Memory 不提供装配器"之后，装配搬去的地方。**

```java
package com.best.assistant_demo.config;

import com.best.ai_common.register.ChatModelRegister;
import com.best.ai_common.register.StreamingChatModelRegister;
import com.best.assistant_demo.assistant.ChatAssistant;
import dev.langchain4j.memory.chat.ChatMemoryProvider;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.model.chat.StreamingChatModel;
import dev.langchain4j.service.AiServices;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * 助手的装配点 —— 属于业务模块，不属于 AI-Memory。
 *
 * <p>为什么放在这里而不是 AI-Memory：
 * <ul>
 *   <li>「用哪个模型、挂哪些工具、提示词是什么」是【这个助手】的决定，
 *       换个助手就全不一样</li>
 *   <li>加工具就是在这里加一行 {@code .tools(...)}，
 *       不用去改任何其他模块的公共 API</li>
 *   <li>不需要记忆的助手（纯分类 / 纯翻译）不引 ai-memory 就行，
 *       不会被拖上一个用不上的依赖</li>
 * </ul>
 *
 * <p>代价是每个助手要写这几行。等真的出现第三个助手、
 * 而且它们的装配长得几乎一样时，再抽 —— 那时抽出来的才是对的形状。
 */
@Configuration(proxyBeanMethods = false)
public class AssistantConfig {

    @Bean
    public ChatAssistant chatAssistant(ChatModelRegister chatModelRegister,
                                       StreamingChatModelRegister streamingRegister,
                                       ChatMemoryProvider chatMemoryProvider) {

        // 两个模型都从 register 取（AI-Common 只提供了 register，没有提供 ChatModel Bean）。
        // 和 LlmConversationSummarizer 的取法一致：getDefault() = ai.chat.profile 那一档。
        //
        // 注意这里是【启动时】解析：配置写错会在启动阶段就报错，
        // 而不是等第一个请求进来。这是刻意的 fail fast。
        ChatModel chatModel = chatModelRegister.getDefault();
        StreamingChatModel streamingChatModel = streamingRegister.getDefault();

        return AiServices.builder(ChatAssistant.class)
                // 返回 String 的方法用 chatModel，
                // 返回 TokenStream / Flux 的方法用 streamingChatModel。
                // 两个都传，同一个助手接口就既能同步调也能流式调。
                .chatModel(chatModel)
                .streamingChatModel(streamingChatModel)

                // ⚠️ 这一行是"多轮对话"能不能成立的关键。
                // 它让每次请求自动带上该 memoryId 的历史 —— 你不用手动 add / messages。
                // 漏了它不会报错，只会表现为"助手不记得上一句话"。
                .chatMemoryProvider(chatMemoryProvider)

                // 将来加工具就在这里加：
                // .tools(new MetricQueryTool())

                .build();
    }
}
```

### 顺手把"漏挂 provider"这件事钉住

上一节说测试比封装便宜，这就是那个测试。**它不联网**——用一个假模型把"这次调用看到了几条消息"当返回值，然后看第二轮是不是比第一轮多：

```java
package com.best.assistant_demo.config;

import com.best.ai_memory.session.SummarizingChatMemoryProvider;
import com.best.ai_memory.session.memory_store.InMemorySessionMemoryStore;
import com.best.ai_memory.session.summarizer.NoOpConversationSummarizer;
import com.best.ai_memory.session.summary_store.InMemorySessionSummaryStore;
import com.best.assistant_demo.assistant.ChatAssistant;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.memory.chat.ChatMemoryProvider;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.model.chat.request.ChatRequest;
import dev.langchain4j.model.chat.response.ChatResponse;
import dev.langchain4j.service.AiServices;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class AssistantWiringTest {

    /** 假模型：不上网，直接把"收到了几条消息"当回复返回 */
    static class MessageCountingChatModel implements ChatModel {
        @Override
        public ChatResponse doChat(ChatRequest request) {
            return ChatResponse.builder()
                    .aiMessage(AiMessage.from("看到了 " + request.messages().size() + " 条消息"))
                    .build();
        }
    }

    @Test
    void 同一会话的第二轮能看到第一轮的历史() {
        ChatMemoryProvider provider = new SummarizingChatMemoryProvider(
                new InMemorySessionMemoryStore(),
                new InMemorySessionSummaryStore(),
                new NoOpConversationSummarizer(),
                20);

        ChatAssistant assistant = AiServices.builder(ChatAssistant.class)
                .chatModel(new MessageCountingChatModel())
                .chatMemoryProvider(provider)
                .build();

        // 注意用的是 ask（阻塞版）—— chat 返回 TokenStream，单测里不好断言。
        // 这正是 4.2 给接口加第二个方法的原因。
        String first  = assistant.ask("u1::s1", "第一句");
        String second = assistant.ask("u1::s1", "第二句");

        // 不写死具体条数（@SystemMessage 会不会算一条会随版本变），
        // 只断言"第二轮看到的比第一轮多" —— 这就足以证明 provider 挂上了。
        int n1 = Integer.parseInt(first.replaceAll("\\D", ""));
        int n2 = Integer.parseInt(second.replaceAll("\\D", ""));
        assertThat(n2).isGreaterThan(n1);
    }

    @Test
    void 不同会话互相看不到() {
        ChatMemoryProvider provider = new SummarizingChatMemoryProvider(
                new InMemorySessionMemoryStore(),
                new InMemorySessionSummaryStore(),
                new NoOpConversationSummarizer(),
                20);

        ChatAssistant assistant = AiServices.builder(ChatAssistant.class)
                .chatModel(new MessageCountingChatModel())
                .chatMemoryProvider(provider)
                .build();

        String a = assistant.ask("u1::s1", "给会话 s1 说的话");
        String b = assistant.ask("u1::s2", "给会话 s2 说的话");

        // 两个都是各自会话的第一轮，看到的条数应该一样
        assertThat(b.replaceAll("\\D", "")).isEqualTo(a.replaceAll("\\D", ""));
    }
}
```

> 这两个用例是**结构断言**：它们不关心模型答得好不好，只关心"记忆有没有接上"。
> 以后有人在 `AssistantConfig` 里重构时误删了 `.chatMemoryProvider(...)`，这里会立刻变红。

> **两个可能碰到的小麻烦**：
> ① 如果 IDE 提示 `MessageCountingChatModel` 还有抽象方法没实现（比如 `defaultRequestParameters()`），
> 按提示补一个返回默认值的方法即可 —— 它只影响请求参数，不影响这个测试。
> ② 如果 `AiServices` 在 `build()` 时就抱怨缺少 `streamingChatModel`（因为这个接口里有 `TokenStream` 方法），
> 把同一个假模型再作为 `.streamingChatModel(...)` 传一遍即可。`StreamingChatModel` 和 `ChatModel`
> 是两个接口，真要传就得再写一个实现 —— 更省事的做法是给测试单独定义一个小接口，只保留 `ask()`。

## 4.4 `assistant-demo/.../controller/ChatStreamController.java`

```java
package com.best.assistant_demo.controller;

import com.best.ai_memory.session.SessionKey;
import com.best.assistant_demo.assistant.ChatAssistant;
import lombok.RequiredArgsConstructor;
import org.springframework.beans.factory.annotation.Value;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;

import java.io.IOException;
import java.util.concurrent.atomic.AtomicBoolean;

@Slf4j
@RestController
@RequestMapping("/chat")
@RequiredArgsConstructor
public class ChatStreamController {

    private final ChatAssistant assistant;

    /**
     * 这个助手是谁 —— 会话记忆的隔离维度之一。
     *
     * <p>不注入它的话，两个助手收到相同的 (userId, sessionId) 就会共用同一份会话历史。
     * 默认取 spring.application.name；想显式覆盖就配 ai.memory.assistant-id
     * （和 ai-common 里 ai.metrics.service-name 的写法一致）。
     */
    @Value("${ai.memory.assistant-id:${spring.application.name:unknown}}")
    private String assistantId;

    /**
     * SSE 流式对话端点。
     *
     * <p>用 SseEmitter 而不是返回 Flux：Spring MVC 里 SseEmitter 是标准做法，
     * 不需要额外引 WebFlux。如果你以后要接 WebFlux，再换成 Flux 版本。
     */
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter stream(@RequestParam String userId,
                             @RequestParam String sessionId,
                             @RequestParam String message) {

        // 超时设成 2 分钟。不设的话默认 30 秒就会被容器掐断 ——
        // 表现为"AI 说到一半突然断了"，而且不报错，很难查。
        SseEmitter emitter = new SseEmitter(120_000L);

        // 用 AtomicBoolean 而不是普通 boolean：
        // 下面几个回调【不在同一个线程上】，普通 boolean 的可见性没保证。
        // 实际情况是：onError 之后 onComplete 仍可能被调到，
        // 那时 emitter 已经结束了，再 send 会抛异常 —— 这个标记就是防它的。
        AtomicBoolean finished = new AtomicBoolean(false);

        String memoryId = SessionKey.of(assistantId, userId, sessionId).toMemoryId();

        assistant.chat(memoryId, message)
                .onPartialResponse(token -> {
                    if (finished.get()) {
                        return;
                    }
                    try {
                        emitter.send(token);
                    } catch (IOException | IllegalStateException e) {
                        // 客户端断开（用户关页面、切网络）会走到这里。
                        // 这不是错误，是常态 —— 计 warn 不计 error。
                        log.warn("推送 token 失败，客户端可能已断开: {}", e.toString());
                        finished.set(true);
                    }
                })
                .onCompleteResponse(response -> {
                    if (finished.compareAndSet(false, true)) {
                        emitter.complete();
                    }
                })
                .onError(error -> {
                    // ⚠️ 这里必须打 error 日志。
                    // 流式的错误默认对用户表现为"什么都没有发生"，
                    // 不打日志的话你根本不知道为什么没回复。
                    log.error("流式对话失败, memoryId={}", memoryId, error);
                    if (finished.compareAndSet(false, true)) {
                        emitter.completeWithError(error);
                    }
                })
                // 少了这一行，上面所有回调都不会执行。
                // TokenStream 是惰性的 —— 前面只是"配置"，start() 才真正发请求。
                .start();

        return emitter;
    }
}
```

## 起不来怎么办

装配从 AI-Memory 搬到了助手侧，**最常见的一个启动失败是漏声明 Bean**：

```
NoSuchBeanDefinitionException: No qualifying bean of type
'com.best.assistant_demo.assistant.ChatAssistant' available
```

症状就是这句。原因只有一个：`ChatAssistant` 这个接口没有实现类、也没有工厂，**必须由 4.3 的 `AssistantConfig` 显式声明成 Bean**。接口本身不会被组件扫描到。

对照检查三件事：

1. `AssistantConfig` 在 `com.best.assistant_demo` 包**之下**（`@SpringBootApplication` 默认扫它的子包）
2. 它带 `@Configuration`
3. `chatAssistant(...)` 方法带 `@Bean`

## 流式不生效怎么办

按这个顺序排查：

1. **`curl` 有没有加 `-N`** → 不加的话是 curl 在缓冲，不是服务的问题
2. **有没有中间代理** → 如果经过了 nginx / ai-gateway，需要它设置 `X-Accel-Buffering: no` 或者关掉 `proxy_buffering`。这个我们在服务端控制不了，得找运维
3. **是不是响应被 Spring 缓冲了** → 检查有没有自定义的 `ResponseBodyAdvice` 或者包装 `HttpServletResponse` 的 Filter。**你从 AI-Common 带过来的 `AiCallContextInterceptor` 不会做这件事**，那个只读请求头
4. **看日志有没有 `推送 token 失败`** → 有的话说明发送侧有问题，不是缓冲
