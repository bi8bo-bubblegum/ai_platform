# 新助手模块接入清单

> 场景：你要开一个新服务（比如 `assistant-yunchou`），要求**多轮对话 + 长期记忆**。
> 这份是照着抄的清单，不用回头翻 01–08。
>
> **本文已与当前代码核对（`assistant-demo` 全绿编译版）。**

---

## 第 0 步 · 先确认能力齐了

| 能力 | 现在有吗 | 由谁提供 |
|---|---|---|
| **多轮对话** | ✅ 有 | `ChatMemoryProvider` / `SummaryStore` / `Summarizer` |
| **长期记忆** | ✅ 有 | `UserMemoryRecorder` / `MemoryRecallService` / `RetrievalAugmentor` |
| **token 台账** | ✅ 有（顺带就有） | ai-common 的 `TokenUsageListener` |
| **用户上下文** | ✅ 有（顺带就有） | ai-common 的 `AiUserContextInterceptor` |

**这四样你都不用写一行代码，引依赖 + 写配置就有。** 你要写的只有三样东西：
**助手接口**、**装配类**、**控制器**。

### 最快的开工方式：复制 `assistant-demo`

它现在的形状就是标准答案。复制目录之后全局替换四处：

| 替换 | 从 | 到 |
|---|---|---|
| 包名 | `com.best.assistant_demo` | `com.best.assistant_yunchou` |
| 启动类 | `AssistantDemoApplication` | `YunchouApplication` |
| 助手接口 | `ChatAssistant` | `YunchouAssistant` |
| 端口 / 服务名 | `8080` / `assistant-demo` | `8081` / `assistant-yunchou` |

比从空白建快，而且天然避开了下面所有容易漏的配置项。

## 第 0.5 步 · 三个挂载点 —— 少一个都不报错

整个接入只有三个"开关"，全部是**往 `AiServices` 上挂东西**。挂上才有效，不挂什么都不发生，
而且**三个都不报错**：

| 开关 | 挂在哪 | 漏了的症状 | 有扩展点吗 |
|---|---|---|---|
| `.chatMemoryProvider(...)` | `AssistantConfig` | 不记得上一句 | ✅ LangChain4j 提供 |
| `.retrievalAugmentor(...)` | `AssistantConfig` | 长期事实注入不进去 | ✅ LangChain4j 提供 |
| `recorder.recordAsync(...)` | **Controller 里手动调** | 长期事实永远不增长 | ❌ **没有扩展点** |

### 为什么"写"这一侧必须手动

LangChain4j 的扩展点全都在**调用链内部**：构建 prompt 时（`ContentRetriever`）、
管理消息时（`ChatMemoryStore`）、模型调用前后（`ChatModelListener`）。

但"这一轮对话值得长期记住"是**业务判断** —— 框架不知道，也不该知道。
所以它给不了 hook，只能在响应结束后由业务侧触发。

> ⚠️ **"手动"指的是「手动触发」，不是「手动实现」。**
>
> 抽取逻辑（`LlmUserMemoryExtractor`）、去重、向量化、落库、容量清理**全在 AI-Memory 里**，
> 你要写的只有那**一行调用**：
>
> ```java
> recorder.recordAsync(memoryId, List.of(UserMessage.from(message), AiMessage.from(aiText)));
> ```
>
> 时机是 `onCompleteResponse`，跑在异步线程上，不阻塞响应。

### 三个开关都是静默失效 —— 这是设计特征，不是巧合

因为三者都是"挂在 `AiServices` 上才生效"，所以**都不会报错**。后果是：

> **"助手不记得上一句"和"长期记忆一条都没写进去"，从日志上看都像正常。**

这就是第 6 步那份结构断言不是可选项的原因。第 3 个开关（写入）目前**没有测试覆盖**，
如果你想加固它，最省事的做法是把 Controller 里那段抽成一个 `MemoryWriteback` 组件，
然后对它做单测。

## 2. 配置（`application.yml`）

**这个文件是接入的重头戏**，六段一个都不能少。

```yaml
server:
  port: 8081                       # 和 assistant-demo 错开

spring:
  application:
    name: assistant-yunchou        # ⚠️ 这就是 assistantId，必须全局唯一

  datasource:                      # token 台账 + 长期记忆都要用，缺了启动就报
    url: jdbc:mysql://localhost:3306/mcp_gateway?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver

  data:
    redis:                         # 会话记忆（store=redis 时才用得上）
      host: localhost
      port: 6379

  mvc:
    async:
      request-timeout: 120s        # ⚠️ 必须 >= SseEmitter 的超时，否则长回答被容器掐断

ai:
  # ---------- 模型 ----------
  chat:
    profile: free                  # 主对话用哪一档
    temperature: 0.7
    max-tokens: 2000
    timeout: 60s
    endpoints:
      free:                        # 主对话
        base-url: ${GATEWAY_BASE_URL}
        api-key: ${GATEWAY_API_KEY}
        model-name: best-1-nothinking
      # 想给"摘要/事实抽取"单独一档就在这里再加一个，然后改下面的 extract-profile

  embed:
    profile: default               # ⚠️ 长期记忆要用，漏了启动就报"未找到指定的模型配置: default"
    dimensions: 1536
    timeout: 60s
    max-retries: 3
    endpoints:
      default:
        base-url: ${CLOSEAI_BASE_URL}
        api-key: ${CLOSEAI_API_KEY}
        model-name: text-embedding-small-3

  # ---------- 观测（可选，不写也有默认） ----------
  metrics:
    service-name: ${spring.application.name}   # token 台账里的"来源服务"

  # ---------- 记忆 ----------
  memory:
    assistant-id: ${spring.application.name}   # 不写也一样，写了更明确

    session:                       # 多轮对话
      store: redis                 # memory | redis
      max-messages: 20
      summary-enabled: true
      ttl: 48h                     # 消息 TTL
      summary-ttl: 96h             # ⚠️ 必须 >= ttl

    user:                          # 长期记忆
      enabled: true
      top-k: 5
      min-score: 0.60
      extract-profile: free        # ⚠️ 必须指向 ai.chat.endpoints 里【真实存在】的档位
      dedup-threshold: 0.95
      max-facts-per-user: 500
```

**四个容易漏的点：**

1. **`spring.application.name` 就是 `assistantId`** —— 它是会话隔离的维度之一。两个服务取同一个名字 → 会话历史会串。
2. **`ai.embed.endpoints` 别漏** —— 长期记忆要。漏了的表现是**启动就报** `未找到指定的模型配置: default`。
3. **`extract-profile` 必须真实存在** —— 写成 `free` 就得在 `ai.chat.endpoints` 里有 `free` 这一档，否则第一次抽取时 `IllegalArgumentException`。
   （注意这个错**不会在启动时暴露**，是第一次对话结束时才炸，而且在异步线程里 —— 只看得到一行 error 日志。）
4. **`spring.mvc.async.request-timeout` 要 >= `SseEmitter` 的超时** —— 两侧不一致会让 AI 说到一半被掐断，且不报错。

## 3. 助手接口

```java
package com.best.assistant_yunchou.assistant;

import dev.langchain4j.service.MemoryId;
import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.TokenStream;
import dev.langchain4j.service.UserMessage;

/**
 * 助手接口 —— 没有实现类，LangChain4j 用动态代理生成。
 *
 * <p>@SystemMessage 放在接口上 = 对所有方法生效。
 * 按你自己的规矩写：不要寒暄、不要空话、能上数字就上数字。
 */
@SystemMessage("你是运筹眼助手。回答只讲事实和指标数值，不要寒暄，不要用'赋能''抓手'这类词。")
public interface YunchouAssistant {

    /** 流式：给前端用。走 streamingChatModel。 */
    TokenStream chat(@MemoryId String memoryId, @UserMessage String message);

    /** 阻塞：给测试和脚本用。走 chatModel。 */
    String ask(@MemoryId String memoryId, @UserMessage String message);
}
```

> **为什么留两个方法**：`ask` 让单测能写成普通断言，不用去接 `TokenStream` 的回调。
> 同一个接口两个方法，也顺带证明了"同一助手既能流式调也能同步调"。

## 4. 装配（这一步在**你的模块里**，不在 AI-Memory）

```java
package com.best.assistant_yunchou.config;

import com.best.ai_common.register.ChatModelRegister;
import com.best.ai_common.register.StreamingChatModelRegister;
import com.best.assistant_yunchou.assistant.YunchouAssistant;
import dev.langchain4j.memory.chat.ChatMemoryProvider;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.model.chat.StreamingChatModel;
import dev.langchain4j.rag.RetrievalAugmentor;
import dev.langchain4j.service.AiServices;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * 助手的装配点 —— 属于业务模块，不属于 AI-Memory。
 */
@Configuration(proxyBeanMethods = false)
public class AssistantConfig {

    @Bean
    public YunchouAssistant yunchouAssistant(
            ChatModelRegister chatModelRegister,
            StreamingChatModelRegister streamingRegister,
            ChatMemoryProvider chatMemoryProvider,                      // ← 多轮对话，AI-Memory 给
            ObjectProvider<RetrievalAugmentor> augmentorProvider) {     // ← 长期记忆，AI-Memory 给（可选）

        ChatModel chatModel = chatModelRegister.getDefault();
        StreamingChatModel streamingChatModel = streamingRegister.getDefault();

        AiServices<YunchouAssistant> builder = AiServices.builder(YunchouAssistant.class)
                .chatModel(chatModel)
                .streamingChatModel(streamingChatModel)

                // ⚠️ 这一行决定"多轮对话"成不成立。
                // 漏了不报错，只表现为"助手不记得上一句话"。第 6 步的测试就是防它的。
                .chatMemoryProvider(chatMemoryProvider);

        // 长期记忆是可选能力：关掉 ai.memory.user.enabled 时，会话记忆照常工作
        RetrievalAugmentor augmentor = augmentorProvider.getIfAvailable();
        if (augmentor != null) {
            builder.retrievalAugmentor(augmentor);
        }

        // 以后加工具就在这里加：
        // builder.tools(new MetricQueryTool());

        return builder.build();
    }
}
```

> **为什么 `ObjectProvider` 而不是直接注入 `RetrievalAugmentor`**：
> 把 `ai.memory.user.enabled` 关掉时那个 Bean 不存在，直接注入会让**整个服务启动失败** ——
> 一个可选能力把核心功能拖下水，代价太大。

## 5. 控制器（SSE + 长期记忆写入）

```java
package com.best.assistant_yunchou.controller;

import com.best.ai_memory.session.SessionKey;
import com.best.ai_memory.user.UserMemoryRecorder;
import com.best.assistant_yunchou.assistant.YunchouAssistant;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.UserMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;

import java.io.IOException;
import java.util.List;
import java.util.concurrent.atomic.AtomicBoolean;

@Slf4j
@RestController
@RequestMapping("/chat")
@RequiredArgsConstructor
public class ChatStreamController {

    private final YunchouAssistant assistant;

    /**
     * ⚠️ 用 ObjectProvider 而不是直接注入 UserMemoryRecorder。
     *
     * <p>UserMemoryRecorder 这个 Bean 属于 ai-memory 的 UserMemoryConfig，
     * 而那个配置类带 @ConditionalOnProperty("ai.memory.user.enabled")。
     * 一旦关掉用户记忆，Bean 就没了 —— 直接注入会让整个服务启动失败，
     * 而我们只是不想要长期记忆而已。
     */
    private final ObjectProvider<UserMemoryRecorder> recorderProvider;

    /**
     * 这个助手是谁 —— 会话记忆的隔离维度之一。
     * 默认取 spring.application.name，想覆盖就配 ai.memory.assistant-id。
     */
    @Value("${ai.memory.assistant-id:${spring.application.name:unknown}}")
    private String assistantId;

    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter stream(@RequestParam String userId,
                             @RequestParam String sessionId,
                             @RequestParam String message) {

        // 超时设 2 分钟。不设的话默认 30 秒被容器掐断 ——
        // 表现为"AI 说到一半突然断了"，而且不报错，很难查。
        SseEmitter emitter = new SseEmitter(120_000L);

        // 用 AtomicBoolean 而不是普通 boolean：几个回调不在同一个线程上。
        // onError 之后 onComplete 仍可能被调到，那时 emitter 已结束，再 send 会抛异常。
        AtomicBoolean finished = new AtomicBoolean(false);

        // ⚠️ 三段都要给：assistantId::userId::sessionId
        // 少了 assistantId，两个助手收到相同 (userId, sessionId) 就会共用一份会话历史。
        String memoryId = SessionKey.of(assistantId, userId, sessionId).toMemoryId();

        assistant.chat(memoryId, message)
                .onPartialResponse(token -> {
                    if (finished.get()) {
                        return;
                    }
                    try {
                        emitter.send(token);
                    } catch (IOException | IllegalStateException e) {
                        // 客户端断开（关页面、切网络）会走到这里。这不是错误，是常态。
                        log.warn("推送 token 失败，客户端可能已断开: {}", e.toString());
                        finished.set(true);
                    }
                })
                .onCompleteResponse(response -> {
                    // 长期记忆的抽取触发点：异步，不阻塞这次响应。
                    // 只传 memoryId —— assistantId / userId / sessionId 由它自己解析。
                    UserMemoryRecorder recorder = recorderProvider.getIfAvailable();
                    if (recorder != null) {
                        recorder.recordAsync(memoryId, List.of(
                                UserMessage.from(message),
                                AiMessage.from(response.aiMessage().text())));
                    }
                    if (finished.compareAndSet(false, true)) {
                        emitter.complete();
                    }
                })
                .onError(error -> {
                    // ⚠️ 必须打日志。流式的错误默认对用户表现为"什么都没发生"。
                    log.error("流式对话失败, memoryId={}", memoryId, error);
                    if (finished.compareAndSet(false, true)) {
                        emitter.completeWithError(error);
                    }
                })
                // 少了这一行，上面所有回调都不会执行 —— TokenStream 是惰性的
                .start();

        return emitter;
    }
}
```

### 可选增强：TTFT（首字延迟）

`ChatModelListener` 只有 `onRequest` / `onResponse` / `onError`，**拿不到 token 级回调**。
所以"用户多久看到第一个字"只能在这里记：

```java
    // 方法里，assistant.chat(...) 之前
    AtomicLong firstTokenAt = new AtomicLong(0);
    long startedAt = System.currentTimeMillis();

    // onPartialResponse 的第一行
    if (firstTokenAt.compareAndSet(0, System.currentTimeMillis())) {
        log.info("TTFT={}ms memoryId={}", firstTokenAt.get() - startedAt, memoryId);
    }
```

**别只看总耗时。** 总耗时 3.2 秒可能意味着 TTFT 只有 0.4 秒，体感完全没问题；
只统计总耗时是给自己找焦虑。

## 6. 必写的测试（**别跳过这个**）

漏挂 `chatMemoryProvider` 是**静默失效**，只有测试能拦住。这份测试不联网：

```java
package com.best.assistant_yunchou.assistant;

import com.best.ai_memory.session.SummarizingChatMemoryProvider;
import com.best.ai_memory.session.memory_store.InMemorySessionMemoryStore;
import com.best.ai_memory.session.summarizer.NoOpConversationSummarizer;
import com.best.ai_memory.session.summary_store.InMemorySessionSummaryStore;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.memory.chat.ChatMemoryProvider;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.model.chat.request.ChatRequest;
import dev.langchain4j.model.chat.response.ChatResponse;
import dev.langchain4j.service.AiServices;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class YunchouWiringTest {

    /** 假模型：不上网，把"这次看到了几条消息"当回复返回 */
    static class MessageCountingChatModel implements ChatModel {
        @Override
        public ChatResponse doChat(ChatRequest request) {
            return ChatResponse.builder()
                    .aiMessage(AiMessage.from("看到了 " + request.messages().size() + " 条消息"))
                    .build();
        }
    }

    private YunchouAssistant assemble(ChatMemoryProvider provider) {
        return AiServices.builder(YunchouAssistant.class)
                .chatModel(new MessageCountingChatModel())
                .chatMemoryProvider(provider)
                .build();
    }

    private ChatMemoryProvider provider() {
        return new SummarizingChatMemoryProvider(
                new InMemorySessionMemoryStore(),
                new InMemorySessionSummaryStore(),
                new NoOpConversationSummarizer(),
                20);
    }

    @Test
    void 同一会话的第二轮能看到第一轮的历史() {
        YunchouAssistant assistant = assemble(provider());

        String first  = assistant.ask("yunchou::u1::s1", "第一句");
        String second = assistant.ask("yunchou::u1::s1", "第二句");

        int n1 = Integer.parseInt(first.replaceAll("\\D", ""));
        int n2 = Integer.parseInt(second.replaceAll("\\D", ""));
        assertThat(n2).isGreaterThan(n1);   // 第二轮多看到了上一轮的 user + ai
    }

    @Test
    void 不同会话互相看不到() {
        YunchouAssistant assistant = assemble(provider());

        String a = assistant.ask("yunchou::u1::s1", "给 s1 说的话");
        String b = assistant.ask("yunchou::u1::s2", "给 s2 说的话");

        assertThat(b.replaceAll("\\D", "")).isEqualTo(a.replaceAll("\\D", ""));
    }

    @Test
    void 不同助手互相看不到() {
        YunchouAssistant assistant = assemble(provider());

        String a = assistant.ask("yunchou::u1::s1", "运筹眼说的话");
        String b = assistant.ask("cs::u1::s1", "客服说的话");   // 只换了 assistantId

        assertThat(b.replaceAll("\\D", "")).isEqualTo(a.replaceAll("\\D", ""));
    }
}
```

> 这三个用例是**结构断言**：不关心模型答得好不好，只关心"记忆有没有接上"。
> 以后有人在 `AssistantConfig` 里重构时误删了 `.chatMemoryProvider(...)`，第一个会红；
> 把 `SessionKey` 改回两段、或者拼 memoryId 时漏掉 assistantId，第三个会红。

## 7. 三个必知的坑（新模块最容易踩）

### 7.1 `UserMemoryRecorder` 是**条件 Bean**

`ai.memory.user.enabled: false` 时它不存在。**直接构造器注入会让整个服务启动失败**，
而我们只是不想要长期记忆。用 `ObjectProvider`（第 5 步已经这么写了）。

### 7.2 `userId` 有**两套来源**，必须对齐

这是个真实的、现在就存在的割裂：

| 用途 | 来源 | 代码位置 |
|---|---|---|
| 会话记忆 / 长期记忆的归属 | **query 参数** `?userId=u1` | 你的 Controller |
| token 台账里的 `user_id` 字段 | **请求头** `X-User-Id` | ai-common 的 `AiUserContextInterceptor` |

所以前端如果只传 query 参数、不带 `X-User-Id` 头，那么：
- 记忆正常工作 ✓
- **但 `ai_token_usage` 表里的 `user_id` 全是 `anonymous`** ✗

**两条路选一条**（新模块开工前就要定，定了写进接口文档）：

- **A. 让前端两个都传** —— 改动最小，但要求调用方遵守
- **B. 让 Controller 在方法开头调一次 `AiUserContext.set(userId)`** —— 一处生效，不依赖前端

B 更稳，代价是 Controller 里多一行：

```java
import com.best.ai_common.context.AiUserContext;
...
AiUserContext.set(userId);   // 让 token 台账的 user_id 和记忆的 userId 是同一个
```

> 注意 `AiUserContextInterceptor` 的 `afterCompletion` 会 `clear()`，
> 所以在 Controller 里 set 是安全的，不会串到下一个请求。

### 7.3 `TaskExecutor` 是隐式依赖

`ai-memory` 的 `userMemoryRecorder` Bean 需要一个 `TaskExecutor`（抽取跑在它上面），
但**没有任何地方显式声明它** —— 它来自 Spring Boot 的 `TaskExecutionAutoConfiguration`
（`applicationTaskExecutor`）。

后果：**如果哪天你自己定义了一个 `Executor` Bean**（比如给某个业务用的线程池），
Boot 可能不再提供默认那个，注入就会歧义或失败。
真需要自定义线程池时，把它命名/标记成 `applicationTaskExecutor`，或者给抽取单独配一个。

> 顺带一个体感问题：**第 21 轮对话会明显变慢。** 因为窗口满了之后，
> 每轮都会**同步**生成一次摘要（`SummarizingChatMemory.add()` 里调 `summarizer.append`），
> 那是又一次模型调用。不想让它拖慢响应，就把 `ConversationSummarizer` 换成异步实现。

## 8. 四个约定 · 上岗检查表

模块管不了这些，**只能靠你守**：

- [ ] `spring.application.name` **全局唯一**（两个服务同名 → 会话历史会串）
- [ ] 长期记忆连的是**同一份** MySQL schema（各连各的 → 用户画像碎成几份）
- [ ] `ttl` / `summary-ttl` / `max-facts-per-user` 与其他服务**保持一致**
- [ ] `userId` 的来源已统一（7.2 选 A 还是 B）
- [ ] 会话记忆的 Redis **不需要**统一 —— key 里带 assistantId，各连各的反而更干净

## 9. 起不来 / 不对时，按这个顺序查

| 症状 | 最可能的原因 |
|---|---|
| `Failed to configure a DataSource` / `suitable driver class` | `spring.datasource` 没配（ai-common 硬依赖 mybatis-plus） |
| `NoSuchBeanDefinitionException: YunchouAssistant` | `AssistantConfig` 没写、或不在 `@SpringBootApplication` 的子包下 |
| `NoSuchBeanDefinitionException: UserMemoryRecorder` | Controller 直接注入了它，但 `ai.memory.user.enabled: false`（见 7.1） |
| `NoSuchBeanDefinitionException: ChatMemoryProvider` | `ai-memory` 依赖没引，或它的 `.imports` 没生效 |
| 助手"不记得上一句" | 装配漏了 `.chatMemoryProvider(...)` —— **不会报错**，跑第 6 步的测试 |
| 两个助手的对话串在一起 | `spring.application.name` 重名，或拼 memoryId 时漏了 `assistantId` |
| 启动报 `未找到指定的模型配置: xxx` | `ai.embed.endpoints` 漏了，或 `extract-profile` 指向了不存在的档位 |
| 长期记忆完全不生效 | `ai.memory.user.enabled: false`；或 embedding 维度与库里存量不一致（查日志 `维度不匹配`） |
| token 台账里 `user_id` 全是 `anonymous` | 请求没带 `X-User-Id` 头（见 7.2） |
| `curl -N` 看不到逐字输出 | 先确认 `-N` 加了；再看中间有没有 nginx / 网关在缓冲 |
| AI 说到一半断掉 | `spring.mvc.async.request-timeout` 小于 `SseEmitter` 的超时 |

## 验收：怎么确认真的接上了

```bash
# 第一轮：埋一句话
curl -N "http://localhost:8081/chat/stream?userId=u1&sessionId=s1&message=我是财务部的，负责月度经营分析"

# 第二轮（同一 sessionId）：它应该知道上下文
curl -N "http://localhost:8081/chat/stream?userId=u1&sessionId=s1&message=我负责什么？"

# 第三轮（换个 sessionId，同一 userId）：验证【长期记忆】跨会话
curl -N "http://localhost:8081/chat/stream?userId=u1&sessionId=s2&message=你还记得我是谁吗？"
```

第三轮能答出"财务部" → **长期记忆真的生效了**（`sessionId` 变了但 `userId` 没变，
所以只能是从 `ai_user_memory` 检索出来的）。

再换个 `userId` 问同样的问题 → 它应该**不知道**。这验证了记忆是按用户隔离的。

同时看这两张表：

```sql
SELECT user_id, content, source_assistant, created_at
FROM ai_user_memory ORDER BY created_at DESC LIMIT 10;

SELECT user_id, service_name, profile, model_name, input_tokens, output_tokens
FROM ai_token_usage ORDER BY created_at DESC LIMIT 10;
```

`ai_user_memory.source_assistant` 应该是 `assistant-yunchou`（不是你另一个服务的名字）——
这一列就是"事实跨助手共享但要能追溯"的落点。
