# 35 · 新增一个图应用：接入清单

> **触发**：想知道"现在这套东西，再加一个图要怎么做"。
>
> **前置**：34 号（建图工厂）已落地。

---

## 0. 先说清楚：现在有三种做法，代价差很多

| 做法 | 怎么做 | 代价 | 现在可行吗 |
|---|---|---|---|
| **A. 同一个服务里加第二个图** | 在 `ai-multiagent` 里再建一张图 | 高 | ❌ **不可行**（见下） |
| **B. 新建一个服务模块，复制** | 复制 `ai-multiagent` 整个模块 | 中（复制 ~10 个文件） | ✅ **推荐** |
| **C. 抽 `ai-graph` 公共模块** | 把可复用的抽出去 | 中（但改变依赖结构） | ⏸ 等第二个图写完 |

### 为什么 A 不可行（不是懒，是硬障碍）

**① `SupervisorAgent` 的返回类型写死了。** 它现在是：

```java
public interface SupervisorAgent {
    Routing route(@UserMessage String conversation);   // ← Routing 是它自己的嵌套枚举
}
```

新图需要**自己的枚举**（比如 `DocRouting{OUTLINE, POLISH, FINISH}`）。看起来可以泛型化：

```java
public interface SupervisorAgent<R extends Enum<R> & ExpertRouting> { R route(...); }
```

**但这会让 LangChain4j 失效。** `AiServices.builder()` 传的是 `SupervisorAgent.class`，
泛型擦除后 `route()` 返回的是裸 `Enum` ——
`DefaultOutputParserFactory` 会因为 `isEnum()` 走 `EnumOutputParser`，**但它拿不到"有哪几个值"**，
提示词里的 `You must answer strictly with one of these enums:` 就生成不出来。

**换句话说：每个图必须有自己的 `SupervisorAgent` 接口。** 这不是设计缺陷 ——
让两个图共用一个"调度器契约"本来就没意义，它们的路由语义完全不同。

**② `createGraph` 硬编码了 `MultiAgentState`。** 新图如果需要额外字段
（比如文档图要 `currentDocId`），得连着 `createGraph` 一起泛型化。

**③ Controller 是单例注入的。** `private final CompiledGraph<MultiAgentState> graph;`
—— 一个服务里两张图，要区分"这个请求走哪张"，那是另一个话题（路由/租户维度）。

**结论：现在一个服务 = 一张图。加图 = 加服务。**

## 1. 推荐做法：复制模块（B）

### 1.1 复制什么

```bash
cd /Users/best/project/ai_platform
cp -r ai-multiagent ai-docgraph          # ← 换成你的模块名
cd ai-docgraph
rm -rf target                            # 别把上一次的编译产物带过去
```

然后**全局替换包名**：

```
com.best.multiagent  →  com.best.docgraph
```

（IDEA 里 `Refactor → Rename` 或全局替换都行。**注意**：`@MapperScan` 里的包路径
、`resources/mapper/` 下的镜像目录名、以及任何字符串里的包名 —— 这几处**不会自动改**，
编译期也不报错。我们这个模块没有 mapper，所以少一层风险。）

### 1.2 要改的地方（完整清单）

| # | 位置 | 改什么 | 为什么 |
|---|---|---|---|
| 1 | `pom.xml` | `artifactId` → `ai-docgraph` | |
| 2 | 父 `pom.xml` | `<modules>` 加一行 | |
| 3 | 包名 | `com.best.multiagent` → `com.best.docgraph` | |
| 4 | `MultiAgentApplication` → `DocGraphApplication` | 类名 | |
| 5 | **`SupervisorAgent` 的枚举** | **重写**（值 + `@Description` + 角色名） | ★ **这是这个应用的核心业务知识** |
| 6 | `SupervisorAgent` 的 `@SystemMessage` | 重写调度规则 | 不同图的派发依据不同 |
| 7 | `MultiAgentState` | 类名 + **按需加字段** | 见 1.3 |
| 8 | `application.yml` | `port` / `spring.application.name` / `assistant-id` / `ai.mcp.servers` | ★ 见 1.4 |
| 9 | `AgentController` | `@RequestMapping` 路径 | 避免和新图概念混淆 |
| 10 | `GraphNodes` | **不用改**（除非你要改节点名） | |

### 1.3 `MultiAgentState` 怎么改

**先问：新图真的需要新字段吗？**

现有字段：`messages` / `userId` / `sessionId` / `next` / `memoryContext` /
`proposedTool` / `proposedArgs` / `proposedBy` / `approvalDecided` / `approved`。

**大多数图一个都不用加。** 需要加的场景是"某个中间产物要跨节点传递"，
比如文档图的 `currentDocId`。

加的时候**两处一起改**（漏一处就是运行时才暴露）：

```java
public static final String CURRENT_DOC_ID = "currentDocId";   // ① 常量

public static final Map<String, Channel<?>> SCHEMA = Map.of(
        ...,
        CURRENT_DOC_ID, Channels.base(() -> "")                // ② SCHEMA
);

public String currentDocId() { return this.<String>value(CURRENT_DOC_ID).orElse(""); }  // ③ 访问器
```

> ⚠️ **改 SCHEMA 会让存量 checkpoint 失效。** 新服务是新 Redis key 空间，没有存量问题 ✓
> 但如果是在**已有服务**上加字段，要知道这一点。

### 1.4 `application.yml` 必须改的四项

| 配置 | 为什么必须唯一 |
|---|---|
| `server.port` | 端口冲突 |
| `spring.application.name` | 默认会被当作 `assistantId` |
| `ai.multiagent.assistant-id` | ★ **它是两件事的标识**：① checkpoint key 的命名空间 ② 长期记忆表的 `source_assistant`。**重复了就会串号** |
| `ai.mcp.servers.*` | 每个服务用自己的 token（就是"这个图能调哪些工具"） |

其余配置——`spring.datasource` / `spring.data.redis` / `ai.chat` / `ai.embed` / `ai.memory`——
如果和现有服务相同，**可以原样留着**（22 号的配置分层方案落地后，它们会变成 import）。

### 1.5 **不用改的地方**（这份清单比"要改的"更有价值）

| 文件 | 为什么不用改 |
|---|---|
| `ExpertRouting` | 纯接口，无业务语义 |
| `MultiAgentGraphFactory` | ★ **这是 34 号的收益所在** —— 它只认枚举，不认具体业务 |
| `GraphNodes` | 四个固定节点名 |
| `SupervisorNode` | 只调 `route()` 和 `edgeKey()` |
| `ExpertNode` | 只认 `role` / `clientKey` / `ExpertAgent` / `McpToolCatalog` |
| `ToolExecuteNode` | ★ 审批 + 执行的全部逻辑 |
| `RecallMemoryNode` / `WriteMemoryNode` | 记忆读写的适配层 |
| `GraphThreadIds` / `NamespacedKeyNamingStrategy` | 纯工具类 |
| `ai-common` / `ai-memory` | **一行都不用动** |

**这意味着：新图的"代码工作"基本只剩三件事 —— 写枚举、写提示词、填 yml。**

## 2. 陷阱清单（今天踩过的每一条，按症状组织）

**这些是今天从 0 到 1 踩出来的。有了这份清单，新的图不该再踩一遍。**

### 2.1 编译期能抓到的

| 症状 | 根因 |
|---|---|
| 写 `InterruptableAction` 却找不到方法 | ★ **真接口是 `InterruptibleAction`（带 i）**；不带 i 的是**空壳标记接口** |
| 节点写好了但中断不生效 | 忘了 `AsyncNodeAction.node_async(...)` 包一层 —— **只有它内部会检测 `InterruptibleAction` 并用动态代理把可中断性带上** |
| 枚举加了值但编译报错 | 穷尽 `switch` 没覆盖（**这是好事**，说明接线点被编译器守住了） |

### 2.2 编译期抓不到、静默失效的（★ 最危险）

| 症状 | 根因 | 怎么防 |
|---|---|---|
| ★ **审批拦不住第二次危险操作** | `approvalDecided` 没被重置 → `interrupt()` 看到 `true` 直接放行 | **所有 return 路径都要过 `finishXxx()`**；两处重置（`finish()` + `/chat` 初始化） |
| ★ **用户点了"拒绝"，工具照样执行** | `apply()` 里**少了拒绝分支** | 判据必须是 `approvalDecided && !approved`（两个条件的**与**） |
| ★ **ReAct 循环转不起来**（每次都直接回调度器） | `finish()` 无条件清空了 `proposedTool`，而条件边要靠它判断 | 拆成 `finishContinue`（保留）/ `finishDone`（写 `NONE`） |
| ★ **长期记忆永远写不进去** | memoryId 手拼时**少一个 `::`** → `SessionKey.parse` 抛异常被 catch 成 warn | **用 `SessionKey.of(...).toMemoryId()`，不手拼** |
| ★ **supervisor 判 FINISH 时路由失败** | `edgeKey()` 返回小写 `"finish"`，而 Map 的 key 是 `"FINISH"` | **Map 的 key 也用 `Routing.FINISH.edgeKey()`**，不写字面量 |
| **Controller 判不出"停在中断点"** | 节点名在两处各写一遍，改名漏了一处 | **节点名走 `GraphNodes` 单一来源** |
| **记忆偶尔不生效** | 把 `state.messages()`（活引用）传给异步线程 → 并发修改异常只打在异步线程日志里 | 传 `List.copyOf(...)` |
| **日志里工具结果占十几行** | `replace` 是**按字面量**替换，`replaceAll` 才是正则 | 用 `replaceAll("\\s+", " ")` |

### 2.3 架构性的（不是 bug，是"选错了路会白干"）

| 症状 | 根因 |
|---|---|
| **工具在专家节点内部就被执行了，审批形同虚设** | 给 `AiServices` 挂了 `.tools(...)`，或注入了 `McpToolProvider` |
| **子图里的中断，父图完全感知不到** | 子图中断**不会传播**（实测）—— 父图静默返回残缺状态，Controller 看不到"需要审批" |
| **审批停不下来 / 所有操作都要审批** | 还在用 `CompileConfig.interruptBefore(...)` —— 它是**编译期无条件中断**，表达不了"按等级决定" |

## 3. 验收：四个用例，一个都不能少

```bash
# ① 低危工具 → 直接执行，不停
curl -s -X POST http://localhost:<新端口>/xxx/chat -H 'Content-Type: application/json' \
  -H 'X-User-Id: u1' -d '{"message":"<一个会命中低危工具的请求>","sessionId":"r1"}'
# 期待 {"status":"done"}，日志有"未达审批阈值，直接执行"

# ② 高危工具 → 必须停下，且工具没执行
curl -s -X POST http://localhost:<新端口>/xxx/chat -H 'Content-Type: application/json' \
  -H 'X-User-Id: u1' -d '{"message":"<一个会命中高危工具的请求>","sessionId":"r2"}'
# 期待 {"status":"waiting_approval","proposedTool":"...","proposedArgs":"..."}

# ③ 批准 → 工具执行，且【只执行一次】
curl -s -X POST http://localhost:<新端口>/xxx/approve -H 'Content-Type: application/json' \
  -d '{"sessionId":"r2","approved":true}'
grep -c "工具执行成功" <日志>          # 必须恰好 1

# ④ 连续两次高危 → 第二次照样必须停
curl -s -X POST http://localhost:<新端口>/xxx/chat ... -d '{...,"sessionId":"r2"}'
# ★ 仍期待 waiting_approval。如果返回 done —— 说明 approvalDecided 没重置
```

**加上 34 号那条硬指标：**

```bash
grep -c "调度决定" <日志>       # ★ 必须 ≤ 2（派发 + 收尾），与工具轮数无关
```

## 4. 什么时候该重构成公共模块

**触发条件：第二个图应用写完、并且验证通过之后。**

那时候你手上会有**两份真实代码**，可以做一个只有那时才能做的判断：

> **不是看"哪些类长得一样"，而是看"哪些改动必须两边同时改"。**

- **必须同时改** → 真共享 → 值得抽
- **长得像但可以各自演化** → 假共享 → 留在各自模块

**从今天的经验猜**，抽出来的大概是这三样：

| 候选 | 判断依据 |
|---|---|
| `MultiAgentGraphFactory` + `ExpertRouting` + `GraphNodes` | 它们**只认枚举、不认业务** —— 两份代码里应该逐字相同 |
| `ToolExecuteNode` | 审批逻辑是纯机制，且**改一次必须两边同时改** |
| `SupervisorNode` / `ExpertNode` | 骨架相同，但**它们认识具体 state** —— 抽出去要泛型化，收益不确定 |

**而 `SupervisorAgent` 的枚举、提示词、`MultiAgentState` 的字段——一定不会抽。** 它们是业务。

**还有一件更确定的事**：`RecallMemoryNode` / `WriteMemoryNode` 里那些
（召回文本模板、memoryId 构造、失败兜底）应该收进 **`ai-memory`** 的
`UserMemoryFacade`。**这个跟抽 `ai-graph` 无关** —— 它本来就是记忆模块的领域，
而且 `ai-memory` 不该被拖上 langgraph4j。
