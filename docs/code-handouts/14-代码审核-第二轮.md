# 二、🔴 P0

## P0-3 `DbUserMemoryStore.deleteOldest` 删的是别人 —— 字段写错了

```java
@Override
public void deleteOldest(String userId, int count) {
    if(count <= 0){
        return;
    }
    List<Long> ids = userMemoryMapper.selectOldestIds(userId, count);   // 拿到的是【主键 id】
    if (ids.isEmpty()){
        return;
    }
    // ❌ 错在这里：ids 里是 id，却拿去匹配 user_id
    userMemoryMapper.delete(new LambdaQueryWrapper<UserMemory>().in(UserMemory::getUserId, ids));
}
```

`ids` 是 `List<Long>`（主键），却拼进了 `WHERE user_id IN (...)`。实际执行的 SQL 是：

```sql
DELETE FROM ai_user_memory WHERE user_id IN (101, 102, 103)
```

`user_id` 是 `VARCHAR`，MySQL 会做隐式类型转换。两种后果，都很难看：

| 你的 userId 长什么样 | 实际后果 |
|---|---|
| UUID / 工号（`u1`、`emp_8271`） | 转成数字后全为 0 → **一条都删不掉** → 容量控制彻底失效，该用户的记忆无限增长 |
| 纯数字（`"101"`） | **删掉 `user_id` 恰好等于这些 id 值的那些用户的记忆** —— 跨用户数据删除 |

**而且它潜伏得很深**：`deleteOldest` 只在 `count > maxFactsPerUser`（默认 500）时才被调到。
所以这个 bug 可能几个月都不会显形，一旦显形就是"某些用户的记忆莫名其妙少了"。

### 修法

```java
@Override
public void deleteOldest(String userId, int count) {
    if (count <= 0) {
        return;
    }
    // 第一步：只查出要删的【主键】
    List<Long> ids = userMemoryMapper.selectOldestIds(userId, count);
    if (ids.isEmpty()) {
        // 必须挡这一下：ids 为空时 Wrapper 会生成 IN ()，
        // 而 MySQL 的 IN () 是语法错误，不是"匹配零行"
        return;
    }
    // 第二步：按【主键】删
    int deleted = userMemoryMapper.delete(
            new LambdaQueryWrapper<UserMemory>().in(UserMemory::getId, ids));

    // 第三步：核对影响行数。少了说明有并发或逻辑错，必须能看见
    if (deleted != ids.size()) {
        log.warn("用户 {} 的旧记忆清理数量不符：预期 {}，实际 {}",
                userId, ids.size(), deleted);
    }
}
```

三处变化：
1. **`UserMemory::getUserId` → `UserMemory::getId`** ← 这是真正的 bug
2. **补上 `log.warn` 核对影响行数** —— 原来 `mapper.delete()` 的返回值直接被丢了。
   这类"按主键删"是**可以精确核对**的（预期 = ids.size()），不核白不核

> 注意：`log.warn` 需要类上加 `@Slf4j`（现在 `DbUserMemoryStore` 上只有 `@RequiredArgsConstructor`）。
>
> **顺便建议**：给这个方法补一个单元测试。它是纯 SQL 逻辑，用 H2 + `@MybatisTest` 就能测，
> 而且"删错了"这种事的代价远高于测试成本。

## P0-4 `ChatAssistantTest` 没重写 —— 现在必挂

**这是上一轮 `11-代码复核报告.md` 里给过重写版、但没有落地的。** 现状：

```java
@SpringBootTest
class ChatAssistantTest {

    @Resource
    private ChatAssistant chatAssistant;

    @Test
    void chat() {
        System.out.println(chatAssistant.chat("u1","我是小明，你记住"));
    }

    @Test
    void ask() {
        System.out.println(chatAssistant.ask("u1","我是谁"));
    }
}
```

四个问题，按严重度：

**① `memoryId = "u1"` 必抛异常。** 调用链是：

```
chatAssistant.ask("u1", ...)
  → ChatMemoryProvider.get("u1")
    → SummarizingChatMemory(memoryId="u1", ...)
      → store.getMessages("u1")
        → SessionRedisKey.of(prefix, "u1")
          → SessionKey.parse("u1")                 ← 只有一个 "::"，找不到第二个
            → throw IllegalArgumentException("memoryId 格式必须是 assistantId::userId::sessionId")
```

**② `chat()` 那句什么都不会发生。** `chat()` 返回 `TokenStream`，它是**惰性**的 ——
不调 `.start()` 就不会发请求。`System.out.println` 只是打印对象，所以这条测试
既不会报错也测不出任何东西。

**③ 零断言。** 只有 `println`。测试通过与否和"记忆有没有接上"完全无关。

**④ `@SpringBootTest` 要真 MySQL + Redis + 网关。** 本地跑得了，CI 上必挂。
而且两个方法共用 `"u1"`、`ask` 依赖 `chat` 先跑 —— JUnit 不保证执行顺序。

### 修法：换成不联网的结构断言

```java
package com.best.assistant_demo.assistant;

import com.best.ai_memory.session.SummarizingChatMemoryProvider;
import com.best.ai_memory.session.memory_store.InMemorySessionMemoryStore;
import com.best.ai_memory.session.summarizer.NoOpConversationSummarizer;
import com.best.ai_memory.session.summary_store.InMemorySessionSummaryStore;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.memory.chat.ChatMemoryProvider;
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.model.chat.request.ChatRequest;
import dev.langchain4j.model.chat.response.ChatResponse;
import dev.langchain4j.service.AiServices;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

/**
 * 装配结构断言 —— 不联网、不需要 MySQL / Redis / 网关。
 *
 * <p>它们不关心模型答得好不好，只关心"记忆有没有接上"。
 * 漏挂 chatMemoryProvider 是静默失效（表现为"不记得上一句"，不报错），
 * 只有这种断言能拦住。
 */
class ChatAssistantTest {

    /** 假模型：把"这次看到了几条消息"当回复返回，用来观察记忆是否生效 */
    static class MessageCountingChatModel implements ChatModel {
        @Override
        public ChatResponse doChat(ChatRequest request) {
            return ChatResponse.builder()
                    .aiMessage(AiMessage.from("看到了 " + request.messages().size() + " 条消息"))
                    .build();
        }
    }

    private ChatAssistant assemble(ChatMemoryProvider provider) {
        return AiServices.builder(ChatAssistant.class)
                .chatModel(new MessageCountingChatModel())
                .chatMemoryProvider(provider)
                .build();
    }

    private ChatMemoryProvider provider() {
        return new SummarizingChatMemoryProvider(
                new InMemorySessionMemoryStore(),
                new InMemorySessionSummaryStore(),
                new NoOpConversationSummarizer(),
                20);
    }

    @Test
    @DisplayName("同一会话的第二轮能看到第一轮的历史")
    void secondTurnSeesFirst() {
        ChatAssistant assistant = assemble(provider());

        String first  = assistant.ask("assistant-demo::u1::s1", "第一句");
        String second = assistant.ask("assistant-demo::u1::s1", "第二句");

        // 不写死具体条数（@SystemMessage 算不算一条会随版本变），
        // 只断言"第二轮看到的比第一轮多" —— 足以证明 provider 挂上了
        int n1 = Integer.parseInt(first.replaceAll("\\D", ""));
        int n2 = Integer.parseInt(second.replaceAll("\\D", ""));
        assertThat(n2).isGreaterThan(n1);
    }

    @Test
    @DisplayName("不同会话互相看不到")
    void differentSessionIsolated() {
        ChatAssistant assistant = assemble(provider());

        String a = assistant.ask("assistant-demo::u1::s1", "给会话 s1 说的话");
        String b = assistant.ask("assistant-demo::u1::s2", "给会话 s2 说的话");

        assertThat(b.replaceAll("\\D", "")).isEqualTo(a.replaceAll("\\D", ""));
    }

    @Test
    @DisplayName("不同助手互相看不到（只换 assistantId）")
    void differentAssistantIsolated() {
        ChatAssistant assistant = assemble(provider());

        String a = assistant.ask("assistant-demo::u1::s1", "demo 助手说的话");
        String b = assistant.ask("another-assistant::u1::s1", "另一个助手说的话");

        assertThat(b.replaceAll("\\D", "")).isEqualTo(a.replaceAll("\\D", ""));
    }
}
```

> 第三个用例把"assistantId 参与隔离"这个决定固化成**可执行断言**。
> 以后谁把 `SessionKey` 改回两段、或者拼 memoryId 时漏掉 assistantId，它会红 —— 比注释可靠得多。
>
> 这个文件建议**每个新助手模块都抄一份**（改包名和类名即可），交付单 10 里已经把它列成必写项。

# 三、🟠 P1

## P1-3 `UserMemoryRecorder.isDuplicate` 没过滤维度差异 → 一条脏数据能永久堵死写入

```java
private boolean isDuplicate(float[] candidate, List<UserMemory> existing) {
    if (existing.isEmpty()) {
        return false;
    }
    return existing.stream()
            .filter(m -> m.getEmbedding() != null && m.getEmbedding().length > 0)
            // ❌ 少了维度检查
            .anyMatch(m -> CosineSimilarity.between(candidate, m.getEmbedding())
                    >= config.dedupThreshold());
}
```

而 `CosineSimilarity.between` 在维度不一致时**抛异常**：

```java
if(a.length != b.length){
    throw new IllegalArgumentException("向量维度不一致：" + a.length + " vs " + b.length + "...");
}
```

**这条异常会从 `isDuplicate` 一路抛到 `record()` 的调用方**，被 `recordAsync` 的
`catch (Exception e)` 接住 → 只留一行 error 日志，什么也写不进去。

**而 `MemoryRecallService` 那边是做了过滤的**（`isValid` 里判了 `length != queryVector.length`
并只报一次 warn）。**两个地方对同一个风险的处理不对称** —— 读的那侧防住了，写的那侧没有。

**后果**：只要库里存在一条维度不同的历史向量（`ai.embed.dimensions` 被改过之后的老数据），
**这个用户的每一条新事实都会写入失败**，而且看起来只是"长期记忆不好使"。

### 修法

```java
private boolean isDuplicate(float[] candidate, List<UserMemory> existing) {
    if (existing.isEmpty()) {
        return false;
    }
    return existing.stream()
            .filter(m -> m.getEmbedding() != null && m.getEmbedding().length > 0)
            // ⚠️ 维度必须一致才能比。库里可能残留 dimensions 改过之前的老向量
            //   （比如 1024 维 vs 现在 1536 维），而 CosineSimilarity 对维度不一致
            //   是抛异常而不是返回 0 —— 不挡这一下，一条脏数据会让该用户的新事实
            //   全部写不进去。这和 MemoryRecallService.isValid 的处理是对称的。
            .filter(m -> m.getEmbedding().length == candidate.length)
            .anyMatch(m -> CosineSimilarity.between(candidate, m.getEmbedding())
                    >= config.dedupThreshold());
}
```

## P1-4 `ChatModelProperties.endpoints` 缺 `@DefaultValue` + `getEndpoint` 没判 null

两个类不对称：

```java
// EmbeddingModelProperties —— 有 ✓
@DefaultValue Map<String, Endpoint> endpoints

// ChatModelProperties —— 没有 ✗
Map<String, Endpoint> endpoints
```

而 `ModelProperties.getEndpoint` 的守卫只判了空 Map，**没判 null**：

```java
default E getEndpoint(String profile){
    Map<String, E> endpoints = endpoints();
    if (endpoints.isEmpty() || !endpoints.containsKey(profile)){    // ← endpoints 为 null 时在这里 NPE
        throw new IllegalArgumentException("未找到制定配置");
    }
    return endpoints.get(profile);
}
```

**症状**：如果 `application.yml` 里整段 `ai.chat.endpoints` 漏了，你不是得到
"未找到指定的模型配置"这个能看懂的报错，而是：

```
java.lang.NullPointerException
    at com.best.ai_common.properties.ModelProperties.getEndpoint(ModelProperties.java:14)
```

**在两处各修一下，双保险**：

```java
// ChatModelProperties：补上 @DefaultValue，与 EmbeddingModelProperties 对齐
@DefaultValue Map<String, Endpoint> endpoints
```

```java
// ModelProperties：守卫补 null，并把已配置的 key 打出来（排查快十倍）
default E getEndpoint(String profile){
    Map<String, E> endpoints = endpoints();
    if (endpoints == null || endpoints.isEmpty() || !endpoints.containsKey(profile)){
        throw new IllegalArgumentException(
                "未找到指定的模型配置: " + profile
                        + "，已配置的有 " + (endpoints == null ? Set.of() : endpoints.keySet()));
    }
    return endpoints.get(profile);
}
```

> 注意原文案是「未找到**制定**配置」——「制定」应为「指定」，顺手改掉。

## P1-5 `singleText()` / `text()` 在多模态与工具消息上会炸

两个 `render` 方法都直接调这两个方法，而它们**不是无条件的 getter**：

```java
// LlmConversationSummarizer.textOf
if(m instanceof UserMessage um) return um.singleText();
if(m instanceof AiMessage am) return am.text();
```

| 方法 | 什么时候会炸 |
|---|---|
| `UserMessage.singleText()` | 消息含**多个 content**（比如图片 + 文字）时抛 `IllegalStateException` —— 它的语义是"只有唯一一段纯文本时才能取" |
| `AiMessage.text()` | 消息**只有工具调用**、没有文本时返回 null（部分版本抛异常） |

现在不炸，因为你还没接图片和工具。**但你马上就要接 MCP 了** —— 一旦助手开始调工具，
`AiMessage` 里就会出现没有文本的轮次，摘要会开始频繁失败。

注意 `LlmUserMemoryExtractor.render` 里是这么写的：

```java
} else if (m instanceof AiMessage am && am.text() != null) {   // ← 判了 null
    sb.append("助手：").append(am.text()).append('\n');
}
```

**它对 `AiMessage` 判了 null，但对 `UserMessage.singleText()` 没做任何防护** —— 这个不对称
说明作者已经意识到"`text()` 可能为空"，只是漏了另一半。

### 修法（两个类各改一处）

**`LlmConversationSummarizer`**（类上已有 `@Slf4j`）：

```java
    private static String render(List<ChatMessage> messages){
        StringBuilder sb = new StringBuilder();
        for(ChatMessage m: messages){
            String text = textOf(m);
            // 取不到文本的消息直接跳过 —— 拼出"助手: null"这种行没有意义，
            // 还会污染摘要
            if (text == null || text.isBlank()) {
                continue;
            }
            sb.append(roleOf(m)).append(": ").append(text).append('\n');
        }
        return sb.toString();
    }

    private static String roleOf(ChatMessage m){
        if(m instanceof UserMessage) return "用户";
        if(m instanceof AiMessage) return "助手";
        if(m instanceof SystemMessage) return "系统";
        return "其他";
    }

    /**
     * 把消息转成纯文本，取不到就返回 null。
     *
     * <p>必须 try-catch 而不能只判 null：
     * <ul>
     *   <li>{@code UserMessage.singleText()} 在消息含多个 content（图片+文字）时
     *       会抛 IllegalStateException，不是返回 null</li>
     *   <li>{@code AiMessage.text()} 在"只有工具调用没有文本"的轮次上可能为 null</li>
     * </ul>
     * 这些消息没法进摘要，跳过比让整次摘要失败好 —— 摘要失败是<b>静默丢内容</b>。
     */
    private static String textOf(ChatMessage m){
        try {
            if(m instanceof UserMessage um) return um.singleText();
            if(m instanceof AiMessage am) return am.text();
            if(m instanceof SystemMessage sm) return sm.text();
        } catch (Exception e){
            log.warn("消息无法转成纯文本，已从摘要中跳过: {}", m.getClass().getSimpleName());
        }
        return null;
    }
```

**`LlmUserMemoryExtractor`** 同样处理（它已经有 `@Slf4j`）：

```java
    private static String render(List<ChatMessage> turns) {
        StringBuilder sb = new StringBuilder();
        for (ChatMessage m : turns) {
            // 只抽用户说的 + 助手的回复，其它类型（工具结果等）不进提示词
            boolean isUser = m instanceof UserMessage;
            if (!isUser && !(m instanceof AiMessage)) {
                continue;
            }
            String text = textOf(m);
            if (text == null || text.isBlank()) {
                continue;
            }
            sb.append(isUser ? "用户：" : "助手：").append(text).append('\n');
        }
        return sb.toString();
    }

    /** 见 LlmConversationSummarizer.textOf 的说明：不能只判 null，必须 try-catch */
    private static String textOf(ChatMessage m) {
        try {
            if (m instanceof UserMessage um) return um.singleText();
            if (m instanceof AiMessage am) return am.text();
        } catch (Exception e) {
            log.warn("消息无法转成纯文本，已跳过: {}", m.getClass().getSimpleName());
        }
        return null;
    }
```

> **另一个顺带的好处**：这样改之后，`ToolExecutionResultMessage` 之类的消息会被自动跳过，
> 而不是像现在这样被 `render` 忽略（`LlmUserMemoryExtractor`）或者拼成"其他: "（摘要器）。

## P1-6 抽取提示词是旧版本 —— 缺「跨助手共享」判据

交付单 05 里已经改过，但**代码没同步**。现在 `LlmUserMemoryExtractor` 的
`@SystemMessage` 里没有这一段：

```
注意：抽出来的事实是【跨助手共享】的 —— 用户在客服里说的话，
运筹眼助手也会看到。所以判断标准里多一条：
换个场景、换个助手，这句话还成立吗？不成立就别抽。
```

而"不该抽的"清单里也缺一条：

```
- 只对本次任务成立的上下文（"这次用表格"、"这个订单"、"刚才那个报表"）
```

**为什么这条重要**：事实是跨助手共享的（这是刻意的设计），所以"这次用表格"这种
只对本次会话成立的偏好，会被写进全局事实库，然后在**别的助手**的对话里被检索出来注入 ——
那一轮它就不成立了。

### 修法：把这两段加进 `@SystemMessage`

```java
        @SystemMessage("""
                你从对话里抽取【关于用户本人的、值得长期记住的】信息。

                注意：抽出来的事实是【跨助手共享】的 —— 用户在客服里说的话，
                运筹眼助手也会看到。所以判断标准里多一条：
                换个场景、换个助手，这句话还成立吗？不成立就别抽。

                该抽的：
                - 身份与角色（部门、岗位、职责范围）
                - 稳定的偏好（喜欢什么形式的输出、习惯用什么工具）
                - 明确说过的长期目标、约束、决策
                - 用户自己确认过的事实

                不该抽的：
                - 一次性的问题（"帮我查一下上周的数据"）
                - 只对本次任务成立的上下文（"这次用表格"、"这个订单"、"刚才那个报表"）
                - 助手说的话（只抽用户的信息）
                - 寒暄、客套、情绪
                - 临时的状态（"我现在有点忙"）
                - 从对话里推断出来的、用户没说过的结论

                每条写成一句话，以「用户」开头，不要分点、不要编号。

                （示例部分保持不变）
                """)
```

> 这一改只动提示词文案，不动任何逻辑。改完建议手工跑一次抽取，看输出里
> 还会不会出现"这次/这个/刚才"这类指代。

> 我建议**删掉注解**（类里确实没有日志需求）。

## 4.2 `InMemorySessionMemoryStore.getMessages` 的 null 分支返回了不可变集合

```java
@Override
public List<ChatMessage> getMessages(Object memoryId) {
    List<ChatMessage> stored = store.get(memoryId);
    if(stored == null){
        return List.of();          // ← 不可变
    }
    return new ArrayList<>(stored);  // ← 可变
}
```

**同一个方法的两条路径返回了不同可变性的对象。** `ChatMemoryStore` 的契约是
"必须返回可变副本"（LangChain4j 拿到之后会**直接 `add()` 改它**）——
这是交付单 01 里专门写过、还配了两个测试固化的。

现在不炸，因为 `SummarizingChatMemory.add()` 里自己包了一层 `new ArrayList<>(...)`。
但**这是靠调用方的宽容活着**，契约本身已经破了。

```java
    if(stored == null){
        // 不用 List.of()：ChatMemoryStore 的契约要求返回【可变】副本。
        // 虽然当前调用方（SummarizingChatMemory）会再包一层，
        // 但契约不该靠调用方兜着 —— 换个调用方就炸了。
        return new ArrayList<>();
    }
```

> 顺带：`ai-memory/test` 下只有 `SessionKeyTest` 一个测试文件。
> `InMemorySessionMemoryStore` 是纯内存逻辑，测它不用任何外部依赖 —— 是补测试成本最低的地方。

## 4.4 摘要没有长度上限

`LlmConversationSummarizer` 的提示词说"写成一到两段"，但**没有任何硬约束**：

- 摘要的输入是「旧摘要 + 窗口外的消息」
- 输出不限制长度 → 下一轮的输入就更长 → 再下一轮更长……

**这是"摘要的摘要的摘要"膨胀问题。** 短期内看不出来，跑几千轮之后摘要本身会变成新的负担，
而摘要的全部意义就是压缩。

两个便宜的缓解（选一个就够）：

```java
// 方案 A：在提示词里加硬约束（推荐，零代码）
// 6. 总长度不超过 300 字，宁可漏掉细节也要控制长度
```

```java
// 方案 B：代码里兜一下
private static final int MAX_SUMMARY_CHARS = 600;
...
String trimmed = summary.trim();
if (trimmed.length() > MAX_SUMMARY_CHARS) {
    log.warn("摘要过长({} 字)，已截断", trimmed.length());
    trimmed = trimmed.substring(0, MAX_SUMMARY_CHARS);
}
summaryStore.save(memoryId, trimmed);
```

> 我推荐 **A** —— 在提示词里约束。截断（B）会把句子切在半截，下一轮模型拿到一个残句，
> 可能补充出错误内容。**A 是让模型自己控制在长度内，语义完整。**

## 4.5 每轮都加载用户的全量向量 —— 一期可以接受，但要记着

`UserMemoryRecorder.record()` 里去重是这么做的：

```java
List<UserMemory> existing = userMemoryStore.findByUserId(userId, config.maxFactsPerUser());
```

`maxFactsPerUser` 默认 500，每条 1536 维 = 6 KB → **每次抽取要往 JVM 里捞 3 MB 向量**，
然后是 5 × 500 = 2500 次 1536 维余弦计算。

**现在不用改**，因为：单用户 3 MB、计算量是毫秒级，而且只在异步线程上跑。
但心里要有个数：**这是 O(事实数) 的操作，每轮都做一次。**

真要优化时，方向是"只跟最近的 N 条比" —— 去重的目的是防重复，而重复的事实
通常是**短时间内重复说的**，没有必要跟半年前的 500 条全比一遍：

```java
// 优化方向（现在不要做）：只跟最近 50 条比
List<UserMemory> existing = userMemoryStore.findByUserId(userId, 50);
```

> 但注意这会**改变语义**：老事实不再参与去重 → 用户过半年又说一遍同样的话，会存第二条。
> 这个取舍要等你观测到真实性能问题之后再定。

## 4.6 `RedisSessionMemoryStore.updateMessages` 的 TTL 重置行为


每次写入都刷新 TTL —— 也就是**只要用户还在聊，历史就不过期**（滑动窗口语义）。
这**是对的**，但值得在注释里点明，因为它和 `ttl: 48h` 这句话给人的直觉（"48 小时后就没了"）
不一样。现在的代码里没有一行注释说明这件事。

同理，`RedisSessionSummaryStore.save` 也用每次写入续期。

## 4.7 `SessionMemoryStore` 是 `ChatMemoryStore` 的空别名接口

```java
public interface SessionMemoryStore extends ChatMemoryStore {
}
```

它没有增加任何方法，纯粹是换个名字。这是**可以接受**的（平台自己的契约名，
将来换实现时使用方不用改），但价值边界要说清楚：

> **它的价值只体现在"将来会加方法"上。** 如果它永远不加，它就只是 `ChatMemoryStore` 的别名 ——
> 而这层别名带来的是：每个新实现类都要 `implements SessionMemoryStore`，
> 每个使用方都要记两个名字。

**判断标准很简单**：什么时候你会往里加方法？比如"列出某个用户的所有会话"
（`listSessions(userId)`，合规删除时需要）。**真加了这个方法的那天，它就物有所值了。**

在那之前，不用动它 —— 因为换名字的收益现在看不见，而成本（改所有引用）是真实的。

## 4.8 `MemoryRecallService` 的 `dimensionMismatchReported` 只在实例内生效

# 五、⚪ 一个观察：`ConversationSummarizer.append` 是同步的

这条在交付单 10 里提过一次，这里补上**具体量级**：

```java
// SummarizingChatMemory.add() 里
if(overflow > 0){
    List<ChatMessage> evicted = new ArrayList<>(all.subList(0, overflow));
    summarizer.append(id, evicted);      // ← 一次真实的 LLM 调用，同步
    all = new ArrayList<>(all.subList(overflow, all.size()));
}
store.updateMessages(id, all);
```

`AiServices` 的执行顺序是：**先 `chatMemory.add(userMessage)`，再调模型**。
所以第 21 轮（窗口刚满）那次请求，用户要等**两次模型调用**：

```
用户提问 → 摘要生成（1 次 LLM 调用，几秒）→ 主对话（1 次 LLM 调用，流式）
```

**这是设计使然，不是 bug。** 但如果你发现"第 21 轮特别慢"，原因就在这里。

真要改成异步，方向是把 `LlmConversationSummarizer` 的 `append` 改成丢给
`TaskExecutor`（和 `UserMemoryRecorder.recordAsync` 一样的做法）。代价是：
**摘要可能来不及生成，用户下一轮问早期内容时它会答不上来** —— 这正是摘要存在的意义。
所以我的建议是**保持同步**，但把这件事写进注释（现在没有）。
