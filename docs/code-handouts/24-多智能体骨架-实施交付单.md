## 0. 前置：API 验证结果

依赖已在本机 `.m2`（core 1.9.2 / langchain4j 1.9.2 / redis-saver 1.9.2），
以下签名全部用 `javap` 核实过：

### ✅ 设计文档写对的

| 用法 | 实际签名 |
|---|---|
| `new StateGraph<>(SCHEMA, State::new)` | `StateGraph(Map<String,Channel<?>>, AgentStateFactory<State>)` |
| `node_async(node)` | `AsyncNodeAction.node_async(NodeAction<S>)` |
| `edge_async(edge)` | `AsyncEdgeAction.edge_async(EdgeAction<S>)` |

| `RunnableConfig.builder().threadId(x)` | ✓ |
| `graph.invoke(input, config)` | 两个重载都存在：`invoke(GraphInput, RunnableConfig)` ✓ / **`invoke(Map, RunnableConfig)` ⚠️ 已弃用（forRemoval）** —— 所以实际要写成 `invoke(GraphInput.args(input), config)`，见下方「已弃用 API 扫描」 |
| `NodeAction.apply(state)` | `Map<String,Object> apply(T) throws Exception` ✓ |

### ❌ 设计文档写错的三处（本文已修正）

| 设计文档 | 实际 |
|---|---|
| `new MessageChannel.Appender()` | **没有 `MessageChannel` 这个类** → 用 `Channels.appender(ArrayList::new)` |
| `new Channel.LastValue()` | **没有这个类** → 用 `Channels.base(() -> "")` |
| `RedisSaver` 坐标不确定 | ✅ `org.bsc.langgraph4j:langgraph4j-redis-saver:1.9.2` **确实存在**，`Builder` 有 `host/port/password/ttl/stateSerializer/redissonClient` |

### 🔴 一个设计文档没提到的重要事实

**`langgraph4j-redis-saver` 依赖的是 Redisson**，而你的项目用的是 **Lettuce**（`spring-boot-starter-data-redis` 默认）。

→ 引它 = **两套 Redis 客户端并存**。骨架阶段可以接受（多占一点内存和连接），
但要知道这件事。`Builder` 提供了 `redissonClient(RedissonClient)` 可以复用外部实例，
等你真想统一客户端时用得上。

### 🔴 第二个：`LC4jStateSerializer` 是必需的

`ChatMessage` 用 Java 原生序列化有问题，`langchain4j` 集成模块提供了
`LC4jStateSerializer`（内部注册了 `ChatMesssageSerializer` / `AiMessageSerializer` /
`ToolExecutionRequestSerializer` 等）。**不注册它，RedisSaver 存消息会失败。**

### 中断的处理方式（关键）

`GraphInterruptException extends GraphRunnerException`，且有静态方法
`GraphInterruptException.of(Throwable)` 返回 `Optional`。

配对使用最稳的写法：**try-catch 住任何异常 → 用 `of()` 判断是不是中断 → 再查 `getState()`**。
这样不依赖"它到底抛不抛异常"这个我无法从签名确定的细节。

### ✅ 补充验证：supervisor 用枚举返回类型

`SupervisorAgent.route()` 的返回类型从 `String` 改成嵌套枚举 `Routing`。三条依据全部核实过：

| 结论 | 证据 |
|---|---|
| **LangChain4j 原生支持枚举返回** | `DefaultOutputParserFactory.get()`：`if (rawClass.isEnum()) return new EnumOutputParser<>(...)`；另有 `EnumListOutputParser` / `EnumSetOutputParser` |
| **`@Description` 确实生效** | `EnumOutputParser.getEnumDescription()` 反射读取它；`Description` 的保留策略是 `RUNTIME`，已用 `javap -v` 确认 |
| **不引入网关兼容性风险** | `DefaultAiServices.supportsJsonSchema()` 取决于 `chatModel.supportedCapabilities()`，而 `OpenAiChatModel.supportedCapabilities()` 默认返回**空集**（只有构造时显式传 `responseFormat("json_schema")` 才会补上 `RESPONSE_FORMAT_JSON_SCHEMA`）→ 走提示词路径，**请求体里不会出现 `response_format`** |

解析行为（读 `EnumOutputParser` 源码得出）：
- 匹配用 `equalsIgnoreCase`，大小写不敏感；
- 会先剥掉模型偶尔套的方括号（`[EXPERT_A]` → `EXPERT_A`）；
- 兼容 JSON 形态（`{"value":"EXPERT_A"}`）；
- **匹配不上就抛 `OutputParsingException`**（`extends LangChain4jException`），**不会返回 null** ——
  所以调用方必须 try-catch（`SupervisorNode` 里已经这么做了）。

> ⚠️ **但这里有个静默开关**：哪天有人给 `ChatModel` 显式加上 `.responseFormat("json_schema")`，
> 或手工传 `supportedCapabilities(RESPONSE_FORMAT_JSON_SCHEMA)`，
> 行为就会**静默切换**到原生 JSON 模式 —— 那时网关必须认得 `response_format` 参数。
> 现在不配，就是安全的。

### ⚠️ 已弃用 API 扫描（本轮新增）

把这篇用到的 langgraph4j API 全过了一遍 `@Deprecated`。`CompiledGraph` 里共 5 个方法带
**`@Deprecated(forRemoval = true)`**（注意：不只是"不推荐"，是**计划移除**）：

| 已弃用（forRemoval） | 官方替代 |
|---|---|
| **`invoke(Map, RunnableConfig)`** ← 初稿用到了这一个 | `invoke(GraphInput, RunnableConfig)` |
| `invoke(Map)` | 同上 |
| `stream(Map, RunnableConfig)` | `stream(GraphInput, RunnableConfig)` |
| `stream(Map)` | 同上 |
| `streamSnapshots(Map, RunnableConfig)` | `streamSnapshots(GraphInput, RunnableConfig)` |

弃用理由（源码 javadoc 原文）：*"use `invoke(GraphInput, RunnableConfig)` instead
**to have more control over the execution configuration**"* ——
也就是说 `GraphInput` 是统一入口，把「新输入 / 恢复」两种情况收进一个类型。

**修法就是包一层**，因为弃用版本的实现本身长这样（源码原文，逐字）：

```java
@Deprecated(forRemoval = true)
public Optional<State> invoke(Map<String,Object> inputs, RunnableConfig config) {
    return invokeFinal(inputs == null ? GraphInput.resume() : GraphInput.args(inputs), config)
            .map(NodeOutput::state);
}
```

所以 `invoke(input, config)` 与 `invoke(GraphInput.args(input), config)` **语义完全等价** ——
不是行为变更，是签名迁移。

> 🔎 **顺手发现一个隐藏语义**：上面那行三元表达式说明，**传 `null` 会被解释成「恢复」而不是「新输入」**。
> 我们的 `/chat` 传的是非 null 的 map，走的是 `args` 分支，没问题。
> 但如果哪天有人图省事传了个 null，行为会从"开始新对话"静默变成"续跑上一次的 checkpoint"。
> 这是那个被弃用的重载最阴的地方 —— 也是它该被弃用的原因之一。

**其余用到的 API 全部未弃用**（逐个 `javap -v` 确认过，没有任何 `Deprecated` 标记）：
`StateGraph` 的构造器 / `addNode` / `addEdge` / `addConditionalEdges` / `compile`、
`CompileConfig.Builder` 全部方法、`RunnableConfig.Builder`、`GraphInput.resume`、
`AsyncNodeAction.node_async` / `AsyncEdgeAction.edge_async`、`NodeAction` / `EdgeAction`、
`Channels.appender` / `Channels.base`、`GraphDefinition.START` / `.END`、
`GraphInterruptException.of`、`StateSnapshot.nextNodeId` / `.state`、
`AgentState.value(String)`、`MemorySaver`、`BaseCheckpointSaver`、
`RedisSaver` / `RedisSaver.Builder`、`LC4jStateSerializer`。

> `AgentState` 上有个坑值得记：**双参数的 `value(String, T)` / `value(String, Supplier<T>)` 已弃用**，
> 但单参数的 `value(String)` → `Optional<T>` **没有**。本篇的 `MultiAgentState` 用的正是单参数版本 ✓
>
> 另外 `StateGraph.getStateFactory()` / `addSubgraph(...)`、`RunnableConfig.graphPath()`、
> `RedisSaver.clearCheckpointsCache(String)`、`AgentState.mergeWith(Map, Map)` 也已弃用 ——
> 本篇都没用到，但将来翻文档时可能撞上。

## 5. `state/MultiAgentState.java`

```java
package com.best.multiagent.state;

import dev.langchain4j.data.message.ChatMessage;
import org.bsc.langgraph4j.state.AgentState;
import org.bsc.langgraph4j.state.Channel;
import org.bsc.langgraph4j.state.Channels;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;

/**
 * 图的共享状态。
 *
 * <p>langgraph4j 的 State 是一条条"通道"（Channel）组成的，每个通道有自己的合并策略。
 * 选错策略的症状很难查 —— 详见下方每个通道的说明。
 */
public class MultiAgentState extends AgentState {

    public static final String MESSAGES        = "messages";
    public static final String USER_ID         = "userId";
    public static final String NEXT            = "next";
    public static final String MEMORY_CONTEXT  = "memoryContext";
    public static final String PENDING_ACTION  = "pendingAction";
    public static final String APPROVED        = "approved";

    /**
     * 通道声明。这个 Map 决定了"节点返回的 Map 怎么合并进当前状态"。
     *
     * <p>两类策略，选错的后果完全不同：
     * <ul>
     *   <li>{@code appender} —— 追加到列表。只增不减，适合历史。用错在"当前值"上会无限膨胀。</li>
     *   <li>{@code base} —— 覆盖。适合"当前值"。用错在历史上一句话就会被顶掉。</li>
     * </ul>
     */
    public static final Map<String, Channel<?>> SCHEMA = Map.of(
            // 对话历史：只增不减。必须用 appender
            MESSAGES,        Channels.<ChatMessage>appender(ArrayList::new),
            // 以下五个都是"当前值"语义 —— 用 base（覆盖），不能用 appender
            USER_ID,         Channels.base(() -> ""),
            NEXT,            Channels.base(() -> ""),
            MEMORY_CONTEXT,  Channels.base(() -> ""),
            PENDING_ACTION,  Channels.base(() -> ""),
            APPROVED,        Channels.base(() -> false)
    );

    public MultiAgentState(Map<String, Object> initData) {
        super(initData);
    }

    // ---------------------------------------------------------------- 类型安全访问

    @SuppressWarnings("unchecked")
    public List<ChatMessage> messages() {
        return this.<List<ChatMessage>>value(MESSAGES).orElseGet(List::of);
    }

    public String userId()          { return this.<String>value(USER_ID).orElse(""); }
    public String next()            { return this.<String>value(NEXT).orElse(""); }
    public String memoryContext()   { return this.<String>value(MEMORY_CONTEXT).orElse(""); }
    public String pendingAction()   { return this.<String>value(PENDING_ACTION).orElse(""); }
    public boolean approved()       { return this.<Boolean>value(APPROVED).orElse(false); }
}
```

> **`Channels.<ChatMessage>appender(...)` 那个显式泛型不能省。** 在 `Map.of(...)` 里
> 编译器推不出 `T`（因为目标类型是 `Channel<?>`），不写会编译错误。

## 6. `agent/SupervisorAgent.java`

```java
package com.best.multiagent.agent;

import dev.langchain4j.model.output.structured.Description;
import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.UserMessage;

/**
 * 调度智能体。
 *
 * <p>骨架阶段它只做一件事：看对话，输出下一个该由谁处理。
 * 用 AiServices 写而不是手写模型调用 —— 因为这样模型注册、重试、计量全都自动接上。
 */
public interface SupervisorAgent {

    /**
     * 路由决策 —— supervisor 的输出契约。
     *
     * <p><b>为什么是枚举而不是 String。</b> 返回 String 时，LangChain4j 不做任何格式约束
     * （String 属于 {@code schemaNotRequired} 的类型，连格式说明都不会追加），
     * 于是只能靠"提示词里写一句只回一个词" + 调用方自己从文本里「捞」节点名。
     * 而"捞"在多命中时是不确定的 —— 详见 SupervisorNode 里那段说明。
     *
     * <p>换成枚举之后 LangChain4j 会自动做两件事：
     * <ol>
     *   <li>往提示词追加 "You must answer strictly with one of these enums:"，
     *       并把每个常量连同它的 {@code @Description} 一起列出来；</li>
     *   <li>把模型输出反向解析成枚举常量 —— 大小写不敏感，还会去掉模型偶尔加的 [方括号]。</li>
     * </ol>
     * 于是"能取哪些值"由框架保证，不再依赖提示词有没有被遵守。
     *
     * <p><b>不会引入网关兼容性风险。</b> LangChain4j 只有在 ChatModel 自称支持
     * {@code RESPONSE_FORMAT_JSON_SCHEMA} 时，才会走原生 JSON schema、往请求里加
     * {@code response_format} 参数；而 {@code OpenAiChatModel} 默认的 supportedCapabilities
     * 是空集，所以实际走的是"往提示词里塞格式说明"这条路，请求体不变。
     *
     * <p>⚠️ 但这是个静默开关：哪天有人给模型显式加上 {@code .responseFormat("json_schema")}，
     * 行为就会切到原生 JSON 模式 —— 那时网关必须认得 {@code response_format} 参数。
     */
    enum Routing {

        @Description("需要【执行操作】的任务：增删改、下单、发消息等会产生副作用的动作")
        EXPERT_A,

        @Description("只需要【查询或回答】的任务：查数据、解释、分析")
        EXPERT_B,

        @Description("任务已经完成，不需要再派发 —— 最近几轮里已经有明确的结论或回答")
        FINISH
    }

    /**
     * @param conversation 压平后的对话文本
     * @return 下一个该交给谁。**不可能为 null** —— 解析不出来时 LangChain4j 抛
     *         {@code OutputParsingException}，而不是返回 null，所以调用方要 try-catch。
     */
    @SystemMessage("""
            你是任务调度器。根据对话内容，判断下一步该交给谁。

            判断依据：如果最近的对话里已经有明确的结论或回答，就选 FINISH。
            """)
    Routing route(@UserMessage String conversation);
}
```

> **三行提示词被删掉了，这是本次改动的直接收益。** 原来那三行
> "可选的下一步（只回一个词，不要有其他内容）：- expertA：..." 里的信息
> **全部搬进了 `@Description`** —— 而框架会把它们自动附在提示词后面，实际发给模型的是：
>
> ```
> You must answer strictly with one of these enums:
> EXPERT_A - 需要【执行操作】的任务：增删改、下单、发消息等会产生副作用的动作
> EXPERT_B - 只需要【查询或回答】的任务：查数据、解释、分析
> FINISH - 任务已经完成，不需要再派发 —— 最近几轮里已经有明确的结论或回答
> ```
>
> 这正是原来手写提示词的加强版，而且**改枚举时提示词自动跟着变** ——
> 不会出现"代码改了、提示词忘了改"这种漂移。（`@Description` 的保留策略是 RUNTIME，
> 框架确实能反射读到，这一点我验证过。）
>
> 两点细节：
> - 枚举名会被 `name().toUpperCase()` 输出。`EXPERT_A` 本身就是大写，所以显示不变；
>   但如果写成 `expertA`，提示词里会显示 `EXPERTA`（无下划线）—— 这就是选 `EXPERT_A` 的原因。
> - 解析侧是 `equalsIgnoreCase`，所以模型返回 `expert_a`、`[EXPERT_A]`、甚至
>   `{"value":"EXPERT_A"}` 都能正确识别。容错比我们手写的 `contains` 匹配好得多。

### 6.1 为什么不连 state 里的 `next` 也一起换成枚举？

这是这个改动必然会引出的追问。答案是**不能，也没必要** —— 有一个硬约束 + 一个软理由。

**硬约束：条件边映射表的 key 恒定是 `String`。**

```java
// langgraph4j 的真实签名（javap 出来的，改不了）
public StateGraph<State> addConditionalEdges(
        String source,
        AsyncEdgeAction<State> action,      // apply(S) → CompletableFuture<String>
        Map<String, String> mappings)       // ← key 是 String
```

`AsyncEdgeAction` 的返回类型被框架写死成 `CompletableFuture<String>`。
就算让 `state.next()` 返回枚举，也得在边上再转回字符串 —— 那只是把转换从节点挪到了边上，
一步都没省，反而多了一个类型。

**软理由：state 是要被序列化进 Redis 的，String 是最安全的载荷。**

`state` 会被 `RedisSaver` + `LC4jStateSerializer` 序列化。`Channels.base` 确实是泛型的，
放枚举理论上能编译（`Channels.base(() -> Routing.FINISH)`），但那引入一条**没验证过的序列化路径** ——
而枚举在这个 state 里只是个"中转值"，马上就被条件边消费掉，没有持久化的价值。

**所以边界是这三条：**

| 在哪 | 用什么 | 为什么 |
|---|---|---|
| Agent 的**输出契约** | `Routing` 枚举 | 需要给模型加格式约束 —— 这正是本次要解决的问题 |
| `SupervisorNode` 的**入参** | `Routing` 枚举 | 接住上面的契约，用穷尽 switch 转成 key |
| state 的 `next` 通道 | `String` | 框架契约 + 序列化安全；它只是内部中转值，不承载语义 |

**一句话**：枚举用在**「模型必须从有限集合里选一个」**的地方；
而 state 是**框架与框架之间**的数据，跟着框架的类型走。

> 澄清一个可能的误解：不是说"state 里放 String 就不类型安全"。
> `MultiAgentState.next()` 返回 `String` 确实弱，但它只被条件边读一次；
> 真正的风险点在上游的"模型输出 → 路由值"那一步（原来是 `contains` 模糊匹配），
> 而枚举已经把它堵上了。

```java
package com.best.multiagent.node;

import com.best.ai_memory.user.MemoryRecallService;
import com.best.ai_memory.user.UserMemory;
import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.ChatMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.action.NodeAction;

import java.util.List;
import java.util.Map;

/**
 * 入口节点：把该用户的长期事实捞出来，放进 state。
 *
 * <p>为什么只在图的入口做一次，而不是每个专家各做一次：
 * state 是全图共享的 —— 入口放进去，后面所有节点都看得到。
 * 每个专家各做一次会带来重复的 embedding 调用，而且"这条事实是谁召回的"无从追溯。
 */
@Slf4j
@RequiredArgsConstructor
public class RecallMemoryNode implements NodeAction<MultiAgentState> {

    private final MemoryRecallService recallService;

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        String userId = state.userId();
        String query = lastUserText(state.messages());

        if (userId.isBlank() || query.isBlank()) {
            return Map.of(MultiAgentState.MEMORY_CONTEXT, "");
        }

        List<UserMemory> facts;
        try {
            facts = recallService.recall(userId, query);
        } catch (Exception e) {
            // 长期记忆是"锦上添花"的能力：检索失败不该让整次对话 500。
            // 但必须留下痕迹 —— 否则"助手想不起来"会被当成模型的问题。
            log.warn("长期记忆召回失败，本次跳过。userId={}", userId, e);
            return Map.of(MultiAgentState.MEMORY_CONTEXT, "");
        }

        log.info("长期记忆召回: userId={} 命中={} 条", userId, facts.size());
        return Map.of(MultiAgentState.MEMORY_CONTEXT, render(facts));
    }

    /** 渲染成一小段文本塞进提示词。骨架阶段用最简单的形式 */
    private String render(List<UserMemory> facts) {
        if (facts.isEmpty()) {
            return "";
        }
        StringBuilder sb = new StringBuilder("[关于这位用户的已知信息，按时间倒序，若冲突以靠前的为准]\n");
        for (UserMemory m : facts) {
            sb.append("- ").append(m.getContent()).append('\n');
        }
        return sb.toString();
    }

    /** 取最后一条用户消息的文本，作为检索的 query */
    private String lastUserText(List<ChatMessage> messages) {
        for (int i = messages.size() - 1; i >= 0; i--) {
            ChatMessage m = messages.get(i);
            if (m instanceof dev.langchain4j.data.message.UserMessage um) {
                // singleText() 在"图文混合"消息上会抛异常，所以用 try 兜住
                try {
                    return um.singleText();
                } catch (Exception e) {
                    return "";
                }
            }
        }
        return "";
    }
}
```

### `node/SupervisorNode.java`

```java
package com.best.multiagent.node;

import com.best.multiagent.agent.SupervisorAgent;
import com.best.multiagent.agent.SupervisorAgent.Routing;
import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.ChatMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.action.NodeAction;

import java.util.List;
import java.util.Map;

/**
 * 调度节点：决定下一个交给谁，写入 state 的 next。
 *
 * <p>条件边读的就是这个 next —— 所以这里必须**只**输出条件边映射表里声明过的 key，
 * 否则图会抛"未知节点"。
 */
@Slf4j
@RequiredArgsConstructor
public class SupervisorNode implements NodeAction<MultiAgentState> {

    private final SupervisorAgent supervisorAgent;

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        Routing routing;
        try {
            routing = supervisorAgent.route(render(state.messages()));
        } catch (Exception e) {
            // 两类失败都落在这里：模型调用失败（网络 / 限流），
            // 以及模型答了枚举之外的东西（LangChain4j 抛 OutputParsingException）。
            // 直接收尾比让整张图崩掉合理 —— 但必须打日志，
            // 否则"调度永远走 FINISH"这种故障在日志里查不出来。
            log.error("调度失败，直接收尾", e);
            routing = Routing.FINISH;
        }

        String edgeKey = edgeKeyOf(routing);
        log.info("调度决定: {} -> {}", routing, edgeKey);

        return Map.of(
                MultiAgentState.NEXT, edgeKey,
                MultiAgentState.MESSAGES, AiMessage.from("（调度：" + routing + "）")
        );
    }

    /**
     * 枚举 → 条件边的 key。
     *
     * <p><b>这里用穷尽 switch，且刻意不写 default。</b>
     * 以后往 {@link Routing} 里加一个值，编译器会立刻报错提醒补映射。
     * 而下面这段是原来的实现（已经删掉）：
     *
     * <pre>{@code
     * private static final Set<String> ALLOWED = Set.of("expertA", "expertB", "FINISH");
     *
     * for (String candidate : ALLOWED) {
     *     if (raw.contains(candidate)) return candidate;   // ← 隐患在这一行
     * }
     * }</pre>
     *
     * <p>它有<b>一个真实的非确定性</b>：模型经常一次提到多个候选
     * （"可以先看 expertB，如果需要清理再走 expertA"），而 {@code contains} 会命中
     * 集合里<b>最先被遍历到</b>的那个 —— 也就是由 {@code Set.of(...)} 的遍历顺序决定，
     * 而不是由语义决定。同一句回答可能被判成不同的路由，而且没有任何日志能解释为什么。
     *
     * <p>换成枚举后这个歧义从根上消失了：模型只能交付<b>一个</b>值；
     * 答了枚举之外的东西就是解析异常，是<b>显式失败</b>而不是静默选错。
     */
    private String edgeKeyOf(Routing routing) {
        return switch (routing) {
            case EXPERT_A -> "expertA";
            case EXPERT_B -> "expertB";
            case FINISH   -> "FINISH";
        };
    }

    /** 把消息列表压成一段文本喂给调度器 */
    private String render(List<ChatMessage> messages) {
        StringBuilder sb = new StringBuilder();
        for (ChatMessage m : messages) {
            String text = textOf(m);
            if (!text.isBlank()) {
                sb.append(roleOf(m)).append(": ").append(text).append('\n');
            }
        }
        return sb.toString();
    }

    private String roleOf(ChatMessage m) {
        String n = m.getClass().getSimpleName();
        return switch (n) {
            case "SystemMessage" -> "系统";
            case "AiMessage"     -> "助手";
            default              -> "用户";
        };
    }

    /** AiMessage.text() 在"只有工具调用"的那一轮是 null；UserMessage.singleText() 多模态会抛 */
    private String textOf(ChatMessage m) {
        try {
            if (m instanceof AiMessage am) {
                String t = am.text();
                return t == null ? "" : t;
            }
            if (m instanceof dev.langchain4j.data.message.UserMessage um) {
                return um.singleText();
            }
        } catch (Exception ignored) {
            // 拿不到文本不是错误，跳过这条消息即可
        }
        return "";
    }
}
```

```java
package com.best.multiagent.node;

import com.best.ai_common.context.AiUserContext;
import com.best.multiagent.agent.ExpertAgent;
import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.ChatMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.action.NodeAction;

import java.util.List;
import java.util.Map;

/**
 * 专家节点。两个专家共用这个类，靠构造参数区分角色。
 *
 * <p>骨架阶段它做两件事：① 调模型给处理意见；② 产出一个"待批准的动作"。
 * 真正执行动作的是 approvalGate 节点 —— 这样"想做什么"和"做了什么"是分开的，
 * 中间正好夹一个人工审批。
 */
@Slf4j
@RequiredArgsConstructor
public class ExpertNode implements NodeAction<MultiAgentState> {

    /** 角色名，出现在提示词里 */
    private final String role;

    /** 这个专家产出的"待执行动作"描述。骨架阶段是写死的假动作 */
    private final String plannedAction;

    private final ExpertAgent expertAgent;

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        String request = lastUserText(state.messages());

        String reply;
        try {
            // 图可能在任意线程执行节点，而 AiUserContext 是 ThreadLocal。
            // 不在这里开作用域，token 台账里的 user_id 会记成 anonymous。
            // 注：类名是 AiUserContext 而不是 AiCallContext —— 交付单 21 建议的"五维上下文"
            // 还没实施，这里必须用现在代码里真实存在的类。
            try (var ignored = AiUserContext.open(state.userId())) {
                reply = expertAgent.handle(role, state.memoryContext(), request);
            }
        } catch (Exception e) {
            log.error("专家 {} 处理失败", role, e);
            reply = "处理失败：" + e.getMessage();
        }

        log.info("专家 {} 产出待批准动作: {}", role, plannedAction);

        return Map.of(
                MultiAgentState.MESSAGES, AiMessage.from("[" + role + "] " + reply),
                // 有 pendingAction 就意味着后面会走到审批闸门
                MultiAgentState.PENDING_ACTION, plannedAction
        );
    }

    private String lastUserText(List<ChatMessage> messages) {
        for (int i = messages.size() - 1; i >= 0; i--) {
            if (messages.get(i) instanceof dev.langchain4j.data.message.UserMessage um) {
                try {
                    return um.singleText();
                } catch (Exception e) {
                    return "";
                }
            }
        }
        return "";
    }
}
```

```java
package com.best.multiagent.node;

import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.AiMessage;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.action.NodeAction;

import java.util.Map;

/**
 * 审批闸门。
 *
 * <p>它在图里的位置很特殊：{@code CompileConfig.interruptBefore("approvalGate")}
 * 让图在**执行这个节点之前**停下来等人。所以这个节点里的代码，只在"人已经批准"之后才会跑到。
 *
 * <p>骨架阶段"执行动作"就是打一行日志；真实业务里这里才是真正调用下游的地方。
 */
@Slf4j
public class ApprovalGateNode implements NodeAction<MultiAgentState> {

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        String action = state.pendingAction();

        if (!state.approved()) {
            log.info("操作被拒绝: {}", action);
            return Map.of(
                    MultiAgentState.MESSAGES, AiMessage.from("操作已被人工拒绝：" + action),
                    MultiAgentState.PENDING_ACTION, ""
            );
        }

        // ---------- 这里是"真正执行"的位置 ----------
        log.info("★ 执行已批准的操作: {}", action);
        // 骨架阶段：只打日志。真实业务在这里调下游系统。
        // ------------------------------------------

        return Map.of(
                MultiAgentState.MESSAGES, AiMessage.from("已执行：" + action),
                MultiAgentState.PENDING_ACTION, ""
        );
    }
}
```

```java
package com.best.multiagent.node;

import com.best.ai_memory.user.UserMemoryRecorder;
import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.ChatMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.action.NodeAction;

import java.util.Map;

/**
 * 出口节点：把这一轮的对话交给长期记忆抽取。
 *
 * <p>只调一次、在图的最末尾 —— 因为抽取是"业务判断"，不该每个专家各做一遍。
 */
@Slf4j
@RequiredArgsConstructor
public class WriteMemoryNode implements NodeAction<MultiAgentState> {

    /** 记忆归属需要的三段标识，格式 view 见 ai-memory 的 SessionKey */
    private final String assistantId;

    private final UserMemoryRecorder recorder;

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        String userId = state.userId();
        if (userId.isBlank()) {
            return Map.of();
        }

        // ⚠️ memoryId 是三段式：assistantId::userId::sessionId
        // 这里没有 sessionId（threadId 才是），所以用一个固定后缀。
        // 图应用的会话粒度由 checkpoint 的 threadId 承担，
        // 长期记忆只需要 userId 正确即可跨会话共享。
        String memoryId = assistantId + "::" + userId + "::graph";

        try {
            recorder.recordAsync(memoryId, state.messages());
        } catch (Exception e) {
            // 写入是异步触发的，失败不该影响本次响应
            log.warn("长期记忆写入触发失败, memoryId={}", memoryId, e);
        }

        return Map.of();
    }
}
```

## 9. `config/MultiAgentGraphConfig.java` —— 本篇的核心

```java
package com.best.multiagent.config;

import com.best.ai_common.register.ChatModelRegister;
import com.best.ai_memory.user.MemoryRecallService;
import com.best.ai_memory.user.UserMemoryRecorder;
import com.best.multiagent.agent.ExpertAgent;
import com.best.multiagent.agent.SupervisorAgent;
import com.best.multiagent.node.*;
import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.service.AiServices;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.CompileConfig;
import org.bsc.langgraph4j.CompiledGraph;
import org.bsc.langgraph4j.GraphDefinition;
import org.bsc.langgraph4j.GraphStateException;
import org.bsc.langgraph4j.StateGraph;
import org.bsc.langgraph4j.action.AsyncEdgeAction;
import org.bsc.langgraph4j.action.AsyncNodeAction;
import org.bsc.langgraph4j.checkpoint.RedisSaver;
import org.bsc.langgraph4j.langchain4j.serializer.std.LC4jStateSerializer;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.Map;
import java.util.concurrent.TimeUnit;

@Slf4j
@Configuration(proxyBeanMethods = false)
public class MultiAgentGraphConfig {

    /** 闸门节点名。中断配置和边的目标都必须用它，所以抽成常量 */
    private static final String GATE = "approvalGate";

    // ---------------------------------------------------------------- AI 智能体

    @Bean
    public SupervisorAgent supervisorAgent(ChatModelRegister chatModelRegister) {
        return AiServices.builder(SupervisorAgent.class)
                // 路由是"简单任务"，本来该用便宜的档位；
                // 骨架阶段先用默认档，等账单出来再决定要不要单独配一个 profile
                .chatModel(chatModelRegister.getDefault())
                .build();
    }

    @Bean
    public ExpertAgent expertAgent(ChatModelRegister chatModelRegister) {
        return AiServices.builder(ExpertAgent.class)
                .chatModel(chatModelRegister.getDefault())
                .build();
    }

    // ---------------------------------------------------------------- 图

    @Bean
    public CompiledGraph<MultiAgentState> multiAgentGraph(
            SupervisorAgent supervisorAgent,
            ExpertAgent expertAgent,
            MemoryRecallService recallService,
            UserMemoryRecorder memoryRecorder,
            @Value("${ai.multiagent.assistant-id:${spring.application.name:multiagent}}")
            String assistantId,
            @Value("${spring.data.redis.host:localhost}") String redisHost,
            @Value("${spring.data.redis.port:6379}") int redisPort,
            @Value("${spring.data.redis.password:}") String redisPassword,
            @Value("${ai.multiagent.checkpoint-ttl-hours:24}") long ttlHours
    ) throws GraphStateException {

        // ---------------------------------------------------------- Checkpoint（会话记忆）
        // stateSerializer 是【必须】的：ChatMessage 用 Java 原生序列化有问题，
        // LC4jStateSerializer 内部注册了一整套消息序列化器。
        var saverBuilder = RedisSaver.builder()
                .host(redisHost)
                .port(redisPort)
                .stateSerializer(new LC4jStateSerializer<>(MultiAgentState::new))
                // 会话状态不是资产，配个 TTL 避免无限堆积
                .ttl(ttlHours, TimeUnit.HOURS);
        // password 只在非空时才设置 —— 空串传给 builder 可能出问题
        if (redisPassword != null && !redisPassword.isBlank()) {
            saverBuilder.password(redisPassword);
        }
        var saver = saverBuilder.build();

        log.info("Checkpoint 已启用: RedisSaver {}:{} ttl={}h", redisHost, redisPort, ttlHours);

        // ---------------------------------------------------------- 装配图
        StateGraph<MultiAgentState> graph = new StateGraph<>(MultiAgentState.SCHEMA, MultiAgentState::new)

                // ① 长期记忆·读（入口，只做一次）
                .addNode("recallMemory", node(new RecallMemoryNode(recallService)))

                // ② 调度
                .addNode("supervisor", node(new SupervisorNode(supervisorAgent)))

                // ③ 两个专家（同一个类，不同参数）
                .addNode("expertA", node(new ExpertNode("数据库操作", "deleteTestData(scope=last-30-days)", expertAgent)))
                .addNode("expertB", node(new ExpertNode("查询分析",   "noop",                                expertAgent)))

                // ④ 审批闸门（中断点）
                .addNode(GATE, node(new ApprovalGateNode()))

                // ⑤ 长期记忆·写（出口，只做一次）
                .addNode("writeMemory", node(new WriteMemoryNode(assistantId, memoryRecorder)))

                // ---------------- 边 ----------------
                .addEdge(GraphDefinition.START, "recallMemory")
                .addEdge("recallMemory", "supervisor")

                // 调度 → 三选一。映射表的 key 必须和 SupervisorNode 的输出一致
                .addConditionalEdges("supervisor",
                        AsyncEdgeAction.edge_async(MultiAgentState::next),
                        Map.of("expertA", "expertA",
                               "expertB", "expertB",
                               "FINISH",  "writeMemory"))

                // 两个专家都汇入闸门
                .addEdge("expertA", GATE)
                .addEdge("expertB", GATE)

                // 审批之后回到调度 —— 由它决定"还要不要继续"
                .addEdge(GATE, "supervisor")

                // 收尾
                .addEdge("writeMemory", GraphDefinition.END);

        // ---------------------------------------------------------- 编译
        return graph.compile(CompileConfig.builder()
                .checkpointSaver(saver)
                // 中断点：执行到 GATE【之前】停下来等人
                .interruptBefore(GATE)
                // 防止模型来回踢皮球把图跑飞
                .recursionLimit(25)
                .build());
    }

    /** NodeAction → AsyncNodeAction 的简写，少写一层泛型噪音 */
    private static AsyncNodeAction<MultiAgentState> node(
            org.bsc.langgraph4j.action.NodeAction<MultiAgentState> action) {
        return AsyncNodeAction.node_async(action);
    }
}
```

> **两处容易踩的**：
> 1. `Map.of(...)` 里条件边的映射表，**key 必须和 `SupervisorNode.edgeKeyOf()` 的输出一致**
>    （`expertA` / `expertB` / `FINISH`）。对不上会抛"未知节点"。
>    **注意这些 key 不是 `Routing` 的枚举名** —— 中间隔着 `edgeKeyOf()` 那次转换。
>    好在那个转换是穷尽 switch，枚举改了编译器会提醒；所以真正的风险只剩下
>    "改了映射表却没改 switch"。这是全篇**唯一**需要人工保持两处一致的地方。
> 2. `.addEdge(GATE, "supervisor")` 形成循环 —— 所以 `recursionLimit` 不能省，
>    否则模型来回踢皮球时图会一直跑。

## 10. `web/AgentController.java` —— 异步两段式

```java
package com.best.multiagent.web;

import com.best.multiagent.state.MultiAgentState;
import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.data.message.UserMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.bsc.langgraph4j.CompiledGraph;
import org.bsc.langgraph4j.GraphInput;
import org.bsc.langgraph4j.GraphInterruptException;
import org.bsc.langgraph4j.RunnableConfig;
import org.bsc.langgraph4j.state.StateSnapshot;
import org.springframework.web.bind.annotation.*;

import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

/**
 * 异步两段式的两个入口。
 *
 * <p>为什么拆两个接口而不是一个阻塞等待：
 * 审批可能隔几分钟甚至几小时才发生，而 HTTP 请求挂不住那么久（超时 + 占线程 + 重启即丢）。
 * 拆开之后第一个请求毫秒级返回，状态留在 Redis 的 checkpoint 里。
 */
@Slf4j
@RestController
@RequestMapping("/agent")
@RequiredArgsConstructor
public class AgentController {

    private final CompiledGraph<MultiAgentState> graph;

    /** 断点所在节点的名字。用于判断"这次是不是停在等人" */
    private static final String GATE = "approvalGate";

    // ================================================================ 第一段：发起

    @PostMapping("/chat")
    public Map<String, Object> chat(@RequestBody ChatRequest req,
                                    @RequestHeader(value = "X-User-Id", required = false) String userId) {

        // threadId 直接复用 sessionId：这样"同一个会话"天然共享 checkpoint 历史，
        // 前端也不需要额外维护一个 id。
        String threadId = req.sessionId();
        RunnableConfig config = RunnableConfig.builder().threadId(threadId).build();

        Map<String, Object> input = new HashMap<>();
        input.put(MultiAgentState.MESSAGES, List.of(UserMessage.from(req.message())));
        input.put(MultiAgentState.USER_ID, userId == null ? "" : userId);
        // 每次新请求都要把这两个"当前值"重置，否则会带着上一轮的残留
        input.put(MultiAgentState.PENDING_ACTION, "");
        input.put(MultiAgentState.APPROVED, false);

        // ⚠️ 必须用 GraphInput.args(...) 包一层。
        // `invoke(Map, RunnableConfig)` 这个重载在 1.9.2 上是 @Deprecated(forRemoval = true)
        // （不只是"不推荐"，是计划移除），官方替代就是 invoke(GraphInput, RunnableConfig)。
        // 而且弃用版本的实现本身就是：
        //     invokeFinal(inputs == null ? GraphInput.resume() : GraphInput.args(inputs), config)
        // 所以包一层之后语义完全等价。
        return run(() -> graph.invoke(GraphInput.args(input), config), threadId, config);
    }

    // ================================================================ 第二段：恢复

    @PostMapping("/approve")
    public Map<String, Object> approve(@RequestBody ApproveRequest req) {

        String threadId = req.sessionId();
        RunnableConfig config = RunnableConfig.builder().threadId(threadId).build();

        log.info("收到审批: threadId={} approved={}", threadId, req.approved());

        // resume(Map) 里的内容会合并进 state —— approvalGate 节点读的就是这个 approved。
        // 这一处本来用的就是 invoke(GraphInput, ...)，是【未弃用】的重载；
        // 上面 /chat 现在也统一走 GraphInput 了（args 给新输入 / resume 续跑）。
        return run(() -> graph.invoke(GraphInput.resume(Map.of(MultiAgentState.APPROVED, req.approved())),
                        config),
                threadId, config);
    }

    // ================================================================ 公共部分

    /**
     * 跑图并翻译成对外状态。
     *
     * <p>这里刻意<b>同时兼容两种情况</b>：中断到底是"抛异常"还是"正常返回"，
     * 我没有从 API 签名里看出结论。所以：
     * <ul>
     *   <li>catch 住任何异常，用 {@link GraphInterruptException#of} 判断是不是中断；</li>
     *   <li>不管抛没抛，最后统一用 {@code getState()} 查"下一个要跑哪个节点"。</li>
     * </ul>
     * 这样两种实现都能正确处理。
     */
    private Map<String, Object> run(GraphRunner runner, String threadId, RunnableConfig config) {
        try {
            Optional<MultiAgentState> result = runner.run();
            if (result.isEmpty()) {
                return Map.of("status", "error", "message", "图没有返回状态");
            }
            return respond(result.get(), threadId, config);

        } catch (Exception e) {
            if (GraphInterruptException.of(e).isPresent()) {
                // 走到闸门之前停下来了 —— 这是正常业务流程，不是错误
                return waiting(threadId, config);
            }
            log.error("图执行失败 threadId={}", threadId, e);
            return Map.of("status", "error", "threadId", threadId, "message", e.getMessage());
        }
    }

    /** 根据"下一个节点是不是闸门"决定对外状态 */
    private Map<String, Object> respond(MultiAgentState state, String threadId, RunnableConfig config) {
        if (GATE.equals(nextNodeOf(config))) {
            return waiting(threadId, config);
        }
        return Map.of(
                "status", "done",
                "threadId", threadId,
                "answer", lastAiText(state.messages())
        );
    }

    private Map<String, Object> waiting(String threadId, RunnableConfig config) {
        StateSnapshot<MultiAgentState> snapshot = graph.getState(config);
        String pending = snapshot == null ? "" : snapshot.state().pendingAction();

        return Map.of(
                "status", "waiting_approval",
                "threadId", threadId,
                "pendingAction", pending
        );
    }

    private String nextNodeOf(RunnableConfig config) {
        StateSnapshot<MultiAgentState> snapshot = graph.getState(config);
        if (snapshot == null) {
            return "";
        }
        String next = snapshot.nextNodeId();
        return next == null ? "" : next;
    }

    private String lastAiText(List<ChatMessage> messages) {
        for (int i = messages.size() - 1; i >= 0; i--) {
            if (messages.get(i) instanceof dev.langchain4j.data.message.AiMessage am) {
                String t = am.text();
                if (t != null && !t.isBlank()) {
                    return t;
                }
            }
        }
        return "";
    }

    /** 让上面两段能共用同一套处理逻辑 */
    @FunctionalInterface
    private interface GraphRunner {
        Optional<MultiAgentState> run() throws Exception;
    }

    // ================================================================ 请求体

    public record ChatRequest(String message, String sessionId) {}

    public record ApproveRequest(String sessionId, boolean approved) {}
}
```

## 13. 三个已知代价（用之前要知道）

| # | 代价 | 说明 |
|---|---|---|
| 1 | **Redisson + Lettuce 并存** | `langgraph4j-redis-saver` 用 Redisson，项目用 Lettuce。骨架阶段接受；要统一可以用 `Builder.redissonClient(...)` |
| 2 | **会话记忆两套** | 图应用的历史在 checkpoint 里，和 `assistant-demo` 的 `ai.mem.session:*` 不共享。长期记忆是共享的 |
| 3 | **每次都走审批** | `interruptBefore` 是**编译期**配置，无法"只有危险操作才中断"。骨架阶段够用；要条件中断得用 `InterruptableAction` 接口 |
