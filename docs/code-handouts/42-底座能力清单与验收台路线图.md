# 42 · 底座能力清单与验收台路线图

> **本文档是一份「盘点」** —— 列出底座已提供什么、每个能力由哪个验收台证明过、还缺什么。
> **不含任何待实施代码。**
>
> **起因**：2026-10-14 用户说明 —— **`ai-multiagent` 只是用来测底座的，不是真实业务需求**。
> 这句话把评价标准从"这个应用做得好不好"改成了"**底座该给谁提供什么**"。
>
> **配套**：41 号（调研与诊断）。41 号管"多智能体该怎么做"，本文档管"底座现在到哪了"。

---

## 一、为什么要这份清单

**验收台的成功判据不是"跑得对"，是"跑遍了"。**

一个没被验证过的能力，比一个做错的能力更危险 —— 因为它**看起来是有的**
（模块名叫 `ai-multiagent`、有 supervisor、有 expert、有枚举）。

这份清单就是用来回答这一句话的：

> **底座现在到底能承诺什么？每一条的凭据是什么？**

---

## 二、已验收的能力（11 项）

| # | 能力 | 验收台 | 凭据 |
|---|---|---|---|
| 1 | 模型登记 / 多 profile 切换 | assistant-demo | `ChatModelRegister` / `StreamingChatModelRegister` 都跑通 |
| 2 | **流式输出**（TokenStream + SseEmitter） | assistant-demo | `ChatAssistant.chat(...)` 返回 `TokenStream`，`ChatStreamController` 用 `SseEmitter` 推流 |
| 3 | 会话记忆（含摘要） | assistant-demo | `SummarizingChatMemoryProvider` 装配进 `AiServices` |
| 4 | 长期记忆写入 | assistant-demo | `UserMemoryRecorder` 在流式 controller 里调用 |
| 5 | 长期记忆召回 | ai-multiagent | `MemoryRecallService` 在 `RecallMemoryNode` 里调用 |
| 6 | **RAG 装配**（可选注入） | assistant-demo | `RetrievalAugmentor` 走 `ObjectProvider` 注入 —— ⚠️ 验的是"**能装配**"，**不是"检索质量"** |
| 7 | token 计量（含流式） | 两者 | `TokenUsageRecorder` + `ai_token_usage` 台账 |
| 8 | MCP 工具接入 + 危险等级 | ai-multiagent | `McpToolCatalog`（`tools/list` + `mcp_gateway.tools.risk` 合流） |
| 9 | **审批中断 / 人在回路** | ai-multiagent | `InterruptibleAction` + `/approve` 跨请求恢复 |
| 10 | checkpoint / 跨请求恢复 | ai-multiagent | `RedisSaver` + 命名空间隔离 |
| 11 | 单 agent ReAct 循环 | ai-multiagent | 条件边驱动的 `propose → toolExecute → propose` 循环 |

> **第 6 项要特别注意**：`RetrievalAugmentor` 是**可选注入**（`ObjectProvider.getIfAvailable()`），
> 所以"装配路径通"不等于"RAG 可用" —— **向量检索的质量、召回率、阈值调参，一项都没验过**。
> （23 号论证过"不用 `EmbeddingStore`"的设计，但那是**设计**，不是**验收**。）

## 三、★ 未验收的能力（5 项）

前 4 项是 41 号诊断出的"多智能体核心能力"，第 5 项是独立挂起的一条。

| # | 能力 | 现状 | 什么时候才该验（触发条件） |
|---|---|---|---|
| 1 | **上下文隔离**（子 agent 独立窗口 + 只看该看的） | 无。三个 expert 读同一个 `messages` | **出现第一个"子任务需要独立上下文"的真实需求时** —— 典型信号是"上下文塞不下"或"专家之间互相干扰" |
| 2 | **并行子任务** | 无。严格串行 | **出现"子任务互相独立且要提速"的真实需求时**。⚠️ 一旦并行，就必须先有第 1 项（隔离）和第 4 项（交接协议），否则就是 Cognition 那个 Flappy Bird |
| 3 | **终止条件**（增量阈值 / token 预算） | 只有 `NONE` + `recursionLimit` | **出现第一个"模型转不停"或"token 超预算"的真实案例时**。也可以现在顺手加预算兜底 —— 它不需要真实数据就能写对 |
| 4 | **交接浓缩协议**（置信度 / 未覆盖项） | 无。`reply` 原样进 messages | **出现"上下文被工具返回值撑爆"时**。这是第 2 项的前置条件 |
| 5 | **真实鉴权链路**（userId 可信性） | 靠 `X-User-Id` 头，**客户端可伪造** | **接入第一个真实业务方时** —— 19 号明确挂起过："后续接真实鉴权再说" |

> **第 3 项和第 5 项性质不同**：第 3 项里"预算兜底"是**不需要真实数据就能做对**的（给个上限总比没有强）；
> 而"增量阈值"需要真实案例才能定。**可以只做前半截。**

## 四、这份清单暴露的三件事

### 4.1 名字在承诺它没验证的东西

`ai-multiagent` 这个名字暗示它验证了"多智能体"，但它验证的是
**「单 agent + 审批 + 记忆」**。按矩阵看，它更贴切的角色是 **`ai-agent-graph`**（图 / 中断 / 审批的验收台）。

**命名不是洁癖** —— 它决定了下次有人（包括你自己）想用"多智能体"时会去哪找，以及会不会以为"已经有现成的了"。

### 4.2 `ai-graph` 的定位需要重新说清楚

它现在装的是"**验收台的脚手架**"，但名字（`graph`）、包结构（`node/` `state/` `graph/`）、
自研动机（"别让第二个图应用复制代码"）都在暗示它是"**业务可用的框架**"。

这两种定位的维护标准不同：

| | 验收台脚手架 | 业务框架 |
|---|---|---|
| 可以随便重构吗 | **可以**（没有业务依赖它） | 不行（改一行动别人） |
| 需要向后兼容吗 | 不需要 | 需要 |
| 该不该追求"通用" | 不该 —— **它只服务验证目标** | 该 |

**现在它拿着"业务框架"的架子，干着"脚手架"的活。**

### 4.3 缺的 4 项里，有 2 项是"不需要真实需求就能做对"的

| 项 | 需要真实需求吗 |
|---|---|
| 终止条件里的**预算兜底** | ❌ 不需要 —— 给个上限永远比没有强 |
| **错误标记**（41 号 5.3 节：`ExpertNode` 的 catch 现在把错误**静默合并**进 messages） | ❌ 不需要 —— 错误要么标记，要么不合并，这是个是非题 |
| 上下文隔离 | ✅ 需要（要先有"子任务独立"的真实形态） |
| 并行 + 交接协议 | ✅ 需要（且依赖上一项） |

**前两项现在改成本最低**（零存量数据），后两项等触发条件。

## 五、待裁定（4 问）

| # | 问题 | 为什么它决定后面的路 |
|---|---|---|
| **1** | **底座的"用户"是谁？** 是你自己学习/内部试验，还是要交付给团队的业务方用？ | ★ **决定一切**：给业务方用 → "自研 vs Spring AI Alibaba Graph"要真算账、向后兼容要真做；自己试验 → 现成的不一定划算，自研有学习价值 |
| **2** | 未验的 4 项：**现在补验，还是挂起等真实需求？** | 41 号的判据是"抽象要等形状" —— 同理，**验收也要等形状**。但第 4.3 节那 2 项可以现在就做 |
| **3** | **命名与定位**：`ai-multiagent` / `ai-graph` 要不要改成反映真实职责的名字？ | 直接决定下一轮该怎么组织代码 |
| **4** | 已验能力里，**审批中断**要不要从 `ai-graph` 里提出来成为独立能力？ | 它是真需求、且不属于"多智能体"，跟着 routing 一起被否掉是浪费 |

## 六、我的建议（一句话版）

> **不做第 3 档（orchestrator），先把这份清单定下来，再做那 2 项"不需要真实需求"的改动。**
>
> 理由：现在缺的不是"更完整的多智能体"，是"**知道底座到哪了**"。
> 那 2 项改动（预算兜底 + 错误标记）是**确定的收益**；
> 而补齐隔离/并行/交接，需要先有一个真实的、确实需要它们的任务 ——
> **否则就是在没有验收标准的情况下造能力。**

## 七、附：本次盘点踩到的一个老坑

第一次搜"有没有用流式"时，我用了：

```bash
grep -rln "StreamingChatModel\|TokenStream" ai-common/src ai-memory/src assistant-demo/src
```

**返回空** —— 于是差点写下"流式没验证"。而实际上 `assistant-demo` 的
`ChatAssistant` 明确 `import dev.langchain4j.service.TokenStream`。

**根因**：本机是 BSD grep，**不支持 `\|` 做"或"**（要用 `grep -E "a|b"`）。
**这个坑我自己记录过，这次又踩了一次。**

> 教训加一条：**"grep 返回空"不等于"不存在"** —— 先确认模式本身能匹配到东西
> （比如随便拿一个已知存在的词试一下），再下结论。
