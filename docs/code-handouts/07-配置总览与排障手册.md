# 第一节 · 数据库准备

## 方案 A（推荐）：直接用 MySQL

和生产保持一致，出问题不用怀疑"是不是数据库不一样"。

```sql
CREATE TABLE ai_user_memory (
    id             BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id          VARCHAR(64)   NOT NULL             COMMENT '用户标识',
    content          VARCHAR(1000) NOT NULL             COMMENT '一条事实，一句话',
    source_assistant VARCHAR(64)   NOT NULL             COMMENT '哪个助手抽出来的（事实跨助手共享，这是追溯线索）',
    embedding      BLOB          NULL                   COMMENT 'float32 大端序列，长度 = 维度 × 4',
    source_session VARCHAR(128)  NULL                   COMMENT '在哪次会话里抽出来的',
    created_at     DATETIME(3)   NOT NULL               COMMENT '毫秒精度',
    INDEX idx_user_memory_user_time (user_id, created_at)
) ENGINE = InnoDB COMMENT '用户长期记忆：一句一条';
```

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/ai_platform?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
```

`assistant-demo/pom.xml` 需要：

```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

## 方案 B：本地用 H2 文件库，不装 MySQL

`assistant-demo/pom.xml`：

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>
```

`assistant-demo/src/main/resources/schema.sql`（**H2 专用，注意和上面 MySQL 的 DDL 有两处不同**）：

```sql
CREATE TABLE IF NOT EXISTS ai_user_memory (
    id             BIGINT        AUTO_INCREMENT PRIMARY KEY,
    user_id        VARCHAR(64)   NOT NULL,
    content        VARCHAR(1000) NOT NULL,
    embedding      BLOB,
    source_session   VARCHAR(128),
    source_assistant VARCHAR(64)   NOT NULL,
    created_at     TIMESTAMP(3)  NOT NULL
);

-- ⚠️ 索引必须【单独一条语句】写。
-- H2 不支持 MySQL 那种在 CREATE TABLE 内部写 INDEX 的语法。
CREATE INDEX IF NOT EXISTS idx_user_memory_user_time
    ON ai_user_memory (user_id, created_at);
```

```yaml
spring:
  datasource:
    # MODE=MySQL 让 H2 认 AUTO_INCREMENT 这种 MySQL 写法
    url: jdbc:h2:file:./data/aimemory;MODE=MySQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
    username: sa
    password: ""
  sql:
    init:
      mode: always
      schema-locations: classpath:schema.sql
```

> **为什么用 H2 的 `file:` 模式而不是 `mem:` 模式**：`mem:` 库在进程退出后就没了，你会在一重启后发现"记忆全丢了"，然后花时间怀疑是不是自己的代码有问题。用 file 模式落到磁盘，行为才和生产接近。

# 第二节 · 完整配置

`assistant-demo/src/main/resources/application.yml` 的完整版本：

```yaml
server:
  port: 8080

spring:
  application:
    name: assistant-demo      # 会作为 token 计量里的 assistantId

  # ===== 数据库（二选一，见第一节）=====
  datasource:
    url: jdbc:mysql://localhost:3306/ai_platform?useSSL=false&serverTimezone=Asia/Shanghai
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver

  # ===== Redis：会话记忆 =====
  data:
    redis:
      host: localhost
      port: 6379

  # ===== SSE 的异步超时，必须 >= SseEmitter 构造器里的超时 =====
  mvc:
    async:
      request-timeout: 120s

# ============================================================
# AI-Common：模型接入
# ============================================================
ai:
  chat:
    # 关掉可以整个跳过对话模型装配（引了这个 jar 但暂时不用的模块）
    enabled: true
    # 默认 profile。下面 endpoints 里的 key 之一
    profile: free
    # 全局默认值，端点级配置可以覆盖它
    temperature: 0.7
    max-tokens: 2000
    timeout: 60

    endpoints:
      free:
        base-url: http://ai-gateway.tz.com/v1
        api-key: ${AI_GATEWAY_KEY}
        model-name: best-1-nothinking      # 便宜档，主对话用它
      fast:
        base-url: http://ai-gateway.tz.com/v1
        api-key: ${AI_GATEWAY_KEY}
        model-name: best-1-fast            # 抽取和摘要用它
        max-tokens: 500                     # 只输出 JSON 或几百字摘要，不需要 2000

  embed:
    enabled: true
    profile: default
    dimensions: 1024          # ⚠️ 改这个 = 历史向量全废
    timeout: 60
    max-retries: 3
    endpoints:
      default:
        base-url: http://ai-gateway.tz.com/v1
        api-key: ${AI_GATEWAY_KEY}
        model-name: best-embedding-v1

# ============================================================
# AI-Memory：记忆
# ============================================================
ai:
  memory:
    # ---------- 会话记忆（episodic）----------
    session:
      store: redis                  # memory | redis
      max-messages: 20              # 窗口大小
      summary-enabled: true
      ttl: 48h                      # 消息过期（滑动刷新）
      summary-ttl: 96h              # ⚠️ 必须 >= ttl，理由见交付单 03

    # ---------- 用户记忆（semantic）----------
    user:
      enabled: true
      top-k: 5                      # 每轮注入几条事实
      min-score: 0.60               # 低于这个相似度不注入
      extract-profile: fast         # 抽取用哪个模型档
      dedup-threshold: 0.95         # 高于它当重复，丢弃
      max-facts-per-user: 500       # 容量上限，防无界增长

    embedding:
      profile: default              # 用哪个 embedding 档

  # ---------- 可观测性（如果 02 的观测性交付单已落地）----------
  observability:
    tenant-header: X-Tenant-Id
    trace-header: X-Trace-Id
```

## 配置项速查表

| 配置项 | 默认值 | 改它会怎样 |
|---|---|---|
| `ai.memory.session.max-messages` | 20 | 窗口变小 → 摘要触发更频繁 → 模型调用变多 |
| `ai.memory.session.summary-enabled` | true | 关掉 → 滑出窗口的内容**永久丢失** |
| `ai.memory.session.ttl` | 48h | 用户 48 小时不说话，整段历史自动清空 |
| `ai.memory.user.top-k` | 5 | 调大 → prompt 变长、成本上升、可能引入噪声 |
| `ai.memory.user.min-score` | 0.60 | 调高 → 更准但可能一条都召不回；调低 → 召回多但夹带无关的 |
| `ai.memory.user.dedup-threshold` | 0.95 | 调低 → 去重更狠，可能把"相似但不同"的事实误杀 |
| `ai.memory.user.max-facts-per-user` | 500 | 超了删最老的。这个值也是每次检索要加载的向量总量 |
| `ai.embed.dimensions` | 1024 | **改它等于让所有历史向量作废** |

# 第三节 · 成本账

## 一轮对话实际发生了几次模型调用

| 环节 | 次数 | 走哪个 profile | 什么时候发生 |
|---|---|---|---|
| 主对话 | 1 | `free`（或你配的） | 每次请求 |
| 用户事实抽取 | 1 | `fast` | 每次请求（异步） |
| 会话摘要 | **1** | **主对话档**（`getDefault()`） | **窗口满了之后，每轮 1 次** |
| 查询向量化 | 1 | `embed` | 每次请求 |
| 事实向量化 | N（N = 抽出的条数） | `embed` | 每次请求（异步） |

**最短路径是 6 次调用（1 主 + 1 抽取 + 1 摘要 + 1 查询向量 + 2 事实向量）。**

## 这里有个成本热点，得说清楚

**摘要一旦开始触发，就是每轮一次。** 原因：窗口设 20 条时，从第 21 条消息起，每次 `add` 都会有 1 条被挤出去 → 每次挤出去都调一次摘要。

如果主对话用的是贵模型，这等于**每轮多花一次模型调用**。

三个缓解方向，按性价比排：

**① 先确认它是不是真的贵**

注意摘要走的是**主对话同一档模型**（`getDefault()`），不是便宜档。这是个刻意的选择：摘要会被反复覆盖，质量损失是累积的，一次糟糕的摘要会污染后面全部。

但它的输入确实很小——旧摘要 + 几条滑出的消息，几百 token 量级。所以在动手优化之前，**先看账单上这一项到底占多少**。如果不到 5%，别动它。

想改成按档位取（摘要单独走便宜档），改法见交付单 02 末尾的说明 —— 三处改动。

**② 攒批摘要**
让窗口"软溢出"：保留 `max-messages + 10` 条，积攒 10 条才摘要一次。代价是实际上下文比配置的多一点，而且实现要改 `SummarizingChatMemory`（多一个 pending 缓冲）。

**③ 摘要只在会话结束时做**
最省，但"会话什么时候结束"没有可靠信号（用户可能再也不回来，也可能五分钟后接着聊）。

**建议先用 ①，等你真的在账单上看到摘要占比过高，再上 ②。**

## 另外两个成本点

- **`top-k` 越大越贵**：每条事实大约 20–40 token，5 条就是 100–200 token 的额外输入。调成 20 条会让每轮输入多 600 token，而且召回质量通常更差
- **`max-facts-per-user` 是隐性的读成本**：检索时要把该用户**全部**事实的向量读出来算相似度。500 条 × 4KB = 2MB 的读放大。所以这个值既是容量上限，也是性能上限

# 第四节 · 排障清单

按"症状 → 原因 → 怎么查"组织。**从上往下查，别跳。**

## 1. 流式不生效，等两秒一次性吐出

| 可能 | 怎么查 |
|---|---|
| curl 没加 `-N` | 加上 `-N` 再试。这是最常见的假问题 |
| 中间有 nginx / 网关缓冲 | 看响应头有没有经过代理。需要代理侧配 `X-Accel-Buffering: no` 或关 `proxy_buffering` |
| 有自定义 Filter 包装了响应 | 搜项目里的 `ResponseBodyAdvice` 和 `HttpServletResponseWrapper` |
| 用了 `spring-boot-starter-webflux` 但走的 MVC 路径 | 看启动日志是 Tomcat 还是 Netty |

## 2. 助手完全不记得上一句

```sql
-- 先确认数据到底有没有写进去
SELECT COUNT(*) FROM ai_user_memory WHERE user_id = 'u1';
```

```bash
# 再看 Redis 里有没有会话
redis-cli --scan --pattern 'ai:mem:session:*'
```

最有可能是 **`ChatMemoryProvider` 没被挂上**。检查：

- `assistant-demo` 启动日志里有没有 `AiMemoryAutoConfiguration` 的输出（加一行 `log.info` 确认 Bean 被创建）
- 助手接口的方法参数上有没有 `@MemoryId`
- 每次请求传的 `memoryId` 是不是**同一个**（用日志打出来看一眼）

## 3. 同一会话记得，换会话就忘

**这是长期记忆没生效，不是 bug。**

按顺序查：

1. `ai.memory.user.enabled` 是不是 true
2. `ai_user_memory` 表里有没有该用户的数据（`SELECT * FROM ai_user_memory WHERE user_id='u1'`）
3. 有数据但召不回 → 把 `min-score` 从 0.60 临时调到 0.0，看是不是能召回了。能 → 阈值太高；还是不能 → 向量或维度的锅
4. 日志里有没有 `向量维度不一致` → 有的话是 `ai.embed.dimensions` 和存量数据对不上

## 4. `ContentRetriever` 根本没被调用

在 `UserMemoryContentRetriever.retrieve()` 第一行加日志。**如果日志不出现**：

- `RetrievalAugmentor` 没被装配上 → 检查 `ObjectProvider.getIfAvailable()` 是不是返回了 null
- `memoryId` 格式不对 → 看有没有 `memoryId 格式不符合 userId::sessionId` 的 warn

## 5. 助手把好几轮前说的话当成"用户事实"

抽取提示词太宽了。改 `LlmUserMemoryExtractor` 的 `@SystemMessage`：

- 在"不该抽的"里再加一条：**"用户转述的第三方信息"**
- 多加两个反例（示例二那种形式）

**抽取类问题的排查顺序永远是：先看提示词，再看代码。** 90% 的问题在提示词。

## 6. 同一件事被记了好几遍

`dedup-threshold` 太高（0.95 意味着几乎要求一模一样）。

调到 0.88 试试。但**不要调到 0.8 以下** —— 那会把"用户喜欢表格"和"用户喜欢图表"这种真正不同的事实误判成重复。

## 7. 启动报 `NoSuchBeanDefinitionException: ChatMemoryProvider`

`AiMemoryAutoConfiguration` 没被加载。检查：

- `ai-memory/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 里有没有那一行
- 文件名是不是**完全正确**（这个文件名不能有任何拼写差异，写错了不会报错，只是静默不生效）
- `AI-Memory` 的 `target/classes/META-INF/spring/` 下有没有这个文件（`mvn clean` 之后再看）

## 8. 启动报 `NoSuchBeanDefinitionException: SessionMemoryStore`

`ai.memory.session.store` 的值不是 `memory` 也不是 `redis`（比如写成了 `Memory`，大小写敏感）。

或者选了 `redis` 但 `spring-boot-starter-data-redis` 没引 —— 那样 `RedisStoreConfig` 整个类因为 `@ConditionalOnClass` 被跳过了。

## 9. 每轮对话明显变慢

按这个顺序查：

1. 摘要是不是变成同步的了 → 看 `LlmConversationSummarizer.append` 有没有被直接调在请求线程上
2. `ai.memory.user.max-facts-per-user` 是不是设得太大 → 每次检索读了太多向量
3. 数据库有没有走索引 → `EXPLAIN SELECT ... FROM ai_user_memory WHERE user_id = '?' ORDER BY created_at DESC LIMIT 500`
4. 网关本身慢不慢 → 看模型调用的 `latency_ms`（观测性交付单里的 `ModelUsage`）

## 10. token 账单涨得比预期快

先算清楚每轮的调用次数（见第三节），然后看这几个参数：

- `max-messages` 调小（窗口小 → 每轮送入的历史少）
- `top-k` 调小
- 抓一轮的真实 prompt 出来看 —— **最有效的办法**。日志里打一次 `chatMemory.messages()` 的 token 估算，你会立刻发现是哪一段在吃 token

## 11. 用户要求"忘掉我说过的"

目前**没有实现这个能力**。这是这一版最大的合规缺口。

最小实现是三件事：

1. `UserMemoryStore.deleteAll(userId)` —— 已经有了
2. `SessionMemoryStore` + `SessionSummaryStore` 按 userId 批量删 —— **还没有，需要加一个"按 userId 前缀扫 key"的方法**
3. 一个管理端点 `DELETE /memory/{userId}`

如果这个系统要面向 C 端用户，**这件事的优先级高于任何功能优化**。

## 12. 用量统计里 token 全是空值

**症状**：调用记录有（助手、耗时、成败都对），但 `inputTokens` / `outputTokens` 全是 null。

**原因**：**流式响应默认不返回 `usage`**。OpenAI 协议里，非流式的响应体带 usage，流式的所有 chunk 里 usage 都是 null —— 除非请求带了 `stream_options: {"include_usage": true}`，服务端才会在最后一个 chunk 里补上。

**怎么查**（按顺序）：

1. 先用一个最小程序直接把 usage 打出来，确认是 `null` 还是数字：

```java
model.chat("说三个字", new StreamingChatResponseHandler() {
    @Override public void onPartialResponse(String t) { }
    @Override public void onCompleteResponse(ChatResponse r) {
        System.out.println("tokenUsage = " + r.metadata().tokenUsage());
    }
    @Override public void onError(Throwable t) { t.printStackTrace(); }
});
```

2. 是 `null` → 看 `OpenAiStreamingChatModel` 的 builder 有没有开关能带上 `stream_options`；没有的话用 `customParameters` 之类的手段透传
3. 参数带上了还是 `null` → **问题在网关**。`ai-gateway` 可能没把这个参数透传给上游，或者透传了但把最后一帧丢了。去找网关的负责人，或者直接抓一次网关的出站请求看
4. 都不行 → 退回客户端估算（用 tokenizer 数），**但要接受它是估算值，和账单对不上**

**最省事的解法**：去找网关做。它是所有模型调用的必经之路，能看到完整响应体，做一次覆盖所有调用方。SDK 层挂 listener 这条路会一直受制于参数透传。详见交付单 04 的 0.2 节。

# 第五节 · 到这里为止，还没做的

诚实列一下这个版本的边界，免得你以为是漏了：

| 没做 | 为什么现在不做 | 什么时候该做 |
|---|---|---|
| **UPDATE / DELETE 事实** | 误删比漏记严重得多；Mem0 2026 也转向 ADD-only 了 | 当"事实会变"成为真实高频场景时 |
| **向量库** | 单用户几百条量级下应用内算余弦足够快 | 单用户记忆过千 |
| **实体/时间检索** | 要图库，且现在没有查询需要它 | 出现"多跳"类问题（"我上次提到的那个项目谁负责"） |
| **按用户删除记忆** | —— | **如果面向 C 端，立刻做** |
| **多租户隔离** | 现在只有 userId 一个维度 | 有第二个租户的第一天 |
| **记忆的质量评估** | 没有 golden set，无法量化 | 有 50 条真实问答应答之后 |
| **摘要的批次优化** | 成本可接受 | 账单显示摘要占比过高时 |

# 接下来做什么

到这里，你最初提的那个需求**已经成立了**：多轮对话 + 长期记忆 + 流式输出。

下一步有三个方向，各自的触发条件不同：

**方向一 · 把这套复制到第二个助手**
最适合现在做。第二个助手会让你第一次遇到"两个助手共用一份记忆表"的真实问题（租户隔离、助手间是否能互相看到记忆）。**在这之前，所有设计都是纸上推演。**

**方向二 · 给记忆加"用户可见、可删"**
如果要做 C 端，这是前置条件。工作量不大，但要改 3 个类 + 加 1 个端点。

**方向三 · 上评测**
构造 50 条问答对，量化"开了记忆"和"没开记忆"的回答差异。**这是唯一能证明这套东西有价值的方式** —— 否则你只能凭感觉说"好像记住了"。

我的建议是**先做方向一**。理由和你之前说过的一句话一致：**你不缺学习方法，缺的是真实场景的入口。** 第二个助手就是那个入口。
