# 20 · AI 底座盘点：边界、契约与缺口

> 这一篇不是"再加什么功能"，是回答**底座该长成什么样**。
> 判断范围限定在非业务能力 —— 具体助手需要什么，这里一概不管。

---

## 0. 判据：什么有资格进底座

三条，必须同时成立：

| # | 判据 | 反例（不该进底座） |
|---|---|---|
| 1 | **所有助手都需要** | 「运筹眼的指标查询工具」 |
| 2 | **与业务语义无关** | 「经营分析的提示词模板」 |
| 3 | **有独立的技术复杂度** | 「一个字符串拼接工具类」 |

第 3 条最容易被忽略。一个能力如果只是几十行代码，做成模块/独立包是负担而不是资产 —— 它的复杂度不足以支撑抽象成本。

### 用判据筛现在的六层

| 层 | 普遍性 | 无业务语义 | 有复杂度 | 结论 |
|---|---|---|---|---|
| 模型接入 | ✓ | ✓ | ✓ | **合格**（已完整） |
| 记忆 | ✓ | ✓ | ✓ | **合格**（已完整） |
| 上下文 | ✓ | ✓ | ✓ | **合格**（缺 4 维） |
| 可观测 | ✓ | ✓ | ✓ | **合格**（半张表） |
| 工具 | ✓ | ✓ | ✓ | 合格，但**闭环依赖业务** |
| 提示词 | ✓ | ✓ | ✗ | **不够格**（见下） |

**提示词为什么不够格**：它的难度在「写什么」，不在「怎么存」。一个模板表 + 版本字段就够了，而"写什么"是业务知识。**给它做成模块 = 给一个配置文件穿西装。**

**工具为什么"合格但特殊"**：机制（客户端管理、注入调用链）是通用的，但**挂哪些工具是业务决定**。所以底座该交付的是"工具怎么被接进来"，不是"工具接完了"。

---

## 1. 第一个决定：现在不要拆模块

`ai-common` 现在有五个包、四个互不相干的关注点：

```
properties / register / mcp / metrics / context / config
   ↑ 模型配置    ↑ 模型     ↑ 工具  ↑ 计量   ↑ 上下文   ↑ 装配
```

按关注点看，它确实该拆成三个模块。**但现在拆是错的**，两个理由：

### 理由一：缝还没显形

六层里，工具层没闭环、可观测层缺字段、提示词层空白。**你不知道该沿哪条线切** —— 现在下刀，很可能切在错误的位置，等能力补齐后还要再切一次。

### 理由二：拆是物理重构，定契约是逻辑调整 —— 而后者拆不拆都要做

| 动作 | 成本 | 照不出来的坑 |
|---|---|---|
| 拆模块/改包名 | 高 | `@MapperScan` 的注解值、mapper XML 里的 `namespace` / `typeHandler` / `type`、`resources/mapper/` 下的镜像目录 —— **编译期全部不校验** |
| 标 optional / 扩上下文 / 补字段 | 低 | 无（包名不变，编译能照出大部分） |

**结论**：先做逻辑调整。等能力补齐、使用点变多，"哪些该在一起"会自己显形 —— 那时候切一刀是准的。

## 2. 缺口一：依赖边界（10 分钟，零风险）

### 问题

`ai-common/pom.xml` 里两个依赖没有 `<optional>`：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
    <version>3.5.17</version>
</dependency>
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-mcp</artifactId>
</dependency>
```

### 后果（不是一个"多引包"的小事）

MyBatis-Plus starter 会带进 `spring-boot-starter-jdbc`，而它会让 `DataSourceAutoConfiguration` 生效 ——

> **任何引 `ai-common` 的服务，不配 `spring.datasource` 就起不来**，哪怕它完全不需要 token 台账落库。

（新助手清单里写的"`spring.datasource` 必需"，根因就是这一行。它被当成了一条"约定"，其实是个可以消掉的约束。）

### 改法：只改 pom，代码一行不动

**你的代码早就把条件门装好了**：

```java
@ConditionalOnClass({BaseMapper.class, DataSource.class})
@ConditionalOnBean(DataSource.class)
static class TokenUsageDbConfig { ... }
```

```java
@ConditionalOnProperty(prefix = "ai.mcp", name = "enabled", havingValue = "true")
static class McpConfig { ... }
```

所以只需要：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
    <version>3.5.17</version>
    <optional>true</optional>
</dependency>
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-mcp</artifactId>
    <optional>true</optional>
</dependency>
```

> **注意 `@ConditionalOnClass` 的组合语义**：`@ConditionalOnClass({BaseMapper.class, DataSource.class})` 要求**两个类都在**才生效，正好对应"引了 mybatis-plus 且配了数据源"。写法本身是对的，不用改。

### 连带要做的两件事

1. **使用方要自己声明依赖**。标 optional 之后，`ai-common` 不再传递 mybatis-plus —— `assistant-demo` 如果要用台账，得自己引。这是**正确**的：用了什么就声明什么，不做幽灵依赖。
2. **`assistant-demo` 的 `spring.datasource` 就不必"必需"了**。如果它不用台账，可以删掉那一段 —— 这条正好可以当作验证。

## 3. 缺口二：上下文扩容（底座的地基）

### 问题：一个 AI 调用有五个身份，现在散在四个地方

| 维度 | 现在从哪来 | 有没有统一入口 |
|---|---|---|
| userId | `AiUserContext`（ThreadLocal） | ✓ |
| assistantId | `@Value("${spring.application.name}")` | ✗ |
| sessionId | Controller 方法参数 | ✗ |
| traceId | **没有** | ✗ |
| tenantId | **没有** | ✗ |

**证据就在代码里**：

```java
// ChatStreamController
SessionKey.of(assistantId, userId, sessionId).toMemoryId();
//            ↑@Value 注入    ↑ThreadLocal  ↑方法参数
```

三个维度、三个来源。这不是写错了 —— 是"没有统一上下文"的必然结果。**每加一个使用点，就再散一次。**

### 为什么这是"地基"而不只是"重构"

看三个使用点各自的维度需求：

| 使用点 | 需要哪些维度 |
|---|---|
| memoryId 拼装 | assistantId + userId + sessionId |
| token 台账 | userId + traceId + serviceName |
| 日志/链路 | traceId |
| 长期记忆检索 | userId |

**每个点取的交集都不同，而来源都不同。** 统一成一个上下文之后，这些点全都变成一次 `AiCallContext.current()`。

### 设计：`AiCallContext`（五维）

```java
package com.best.ai_common.context;

/**
 * 一次 AI 调用的完整身份上下文。
 *
 * <p>替代原来的 AiUserContext —— 从「只有 userId」扩到「五个维度」。
 * 理由：memoryId 拼装要 3 维、台账要 2 维、日志要 1 维，
 * 而这些维度现在来自 @Value / ThreadLocal / 方法参数三处，
 * 每加一个使用点就再散一次。
 *
 * <p>不变的部分：仍然是 ThreadLocal，仍然需要 Scope 传给线程池任务
 * （见 open/wrap —— 后台抽取任务靠它）。
 */
public final class AiCallContext {

    /**
     * 不可变快照。之所以用 record + 不可变，是因为它要被塞进
     * ChatModelListener 的 attributes（跨线程），可变对象会有可见性问题。
     */
    public record Snapshot(String userId, String tenantId, String assistantId,
                           String sessionId, String traceId) {
        public static final Snapshot EMPTY = new Snapshot(null, null, null, null, null);
    }

    private static final ThreadLocal<Snapshot> HOLDER = new ThreadLocal<>();

    private AiCallContext() {}

    // ============================================ 读写

    public static void set(Snapshot snapshot) { HOLDER.set(snapshot); }

    public static Snapshot current() {
        Snapshot s = HOLDER.get();
        return s == null ? Snapshot.EMPTY : s;
    }

    public static void clear() { HOLDER.remove(); }

    // ============================================ 便捷读取（带兜底）

    /** 缺省兜底成 anonymous —— 计量场景用这个口径 */
    public static String userIdOrAnonymous() {
        String v = current().userId();
        return v == null || v.isBlank() ? "anonymous" : v;
    }

    /** 缺省返回 null —— 需要区分「没有」和「匿名」的场景用这个 */
    public static String userId() { return current().userId(); }

    public static String assistantId() { return current().assistantId(); }

    public static String traceId() { return current().traceId(); }

    // ============================================ 作用域（线程池传递）

    /** 覆盖式：只改其中一个维度，其余继承 */
    public static Scope withUserId(String userId) {
        Snapshot previous = HOLDER.get();
        Snapshot base = previous == null ? Snapshot.EMPTY : previous;
        HOLDER.set(new Snapshot(userId, base.tenantId(), base.assistantId(),
                base.sessionId(), base.traceId()));
        return () -> {
            if (previous == null) HOLDER.remove(); else HOLDER.set(previous);
        };
    }

    public static Scope open(Snapshot snapshot) {
        Snapshot previous = HOLDER.get();
        HOLDER.set(snapshot);
        return () -> {
            if (previous == null) HOLDER.remove(); else HOLDER.set(previous);
        };
    }

    @FunctionalInterface
    public interface Scope extends AutoCloseable { @Override void close(); }
}
```

**三个设计点，都是被现有代码逼出来的**：

1. **`userIdOrAnonymous()` 和 `userId()` 并存** —— `TokenUsageListener` 需要前者（attributes 不接受 null，必须兜底），而"拒绝匿名"的校验需要后者（要能区分"没有"和"匿名"）。**两套口径在代码里已经存在了，只是没被命名。**
2. **`withUserId` 是覆盖式** —— 后台抽取任务只需要换 userId，其余维度（assistantId）应该继承。原来的 `open(String)` 会**丢掉其他维度**。
3. **`Snapshot` 不可变** —— 它要被塞进 `attributes` 跨线程，可变对象会有可见性问题。

### 装配改动（Interceptor）

```java
public class AiCallContextInterceptor implements HandlerInterceptor {

    @Value("${ai.context.assistant-id:${spring.application.name:unknown}}")
    private String assistantId;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) {
        AiCallContext.set(new AiCallContext.Snapshot(
                request.getHeader("X-User-Id"),
                request.getHeader("X-Tenant-Id"),
                assistantId,                                     // 服务名，不用从请求取
                request.getParameter("sessionId"),               // 会话 id，请求里的才有效
                resolveTraceId(request)));
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        AiCallContext.clear();      // 必须清 —— 线程池会复用线程
    }

    private String resolveTraceId(HttpServletRequest request) {
        String fromMdc = MDC.get("traceId");   // 链路组件写进来的优先
        return (fromMdc != null && !fromMdc.isBlank())
                ? fromMdc : request.getHeader("X-Trace-Id");
    }
}
```

> **`sessionId` 从请求参数取，这是刻意的**：它是"业务会话"，只有调用方知道。而 `assistantId` 从配置取，因为它是"这个服务是谁"，与请求无关。**两个维度两种来源 —— 但在上下文里待遇相同。**

## 4. 缺口三：可观测补全（让台账能排障）

### 问题：两种完全不同的情况，在表里长得一样

现在的 `onError`：

```java
@Override
public void onError(ChatModelErrorContext errorContext) {
    recorder.record(new TokenUsageRecord(
            userIdOf(errorContext.attributes()), serviceName, profile, modelName,
            null, null, null,          // ← token 全 null
            Instant.now()));
}
```

而 `onResponse` 在拿不到 usage 时 `return` —— **不记任何东西**。

所以表里出现 `token = null` 时，你分不清是：

- **调用失败了**（onError）
- **调用成功了但网关没返回 usage**（理论上，虽然现在是 return 掉的）

**加一个 `success` 字段就能分开。** 这是最要紧的一条。

### 新契约

```java
package com.best.ai_common.metrics;

import java.time.Instant;

/**
 * 一次模型调用的记账。字段分三组：
 * <ul>
 *   <li>身份：userId / serviceName / profile / modelName</li>
 *   <li>用量：input / output / total tokens</li>
 *   <li>诊断：success / latencyMs / traceId / errorType ← 本次新增</li>
 * </ul>
 *
 * <p>为什么要诊断组：token 台账原来只能回答「花了多少钱」，
 * 回答不了「为什么慢、为什么错」。而后者才是排障要的。
 */
public record TokenUsageRecord(
        // ---- 身份 ----
        String userId,
        String serviceName,
        String profile,
        String modelName,

        // ---- 用量 ----
        Integer inputTokens,
        Integer outputTokens,
        Integer totalTokens,

        // ---- 诊断（新增）----
        /** 调用是否成功。区分「失败」和「成功但没返回 usage」的唯一手段 */
        boolean success,
        /** 端到端耗时（毫秒）。-1 表示没测到 */
        long latencyMs,
        /** 链路 id。用来和日志、其他服务串起来 */
        String traceId,
        /** 失败时的异常类名（只留类型，不留 message —— 可能含敏感内容） */
        String errorType,

        Instant occurredAt
) {}
```

### Listener 改法（完整文件）

```java
package com.best.ai_common.metrics;

import com.best.ai_common.context.AiCallContext;
import dev.langchain4j.model.chat.listener.ChatModelErrorContext;
import dev.langchain4j.model.chat.listener.ChatModelListener;
import dev.langchain4j.model.chat.listener.ChatModelRequestContext;
import dev.langchain4j.model.chat.listener.ChatModelResponseContext;
import dev.langchain4j.model.output.TokenUsage;

import java.time.Instant;
import java.util.Map;

public class TokenUsageListener implements ChatModelListener {

    private static final String ATTR_USER_ID = "ai.user.id";
    private static final String ATTR_TRACE_ID = "ai.trace.id";
    private static final String ATTR_START_NANOS = "ai.start.nanos";

    private final String serviceName;
    private final String profile;
    private final String modelName;
    private final TokenUsageRecorder recorder;

    public TokenUsageListener(String serviceName, String profile,
                              String modelName, TokenUsageRecorder recorder) {
        this.serviceName = serviceName;
        this.profile = profile;
        this.modelName = modelName;
        this.recorder = recorder;
    }

    /**
     * 在调用线程上把上下文快照进 attributes。
     *
     * <p>两个必须注意的点：
     * <ol>
     *   <li>attributes 是 ConcurrentHashMap，<b>不接受 null value</b>，put(null) 直接抛 NPE。
     *       而「非请求线程读 ThreadLocal 得 null」是常态（后台抽取任务），所以必须兜底。</li>
     *   <li>onRequest 跑在调用线程 —— 这是 StreamingChatModel.chat() 的
     *       接口 default 方法里触发的（字节码已验证）。所以 ThreadLocal 在这里读得到。</li>
     * </ol>
     */
    @Override
    public void onRequest(ChatModelRequestContext requestContext) {
        Map<Object, Object> attributes = requestContext.attributes();
        attributes.put(ATTR_USER_ID, AiCallContext.userIdOrAnonymous());
        attributes.put(ATTR_TRACE_ID, nvl(AiCallContext.traceId()));
        attributes.put(ATTR_START_NANOS, System.nanoTime());
    }

    @Override
    public void onResponse(ChatModelResponseContext responseContext) {
        TokenUsage usage = responseContext.chatResponse().tokenUsage();
        recorder.record(new TokenUsageRecord(
                userIdOf(responseContext.attributes()),
                serviceName, profile, modelName,
                usage == null ? null : usage.inputTokenCount(),
                usage == null ? null : usage.outputTokenCount(),
                usage == null ? null : usage.totalTokenCount(),
                true,                                    // ← 走到这里就是成功
                latencyMs(responseContext.attributes()),
                traceIdOf(responseContext.attributes()),
                null,
                Instant.now()));
    }

    @Override
    public void onError(ChatModelErrorContext errorContext) {
        recorder.record(new TokenUsageRecord(
                userIdOf(errorContext.attributes()),
                serviceName, profile, modelName,
                null, null, null,
                false,                                   // ← 关键：区分失败
                latencyMs(errorContext.attributes()),
                traceIdOf(errorContext.attributes()),
                errorContext.error() == null
                        ? "Unknown" : errorContext.error().getClass().getSimpleName(),
                Instant.now()));
    }

    // ============================================ 取值辅助

    private static String userIdOf(Map<Object, Object> attributes) {
        Object v = attributes.get(ATTR_USER_ID);
        return v instanceof String s && !s.isBlank() ? s : "anonymous";
    }

    private static String traceIdOf(Map<Object, Object> attributes) {
        Object v = attributes.get(ATTR_TRACE_ID);
        return v instanceof String s && !s.isBlank() ? s : null;
    }

    /** attributes 是 request 与 response 之间唯一的桥 —— 跨线程靠它，不靠 ThreadLocal */
    private static long latencyMs(Map<Object, Object> attributes) {
        Object start = attributes.get(ATTR_START_NANOS);
        return start instanceof Long s ? (System.nanoTime() - s) / 1_000_000 : -1L;
    }

    private static String nvl(String s) { return s == null ? "" : s; }
}
```

> ⚠️ `nvl(AiCallContext.traceId())` 那行是**必须的** —— `traceId` 可能为 null，而 `attributes` 不接受 null。这就是当初 `userId` 那个 NPE 的同一个坑，别在 traceId 上再踩一次。

### 建表改动

```sql
ALTER TABLE ai_token_usage
    ADD COLUMN success    TINYINT(1)  NOT NULL DEFAULT 1 COMMENT '0=失败；区分「失败」与「成功但无 usage」',
    ADD COLUMN latency_ms BIGINT      NOT NULL DEFAULT -1 COMMENT '端到端耗时；-1=未测到',
    ADD COLUMN trace_id   VARCHAR(64) NULL             COMMENT '链路 id，用于串联日志',
    ADD COLUMN error_type VARCHAR(128) NULL            COMMENT '异常类名，不含 message',
    ADD INDEX idx_trace (trace_id);
```

**`error_type` 只留类名、不留 message**，是刻意的：异常 message 里经常带请求内容（可能含用户隐私）。要详情去日志里按 `traceId` 捞。

## 5. 缺口四：工具接入的"最后一段通用闭环"

现状（`AiCommonAutoConfiguration` 的 `McpConfig`）：

```java
@Bean
public McpToolProvider mcpToolProvider(McpClientRegister register) {
    return McpToolProvider.builder().mcpClients(register.all())
            .failIfOneServerFails(false).build();
}
```

**这个 Bean 没有任何消费者。** 底座侧的活到这里就断了 —— 因为"把工具挂进 `AiServices`"是装配动作，而那件事在业务模块。

**底座该做的不是接完它，是把"接的姿势"标准化**。具体两件事：

### 一是给业务一个"取工具"的稳定入口

现在业务要注入 `McpToolProvider` 并自己判断 null（没开 MCP 时 Bean 不存在）。把它们收进一个门面：

```java
package com.best.ai_common.mcp;

/**
 * 工具的统一取用入口。
 * 它解决的是「业务侧怎么拿到工具」这个问题，而不是「有哪些工具」——
 * 后者由 MCP 服务端决定，属于业务。
 */
public interface ToolProvider {

    /** 供 AiServices.builder().toolProvider(...) 使用；没有工具时返回一个空实现 */
    dev.langchain4j.service.tool.ToolProvider asLangChain4j();

    /** 当前挂了哪些 MCP 服务，给健康检查和运维页用 */
    java.util.Set<String> connectedServers();
}
```

### 二是让"工具调用"进可观测

工具调用是**费用和延迟的第二大来源**（一次工具调用 = 一次额外往返，还常常触发第二轮模型调用）。而 `ChatModelListener` **看不到工具**。

LangChain4j 里能看工具的地方只有 `TokenStream` 的事件：

```java
assistant.chat(memoryId, message)
        .beforeToolExecution(req -> log.info("调用工具 {}", req.toolExecutionRequest().name()))
        .onToolExecuted(exec -> log.info("工具 {} 返回", exec.toolExecutionRequest().name()))
        // ...
```

**底座能做的是一次性把这两个回调接进计量**，而不是让每个助手各写一遍。

> 这一条**依赖流式端点归谁**。如果 SSE 端点在业务模块（现状），那工具事件的采集也只能在业务里 —— 这就是它和"契约强度"那个待定问题的交叉点。

## 6. 待拍板：底座的"契约强度"该定在哪一档

这是本文唯一没有结论的一节，因为它取决于你的目标。

### 两档的差别

| | **弱契约（现状）** | **强契约** |
|---|---|---|
| 业务侧写什么 | 接口 + `@Configuration` 里的 `AiServices.builder(...)` | 接口 + 注解 |
| 装配谁做 | 业务 | 底座（动态代理/BeanPostProcessor） |
| 业务要知道 | LangChain4j 的 builder、要挂哪些 provider、memoryId 怎么拼 | 只有注解 |
| 漏挂的后果 | 静默失效（不报错） | 不存在（底座统一挂） |
| 底座要长成 | 一组 Bean | 一个装配框架 |
| 与 LangChain4j 的耦合 | 松（业务直接用它） | **紧**（底座要追上它的版本演进） |
| 加新能力（工具/审核/校验） | 业务自己加一行 | 底座加参数，**改公共 API** |

### 判断依据

**选弱契约，如果**：
- 你希望助手能自由用 LangChain4j 的全部能力（工具、审核、自定义参数）
- 你能接受"漏挂 provider 会静默失效"，并用测试兜住（`AssistantWiringTest` 就是这么做的）
- 你不想维护一个追上上游版本的框架

**选强契约，如果**：
- 你要开放给很多不熟悉 LangChain4j 的人写助手
- 你希望"挂工具/开审核"是配置而不是代码
- 你接受底座和 LangChain4j 版本绑定

### 我的倾向

**一期保持弱契约。** 三个理由：

1. **强契约的收益随"写助手的人数"增长，而你现在只有你一个。** 收益为零，成本却是立刻的。
2. **LangChain4j 还在快速演进**（你已经在 `OpenAi*` / `OpenAiOfficial*` 上撞过一次版本迁移）。底座长成框架之后，每次升级都要跟着改。
3. **弱契约缺的那个"防漏"可以用测试补** —— 你已经有 `AssistantWiringTest` 的结构断言。**测试比封装便宜，且不限制加能力。**

> 但这一条**有一个前提**：那三个"静默失效"的开关（记忆、检索、工具）**必须有测试兜住**。如果测试没写，弱契约就从"灵活"变成"危险"。
>
> 所以选弱契约的隐含动作是：**把 `AssistantWiringTest` 扩到三个开关全覆盖**（会话记忆、长期检索、工具）。

## 7. 建议的动作顺序

| 顺序 | 动作 | 成本 | 前置 |
|---|---|---|---|
| **1** | pom 标 `<optional>`（两个依赖） | 10 分钟 | 无 |
| **2** | `AiUserContext` → `AiCallContext`（五维 + `withUserId`） | 半天 | 无 |
| **3** | `TokenUsageRecord` 加 4 个字段 + 建表 + listener 改 | 2 小时 | 无 |
| **4** | 工具门面 `ToolProvider`（统一取用入口） | 1 小时 | 无 |
| **5** | `AssistantWiringTest` 扩到三个开关 | 2 小时 | 4 |
| — | **暂不做**：拆模块、提示词层、SSE 端点归位 | — | 等第 2–5 步落地后重估 |

### 第 2 步为什么排在第 3 步前面

`TokenUsageListener` 要写 `traceId`，而 `traceId` 只有上下文有了才能取到。**先扩上下文，台账才有东西可记。**

### 第 5 步为什么不能省

如果你选了弱契约，那三个开关的静默失效就是**唯一的风险来源**。测试是这一档契约的安全带 —— 没有它，弱契约不成立。

## 8. 一句话总结

> **底座不是"一堆能力"，是"使能"——它的验收标准不是功能多，而是"上面的助手只需要写业务"。**
>
> 按这个标准看，你现在缺的不是新模块，是三件小事：**依赖边界**（别强拖别人下水）、
> **上下文**（五个维度一个来源）、**可观测**（让台账能排障而不只记账）。
>
> 而"要不要拆模块"这个问题，等这三件事落地之后再问 —— 那时答案会自己浮出来。
