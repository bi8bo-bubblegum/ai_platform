# 交付单 02 · 摘要机制

> **本篇目标**：让窗口滑出去的消息不丢，而是压缩成摘要持续带在上下文里。
> **前置**：交付单 01 已跑通（6 个测试绿）。

---

## 先回答 01 结尾那个问题

> `ChatMemoryStore` 只有 `getMessages` / `updateMessages`。窗口把最老的消息挤出去时，我们怎么知道被挤掉的是哪几条？

**答案是：不要猜，接管它。**

`MessageWindowChatMemory` 在内部裁剪完才调 `updateMessages`，传给你的已经是裁好的列表——被挤掉的那几条你在这一层根本看不到。你可以拿新列表和旧列表做差集去反推，但那是**依赖第三方库的内部行为**：它哪天改成从中间删、或者一次加多条，你的差集就算错了，而且错得很安静。

所以本篇我们自己实现 `ChatMemory` 接口：

```
add(message) 时：
    all = 存量 + 新消息
    if all.size() > maxMessages:
        evicted = all 的前 (all.size() - maxMessages) 条   ← 这里我们【确切知道】是哪几条
        把这些交给摘要器
        all = all 的后 maxMessages 条
    写回存储
```

自己实现要多写大约 60 行，换回来的是：**摘要的触发点是你自己说了算的，不用反推任何东西。**

# 第一节 · SessionKey

## 为什么需要它

`ChatMemoryProvider.get(Object memoryId)` 只拿到**一个** id。但我们的记忆要同时知道三件事：**哪个助手**、**哪个用户**、**哪一次会话**。

于是把三者编进一个 id：`assistantId::userId::sessionId`。

**`assistantId` 这一段不是可选的，它防的是一个真实的串号。** 会话历史是「每个助手各一份」的，
而 `sessionId` 由调用方生成 —— 没有任何机制保证它全局唯一。少了 `assistantId`，只要两个助手
收到相同的 `(userId, sessionId)`，它们就会落进**同一个 Redis key**，共享同一份对话历史。

症状很具体：在客服助手说"我叫熊鑫"，切到运筹眼问"我叫什么"，它答得出"熊鑫"；
而且两边的对话会交替滑出窗口，**摘要被两边的对话交替污染**。

> 注意这和**长期记忆**的取舍正好相反：用户事实是**用户级、跨助手共享**（那是刻意的，见交付单 05/06）；
> 会话上下文是**助手级、不该跨**。两个作用域不能混 ——
> 用会话记忆去实现"跨助手连续性"，等于让上下文无界增长，而那正是长期记忆要解决的问题。

> 为什么用 `::` 而不是 `:`？因为 userId 或 sessionId 里更可能出现单个冒号（比如时间戳里的 `10:30`），而 `::` 几乎不会。分界符选得越"不可能出现"，解析就越不需要考虑转义。

## `session/SessionKey.java`

```java
package com.best.ai_memory.session;

/**
 * 「一次会话」的完整标识：哪个助手 + 谁 + 哪一次。
 *
 * <p>为什么不直接用几个独立参数传？
 * 因为 LangChain4j 的 ChatMemoryProvider 和 ContentRetriever 都只认一个 id，
 * 我们没有地方挂后面的几个。所以把三段编码进一个字符串，在需要的地方解析回来。
 *
 * <p><b>为什么必须有 assistantId：</b>会话历史是【每个助手各一份】的。
 * 少了它，只要两个助手收到相同的 (userId, sessionId) —— 而 sessionId 由调用方生成，
 * 没有任何机制保证全局唯一 —— 它们就会落进同一个 Redis key，共享同一份历史。
 * 症状是：在客服里说的事，运筹眼"记得"；而且摘要会被两边的对话交替污染。
 *
 * <p>用 record 而不是普通类：它是纯值对象，天然需要 equals / hashCode / toString，
 * 而且不可变，跨线程传不会有意外。
 */
public record SessionKey(String assistantId, String userId, String sessionId) {

    /**
     * 分界符。
     * 选双冒号而不是单冒号：userId / sessionId 里出现单个冒号很正常
     * （时间戳、命名空间前缀），出现双冒号的概率可以忽略。
     */
    private static final String SEPARATOR = "::";

    /**
     * 紧凑构造器：把"格式约定"从注释变成"构造时就炸"。
     *
     * <p>前两段不允许含分隔符 —— 否则 memoryId 无法无歧义地解析回来。
     * 与其等到解析时才发现，不如在这里就拦下来。
     */
    public SessionKey {
        requireNoSeparator(assistantId, "assistantId");
        requireNoSeparator(userId, "userId");
        // sessionId 允许含 ::（它是最后一段，解析时不歧义），但不能为空 ——
        // 否则 toMemoryId() 会拼出 "a::b::null" 这种看着正常、实际永远查不到东西的 key
        if (sessionId == null || sessionId.isBlank()) {
            throw new IllegalArgumentException("sessionId 不能为空");
        }
    }

    /** 工厂方法，可读性比 new 好一点（new 也行，record 的构造器是公开的） */
    public static SessionKey of(String assistantId, String userId, String sessionId) {
        return new SessionKey(assistantId, userId, sessionId);
    }

    /**
     * 拼成 LangChain4j 能用的 memoryId。
     *
     * <p>为什么叫 toMemoryId 而不是 toString？
     * toString 是"给人看的"，语义上可以随时改格式；toMemoryId 是"给框架用的"，
     * 改它会让存量数据的 key 全部失效。名字分开，改的时候心里有数。
     */
    public String toMemoryId() {
        return assistantId + SEPARATOR + userId + SEPARATOR + sessionId;
    }

    /**
     * 从 memoryId 解析回来。
     *
     * <p>只找【前两个】分隔符：第三段往后全部归 sessionId。
     * sessionId 里带 :: 是允许的，所以不能用 split 切成三段。
     */
    public static SessionKey parse(String memoryId) {
        if (memoryId == null) {
            throw new IllegalArgumentException("memoryId 不能为 null");
        }
        int first = memoryId.indexOf(SEPARATOR);
        int second = first < 0 ? -1 : memoryId.indexOf(SEPARATOR, first + SEPARATOR.length());
        if (second < 0) {
            // 直接抛异常而不是给默认值：
            // 格式错了意味着上游装配错了，这种错必须立刻炸出来，
            // 而不是悄悄把用户 A 的记忆记到用户 B 头上。
            throw new IllegalArgumentException(
                    "memoryId 格式必须是 assistantId" + SEPARATOR + "userId" + SEPARATOR
                            + "sessionId，实际收到: " + memoryId);
        }
        return new SessionKey(
                memoryId.substring(0, first),
                memoryId.substring(first + SEPARATOR.length(), second),
                memoryId.substring(second + SEPARATOR.length()));
    }

    private static void requireNoSeparator(String value, String name) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(name + " 不能为空");
        }
        if (value.contains(SEPARATOR)) {
            throw new IllegalArgumentException(
                    name + " 不能包含 " + SEPARATOR + "，否则 memoryId 无法解析，实际: " + value);
        }
    }
}
```

## 测试：`test/.../session/SessionKeyTest.java`

```java
package com.best.ai_memory.session;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class SessionKeyTest {

    @Test
    @DisplayName("拼出来再解析回去，内容一模一样")
    void roundTrip() {
        SessionKey key = SessionKey.of("assistant-demo", "u123", "s456");

        assertThat(key.toMemoryId()).isEqualTo("assistant-demo::u123::s456");
        assertThat(SessionKey.parse("assistant-demo::u123::s456")).isEqualTo(key);
    }

    @Test
    @DisplayName("只分开前两段，后面全部归 sessionId")
    void onlyFirstTwoSeparatorsSplit() {
        // 这条固化一个设计决策：parse 用的是 indexOf 而不是 split。
        // 谁要是改成 split 切成三段，这个用例会红。
        SessionKey key = SessionKey.parse("assistant-demo::u123::s456::extra");

        assertThat(key.assistantId()).isEqualTo("assistant-demo");
        assertThat(key.userId()).isEqualTo("u123");
        assertThat(key.sessionId()).isEqualTo("s456::extra");
    }

    @Test
    @DisplayName("只有两段（老格式）必须抛异常，不能被静默解读")
    void legacyTwoSegmentFormatThrows() {
        // "u123::s456" 是加 assistantId 之前的格式。
        // 如果 parse 对它宽容，就会被读成 assistantId=u123, userId=s456 —— 一段都不对。
        assertThatThrownBy(() -> SessionKey.parse("u123::s456"))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("assistantId::userId::sessionId");
    }

    @Test
    @DisplayName("assistantId / userId 里带 :: 时，构造就炸 —— 不留到解析时才暴露")
    void segmentMustNotContainSeparator() {
        assertThatThrownBy(() -> SessionKey.of("a::b", "u1", "s1"))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("assistantId");

        assertThatThrownBy(() -> SessionKey.of("assistant-demo", "u::1", "s1"))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("userId");
    }

    @Test
    @DisplayName("null 也要抛 IllegalArgumentException，而不是 NPE")
    void nullThrows() {
        assertThatThrownBy(() -> SessionKey.parse(null))
                .isInstanceOf(IllegalArgumentException.class);
    }
}
```

# 第二节 · 摘要的存储与生成

## 2.1 `session/SessionSummaryStore.java`

```java
package com.best.ai_memory.session;

/**
 * 会话摘要的存储。
 *
 * <p>为什么和 SessionMemoryStore 分开，不塞进同一个接口？
 * 因为它们的生命周期和存储介质可能不同：
 * 消息是"流水"，摘要是一行会被反复覆盖的记录；
 * 消息量大、摘要量小。将来消息挪到 Redis、摘要挪到 MySQL 也完全合理。
 * 现在分开放，将来就不用改接口。
 */
public interface SessionSummaryStore {

    /** 取摘要。没有就返回 null —— 这里 null 有明确含义："还没生成过" */
    String get(Object memoryId);

    /** 覆盖写入。注意是覆盖，不是追加 */
    void save(Object memoryId, String summary);

    void delete(Object memoryId);
}
```

## 2.2 `session/InMemorySessionSummaryStore.java`

```java
package com.best.ai_memory.session;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/** 内存版摘要存储。同样只用于开发和测试，不能上生产。 */
public class InMemorySessionSummaryStore implements SessionSummaryStore {

    private final Map<Object, String> store = new ConcurrentHashMap<>();

    @Override
    public String get(Object memoryId) {
        return store.get(memoryId);
    }

    @Override
    public void save(Object memoryId, String summary) {
        // put 而不是 merge：摘要是【整体覆盖】，不是拼接。
        // 如果这里写成 merge，摘要会无限增长，最后又变成一个放不下的上下文 ——
        // 那就白做摘要了。
        store.put(memoryId, summary);
    }

    @Override
    public void delete(Object memoryId) {
        store.remove(memoryId);
    }
}
```

## 2.4 `session/LlmConversationSummarizer.java`

```java
package com.best.ai_memory.session;

import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.data.message.SystemMessage;
import dev.langchain4j.data.message.UserMessage;
import dev.langchain4j.model.chat.ChatModel;
import lombok.extern.slf4j.Slf4j;

import java.util.List;

/**
 * 用 LLM 生成摘要。
 *
 * <p>它只收一个 {@link ChatModel}，<b>不认识</b> ChatModelRegister ——
 * "用哪一档"的决定权在装配层，这个类不需要知道 profile 这个概念。
 * 这是全项目统一的一条规则（见交付单 04 第三节），好处具体有三个：
 * <ul>
 *   <li>ChatModel 是接口，单测里 new 一个假的就够；换成依赖 ChatModelRegister
 *       （具体类，构造器还要 ChatModelProperties）测试就难写了</li>
 *   <li>这个类真正需要的是"一个能 chat 的模型"，不是"一个按档取模型的工厂"</li>
 *   <li>搜 profile 时只会命中配置类和装配类，不用翻遍业务代码</li>
 * </ul>
 *
 * <p>代价是<b>模型热更新对这个类不生效</b> —— 它持的是启动时解析好的实例。
 * 但这一期本来就不做热更新，而且真正的瓶颈在 AiServices（构建期绑定），
 * 所以这个代价目前不存在。详见交付单 04 第三节。
 */
@Slf4j
public class LlmConversationSummarizer implements ConversationSummarizer {

    /**
     * 提示词。
     *
     * <p>写成 text block（Java 15+ 的三引号）而不是拼接字符串，
     * 是为了让提示词在源码里就是它最终的样子 —— 调提示词的时候
     * 不用在脑子里做字符串拼接。
     *
     * <p>五条约束里，第 2 条和第 3 条最关键：
     * 「丢弃寒暄」防止摘要被"你好""谢谢"填满；
     * 「第三人称陈述」防止摘要退化成逐句转述，那样还不如不压缩。
     */
    private static final String PROMPT = """
            你是对话摘要器。下面给了【已有摘要】和【新增对话】。

            请把两者合并成一段新摘要，规则：
            1. 保留事实：人名、数字、决定、偏好、未完成的事项
            2. 丢弃寒暄、客套、重复内容
            3. 用第三人称陈述，不要写"用户说""助手回答"这类转述
            4. 不要分点，写成一到两段连续的话
            5. 只输出摘要正文，不要标题、不要解释

            【已有摘要】
            %s

            【新增对话】
            %s
            """;

    private final ChatModel chatModel;
    private final SessionSummaryStore summaryStore;

    /**
     * @param chatModel    由装配类从 ChatModelRegister 解析好后传进来。
     *                     注意这里【刻意】只收一个 ChatModel，不收 register —— 理由：
     *                     ① ChatModel 是接口，单测里 new 一个假的就够；
     *                        ChatModelRegister 是具体类，测试里造它很别扭
     *                     ② 这个类真正需要的是"一个能 chat 的模型"，
     *                        不是"一个按档取模型的工厂"
     *                     ③ 这样 profile 只出现在装配层，搜 profile 时不用翻遍业务代码
     * @param summaryStore 摘要的存储
     */
    public LlmConversationSummarizer(ChatModel chatModel,
                                     SessionSummaryStore summaryStore) {
        this.chatModel = chatModel;
        this.summaryStore = summaryStore;
    }

    @Override
    public void append(Object memoryId, List<ChatMessage> evicted) {
        if (evicted == null || evicted.isEmpty()) {
            return;   // 空批次直接返回，省一次模型调用
        }

        try {
            String previous = summaryStore.get(memoryId);
            String prompt = PROMPT.formatted(
                    previous == null ? "（无）" : previous,
                    render(evicted));

            String summary = chatModel.chat(prompt);
            if (summary == null || summary.isBlank()) {
                log.warn("摘要在{}上生成了空结果，保留旧摘要", memoryId);
                return;   // 关键：宁可保留旧摘要，也不要用一个空字符串覆盖掉它
            }
            summaryStore.save(memoryId, summary.trim());

        } catch (Exception e) {
            // 摘要失败不能影响对话本身。
            // 这里的取舍是：宁可这段摘要暂时缺失，也不要把异常抛给用户。
            // 代价是这几条消息永久性地不在摘要里了 —— 所以要打 error 级别的日志。
            log.error("生成会话摘要失败，memoryId={}，本条摘要丢失 {} 条消息",
                    memoryId, evicted.size(), e);
        }
    }

    /** 把消息列表拼成纯文本，给模型看 */
    private static String render(List<ChatMessage> messages) {
        StringBuilder sb = new StringBuilder();
        for (ChatMessage m : messages) {
            sb.append(roleOf(m)).append("：").append(textOf(m)).append('\n');
        }
        return sb.toString();
    }

    private static String roleOf(ChatMessage m) {
        if (m instanceof UserMessage) return "用户";
        if (m instanceof AiMessage) return "助手";
        if (m instanceof SystemMessage) return "系统";
        return "其他";
    }

    private static String textOf(ChatMessage m) {
        // 这里刻意只取纯文本。工具调用消息（ToolExecutionResultMessage）
        // 的内容通常很长且是 JSON，塞进摘要会把摘要挤爆。
        // 等你真的用上工具了，再决定要不要把它们也摘要进去。
        if (m instanceof UserMessage um) return um.singleText();
        if (m instanceof AiMessage am) return am.text();
        if (m instanceof SystemMessage sm) return sm.text();
        return "";
    }
}
```

## 3.1 `session/SummarizingChatMemory.java`

```java
package com.best.ai_memory.session;

import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.data.message.SystemMessage;
import dev.langchain4j.memory.ChatMemory;

import java.util.ArrayList;
import java.util.List;

/**
 * 带摘要的会话记忆。
 *
 * <p>核心决策：<b>不使用 MessageWindowChatMemory，自己实现 ChatMemory。</b>
 *
 * <p>原因是 MessageWindowChatMemory 在内部裁剪完才回调 updateMessages，
 * 被挤掉的消息在这一层看不到。要拿到它们只能拿新旧列表做差集去反推，
 * 而那是依赖第三方库内部行为的写法 —— 它哪天改成从中间删就静默算错。
 * 自己实现之后，"挤掉哪几条"是我们自己算出来的，不需要反推任何东西。
 */
public class SummarizingChatMemory implements ChatMemory {

    private final Object id;
    private final SessionMemoryStore store;
    private final SessionSummaryStore summaryStore;
    private final ConversationSummarizer summarizer;

    /** 窗口大小：最多保留多少条原文。超过的压缩进摘要 */
    private final int maxMessages;

    public SummarizingChatMemory(Object id,
                                 SessionMemoryStore store,
                                 SessionSummaryStore summaryStore,
                                 ConversationSummarizer summarizer,
                                 int maxMessages) {
        if (maxMessages <= 0) {
            throw new IllegalArgumentException("maxMessages 必须大于 0");
        }
        this.id = id;
        this.store = store;
        this.summaryStore = summaryStore;
        this.summarizer = summarizer;
        this.maxMessages = maxMessages;
    }

    @Override
    public Object id() {
        return id;
    }

    @Override
    public void add(ChatMessage message) {
        add(List.of(message));
    }

    /**
     * 批量加入消息。
     *
     * <p>⚠️ 签名是 {@code Iterable<ChatMessage>}，不是 {@code List<ChatMessage>}。
     *
     * <p>ChatMemory 接口里【必须实现】的抽象方法只有四个：
     * {@code id()} / {@code add(ChatMessage)} / {@code messages()} / {@code clear()}。
     * 批量那个是默认方法 {@code default void add(Iterable<ChatMessage> messages)}。
     * 写成 {@code add(List<ChatMessage>)} 再标 {@code @Override} 会编译不过，
     * 报 "method does not override or implement a method from a supertype"。
     *
     * <p>用 Iterable 而不是 List 还有个实际好处：调用方传 Set、传自定义集合都能接住。
     *
     * <p>为什么必须覆盖这个 default？它的默认行为是逐条调 add(ChatMessage)，
     * 那样一次加 4 条消息会触发 4 次溢出检查、调 4 次摘要器。
     * 我们要的是整整一批当作一次操作。
     */
    @Override
    public void add(Iterable<ChatMessage> messages) {
        List<ChatMessage> incoming = new ArrayList<>();
        messages.forEach(incoming::add);

        if (incoming.isEmpty()) {
            return;
        }

        List<ChatMessage> all = new ArrayList<>(store.getMessages(id));
        all.addAll(incoming);

        int overflow = all.size() - maxMessages;
        if (overflow > 0) {
            // 就是这里 —— 我们【确切知道】被挤掉的是前 overflow 条，
            // 因为是我们自己加的、自己数的。
            List<ChatMessage> evicted = new ArrayList<>(all.subList(0, overflow));

            // 交给摘要器。注意是 append 而不是 replace：
            // 摘要是"累积"的，每次都把新滑出的内容并进旧摘要。
            summarizer.append(id, evicted);

            all = new ArrayList<>(all.subList(overflow, all.size()));
        }

        store.updateMessages(id, all);
    }

    /**
     * 整体替换消息列表。
     *
     * <p>为什么也要覆盖？接口的默认实现是 {@code clear()} + {@code add(Iterable)}
     * —— 而我们的 {@code clear()} 会【连摘要一起删掉】。
     * 但 set 的语义是"替换消息"，不是"清空整段对话"。
     * 摘要代表的是更早的历史，不该被这次替换波及。
     *
     * <p>LangChain4j 不会自动调这个方法（接口 javadoc 里写明了）。
     * 但 javadoc 同时说 set 的典型用途是 "memory compaction" ——
     * 那正是我们这套东西在做的事。留一个语义正确的实现，免得以将来踩坑。
     *
     * <p>注意这里【不做窗口裁剪】：调用方既然用 set 整体替换，
     * 就说明它已经自己整理过了，我们再裁一次会把它的意图改掉。
     */
    @Override
    public void set(Iterable<ChatMessage> messages) {
        List<ChatMessage> incoming = new ArrayList<>();
        messages.forEach(incoming::add);
        store.updateMessages(id, incoming);
    }

    @Override
    public List<ChatMessage> messages() {
        List<ChatMessage> result = new ArrayList<>();

        // 摘要在最前面。
        //
        // 为什么包成 SystemMessage 而不是 UserMessage？
        // 因为它是"背景知识"，不是"用户说的话"。用 SystemMessage 语义更准，
        // 而且模型对 system 的注意力权重通常更高。
        //
        // 注意：这样会和服务接口上的 @SystemMessage 并存，也就是 prompt 里
        // 有两条 system 消息。OpenAI 兼容协议允许，你的 ai-gateway 应该也没问题。
        // 如果网关报了"只允许一条 system 消息"，就把它改成 UserMessage 加前缀。
        String summary = summaryStore.get(id);
        if (summary != null && !summary.isBlank()) {
            result.add(SystemMessage.from("[更早的对话摘要]\n" + summary));
        }

        result.addAll(store.getMessages(id));
        return result;
    }

    @Override
    public void clear() {
        store.deleteMessages(id);
        summaryStore.delete(id);
    }
}
```

> **`ChatMemory` 接口到底要实现几个方法**
>
> 必须实现（抽象方法）只有四个：
>
> ```java
> Object id();
> void add(ChatMessage message);
> List<ChatMessage> messages();
> void clear();
> ```
>
> 其余全是 `default`，不实现也能编译：
>
> | 方法 | 默认行为 | 要不要覆盖 |
> |---|---|---|
> | `add(ChatMessage...)` | 逐条调 `add(ChatMessage)` | 不用 |
> | `add(Iterable<ChatMessage>)` | 逐条调 `add(ChatMessage)` | **要覆盖** —— 见上面注释 |
> | `set(Iterable<ChatMessage>)` | `clear()` + `add(Iterable)` | **要覆盖** —— 默认实现会把摘要也清掉 |
> | `addAsync(List)` / `setAsync(List)` / `messagesAsync()` | 返回失败的 future（`AsyncNotSupportedException`） | 现在不用。**但如果你以后把助手接口的返回类型改成 `Flux`（需要 `langchain4j-reactor`），这三个就必须实现** —— 否则异步链路会直接拿到一个失败的 future |
>
> 最后一行是个提前预警：`TokenStream` 走的是回调，不碰这几个 async 方法；`Flux` 会碰。

## 3.2 `session/SummarizingChatMemoryProvider.java`

```java
package com.best.ai_memory.session;

import dev.langchain4j.memory.ChatMemory;
import dev.langchain4j.service.memory.ChatMemoryProvider;

/**
 * 按 memoryId 造 SummarizingChatMemory。
 *
 * <p>LangChain4j 的 AiServices 每收到一个请求，都会先调这个 provider
 * 拿到该会话的 ChatMemory，然后 add 用户消息、读 messages() 发给模型。
 * 我们不手动调 add / messages —— 框架全包了。
 */
public class SummarizingChatMemoryProvider implements ChatMemoryProvider {

    private final SessionMemoryStore store;
    private final SessionSummaryStore summaryStore;
    private final ConversationSummarizer summarizer;
    private final int maxMessages;

    public SummarizingChatMemoryProvider(SessionMemoryStore store,
                                         SessionSummaryStore summaryStore,
                                         ConversationSummarizer summarizer,
                                         int maxMessages) {
        this.store = store;
        this.summaryStore = summaryStore;
        this.summarizer = summarizer;
        this.maxMessages = maxMessages;
    }

    @Override
    public ChatMemory get(Object memoryId) {
        // 每次都 new 一个 ChatMemory 对象，但【数据】是从 store 里读的。
        // 所以即使每次都是新对象，历史也不会丢 —— 状态在 store 里，不在对象里。
        // 这一点很重要：SummarizingChatMemory 必须是无状态的（除了 id 和依赖），
        // 否则多副本部署就会出问题。
        return new SummarizingChatMemory(memoryId, store, summaryStore, summarizer, maxMessages);
    }
}
```

## 3.3 测试：`test/.../session/SummarizingChatMemoryTest.java`

```java
package com.best.ai_memory.session;

import dev.langchain4j.data.message.AiMessage;
import dev.langchain4j.data.message.ChatMessage;
import dev.langchain4j.data.message.UserMessage;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.util.ArrayList;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class SummarizingChatMemoryTest {

    private InMemorySessionMemoryStore store;
    private InMemorySessionSummaryStore summaryStore;
    private RecordingSummarizer summarizer;
    private SummarizingChatMemory memory;

    /** 假的摘要器：只记录"被挤掉了哪些"，不真的调模型 */
    static class RecordingSummarizer implements ConversationSummarizer {
        final List<List<ChatMessage>> batches = new ArrayList<>();

        @Override
        public void append(Object memoryId, List<ChatMessage> evicted) {
            batches.add(new ArrayList<>(evicted));
        }

        List<ChatMessage> allEvicted() {
            return batches.stream().flatMap(List::stream).toList();
        }
    }

    @BeforeEach
    void setUp() {
        store = new InMemorySessionMemoryStore();
        summaryStore = new InMemorySessionSummaryStore();
        summarizer = new RecordingSummarizer();
        // 窗口设成 3，方便用很少的消息就触发溢出
        memory = new SummarizingChatMemory("s1", store, summaryStore, summarizer, 3);
    }

    @Test
    @DisplayName("没溢出时不调摘要器")
    void noOverflowNoSummarize() {
        memory.add(UserMessage.from("1"));
        memory.add(UserMessage.from("2"));

        assertThat(summarizer.batches).isEmpty();
        assertThat(memory.messages()).hasSize(2);
    }

    @Test
    @DisplayName("溢出时，被挤掉的正好是最老的那几条")
    void evictsOldest() {
        memory.add(UserMessage.from("1"));
        memory.add(UserMessage.from("2"));
        memory.add(UserMessage.from("3"));
        memory.add(UserMessage.from("4"));   // 第 4 条进来，第 1 条被挤掉

        assertThat(summarizer.batches).hasSize(1);
        assertThat(texts(summarizer.allEvicted())).containsExactly("1");
        assertThat(texts(memory.messages())).containsExactly("2", "3", "4");
    }

    @Test
    @DisplayName("连续溢出，每次都只把新滑出的那几条交给摘要器")
    void evictsIncrementally() {
        for (int i = 1; i <= 5; i++) {
            memory.add(UserMessage.from(String.valueOf(i)));
        }
        // 第 4 条挤掉 1，第 5 条挤掉 2 → 两次调用，各一条
        assertThat(summarizer.batches).hasSize(2);
        assertThat(texts(summarizer.allEvicted())).containsExactly("1", "2");
    }

    @Test
    @DisplayName("有摘要时，messages() 会把摘要放在最前面")
    void summaryIsPrepended() {
        summaryStore.save("s1", "用户叫熊鑫，做 Java 后端。");
        memory.add(UserMessage.from("继续说"));

        List<ChatMessage> messages = memory.messages();

        assertThat(messages).hasSize(2);
        assertThat(messages.get(0).getClass().getSimpleName()).isEqualTo("SystemMessage");
        assertThat(texts(messages).get(0)).contains("熊鑫");
        assertThat(texts(messages).get(1)).isEqualTo("继续说");
    }

    @Test
    @DisplayName("clear 之后消息和摘要都没了")
    void clearRemovesBoth() {
        summaryStore.save("s1", "旧摘要");
        memory.add(UserMessage.from("1"));

        memory.clear();

        assertThat(memory.messages()).isEmpty();
        assertThat(summaryStore.get("s1")).isNull();
    }

    @Test
    @DisplayName("一次加多条也会正确裁剪")
    void addMultipleAtOnce() {
        memory.add(List.of(
                UserMessage.from("1"),
                AiMessage.from("2"),
                UserMessage.from("3"),
                AiMessage.from("4")));

        assertThat(texts(memory.messages())).containsExactly("2", "3", "4");
        assertThat(texts(summarizer.allEvicted())).containsExactly("1");
    }

    @Test
    @DisplayName("set 只替换消息，不动摘要 —— 这就是要覆盖默认实现的原因")
    void setReplacesMessagesButKeepsSummary() {
        summaryStore.save("s1", "摘要还在");
        memory.add(UserMessage.from("旧的"));

        memory.set(List.of(UserMessage.from("新的")));

        // 消息被换掉了
        assertThat(texts(store.getMessages("s1"))).containsExactly("新的");
        // 摘要在。如果用接口的默认实现（clear + add），这里会变成 null
        assertThat(summaryStore.get("s1")).isEqualTo("摘要还在");
    }

    private static List<String> texts(List<ChatMessage> messages) {
        List<String> out = new ArrayList<>();
        for (ChatMessage m : messages) {
            if (m instanceof UserMessage um) out.add(um.singleText());
            else if (m instanceof AiMessage am) out.add(am.text());
            else if (m instanceof dev.langchain4j.data.message.SystemMessage sm) out.add(sm.text());
        }
        return out;
    }
}
```
