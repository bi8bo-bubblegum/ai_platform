## 二、P0 · 两个真问题（都是装配/挂载漏了，不报错）

### P0-1 `McpAutoConfiguration` 没有进 `.imports` → MCP 整体失效

`ai-common` 的装配清单里只有两行：

```
com.best.ai_common.config.AiCommonAutoConfiguration
com.best.ai_common.metrics.TokenUsageDbAutoConfiguration
```

而 `mcp/McpAutoConfiguration` 是**第三个**装配类，它不在清单里。它的条件是
`@ConditionalOnProperty("ai.mcp.enabled")` —— 也就是说：

> **你在 yml 里写 `ai.mcp.enabled: true` 也不会生效，因为那个类根本没被 Spring 读进来。**

症状有两种：
- 业务代码注入 `McpToolProvider` → 启动报 `NoSuchBeanDefinitionException: McpToolProvider`
- 用 `ObjectProvider` 兜着 → **静默没有任何工具**，加工具时完全摸不着头脑

**根因不是漏了一行，是装配清单会随包增长。** 三个 `@AutoConfiguration` 类散在
`config/` `metrics/` `mcp/` 三个包里，`.imports` 就得跟着长 —— 而这个文件是**纯文本，
编译器不管、IDE 不管**，写漏了只会得到一个语焉不详的 `ClassNotFoundException`。

**修法（推荐）：把三个装配类收成一个。** `ai-memory` 已经用了正确的模式，
`ai-common` 抄它就行：

```java
// config/AiCommonAutoConfiguration.java —— 唯一进 .imports 的类
@AutoConfiguration
@EnableConfigurationProperties({
        ChatModelProperties.class,
        EmbeddingModelProperties.class,
        McpProperties.class          // ← 原来在 McpAutoConfiguration 上
})
public class AiCommonAutoConfiguration {

    // ---------- 模型 ----------
    @Bean @ConditionalOnMissingBean
    public ChatModelRegister chatModelRegister(...) { ... }

    @Bean @ConditionalOnMissingBean
    public StreamingChatModelRegister streamingChatModelRegister(...) { ... }

    @Bean @ConditionalOnMissingBean
    public EmbeddingModelRegister embeddingModelRegister(...) { ... }

    // ---------- 用户上下文 ----------
    @Bean @ConditionalOnMissingBean
    @ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
    public AiUserContextInterceptor aiUserContextInterceptor() { ... }

    // ---------- token 台账（原来是独立的 TokenUsageDbAutoConfiguration）----------
    @Configuration(proxyBeanMethods = false)
    @ConditionalOnClass({BaseMapper.class, DataSource.class})
    @ConditionalOnBean(DataSource.class)                 // ⚠️ 见下方说明
    @MapperScan("com.best.ai_common.metrics.db")
    static class TokenUsageDbConfig {
        @Bean @ConditionalOnMissingBean
        public TokenUsageRecorder tokenUsageRecorder(AiTokenUsageMapper mapper) {
            return new DbTokenUsageRecorder(mapper);
        }
    }

    // ---------- MCP（原来是独立的 McpAutoConfiguration）----------
    @Configuration(proxyBeanMethods = false)
    @ConditionalOnProperty(prefix = "ai.mcp", name = "enabled", havingValue = "true")
    static class McpConfig {
        @Bean @ConditionalOnMissingBean
        public McpClientRegister mcpClientRegister(McpProperties properties) { ... }

        @Bean @ConditionalOnMissingBean
        public McpToolProvider mcpToolProvider(McpClientRegister register) { ... }
    }
}
```

`.imports` 从此**永远只有一行**：

```
com.best.ai_common.config.AiCommonAutoConfiguration
```

> **一个必须注意的顺序陷阱**：原来 `TokenUsageDbAutoConfiguration` 上有
> `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`。收成嵌套类之后，
> 类级没有 `after` 了，而 `@ConditionalOnBean(DataSource.class)` 会在 DataSource
> **注册之前**求值 → 永远 false → **整块静默不装载**。
>
> 两个办法，选一个：
> - 给**外层**类加 `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`
>   （`ai-memory` 就是这么做的，最省事）
> - 或者嵌套类不用 `@ConditionalOnBean`，改成对 `DataSource` 的类型条件

### P0-2 `StreamingChatModelRegister` 没挂 `TokenUsageListener` → 流式调用不计费

```java
// ChatModelRegister：挂了 ✓
List<ChatModelListener> listeners = recorder == null ? List.of()
        : List.of(new TokenUsageListener(serviceName, profile, endpoint.modelName(), recorder));
return OpenAiChatModel.builder()... .listeners(listeners).build();

// StreamingChatModelRegister：只收 properties，根本没这个参数 ✗
public StreamingChatModelRegister(ChatModelProperties chatModelProperties) { ... }
return OpenAiStreamingChatModel.builder()... .build();
```

**而流式恰恰是主场景** —— 你那个 `ChatStreamController` 走的就是它。
结果是：`ai_token_usage` 表里只会有同步调用的记录，**用户在页面上聊天烧掉的 token 一条都不记**。

你之前专门问过「流式模型不能统计 token 吗」，当时确认过：
`OpenAiStreamingChatModel` **支持 `.listeners(...)`**，和阻塞式用的是同一个接口。
所以这是漏了，不是做不到。

修法照抄 `ChatModelRegister` 的形状：

```java
public class StreamingChatModelRegister extends ModelRegister<StreamingChatModel> {

    private final ChatModelProperties properties;
    private final String serviceName;
    private final TokenUsageRecorder recorder;

    public StreamingChatModelRegister(ChatModelProperties properties,
                                      String serviceName,
                                      TokenUsageRecorder recorder) {
        this.properties = properties;
        this.serviceName = serviceName;
        this.recorder = recorder;
    }

    @Override
    protected StreamingChatModel create(String profile) {
        ChatModelProperties.Endpoint endpoint = properties.getEndpoint(profile);
        List<ChatModelListener> listeners = recorder == null ? List.of()
                : List.of(new TokenUsageListener(serviceName, profile, endpoint.modelName(), recorder));
        return OpenAiStreamingChatModel.builder()
                ...
                .listeners(listeners)      // ← 就是这一行
                .build();
    }
}
```

装配处也要跟着改（`AiCommonAutoConfiguration` 里那个 Bean 现在只传 properties）：

```java
@Bean
@ConditionalOnMissingBean
public StreamingChatModelRegister streamingChatModelRegister(
        ChatModelProperties properties,
        ObjectProvider<TokenUsageRecorder> recorderProvider,
        @Value("${ai.metrics.service-name:${spring.application.name:unknown}}") String serviceName) {
    return new StreamingChatModelRegister(properties, serviceName, recorderProvider.getIfAvailable());
}
```

> **顺带一个关于包结构的观察**：`ChatModelRegister` 和 `StreamingChatModelRegister`
> 住在同一个 `register` 包里，但一个收 3 个参数、一个收 1 个，用法完全不对称。
> **同一个包里两个"平级"的实现，只要形状不同，就一定有一个是漏的** ——
> 这类不一致是很好的排查线索，值得养成习惯去盯。

## 三、P1 · 两处越界（现在改最便宜）

判据只有一条：

> **只被一个子包用，就住进那个子包。**

### P1-1 `VectorCodec` 应该下沉到 `user/db/`

实测引用点只有一处：

```
user/db/FloatArrayTypeHandler.java:18  ps.setBytes(i, VectorCodec.encode(parameter));
user/db/FloatArrayTypeHandler.java:23  return VectorCodec.decode(rs.getBytes(columnName));
```

`VectorCodec` 做的是 `float[] ↔ BLOB` 的编解码 —— 这是**存储格式**，不是领域概念。
`UserMemory` 的那个 `float[] embedding` 字段对调用方是透明的，靠的是 `FloatArrayTypeHandler`。
所以 `VectorCodec` 只服务 `db` 层，却在 `user` 顶层，**出现在了对外可见的包面上**。

挪到 `user/db/VectorCodec` 之后，`user` 顶层的 9 个类里就少了一个"实现细节"。

### P1-2 `AiTokenUsageEntity` 应该下沉到 `metrics/db/`

它的引用点全在 `metrics/db/` 里：

```
metrics/db/AiTokenUsageMapper.java      extends BaseMapper<AiTokenUsageEntity>
metrics/db/DbTokenUsageRecorder.java    toEntity(TokenUsageRecord)
```

**现在层级是反的** —— 实体在父包，它的 Mapper 在子包，从 `metrics/` 顶层看过去
完全想不到"这个实体只属于 db 那一层"。

## 四、P2 · 风格问题（**建议不动**）

这几条都是"看着有点别扭"，但改了收益极小、diff 很大，而且会连带改文档：

| # | 现象 | 我的判断 |
|---|---|---|
| 1 | `AiUserContextInterceptor` 住在 `config/`，但它是 Web 组件 | 挪到 `context/web/` 更准。但只有这一个类，为一个类开包不划算 |
| 2 | `memory_store` / `summary_store` 用下划线 | Java 包名惯例不加下划线（`memorystore` / `store.memory`）。但你的两个包名**对称**，可读性其实还行 |
| 3 | `session/` 顶层同时有 `SessionKey`（契约）和 `SessionRedisKey`（Redis 实现细节） | 真正的分层问题，但只有一个实现类，拆 `session/key/` 收益不明显 |
| 4 | `user/` 顶层 9 个类，看不出分层 | 9 个不算多。等它到 15 个再拆 |
| 5 | `McpProperties` 在 `properties/`，`mcp` 其他类在 `mcp/` | **保留现状**。`properties` 包作为"所有配置属性的家"是自洽的，而找 MCP 配置的人多半先 grep `ai.mcp` |
| 6 | `session.memory_store` 里的类是 `SessionMemoryStore`，`summary_store` 里是 `SessionSummaryStore` | 命名不对称（一个 memory、一个 summary），但**语义准确**：一个是消息存储、一个是摘要存储。别为对称硬改 |

### 为什么建议不动

三件事叠加：

1. **包名是内部实现细节，不是对外契约。** 使用方（未来的 `assistant-yunchou`）只 import
   `SessionKey`、`ChatMemoryProvider`、`UserMemoryRecorder` 这几个类，不关心它们在哪个包
2. **只有一个使用者。** 我们之前定过：*先跑通、再抽象；在没验证的抽象上加码是风险*。
   包结构同理 —— 等第二个助手进来，你会知道哪一层真的需要拆
3. **改包名的连带成本被低估了** —— 见下面第五节，有三处**字符串引用**不会跟着自动改

## 五、如果真要改包名：三处字符串陷阱

IDE 的 Move Class 会改所有 Java `import`，但**改不了字符串**。下面这些必须手工核对：

| 位置 | 内容 | 为什么不会自动改 |
|---|---|---|
| `@MapperScan` | `@MapperScan("com.best.ai_memory.user.db")` | 注解值是**字符串** |
| Mapper XML | `namespace="com.best.ai_memory.user.db.UserMemoryMapper"` | XML 里的字符串 |
| Mapper XML | `typeHandler="com.best.ai_memory.user.db.FloatArrayTypeHandler"` | 同上 |
| Mapper XML | `type="com.best.ai_memory.user.UserMemory"` | 同上 |
| **资源目录** | `resources/mapper/com/best/ai_memory/user/db/` | **目录名镜像包名**，要跟着挪 |

最后一条最容易被忘 —— 你现在的 mapper XML 目录结构和包名是一一对应的：

```
src/main/resources/mapper/com/best/ai_memory/user/db/UserMemoryMapper.xml
                                  └────────── 与包名镜像 ──────────┘
```

MyBatis-Plus 默认扫 `classpath*:/mapper/**/*.xml`，所以**不改也能跑**（它不校验目录与包名对应）。
但这会留下"目录结构撒谎"的隐患：以后有人按目录找类，找不到。

> **验证方式**：改完跑一次真实查询，别只跑编译。
> `@MapperScan` 或 XML namespace 写错，**编译期完全看不出来**，只在第一次查库时炸。

## 六、建议动作（按性价比排序）

| 优先级 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **1** | **P0-1**：三个装配类收成一个 + 补 `after = DataSourceAutoConfiguration.class` | ~15 分钟 | 消灭"漏装配"这一整类 bug；`.imports` 永不增长 |

## 七、一个更根本的观察

两个模块的**包组织原则不一样**：

| 模块 | 原则 | 体现 |
|---|---|---|
| `ai-common` | 按**技术角色** | `properties` / `register` / `context` / `metrics` |
| `ai-memory` | 按**业务能力** | `session` / `user` |

**这不一定是问题**，因为两者的产出不同：ai-common 交付"一组可复用的技术能力"，
按角色分方便查；ai-memory 交付"两个业务能力"，按能力分最直观。

但 `ai-common/mcp/` 是个**例外** —— 它是唯一按功能分包的地方，而它的 `McpProperties`
又回到了 `properties/`。一个原则一旦有例外，就说明它在这里不够用了。

**如果你以后想彻底一点**，方向是把 `ai-common` 也改成按能力分：

```
com.best.ai_common
├── config/          ← 只放装配清单，1 个类
├── model/           ← properties + register 合并（它们本来就是一件事）
├── metrics/         ← token 台账
├── mcp/             ← 工具（含 McpProperties）
└── context/         ← 用户上下文（含 web 拦截器）
```

**但我不建议现在做。** `properties` 和 `register` 分开有一个实际好处 ——
"配置项定义"和"实例工厂"是两件事，混进一个 8 个类的 `model` 包之后，
你会分不清哪个类是拿来看配置的、哪个是拿来取模型的。等真觉得难找了再动。

---

## 一句话总结

> **结构本身没大毛病，但它掩盖了两个真 bug**：装配清单会随包增长（`mcp` 就是这么漏的），
> 以及同在 `register` 包里的两个类形状不对称（`Streaming` 那个少了 listener）。
> **先修这两个，别动 P2。**
