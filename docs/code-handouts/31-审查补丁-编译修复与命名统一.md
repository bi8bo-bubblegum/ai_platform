```java
import lombok.extern.slf4j.Slf4j;
```

## 2. `SupervisorAgent.Routing` —— 加 `edgeKey()`，让字符串只有一个来源（对应 #1 的根因）


## 3. `ToolExecuteNode.apply()` —— 完整替换（对应 #3、#4、#7）

**这是本补丁最重要的一段。** 现在这个方法的三个返回路径都绕过了 `finish()`，
等于 30 号第 2 节讲的那个静默漏洞**原样存在**。

```java
@Slf4j
public class ToolExecuteNode implements NodeAction<MultiAgentState>, InterruptibleAction<MultiAgentState> {

    private static final String NO_TOOL = "NONE";

    private final McpClientRegister register;
    private final McpToolCatalog toolCatalog;
    private final ToolRisk approvalMinRisk;

    public ToolExecuteNode(McpClientRegister register, McpToolCatalog toolCatalog, ToolRisk approvalMinRisk) {
        this.register = register;
        this.toolCatalog = toolCatalog;
        this.approvalMinRisk = approvalMinRisk;
    }

    @Override
    public Map<String, Object> apply(MultiAgentState state) {
        String tool = state.proposedTool();
        if (isNoTool(tool)) {
            return Map.of();
        }

        // ★★ 这一段【必须有】。没有它，用户点了"拒绝"之后工具照样会被执行 ——
        //     因为 interrupt() 看到 approvalDecided=true 就放行了，
        //     而 apply() 里没人看 approved()，直接往下走到 executeTool。
        //
        //     判据是两个条件的与：approvalDecided && !approved
        //     只看 !approved 会把【所有低危工具】误判成"被拒绝" ——
        //     它们从来没问过人，approved 也是默认的 false。
        if (state.approvalDecided() && !state.approved()) {
            log.info("工具 {} 被人工拒绝", tool);
            return finish(AiMessage.from("[操作被拒绝] 已取消：" + tool
                    + "。如果用户另有需要，可以改用别的方式帮他。"));
        }

        McpClient client = register.get(state.proposedBy());
        if (client == null) {
            log.error("找不到 MCP 客户端: clientKey={}，无法执行工具 {}", state.proposedBy(), tool);
            return finish(AiMessage.from("[工具 " + tool + " 未能执行] 未配置 "
                    + state.proposedBy() + " 的 MCP 通道"));
        }

        try {
            ToolExecutionRequest request = ToolExecutionRequest.builder()
                    .id(UUID.randomUUID().toString())
                    .name(tool)
                    .arguments(state.proposedArgs())
                    .build();

            ToolExecutionResult result = client.executeTool(request);
            boolean failed = result.isError();
            String text = result.resultText();
            log.info("工具执行{}: tool={} by={} result={}",
                    failed ? "返回错误" : "成功", tool, state.proposedBy(), abbreviate(text));

            return finish(AiMessage.from("[" + (failed ? "工具 " + tool + " 返回错误"
                    : "工具 " + tool + " 结果") + "]\n" + text));
        } catch (Exception e) {
            log.error("工具执行异常: tool={} by={} args={}",
                    tool, state.proposedBy(), state.proposedArgs(), e);
            return finish(AiMessage.from("[工具 " + tool + " 执行失败] " + e.getMessage()));
        }
    }

    // interrupt() 不用改，你写的四条分支是对的

    /**
     * 统一的收尾动作。
     *
     * <p><b>每次改动这个方法时问自己一句：所有从 apply() 出去的路径都经过它了吗？</b>
     * 只要有一条路径绕过去（直接 return Map.of(...)），
     * <b>{@code approvalDecided} 就不会被重置</b> ——
     * 于是同一次会话里的第二次危险操作会被直接放行。
     * 这个漏洞是静默的：日志上只有"执行成功"。
     */
    private Map<String, Object> finish(AiMessage message) {
        return Map.of(
                MultiAgentState.MESSAGES, message,
                MultiAgentState.PROPOSED_TOOL, "",
                MultiAgentState.APPROVAL_DECIDED, false
        );
    }

    private static boolean isNoTool(String tool) {
        return tool == null || tool.isBlank() || NO_TOOL.equals(tool);
    }

    /** 合并空白，避免工具返回的多行文本把日志撑成十几行 */
    private static String abbreviate(String s) {
        if (s == null) {
            return "";
        }
        // ★ replaceAll 不是 replace。replace 是【按字面量】替换，
        //   传 "\s+" 它会去找字符串里真的有没有 "\s+" 这四个字符 —— 永远找不到，
        //   等于这一行什么都没做，换行照样进日志
        String oneLine = s.replaceAll("\\s+", " ");
        return oneLine.length() <= 200 ? oneLine : oneLine.substring(0, 200) + "...(截断)";
    }
}
```

## 7. 命名统一（对应 #12）—— 这是你说"容易误导"的那处

**问题的本质**：同一个东西在两层各有一个名字。

| 层面 | 名字 | 谁在用 |
|---|---|---|
| state 字段（checkpoint 里） | `proposedTool` / `proposedArgs` / `proposedBy` | 节点之间 |
| HTTP 响应体 | `pendingAction` / `pendingArgs` | 前端 |

**统一方案：两层同名，都用 `proposedTool` / `proposedArgs`。**

理由是"名字只在需要区分时才应该不同" —— 这里没有任何需要区分的语义，
**两个名字只会让下次读代码的人多花一分钟确认"这是不是同一个字段"**。
而这一分钟正是你说"容易误导"的来源。

**连带要改的文档**（这些是历史文档，不影响代码，但会继续误导）：

**③ 跑 30 号第 4 节的四个用例**，重点是这两个：

```bash
# 低危：不停，直接执行
curl -s -X POST http://localhost:8081/agent/chat -H 'Content-Type: application/json' \
  -H 'X-User-Id: u1' -d '{"message":"查一下订单 12345 的状态","sessionId":"s1"}'
# 期待 {"status":"done",...}

# 高危 + 拒绝 → ★ 工具必须【没有】被执行
curl -s -X POST http://localhost:8081/agent/chat -H 'Content-Type: application/json' \
  -H 'X-User-Id: u1' -d '{"message":"查一下数据库里有多少条订单记录","sessionId":"s2"}'
# → waiting_approval
curl -s -X POST http://localhost:8081/agent/approve -H 'Content-Type: application/json' \
  -d '{"sessionId":"s2","approved":false}'
# 期待 {"status":"done"}，answer 里是"操作被拒绝"，且【日志里没有"工具执行成功"】

# 连续两次高危 → 第二次也必须停（验 #4）
curl -s -X POST http://localhost:8081/agent/chat -H 'Content-Type: application/json' \
  -H 'X-User-Id: u1' -d '{"message":"再统计一下库里表的总数","sessionId":"s2"}'
# ★ 期待仍然是 waiting_approval。如果是 done，说明 finish() 还没接上
```
