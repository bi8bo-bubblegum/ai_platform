AI 平台 · 按需取用架构

多种 AI 服务共用一套能力底座，各取所需 · v1.0 · 2026-10-10

三条设计锚点：

① 底座交付「可选 Bean」，不交付框架。 —— 服务自己写 AiServices.builder()，底座不代劳装配，也不长成框架。

② 每个能力都能单独取用、也能单独不取。 —— 一个只做结构化输出的服务，不该被迫理解什么叫会话窗口。

③ 计量与上下文自动生效，不需要显式取用。 —— 它们是横切的，挂在模型实例上，服务侧零代码即可获得。

1. 平台分层 2. 底座能力池 3. 各取所需：服务与能力的组合 4. 装配纪律：三个静默失效的开关

1. 平台分层

服务层只写业务；底座层提供能力；上游是既有的基础设施 —— 底座不做路由、不做限流、不做凭证托管，那些在 ai-gateway。

图 1 平台分层：底座只提供能力、不提供装配，服务层的取用组合完全自由

依赖方向是单向的：服务 → ai-memory → ai-common。 ai-memory 里的模型、计量、上下文全部来自 ai-common，它自己只实现"记忆"这一件事。

2. 底座能力池

每个 Bean 都是可选的 —— 没有引用它的服务，它就不存在，也不会拖任何依赖进来。

能力（Bean）来源作用
ChatModelai-common同步对话、结构化输出、文本生成、摘要与事实抽取
StreamingChatModelai-common流式对话（SSE 逐字输出）
EmbeddingModelai-common向量化。长期记忆的写入与检索都依赖它
ChatMemoryProviderai-memory会话记忆：窗口裁剪 + 滑出内容自动摘要
RetrievalAugmentorai-memory每轮自动检索用户长期事实并注入提示词
McpToolProviderai-common工具调用。当前已装配、尚无消费者，接工具时才用得上

AiCallContextai-common用户 / 租户 / 助手 / 会话 / 链路五个标识的载体

3. 各取所需：服务与能力的组合

"取用"不是全有或全无，而是一张可以自由勾选的清单。

三个形态的差别可以一句话说清：

  • 对话助手：全取。它是唯一同时需要"记住上一句"和"调用外部系统"的形态。
  • 单轮问答：取检索、不取会话记忆。每次都从长期记忆里捞事实，但不保留对话历史。适用于"一次问清"的场景。
  • 轻量 AI 服务：只取 ChatModel。做结构化输出（返回 POJO）或简单文本生成，不需要记忆、检索、工具、流式。
这张表是这张架构图最有价值的部分。它说明底座的能力划分是"可组合"的 —— 如果一个能力无法被单独取用（比如"要记忆就必须同时引入工具"），那说明底座切错了。

4. 装配纪律：三个静默失效的开关

服务侧的装配长这样。它只有五行，但其中三行漏了都不会报错：

@Bean
public ChatAssistant chatAssistant(ChatModelRegister chatModelRegister,
                                   StreamingChatModelRegister streamingRegister,
                                   ChatMemoryProvider chatMemoryProvider,
                                   ObjectProvider<RetrievalAugmentor> augmentorProvider) {
    var builder = AiServices.builder(ChatAssistant.class)
            .chatModel(chatModelRegister.getDefault())                    // ← 必需
            .streamingChatModel(streamingRegister.getDefault())           // ← 流式必需
            .chatMemoryProvider(chatMemoryProvider);                      // ← 漏了：不记得上一句
    augmentorProvider.ifAvailable(builder::retrievalAugmentor);           // ← 漏了：长期事实注入不进去
    return builder.build();
}
开关挂在哪漏了的症状有扩展点吗
.chatMemoryProvider(...)装配处不记得上一句有
.retrievalAugmentor(...)装配处长期事实永远注入不进去有
recorder.recordAsync(...)控制器手动调长期事实永远不增长没有
三者都不报错。也就是说 —— "助手不记得上一句"和"长期记忆一条都没写进去"，从日志上看都像正常。

这是选择"弱契约"的必然代价：底座不替你做装配，就不能替你保证装配正确。 所以那份接入清单和钉住这三个开关的结构测试，和代码同等重要 —— 它们是这个选择能成立的前提。

为什么"写"没有扩展点

LangChain4j 的挂载点全在调用链内部（ContentRetriever / ChatMemoryStore / ChatModelListener）， 而"这一轮值不值得长期记住"是业务判断 —— 框架不知道、也不该知道。所以它只能在响应结束后由服务自己触发。
