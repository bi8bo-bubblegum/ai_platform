多智能体骨架 · 设计文档

langgraph4j · 会话记忆 + 长期记忆 + 人在回路（异步两段式）· v1.0 · 2026-10-10

三条设计锚点：

① 骨架优先。 —— 智能体用占位实现，这一版验证的是结构与三个能力，不是智能程度。业务逻辑后填。

② 记忆分两层，各有归属。 —— 会话记忆交给 CheckpointSaver（官方机制）；长期记忆接我们自己的表（ai_user_memory）。

③ 人在回路用异步两段式。 —— 请求毫秒级返回，人批准后由第二个请求 resume 继续。不占用线程、不受 HTTP 超时限制。

1. 范围与已定决策 2. 图结构 3. 状态与记忆 4. 接口契约 5. 与底座的关系 6. 验收标准与待验证项

1. 范围与已定决策

这一版要做的是可运行的骨架，不是可用的产品。判断标准是"三个能力都真的跑通了"，而不是"回答得好不好"。

决策项结论理由
业务定位骨架，智能体占位先验证结构；业务逻辑进来之后会改变节点划分，现在做细是浪费
Checkpoint 存储RedisSaver已有 Redis；且会话记忆会与 ai.mem.* 分属两个 key 空间，互不干扰
人在回路异步两段式审批天然是"人可能不在电脑前"；同步等待受 HTTP 超时限制且重启即丢
新模块ai-multiagent与 assistant-demo 平级；不污染底座
不做什么（明确列出，防止范围蔓延）：
  • 不做真实业务逻辑（智能体的提示词可以是占位的）
  • 不做前端（用 curl 验证两段式）
  • 不做鉴权（沿用现有的 X-User-Id 约定，与 19 号文档的待办一致）
  • 不给底座加新能力（长期记忆复用现有 MemoryRecallService / UserMemoryRecorder）

2. 图结构

图 1 拓扑：记忆读写在头尾（绿），审批闸门是唯一的中断点（琥珀虚线），FINISH 分支让"无需操作"的请求可以直接收尾

节点职责

节点做什么实现方式
recallMemory用最后一条用户消息去检索该用户的长期事实，写进 state 的 memoryContext调 MemoryRecallService.recall(userId, query)
supervisor看 messages，决定下一个交给谁，写入 nextAiServices 接口，返回 Routing 枚举（EXPERT_A / EXPERT_B / FINISH）
expertA / expertB各自处理一类任务，把结果追加到 messagesAiServices 接口；其中一个带假工具，用来触发闸门
approvalGate需要人批准的操作在这里停下CompileConfig.interruptBefore("approvalGate")
writeMemory把这一轮的用户消息 + 最终回答交给长期记忆抽取调 UserMemoryRecorder.recordAsync(memoryId, messages)
一个刻意的设计：记忆节点只在头尾各一个，不放进每个专家。 因为 state 是全图共享的 —— 入口召回一次，所有专家都看得到；出口写一次，不需要每个专家各写一遍。 把记忆放进每个专家会带来两个问题：重复的 embedding 调用，以及"哪个专家写的"难以追溯。

3. 状态与记忆

State schema

public class MultiAgentState extends AgentState {

    public static final String MESSAGES        = "messages";
    public static final String NEXT            = "next";
    public static final String MEMORY_CONTEXT  = "memoryContext";
    public static final String PENDING_ACTION  = "pendingAction";

    public static final Map<String, Channel<?>> SCHEMA = Map.of(
        MESSAGES,       Channels.<ChatMessage>appender(ArrayList::new),  // 对话历史，追加
        NEXT,           Channels.base(() -> ""),    // 调度决定（条件边的 key），覆盖
        MEMORY_CONTEXT, Channels.base(() -> ""),    // 召回的事实，覆盖
        PENDING_ACTION, Channels.base(() -> "")     // 待批准的操作，覆盖
    );

    public MultiAgentState(Map<String, Object> initData) { super(initData); }
}
上面这段代码块在初稿里写错了两个类名，已按本机反编译结果修正： MessageChannel.Appender 和 Channel.LastValue 在 langgraph4j 里都不存在， 实际要用 Channels.appender(...) 和 Channels.base(...)。 其余同类偏差（以及 RedisSaver 的真实坐标）见 docs/code-handouts/24-多智能体骨架-实施交付单.md 第 0 节。
注意 next 通道存的是 String，不是枚举。 Routing 枚举只存在于 Agent 的输出契约和 SupervisorNode 的入参； 条件边的映射表 key 被框架固定为 String，state 又会被序列化进 Redis， 所以枚举在节点里转成 key 之后就结束，不进入 state。
Channel为什么是这种合并策略
messages → Appender历史只增不减。用 MessageChannel.Appender 而不是普通 Appender，因为它处理消息的 ID 更新/删除（编辑历史时不会产生重复）
其余三个 → LastValue这三条都是"当前值"语义：这次决定交给谁、当前召回的事实、当前待批准的动作。**如果是 Appender，它们会无限累积成一个没人看的列表**

三个能力各落在哪

能力落点和现有底座的关系
会话记忆整张图（不占节点）❌ 不共享。官方 saver 存 AgentState 快照，与 assistant-demo 的 ai.mem.session:* 是两套结构
长期记忆·读recallMemory 节点✅ 共享。同一个 ai_user_memory 表，按 userId 查
长期记忆·写writeMemory 节点✅ 共享。同一个 UserMemoryRecorder
人在回路approvalGate 之前新增能力，底座不涉及
一个要记住的边界：同一个用户在 assistant-demo 里说过的偏好， 这个多智能体应用读得到（长期记忆共享）；但两个应用里的对话历史互不可见（会话记忆各自一套）。

这不是缺陷，是设计使然 —— 会话记忆是 thread 级的即用即弃，长期记忆是用户级的资产。

4. 接口契约

图 2 时序：第一个请求在闸门处就结束（线程释放），第二个请求从检查点恢复 —— 中间可以隔任意长时间，进程重启也不影响

接口一：发起

POST /agent/chat
Content-Type: application/json
X-User-Id: u1                       # 沿用现有约定（19 号文档的鉴权待办不变）

{ "message": "帮我查一下上个月的指标然后删除测试数据", "sessionId": "s1" }

---- 情况 A：跑完了，不需要审批 ----
200 { "status": "done", "threadId": "t-8f3a...", "answer": "..." }

---- 情况 B：停在闸门 ----
200 { "status": "waiting_approval",
      "threadId": "t-8f3a...",
      "pendingAction": { "tool": "deleteTestData", "args": {...} } }

接口二：恢复

POST /agent/approve
{ "threadId": "t-8f3a...", "approved": true }

200 { "status": "done", "answer": "..." }
两个接口的 status 是同一个枚举（done / waiting_approval）， 因为恢复之后还可能再次停在闸门（图里多步操作、每步都要批）。客户端应该按同一个状态机处理， 而不是假设"approve 一定会返回 done"。

可选：待办列表

GET /agent/pending?userId=u1
→ [{ "threadId": "...", "pendingAction": {...}, "createdAt": "..." }]

用 BaseCheckpointSaver.list() 实现。这一版可以先不做，但接口设计上要留位置 —— 因为前端一旦用起来，第一件事就是问"我有没有待审批的"。

5. 与底座的关系

底座能力在本模块里怎么用
ChatModelRegister✅ 复用supervisor 和两个专家都用 getDefault()（或按档位取）
TokenUsageRecorder✅ 自动生效它挂在模型实例上，图里的节点调模型同样被计入账
AiCallContext⚠️ 要显式传节点可能跑在别的线程，入口要 try (var s = AiCallContext.open(...)) 包住，否则台账记成 anonymous
MemoryRecallService✅ 复用recallMemory 节点里直接调（纯 POJO 进出，无框架依赖）
UserMemoryRecorder✅ 复用writeMemory 节点里直接调
ChatMemoryProvider / RetrievalAugmentor❌ 不需要它们是 AiServices 的挂载点，图里没有这个位置

6. 验收标准与待验证项

验收标准（骨架算跑通的四条）

#验收什么怎么验
1会话记忆生效同一 sessionId 连续两轮，第二轮能引用第一轮的内容
2长期记忆跨会话生效第一轮告知偏好 → 换 sessionId（同 userId）→ 第三个问题能体现这个偏好。这是记忆真正跑通的唯一证据
3异步两段式生效第一个请求返回 waiting_approval；approve 后返回 done 且动作真的执行了
4重启后可恢复停在闸门后重启服务，再提交 approve —— 仍能继续。这条是 checkpoint 价值的唯一验证

待验证项 —— 已全部验证（结论见交付单 24 第 0 节）
