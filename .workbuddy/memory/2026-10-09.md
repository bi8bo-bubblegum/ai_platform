## AI-Memory 模块（本日设计结论，尚未动手）

**代码归属**：新建 `AI-Memory`，不塞进 AI-Common。
理由一，AI-Common 现在零基础设施依赖，记忆要落库，塞进去会污染所有引用方；
理由二，按「共性 vs 差异」那把尺子，记忆属于「执行编排」，而 AI-Common 只覆盖「依赖能力」里的模型一格。
依赖方向：`AI-Common ← AI-Memory ← assistant-*`

**数据归属**：用户级记忆必须**跨助手共享同一 schema** —— 否则用户画像碎成三份，"用户级"名存实亡。
代码分模块，数据共享；记忆表的 owner 只有 AI-Memory，助手只走接口不碰表。

**暂不做独立服务**：记忆在请求路径上是强依赖，远程化等于给每轮加一跳。
留 `UserMemoryStore` 接口 + 进程内实现作为切换点（复用 AI-Common 的 direct/remote 模式）。

内部两块，同一模块（共享同一份会话原文与写入时机）：
- 会话记忆（episodic）：实现 LangChain4j `ChatMemoryStore`，语义是「窗口 + 摘要覆盖」→ 挂到
  `MessageWindowChatMemory`，`AiServices` 零改动。存储用 Redis，TTL 24–48h
- 用户记忆（semantic）：抽取（LLM，走 `chat.fast`）+ 存储（MySQL 事实表）+ 检索
  （实现 `ContentRetriever`，经 `RetrievalAugmentor` 每轮自动注入）

分层裁剪：做 working（现成）/ episodic / semantic，**不做 procedural**。

**调研结论**：三流派 —— Mem0（旁挂，向量+图+KV；抽取后逐条做 ADD/UPDATE/DELETE/NOOP 判定）、
Zep/Graphiti（时序知识图谱）、Letta/MemGPT（OS 式三层，agent 自管内存）。
业界共识：难点不在「存」在「管」。Mem0 2026 版已转向 **ADD-only** 单遍抽取，把收益压在检索侧。
采纳：**抄 Mem0 骨架，砍掉阶段 2 的 LLM 判定** —— 一期只做去重（相似度 > 0.95 丢弃），不做 UPDATE/DELETE。
理由：误删一条用户事实比漏记一条严重得多，风险不对称。

待确认（默认按"接受降级"执行）：**一期不做 UPDATE/DELETE**。

## 用户 review 交付单 02 后修正的两处（重要，避免以后重犯）

**1. `ChatMemory` 接口的准确签名（我原来写错了，会编译不过）**

`dev.langchain4j.memory.ChatMemory` 必须实现的抽象方法只有四个：

```java
Object id();
void add(ChatMessage message);
List<ChatMessage> messages();
void clear();
```

批量加消息是 `default void add(Iterable<ChatMessage> messages)` —— **不是** `add(List<ChatMessage>)`。
写成 `add(List<ChatMessage>)` 再标 `@Override` 会编译失败
（"method does not override or implement a method from a supertype"）。

其余都是 default，按需覆盖：
- `add(Iterable)` —— 默认逐条调 `add(ChatMessage)`，我们**要覆盖**（否则一次加 4 条会触发 4 次摘要）
- `set(Iterable)` —— 默认是 `clear()` + `add(Iterable)`，会把摘要一起清掉，我们**要覆盖**
- `addAsync(List)` / `setAsync(List)` / `messagesAsync()` —— 默认返回失败的 future
  （`AsyncNotSupportedException`）。**返回类型改成 `Flux`（需 langchain4j-reactor）时就必须实现**

**2. 摘要模型的取法（用户指定）**

字段保持 `private final ChatModel chatModel;`，在构造器里解析：

```java
public LlmConversationSummarizer(ChatModelRegister chatModelRegister,
                                 SessionSummaryStore summaryStore) {
    this.chatModel = chatModelRegister.getDefault();
    this.summaryStore = summaryStore;
}
```

`getDefault()` = `ai.chat.profile` 那一档，**和主对话同一个模型**。
这是刻意的：摘要会被反复覆盖，质量损失累积，不值得为省钱降档。
因此 `AiMemoryProperties.Session.summarizeProfile` 已**移除**（死配置项）。
想改成按档位取的方法写在交付单 02 末尾（三处改动）。

## 用户追问：03 为什么不直接用 langchain4j 现成的 Redis 实现

**现成的确实有**：`dev.langchain4j:langchain4j-community-redis` 里的
`dev.langchain4j.community.store.memory.chat.redis.RedisChatMemoryStore`，
builder 支持 `host / port / password / ttl / prefix`，**key 前缀和 TTL 都是可配的**。
所以"不可配"这个理由不成立 —— 原文档漏了这一步对比，是个缺口，已补进 03 的 4.0 节。

**不用它的四条理由（按强度）**：

1. **key 脱敏做不到（最硬）**：`prefix` 是固定字符串，剩余部分仍是 memoryId 原样，
   最终 key 形如 `chat:memory:u123::s456`，明文 userId 照样进 Redis。
   而我们要 SHA-256 掉 userId —— 拼装在它内部，改不了。
2. **Redis 连接配置要写两遍**：它自己管一套连接池（host/port/password），
   和 Spring 的 `spring.data.redis.*` 重复，改地址容易漏。
3. **Jedis / Lettuce 并存**：它底层用 Jedis，而 `spring-boot-starter-data-redis`
   默认带 Lettuce，两套客户端同时存在。
4. **版本线不同步**：它的版本号是 `1.15.0-beta25` 这种形式，community 模块有
   独立的 beta 发布线，和 core 不是同一节奏；我们的 core 是 1.20.0。

**长远理由**：我们真正需要的是平台契约 `SessionMemoryStore`，将来要加
`listSessions(userId)` 和 `deleteByUserId(userId)`（合规要求），community 版给不了。

**判断依据（写进文档了）**：没有脱敏要求 + 不介意 Jedis 并存 + 版本对得上 → 直接用现成的。

## 用户追问：流式模型能不能统计 token

**结论分三层，已补进 04 的 0.2 节 + 07 的排障第 12 条**：

1. **类型上能**：`StreamingChatModel` 支持 `ChatModelListener`（和阻塞式同一个接口，无专用版本），
   `onCompleteResponse(ChatResponse)` 里的 `metadata()` 是完整的。
2. **数据上不一定**：**OpenAI 协议流式响应默认不返回 `usage`**，所有 chunk 的 usage 都是 null。
   需要请求带 `stream_options: {"include_usage": true}`，服务端才会在最后一个 chunk 补上。
   所以取决于 ① LangChain4j 1.20.0 有没有自动带这个参数 ② ai-gateway 透不透传。
   **必须实测，不能假定。**
   注意失败方式是**静默的**：`ChatTokenUsageListener` 里本来就判空了，所以症状是
   "统计里 token 全是空"，不是报错。
3. **就算能拿到，也未必该在 SDK 做（最重要的一条）**：
   **已有 ai-gateway，它才是 token 计量的天然位置** —— 所有模型调用的必经之路、
   能看到完整响应体、做一次覆盖所有调用方（含非 Java 的）。
   SDK listener 只覆盖用了 AI-Common 的 Java 助手，且受参数透传制约。

**建议的分工**（待用户与网关负责人确认）：

| 谁 | 统计什么 |
|---|---|
| ai-gateway | token 用量、模型耗时、成功率（**权威数据**） |
| AI-Common listener | assistantId / traceId / 业务侧耗时 / 失败原因（网关看不到的业务维度） |

让网关知道"是哪个助手"的办法：`OpenAiChatModel` / `OpenAiStreamingChatModel` 的
builder 都支持 `.customHeaders(...)`，带上 `X-Assistant-Id` / `X-Trace-Id`。

## 用户决定：token 计量就在 SDK 层（AI-Common）做

不再是"建议去网关"——用户明确要在这层做。方案已补进 04 的 0.2 节。

**两个必须处理的点**（不处理就是做不出对得了账的报表）：

1. **`ModelUsage` 加 `estimated` 布尔字段。** 报表里混着"准确值"和"估算值"是最坏情况 ——
   拿估算值去对账会发现对不上，且不知道该信哪些行。
2. **先花 10 分钟实测 usage 到底能不能拿到**（直连 / 经网关 / 带 `stream_options.include_usage`
   三个 case）。三种结果对应三条路，其中"直连有、经网关没有"最简单 —— 让网关加一行透传，
   比估算准得多。

**估算兜底**：`dev.langchain4j.model.openai.OpenAiTokenCountEstimator`（jtokkit，OpenAI 真实 BPE），
在已引入的 `langchain4j-open-ai` 里，不加新依赖。词表是借 OpenAI 的，
**中文偏差通常偏大**，只能用于相对比较和告警，不能用于计费。
API：`estimateTokenCountInMessages(Iterable<ChatMessage>)` / `estimateTokenCountInText(String)`。

**这一层独有的硬限制：拿不到 TTFT。**
`ChatModelListener` 只有 onRequest / onResponse / onError，**没有 token 级回调**；
流式下 onResponse 只在流结束时触发一次，所以这层只有"总耗时"，没有"首字延迟"。
TTFT 只能在业务侧 `TokenStream.onPartialResponse` 的第一次回调里自己记
（用 `AtomicLong.compareAndSet(0, now)`）。**这是流式监控最容易漏、也最该看的指标**。

## 用户 review 交付单 04：AiServices 装配该不该写在 AI-Memory（待用户拍板）

**发现一处硬伤（按现文档敲完起不来）**：04 里 `ChatAssistant` 接口只在 4.2 定义、4.3 的控制器注入，
但**全文没有任何地方把它声明成 Bean**，`MemoryAwareAssistantFactory.build()` 从未被调用。
启动即 `NoSuchBeanDefinitionException: ChatAssistant`。需补一个
`@Configuration AssistantConfig { @Bean ChatAssistant assistant(MemoryAwareAssistantFactory f) }`。

**归属分析结论**：
- `MemoryAwareAssistantFactory` 的入参跨两个模块（`ChatModel`/`StreamingChatModel` 来自 AI-Common，
  `ChatMemoryProvider` 来自 AI-Memory），本质是**接缝 / 粘合层**，住在被粘的某一方里会持续腐化。
- 证据：06 已经要给它加 `RetrievalAugmentor` 参数。往后 tools / contentModerator /
  hallucinationStrategy / chatRequestParameters 每加一样，都要改 **AI-Memory 的公共 API**。
  这个类最终会长成 `AiServices.Builder` 的镜像，而且永远慢上游半拍。
- LangChain4j 的设计意图很清楚：记忆的扩展点是 `ChatMemoryStore`/`ChatMemoryProvider`，
  检索是 `ContentRetriever`，观测是 `ChatModelListener`，**装配的扩展点就是 builder 本身**。
  所以 AI-Memory 的正确交付物是一组 **Bean**，不是装配器。
- 一个反直觉点：抽了 factory 之后，"忘记挂 chatMemoryProvider"从**静默失效**
  变成"忘记声明 Bean"→**启动直接失败**。从防静默错误的角度，factory 的收益反而变小了。

**三个候选落点**：① 留 AI-Memory（现状，改动最小，边界会腐化）
② 挪 AI-Common（`ChatMemoryProvider`/`RetrievalAugmentor` 都是 LangChain4j 类型，
挪过去不会产生对 AI-Memory 的依赖）③ 独立模块 AI-Assistant（边界最干净，但单助手时空转）

**倾向**：一期按 ②，或者干脆不做装配器、装配写在使用方 —— 因为目前只有一个使用者，
抽象抽早了，与用户一贯的"先跑通再抽象"不一致。

## 用户追问：流式输出用 TokenStream 还是 Flux（已补进 04 的 4.2 节）

**结论：保持 `TokenStream`。** 已写成 04 的「为什么是 `TokenStream`，不是 `Flux`」小节。

**核实到的事实（来自官方文档 docs.langchain4j.dev/tutorials/non-blocking/）**：

- LangChain4j 1.20 的流式有**四种返回类型**，只由方法签名决定：
  `String`/POJO（同步）、`TokenStream`（回调）、`CompletableFuture`（非阻塞单次）、`Flow.Publisher`（非阻塞事件流）
- **`TokenStream` 与同步 API 是稳定契约；异步/响应式是 `@Experimental`** —— 官方原话
- `Flux` = `Flow.Publisher` 的 Reactor 适配形态，加 `langchain4j-reactor` 即可（ServiceLoader 自动注册）
- **`Flow.Publisher` 是冷流：「每一次订阅都会开启一次新的交互」** —— 这是 Flux 方案最阴的一条，
  而 `TokenStream` 是显式 `.start()`，调一次就是一次请求
- 事件走**有界缓冲，默认 16384**，订阅者落后太多抛 `IllegalStateException`；
  `AiServices.builder(...).streamingBufferSize(int)` 可调

**本项目实测**：`reactor-core:3.7.19` **已在 classpath**（`spring-boot-starter-data-redis` → lettuce 带进来的），
工程里**没有 WebFlux**，是 Spring MVC + `SseEmitter`。所以切 Flux 的成本只有 `langchain4j-reactor` 一个 jar，
但**收益为零**（背压/算子/WebFlux 集成/多流合并，四个都用不上）。

**决定性理由（不是"Flux 差"）**：
① 稳定 vs 实验性；② 返回 `Flux` 会让 `SummarizingChatMemory` 必须补
`addAsync`/`setAsync`/`messagesAsync`（默认抛 `AsyncNotSupportedException`，漏了就是"能流式但记不住"且不报错）；
③ **`TokenStream` 是信息最全的句柄** —— 还有 `onPartialThinking` / `beforeToolExecution` /
`onToolExecuted` / `onRetrieved`。用户项目已引 `ai-common/mcp/McpClientRegister`，
接上工具后 `onToolExecuted` 是唯一能看到"调了哪个工具、参数是什么"的地方，`Flux<String>` 全丢；
④ 接口定成 `TokenStream` 后转 WebFlux 只改控制器，不定契约。

**该翻成 Flux 的两种情况**（都是全项目决定，不是流式这一个点能定的）：
整个应用切 WebFlux；或要做"多助手并发回答、结果 merge 成一个流"。

## 用户决定：05 的存储层改用 MyBatis-Plus（不手写 JDBC）

用户原话："05 记忆抽取使用本就有的 MyBatis plus 框架吧，不手写 jdbc"，
接着一句"考虑这么多不使用 record 使用 class 不就好了"—— 判断完全正确，直接照做。

**我实测出来的硬事实（不是搜索结论，是本机字节码 + 运行时验证）**：

1. **MyBatis 3.5.19 的 `Reflector` 里有 `isRecord` / `addRecordGetMethods`** → record 的**读**是官方支持的。
2. 但运行时实测（`SystemMetaObject.forObject`）：
   ```
   [record] getValue(id)  = 1        [record] hasSetter(id) = false
   [record] setValue(id)  = 抛 ReflectionException
   [class ] hasSetter(id) = true     [class ] setValue(id)  = 正常
   ```
   → record **不可写**。而 MP 的 `IdType.AUTO` 要在 insert 后回填主键、`updateById` 要求实体可变。
   **结论：实体必须 class + `@Data`。**
3. **MP 3.5.17 的 `SqlScriptUtils.safeParam(String, String)`** + `TableFieldInfo` 里的 `, typeHandler=`
   → `@TableField(typeHandler = ...)` 会被拼进生成的 SQL，**insert 和 select 两条路都覆盖**。
4. **`@TableName(autoResultMap = true)` 不能省** —— 不写的话 MP 自动生成的 resultMap
   不带 typeHandler，症状是「能存进去、读不出来」。这是 MP 最经典的坑，已写进 05。

**05 的改动**：删 `JdbcUserMemoryStore`，新增
`user/db/FloatArrayTypeHandler` + `user/db/UserMemoryMapper` + `UserMemoryMapper.xml` + `user/db/MybatisUserMemoryStore`。
`UserMemory` 从 record 改成 `@Data` class（带 `@TableId(IdType.AUTO)` / `@TableField(typeHandler=...)`）。
只有两个 Mapper 方法要自己写（都因为带 LIMIT）；其余用 `BaseMapper` 的 `selectCount` / `delete`。

**06 同步改动**：`UserMemoryConfig` 的 `JdbcTemplate` → `UserMemoryMapper`，
条件从 `@ConditionalOnClass(JdbcTemplate.class)` 换成三件套
`@ConditionalOnClass({BaseMapper, DataSource})` + `@ConditionalOnBean(DataSource.class)` + `@MapperScan`，
**并且外层类要改成 `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`** ——
不加这个，`@ConditionalOnBean` 会在 DataSource 注册前求值 → 永远 false → 整块静默不装载。
（这个套路和用户已有的 `TokenUsageDbAutoConfiguration` 完全一致。）

**两个前置条件（已写进 05 的 0.0 节）**：
① ai-memory 要显式声明 mybatis-plus（避免幽灵依赖）；② **assistant-demo 必须先配 `spring.datasource`**，

## 用户追问：长期记忆跨服务可读，会不会导致会话记忆混乱

**结论：长期记忆的共享不会污染会话记忆（两套完全不同的 key 空间 / 表）；但会话记忆本身
确实会串 —— 而且和长期记忆无关，是个独立的结构性缺陷。** 已全部改掉。

### 会串的机制（已修）

`memoryId` 原来是 `userId::sessionId`，Redis key 是
`ai.mem.session:<sha256(userId)>::<sessionId>` —— **`assistantId` 不在里面**。
`sessionId` 由调用方生成，**没有任何机制保证全局唯一**（文档里的示例就是 `?userId=u1&sessionId=s1`）。
两个助手收到相同 `(userId, sessionId)` → 同一个 Redis key → 共用一份对话历史。

症状：客服里说"我叫熊鑫"，运筹眼也答得出；且两边的对话交替滑出窗口，**摘要被交替污染**。

**修法**：`memoryId` 改成三段 **`assistantId::userId::sessionId`**，
`SessionKey` 的 parse 只找**前两个** `::`（第三段往后全归 sessionId），
前两段不允许含 `::`（在 record 紧凑构造器里就抛）。
调用点只有两处：控制器（`@Value("${ai.memory.assistant-id:${spring.application.name:unknown}}")`）
和测试；解析侧（`RedisSessionMemoryStore`、`MemoryRecallService`）走 `SessionKey.parse`，签名不变。

**原理层面的判据**（写进 02 了）：
| 记忆 | 作用域 |
|---|---|
| 会话记忆 | **助手 × 用户 × 会话** —— 助手级，不该跨 |
| 长期记忆 | **用户** —— 跨助手共享是刻意的 |

用会话记忆去实现"跨助手连续性"，等于让上下文无界增长 —— 而那正是长期记忆要解决的问题。

### 顺带挖出一个真 bug（用户代码里也有）

`RedisSessionSummaryStore` 的 key 是 `KEY_PREFIX + sessionId`，而传进来的其实是 **memoryId**
→ 实际 key = `ai.mem.summary:u123::s456`，**明文 userId 直接进 Redis**。
03 花了整页讲这个隐私风险，结果摘要这条路上毫无防护。

**根因是命名**：那个参数叫 `sessionId`，承载的却是 memoryId —— 看名字会以为它是
"我们自己生成的不透明 id"，于是放心拼进 key。**名字骗了实现者。**

修法两层：① key 构造收进新的 `SessionRedisKey`（两个前缀共用一套规则，
形状 `<prefix><assistantId>:<sha256(userId)>:<sessionId>`）；
② 那条链路上的参数名统一改成 `memoryId`（`SessionSummaryStore`、`ConversationSummarizer`、两个实现）。

### 长期记忆侧的对应处理

- `ai_user_memory` 加 **`source_assistant`** 列（05/07 的两份 DDL + 实体 + XML）——
  事实跨助手共享是刻意的，但必须能追溯"这条是谁写进来的"，也是将来按助手过滤的落点
- `UserMemory.of(assistantId, userId, content, sourceSession)`，多一个参数

- 抽取提示词加了一条判据：**"换个场景、换个助手，这句话还成立吗？不成立就别抽"**，
  并明确"事实是跨助手共享的，运筹眼也能看到客服里说的话"

### 三个坑（本次新发现，都是真实代码里的）

1. **`UserMemoryRecorder` 是条件 Bean** —— `ai.memory.user.enabled: false` 时不存在，
   而 `ChatStreamController` 直接构造器注入了它 → **整个服务启动失败**。
   修法：`ObjectProvider<UserMemoryRecorder>` + `getIfAvailable()`。
2. **`userId` 有两套来源** —— 会话/长期记忆用 query 参数 `?userId=`；
   token 台账的 `user_id` 用请求头 `X-User-Id`（`AiUserContextInterceptor`）。
   只传 query 参数时台账里全是 `anonymous`。新模块开工前必须定一条
   （推荐 Controller 里 `AiUserContext.set(userId)`）。
3. **`TaskExecutor` 是隐式依赖** —— `userMemoryRecorder` 需要它，但没有任何地方显式声明，
   来自 Boot 的 `TaskExecutionAutoConfiguration`。自定义 Executor Bean 时要留意。

### 另外两点

- **`SummarizingChatMemory.add()` 里摘要是同步生成的** → 第 21 轮（窗口刚满）会明显变慢，
  因为那次请求要等一次额外的模型调用。想异步得换 `ConversationSummarizer` 实现。
- **`assistant-demo` 没配 `spring-boot-maven-plugin`** → 打不出可执行 jar，只能从 IDE 跑。
  新模块清单里加上了。

### 用户总结核对（他总结得基本对，一处措辞要纠）

他的总结：① 多轮对话记忆只需装配 `chatMemoryProvider`；② 长期记忆的「注入」装配 augmentor；
③ 长期记忆抽取要在业务代码里「手动抽取」。

核对：
- ① 对，但要补一句：**光装配不够** —— Controller 里拼的 memoryId 必须是三段
  （`assistantId::userId::sessionId`），漏了 assistantId 隔离就失效。另外 `ai.memory.session.store`
  不配的话默认是进程内 memory，重启就丢。
- ② 对。AI-Memory 把 `ContentRetriever` 和 `RetrievalAugmentor` 都给了，业务侧只挂 augmentor。
- ③ 方向对，但**「手动抽取」这个词会误导** —— 准确说法是**「手动触发」**：
  抽取逻辑/去重/向量化/落库/容量清理全在 AI-Memory 里，业务侧只写那一行 `recordAsync`。

**由此提炼出一个更重要的观察（已写进交付单 10 的第 0.5 步）**：

**整个接入只有三个挂载点，三个都静默失效**：

| 开关 | 挂在哪 | 漏了的症状 |
|---|---|---|
| `.chatMemoryProvider(...)` | AssistantConfig | 不记得上一句 |
| `.retrievalAugmentor(...)` | AssistantConfig | 长期事实注入不进去 |
| `recorder.recordAsync(...)` | Controller（**无扩展点，必须手动**） | 长期事实永远不增长 |

**为什么写这一侧没有扩展点**：LangChain4j 的 hook 全在**调用链内部**
（`ContentRetriever` / `ChatMemoryStore` / `ChatModelListener`），而"这轮值不值得长期记住"
是**业务判断**，框架不知道也不该知道。所以只能由响应结束后业务侧触发。

三者都不报错 —— 这是设计特征。**"助手不记得上一句"和"长期记忆一条都没写进去"，
在日志上看都像正常。** 所以结构断言不是可选项。
第 3 个开关（写入）目前没有测试覆盖，加固办法：把 Controller 里那段抽成
`MemoryWriteback` 组件再单测。
