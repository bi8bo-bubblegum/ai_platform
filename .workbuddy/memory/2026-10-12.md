## langgraph4j 弃用 API 扫描（用户提醒"graph.invoke 好像已经弃用了"）

用户说得对，而且比"弃用"更严重：**`@Deprecated(forRemoval = true)` —— 计划移除**。

### 扫描结果（`javap -v` + 读 1.9.2 的 sources jar）

`CompiledGraph` 里共 **5 个**方法带 `forRemoval`：

| 已弃用 | 官方替代 |
|---|---|
| **`invoke(Map, RunnableConfig)`** ← 交付单初稿用的正是这个 | `invoke(GraphInput, RunnableConfig)` |
| `invoke(Map)` | 同上 |
| `stream(Map, RunnableConfig)` / `stream(Map)` | `stream(GraphInput, RunnableConfig)` |
| `streamSnapshots(Map, RunnableConfig)` | `streamSnapshots(GraphInput, RunnableConfig)` |

弃用理由（javadoc 原文）：*"use `invoke(GraphInput, RunnableConfig)` instead
**to have more control over the execution configuration**"*。

**修法就是包一层** —— 因为弃用版本的实现本身就是：

```java
return invokeFinal(inputs == null ? GraphInput.resume() : GraphInput.args(inputs), config)
        .map(NodeOutput::state);
```

所以 `invoke(input, config)` ≡ `invoke(GraphInput.args(input), config)`，
**是签名迁移，不是行为变更**。

### 🔎 顺手发现的隐藏语义（值得记住）

上面那行三元表达式说明：**传 `null` 会被解释成「恢复」而不是「新输入」**。
哪天真有人图省事传个 null，行为会从"开始新对话"静默变成"续跑上一次的 checkpoint"。
这是那个被弃用重载最阴的地方。

### 其余用到的 API 全部未弃用（逐个 `javap -v` 确认）

`StateGraph` 构造器 / `addNode` / `addEdge` / `addConditionalEdges` / `compile`、
`CompileConfig.Builder` 全部方法、`RunnableConfig.Builder`、`GraphInput.*`、
`AsyncNodeAction.node_async` / `AsyncEdgeAction.edge_async`、`NodeAction` / `EdgeAction`、
`Channels.appender` / `Channels.base`、`GraphDefinition.START` / `.END`、
`GraphInterruptException.of`、`StateSnapshot.nextNodeId` / `.state`、
`AgentState.value(String)`（**单参数版**）、`MemorySaver`、`BaseCheckpointSaver`、
`RedisSaver` + `RedisSaver.Builder`、`LC4jStateSerializer`。

> ⚠️ 注意 `AgentState` 的**双参数** `value(String, T)` / `value(String, Supplier<T>)` 已弃用，
> 单参数 `value(String)` → `Optional<T>` 未弃用。`MultiAgentState` 用的正是单参数版 ✓

另外已弃用但本篇没用到：`StateGraph.getStateFactory()` / `addSubgraph(...)`、
`RunnableConfig.graphPath()`、`RedisSaver.clearCheckpointsCache(String)`、
`AgentState.mergeWith(Map, Map)`。

**1.9.2 是唯一"三件套齐全"的版本**：core + langchain4j 集成 + redis-saver。
1.9.3 只有 core，没有配套的集成与 saver 模块 → 用 1.9.2。

## 复核 ai-multiagent **真实代码**（用户已落盘 11 个源文件）

用户问"语法是否过时" —— 顺手把整个模块查了一遍，**发现 3 个真问题**。

### ① 🔴 `approvalGate` 从未 `addNode` → 应用起不来

`MultiAgentGraphConfig` 声明了 5 个节点，但 `addEdge("expertA", GATE)`、
`addEdge("expertB", GATE)`、`addEdge(GATE, "supervisor")`、`interruptBefore(GATE)`
四处都在引用它。缺 `.addNode(GATE, node(new ApprovalGateNode()))`。

**它炸在启动时** —— `CompiledGraph` 构造器里有：

```java
// CHECK INTERRUPTIONS
for (String interruption : processedData.interruptsBefore() ) {
    if (!processedData.nodes().anyMatchById( interruption )) {
        throw StateGraph.Errors.interruptionNodeNotExist.exception(interruption);
    }
}
```

> 🔎 **反直觉发现（值得记）**：`Edge.validate()` **只校验边的起点、不校验终点**：
> `if (!Objects.equals(sourceId(), START) && !nodes.anyMatchById(sourceId())) throw ...`
> 所以 `addEdge("expertA", "不存在的节点")` 在 compile 时**不报错** ——
> 这次是 `interruptBefore` 那条路径替我们拦住的。
> **哪天去掉 `interruptBefore`，这类错误会一直潜伏到运行时。**

### ② 🔴 `SupervisorNode:35` 字符串转义写错（编译能过）

```java
AiMessage.from("（调度：\" + routing + \"）")   // 整段是【一个】字符串字面量，routing 没被求值
```

应为 `"（调度：" + routing + "）"`。`\"` 是合法转义 → 编译器不报错。
因为 `MESSAGES` 是 appender（只增不减）且会被 `render()` 进提示词 →
**持续污染后续所有轮次**。
⚠️ **坑点：日志里 `调度决定: {} -> {}` 那行是正常的（独立 log.info），只看日志发现不了。**

### ③ 🟠 `AgentController:40` 用了弃用的 `invoke(Map, config)`

编译器实测原文：`已过时, 且标记为待删除`。改成 `invoke(GraphInput.args(input), config)`。

### ④ ⚪ 缺 `/approve` 端点（`ApproveRequest` 定义了但没用）→ 两段式只实现一半

## 讲解图流程时又看出两条（已补进 25 号文档第 6 节）

### ① `expertB` 也会触发审批，而它的动作是 `noop`

`ExpertNode` **无条件**写 `pendingAction = plannedAction`，而 expertB 的构造参数是
`new ExpertNode("查询分析", "noop", expertAgent)` → **纯查询的请求也会停在审批闸门**。

根因不是写错，是能力缺失：`interruptBefore` 是编译期配置，表达不了"只有危险操作才停"
（交付单 24「三个已知代价」的第 3 条）。要修得用 `InterruptableAction`。

### ② `writeMemory` 的 sessionId 硬编码 `"graph"` —— 根因是 **state 里没有 sessionId channel**

```java
String memoryId = assistantId + "::" + userId + "::graph";   // 硬编码
```

格式正确（parse 没问题）、检索也不受影响（长期记忆按 userId），
但 `source_session` 永远是 "graph" → **丢掉"哪次会话抽的"这个溯源信息**。

**根因值得记**：`NodeAction` 的签名里**没有 `RunnableConfig`**，
所以节点既看不到 HTTP 请求、也读不到 `threadId()` ——
**凡是节点需要用到的请求上下文，都必须在 state 里显式开一个 channel**。
`userId` 当初就是这么进来的，`sessionId` 只是漏了一个。

修法：`MultiAgentState` 加 `SESSION_ID` channel + `Channels.base(() -> "")`，
Controller 初始 input 里 `input.put(SESSION_ID, req.sessionId())`，WriteMemoryNode 里 `state.sessionId()`。

## 追加：threadId 为什么不像 memoryId 那样三段式（用户提问）

查了 `RedisSaver` 源码 → 结论：**不该照抄，但确实有个隐患。**

### 🔎 核心发现：`RunnableConfig.threadId(x)` 里的 `x` 其实是「threadName」

```java
final var threadName = threadId(config);                       // 我们传的 "s1"
final var threadNameKey = keyNamingStrategy.threadNameKey(threadName);
final var threadId = redissonClient.<String>getBucket(threadNameKey).get();  // 内部 UUID
```

默认 key（`DefaultKeyNamingStrategy`）：
```
langgraph4j:thread:{threadId}
langgraph4j:thread:name:{threadName}:active      ← 我们的 "s1" 出现在这里
langgraph4j:checkpoint:{checkpointId}
langgraph4j:thread:{threadId}:checkpoints
```

→ **两个图用同样的 threadName 会命中同一个 key → 共用 checkpoint 空间**
（state 结构不同 → 反序列化失败或字段错乱）。这就是串号的真实机制。

### ✅ 隔离手段是现成的

`RedisSaver.Builder.keyNamingStrategy(...)` **存在**（不配则用 `DefaultKeyNamingStrategy`）。
`KeyNamingStrategy` 5 个方法可覆写：`threadKey` / `threadNameKey` / `checkpointKey` /
`checkpointsKey` / `keyPrefix`。

### 为什么不该照抄 memoryId 的格式

**langgraph4j 不该带 userId** —— `state` 里已经有 `USER_ID` channel 了。
硬编进 threadId 反而把"明文 userId 进 Redis key"这个问题**重新引进来**
（ai-memory 那边是被 `ChatMemory` 只有 memoryId 一个参数逼的，躲不开）。

### 三种做法
- A 照抄 `assistantId::userId::sessionId` → ❌ 引入明文 userId
- B `assistantId::sessionId` → ○ 可用，但把"部署隔离"混进了业务 id
- **C（推荐）配 `KeyNamingStrategy` 加服务前缀，`threadId` 保持 `sessionId`** ——
  隔离是**部署问题**，用前缀表达比塞进 id 更自然，业务 id 保持语义单纯

**什么时候必须处理**：出现第二个 langgraph4j 服务、且与这个共用同一个 Redis 时。
**现在只有一个图应用 + Redis 独占 → 不用改。**

### 附带的一致性观察（值得记）

`memoryId` 是**有语义的复合 key**（要 parse、要校验、要能反推用户）；
`threadId` 是**不透明标识**（只被拼进 key，从不解析）。
**两套 id 的格式要求本来就不同，不该无脑统一。**

## 追加：threadId / key 隔离的**提前准备**（用户决定"应该为此提前考虑"）

### 先做了一次辨析（这条判据已进 MEMORY.md 第三节）

项目纪律"只有一个使用者时不抽抽象"的**判据是「形状未知」**；
而 threadId/key 的格式属于**「不可逆契约」**（有存量数据后改动成本上升）。

> **判据一句话：抽象要等形状，契约要趁没数据。**

| | 判据 | 何时定 |
|---|---|---|
| 抽 `BaseAgentState` | 形状未知 | ❌ 等第二个图 |
| threadId / key 命名空间 | 不可逆（存量数据） | ✅ 现在 |

**关键窗口**：服务还没跑通（缺 `approvalGate`）、Redis 里零 checkpoint
→ **正好在最便宜的时点**。过了就要迁移。

### 两个动作（落在 `docs/code-handouts/26-threadId与checkpoint-key隔离准备.md`）

**A. `NamespacedKeyNamingStrategy`（新类）—— 立刻生效的隔离**
- 默认 key 无服务维度（`langgraph4j:thread:{threadId}`）→ 多服务共用 Redis 会串号
- 配 `.keyNamingStrategy(new NamespacedKeyNamingStrategy(assistantId))`
- **复用已有的 `assistantId` 参数**，不新增配置项
- 格式照抄 `DefaultKeyNamingStrategy`，只把 `langgraph4j:` 换成 `langgraph4j:<ns>:`（风险最低）
- ⚠️ `keyPrefix()` 必须和其余 4 个方法用同一前缀，否则 `cleanupAll()` 会静默漏清

**B. `GraphThreadIds.of(sessionId)`（新类）—— threadId 构造收口**
- 现在 Controller 里两处各拼一遍（`/chat`、`/approve`）→ 将来改格式必漏一处
  （**完全对应 `SessionRedisKey` 的教训**：两处各写一遍 → 一处漏了脱敏）
- `of()` 现在**只校验不加工**（加工一旦开始难回头），校验：非空、不含 `::`

### 明确不做（同样是"提前考虑"的一部分）
- 不抽 `BaseAgentState` —— 第二个图的 state 形状只能猜
- 不把命名空间**也**塞进 threadId —— 与 key 前缀是**替代关系**，两个都做等于双重维护
- 不加 `withGraph()` 备用方法 —— **不被调用的代码就是死代码**，真需要时改 `of()` 的实现即可

## 追加：**multiagent 工具接入**（用户两个新需求 + 一条关键背景）

需求：**1. 给 expert 装不同工具 2. 按工具危险等级判断是否过审**。

### 🔴 核心矛盾（本轮最重要的结论）

**这两个需求在 AiServices 下不可调和**：
- LangChain4j 的工具调用是「模型决定 → AiServices **当场同步执行**」，跑在 `ExpertNode.apply()` **内部**
- 审批是**跨 HTTP 请求的异步暂停**（`waiting_approval` → 批准 → 第二个请求 resume）
- **同步钩子表达不了跨请求的暂停** → 工具挂进 AiServices 就"来不及审批"

**javap 核实过的 LangChain4j 挂载点（全部不够用）**：
| 挂载点 | 为什么不行 |
|---|---|
| `beforeToolExecution(Consumer<BeforeToolExecution>)` | `BeforeToolExecution` 只有 `request()` / `invocationContext()` —— **只能观察，不能否决** |
| `afterToolExecution` | 事后 |
| `tools(Map<ToolSpecification, ToolExecutor>)` | 自定义 executor 能接管执行，但只能"同步执行 or 抛异常失败"，**不能暂停** |
| `observability.api.event` 全部事件 | 只有 `ToolExecutedEvent` / `ToolCompensatedEvent` —— **没有"将执行"事件** |
| Guardrail | 输入/输出**文本**级，不是工具级 |

→ **结论：工具不能挂给 AiServices，必须由图节点执行**；"要不要停"交给 `InterruptibleAction`。

### ⭐ 中断时序（字节码核实，决定审批是否有效）

`NodeHooks.applyActionWithHooksHandlingInterruption`：**`interrupt()` 先调、`apply()` 后调**。
→ 返回 `Optional.of(...)` 时**节点根本不执行** → **"停下那一刻工具真的没被执行"**，
这才是审批唯一有意义的形态。

### 🆕 MCP 网关侧事实（连库 + 读 GitHub 源码得到）

**仓库**：`github.com/bi8bo-bubblegum/mcp-gateway`（Python + SQLAlchemy + fastmcp）。
有一个 commit 叫「**工具风险等级透传给下游**」，但它**改成了"不靠协议透传"**：
> 精确等级（low/medium/high）不走协议透传，**由下游按工具名查 tools 表** ——
> 那里是 risk 的源头，也拿得到管理员改动后的最新值，不受 `tools/list` 快照时效限制。
> `annotations` 只给 high 写 `destructiveHint`，给通用客户端一个粗粒度信号。

**`mcp_gateway` 库 `tools` 表**（实测）：
`id / service_id / upstream_name / effective_name(UNI) / description / input_schema /
schema_hash / risk(varchar8, NOT NULL) / enabled / available / discovered_at / updated_at`

**实际 4 个工具**：`order__searchMultipartBizOrder`(low)、`outline__list_documents`(low)、
`outline__fetch`(low)、`mysql__mysql_query`(**high**)。
命名 = `<service_slug>__<upstream_name>`。

## 追加：用户质疑"**为什么不在每个 expert 处 ReAct**"（很好的架构问题）

用户的观察准确：现在的设计是**把 ReAct 摊在图上** —— supervisor 兼了"循环还要不要继续"的判断。

### 🔴 硬约束：expert 节点内 for 循环 与 审批 **互斥**

- `interrupt()` 是**节点级**的，只在节点执行**前**调一次
- 节点内循环 N 次工具调用 → 框架只问了 1 次 → **审批最多拦住第一次，第 2~N 次直接执行**
- ⭐ **langgraph4j 1.9.2 没有"节点内主动暂停"机制**。全 jar 里跟中断有关的只有
  `InterruptibleAction` / `InterruptionMetadata` / `GraphInterruptException` 三个类 ——
  **没有 Python 版 langgraph 那个可在节点内调用的 `interrupt()` 函数**。
  `GraphInterruptException` 的构造器虽是 public，但 `NodeAction` 签名里连 `RunnableConfig`
  都没有，手抛异常无任何文档保证 → **不可用**

→ **结论：「在 expert 处 ReAct」不能用 Java 循环写，必须写成子图。**

### ⭐ 用户指出的真代价（成立，我之前没讲）

当前设计**每调一次工具就要回 supervisor 一次**（多一轮模型调用）：
N 次工具调用 = N 次 expert 调用 + **N+1 次 supervisor 调用**；
ReAct 内循环只需 1 次 expert 调用 + N 轮工具。**模型调用次数差近一倍。**

### 正解：**子图**（循环体是节点，不是 Java 代码）

```
父图:  supervisor → expertOrder(子图) → supervisor
子图:  proposeTool → toolExecute →(还需工具?)→ proposeTool
                          ↓ 工具够了
                        END
```
- 循环是**图内**的 → 每一步都是 checkpoint 节点
- 审批点在子图的 `toolExecute` → `InterruptibleAction` 依然生效
- supervisor **不再为每次工具调用介入** → 省掉 N 次模型调用
- ⭐ **附带好处（重要）：supervisor 职责变纯** —— 从"ReAct 循环控制 + 跨专家路由"
  变成**纯跨专家路由**，这才符合多智能体的语义（调度器不该管单个专家的内部循环）

**已核实**：`addNode(String, CompiledGraph)` 重载存在 ✓；jar 里另有 `SubCompiledGraphNodeAction`。

### ⏳ 子图方案待验证（第 3 步再动）

1. `addNode(String, CompiledGraph<State>)` 是否要求子图 state 与父图**类型一致**
2. 子图的 checkpoint 由父图 saver 统一处理，还是要给子图单独 compile 带 saver
3. `SubCompiledGraphNodeAction` 是公开 API 还是内部类
4. 调试难度上升一层（日志/断点嵌套）

### 建议顺序（已告知用户）

第 1 步（工具能否调通）→ 第 2 步（按 risk 中断）→ **子图作为第 3 步**。
理由：现在连"工具能否调通"都还没验证，上子图会同时引入
"嵌套 state / checkpoint / 调试"三个新变量。

### ⭐ 一条可复用的判据（值得进 MEMORY.md）

> **"框架看不看得见"决定了一个循环能不能被中途干预。**
> 循环写在节点**内**（Java 代码里）→ 框架只看到"这个节点跑完了"；
> 循环写在图**上**（节点 + 边）→ 框架能看到每一步。
> **凡需要"中途干预"（审批 / 人工介入 / 断点续跑）的逻辑，
> 循环体必须拆成节点，不能是 Java 循环。**

## 追加：第 2 步交付单（30 号）+ 写单时发现一个安全漏洞

### 用户决定

### ★★ 写单时发现：`approvalDecided` 必须被**重置**

语义必须是「**当前这个提议**已经被人回答过」，**不是**「这个人曾经回答过」。

不重置的后果（**静默漏洞**）：
```
第一轮  "删测试数据" → high → 停下 → 批准 → 执行（approvalDecided 仍为 true）
第二轮  "再删生产备份" → high → interrupt() 看到 true → 【直接放行】
```
→ **危险操作绕过审批被执行**，而且日志上只有"执行成功"，
要对比"这次有没有停下来问"才能发现。

**重置点两处，缺一不可**：
1. `ToolExecuteNode.finish()` —— 保证**同一轮内**第二次提议仍被拦
2. `/chat` 初始化 —— 防御性（防止将来有路径没走到 finish 时脏标记跨请求残留）

### 另一个细节：判"被拒绝"必须用 `approvalDecided && !approved`

只看 `!approved` 会把**所有低危工具**误判成"被拒绝" ——
因为它们从没问过人，`approved` 也是默认的 false。

### 29 号的修正：`McpToolCatalog` 直接注入，不用 `ObjectProvider`

初版推理"没数据库的服务也要能启动"**是错的** ——

DataSource 已指向 `mcp_gateway` 库），**"没数据库的 ai-multiagent"这个场景不存在**。
为一个不存在的场景加降级分支，代价是每个节点里到处 null 判断。**29 号文档已改。**

### 新增件：`ai-multiagent/graph/GraphNodes`

节点名（`recallMemory` / `supervisor` / `toolExecute` / `writeMemory`）原来在
`MultiAgentGraphConfig` 和 `AgentController` **各写一遍**（`"approvalGate"`）。

### 🔎 新发现 1：`Channels.appender` 是【就地追加】，不是快照

字节码核实 `AppenderChannel$ReducerDisallowDuplicate.apply(old, new)`：
```
if (old == null) return new;              // 不拷贝
for (x : new) old.add(x);                 // ★ oldList 被原地修改
return old;
```
→ **`MESSAGES` 的值始终是同一个 `ArrayList` 实例**（跨多个 state 对象共享）。
→ **节点里 `state.messages()` 拿到的是"活引用"**。

**当前不是 bug**（`writeMemory` 是最后一个节点，执行完图就结束；下一请求从 checkpoint 反序列化出新 list），
**但很脆弱**：在 `writeMemory` 后面加节点、或把它挪到中间 → 异步线程与主线程同时操作同一个 list
→ `ConcurrentModificationException`，且**只打在异步线程的日志里**。

**建议（一行改动，待用户决定）**：
```java
recorder.recordAsync(memoryId, List.copyOf(state.messages()));
```

### 🔎 新发现 2：`applicationTaskExecutor` 实际并发上限 = 8

Spring Boot `TaskExecutionAutoConfiguration` 默认：
`corePoolSize=8` / `queueCapacity=Integer.MAX_VALUE` / `maxPoolSize=Integer.MAX_VALUE`。
⭐ **队列无限大 → 永不触发扩容 → 真实并发就是 8**。

而抽取任务（几秒一次 LLM 调用）用的正是这个池，且**全应用共用**
→ 高并发时抽取排队（**不阻塞图，只让记忆延迟变大**）。
**排查"记忆延迟很久"时第一个该看这里。**

### 另一个观察（写在这里备查）

`writeMemory` 是全图**唯一不改变 state** 的节点（返回 `Map.of()`），唯一作用是"触发一次异步抽取"。
**它其实也可以放在 Controller 里**（`invoke` 返回后调用），省一次图节点开销。
保留在图里的**唯一理由**是"将来要按图的状态决定记不记"（只记成功的 / 某些专家产生的 /
根据 `approvalDecided` 判断这轮有没有被拒过）—— 这个理由**目前还没用上**。

## 追加：35 号 —— 新增一个图应用怎么做（用户提问）

### 三种做法，只有一种现在可行

| 做法 | 可行 |
|---|---|
| A. 同一个服务里加第二个图 | ❌ **不可行**（硬障碍，见下） |

### 🔴 「同服务多图」为什么不可行（新核实的硬障碍）

看起来可以泛型化 `SupervisorAgent`：`interface SupervisorAgent<R extends Enum<R>> { R route(...); }`

**但这会让 LangChain4j 失效**：`AiServices.builder()` 传的是 `SupervisorAgent.class` →
**泛型擦除后 `route()` 返回裸 `Enum`** → `DefaultOutputParserFactory` 虽会因 `isEnum()`
走 `EnumOutputParser`，**但拿不到"有哪几个值"** → 提示词里
`You must answer strictly with one of these enums:` 生成不出来。

→ **每个图必须有自己的 `SupervisorAgent` 接口**（这不是缺陷：让两个图共用同一个
"调度器契约"本来就没意义，路由语义完全不同）。

另两条：`createGraph` 硬编码 `MultiAgentState`；Controller 单例注入 `CompiledGraph`。

→ **现在一个服务 = 一张图。加图 = 加服务。**

### 35 号的核心价值：「不用改的清单」

`ExpertRouting` / `MultiAgentGraphFactory` / `GraphNodes` / `SupervisorNode` / `ExpertNode` /
`ToolExecuteNode` / `RecallMemoryNode` / `WriteMemoryNode` / `GraphThreadIds` /
`NamespacedKeyNamingStrategy` / **`ai-common` / `ai-memory` 一行都不用动**。

→ **新图的代码工作只剩三件事：写枚举、写提示词、填 yml。**

### ⚠️ 新图必须唯一的四项配置

`server.port` / `spring.application.name` / **`ai.multiagent.assistant-id`** /
`ai.mcp.servers.*`。

★ `assistant-id` 是**双重标识**：checkpoint 的 key 命名空间 + 长期记忆表的 `source_assistant`。
**重复 = 串号**（两件事都会坏）。

### 13 条陷阱清单（按症状组织，这是最实用的部分）

- **编译期能抓**：`InterruptibleAction` 带 i / 必须 `node_async()` 包一层 / 穷尽 switch 报错
- **★ 静默失效的 8 条**：`approvalDecided` 没重置、缺拒绝分支、`proposedTool` 被清空、
  memoryId 少 `::`、`"FINISH"` 大小写、节点名两处定义、`messages()` 活引用、`replace` vs `replaceAll`

**那时的判断方法**（只有那时才能做）：
> **不是看"哪些类长得一样"，而是看"哪些改动必须两边同时改"。**

- 必须同时改 → 真共享 → 值得抽
- 长得像但可各自演化 → 假共享 → 留在各自模块

值得抽；`SupervisorNode` / `ExpertNode` 认识具体 state，收益不确定。
**枚举、提示词、state 字段一定不抽**（它们是业务）。

**另一件更确定的事**：`RecallMemoryNode` / `WriteMemoryNode` 里的
（召回文本模板、memoryId 构造、失败兜底）该收进 **`ai-memory`** 的 `UserMemoryFacade` ——

## 追加：用户提议「把 expert 写成接口，实现 prompt / tools / role」—— 逐个裁定

**用户原话**："感觉抽得不够好，可不可以把expert写成一个接口，实现prompt、tools、role等等方法，
然后去图里使用可不可以"

### 裁定：一该做 / 一不该做 / 一形式要调整

**① `prompt` —— 该做，但建议做成 `rules()`（工作准则）而不是完整提示词。**

现状况：`ExpertAgent` 的 `@SystemMessage` 是**全平台一份骨架**，用 `{{role}}` 参数化 ——
**所有专家只能变一个角色名**，表达不了真正的差异（"订单助手不要展示完整手机号" /
"数据分析助手只读不写" 这类准则没地方放）。

⭐ **方案：加一个 `{{rules}}` 占位符，每个 expert 提供自己的准则**：
```java
@SystemMessage("""
        你是{{role}}专家。
        ## 你的工作准则
        {{rules}}          ← 新增
        ## 你可以调用的工具
        {{tools}}
        ...
        """)
ExpertProposal propose(@V("role") String role, @V("rules") String rules, ...);
```

**为什么不做成"完整提示词"**：
- 提示词**骨架该统一**（保证输出格式一致、工具/记忆的注入点固定）
- 完整提示词会**失去 `{{}}` 占位符机制** —— 那个机制是 `@SystemMessage` 注解提供的；
  改用 `AiServices.systemMessage(runtimeString)` 就没有占位符了 ✗
  而动态部分（tools / memory）**必须**走方法参数注入（每个请求都不同，不能进编译期固定的 systemMessage）

**② `tools` —— 不该做。**

**工具清单的唯一来源是 MCP `tools/list`（按 token 过滤）**。
静态声明 = **第二份真相** → 必然和网关的授权漂移（网关加了工具你得改代码）。

而"这个专家能用什么工具"**已经由 `clientKey`（= MCP server key = token）表达了** ✓
不需要再声明一遍。

**③ 形式：不建议从枚举改成"接口 + 实现类集合"，建议【枚举持有 Expert 实例】。**

**硬约束**：`SupervisorAgent.route()` **必须返回枚举** ——
这是 LangChain4j `EnumOutputParser` 自动生成提示词的唯一途径
（`You must answer strictly with one of these enums:` + `@Description`）。

而路由枚举的值**必须和 expert 一一对应**。所以如果 expert 改成"实现类集合"，
就变成**两处声明**（枚举 + 类）→ 又回到"漏改一处就静默失效"。

⭐ **推荐形态**：
```java
enum Routing implements ExpertRouting {
    ORDER("订单助手", new OrderExpert()),
    FINISH(null, null);
    // ExpertRouting 加一个 expert() 方法，返回 null 表示"非专家"
}
```
**枚举仍是唯一事实来源，而准则住在独立的类里。**

**顺带一条参数设计提醒**：`ExpertNode` 现在接收 `role` + `clientKey`（都是从枚举拆出来的字段）。
再加 `rules` 就是**第三个**从同一个对象拆出来的参数 →
⭐ **当发现自己在拆同一个对象的多个字段时，就该直接传那个对象**（改传 `ExpertRouting`）。

**状态**：以上为讨论结论，**待用户确认后再落地**（按项目纪律：先对齐再出单）。

如果专家漏写 `{{tools}}`，后果是**静默**的：

## 23:00 用户提出"把整套 ReAct 图抽成 `ai-graph`，其他模块直接依赖"（第三轮 ai-graph 讨论）

**结论：可以抽，我这次签字**（与前两轮立场相反），但有一个前提、三个代价、一个顺序要求。

### 前提：`SupervisorNode` 必须解绑 —— 有两处绑定，不只是类型

```java
private final SupervisorAgent supervisorAgent;   // ① 类型绑业务接口
} catch (Exception e){ routing = Routing.FINISH; } // ② 兜底直接引用业务枚举常量
```

② 更隐蔽：把"调度失败就收尾"这个**业务判断**写进了框架节点。

**解法（零反射）**：ai-graph 定义函数式接口
```java
@FunctionalInterface public interface RouteDecider {
    ExpertRouting decide(List<ChatMessage> messages);
}
```
`SupervisorNode(RouteDecider decider, String fallbackEdgeKey)`；业务侧
`new SupervisorNode(msgs -> supervisorAgent.route(ChatMessageTexts.render(msgs)), Routing.FINISH.edgeKey())`。
`Routing implements ExpertRouting` → lambda 返回子类型，兼容。

**连带**：`createAgent` 从 2 参数变 3 个（枚举 + RouteDecider + fallback）。这是把
`SupervisorAgent` 剔出框架后必须显式传回来的两个业务依赖点。

### 三个代价（要认）
1. **`ai-graph` → `ai-memory`**：记忆节点必带 → 使用者被迫拖上 MySQL/向量库。
   对"要建这种 ReAct 图的应用"是**必然成本**（图里总有记忆节点）→ 代价匹配 ✓。
   ⚠️ **28 号那条"ai-graph 不依赖 ai-memory"要作废** —— 定位从"纯 langgraph4j 适配件"
   变成了"平台级多智能体编排层"。
2. **`MultiAgentState` 10 字段固定** → 业务图加不了自己的字段。
3. **改框架件要动公共模块** → 迭代速度降一档。

### 顺序要求（重要）
**先落地 38 号（在 `ai-multiagent` 内），跑通，再搬。**
理由：搬移是纯 move，何时做都行；但必须先有一个**能跑的基线**，否则搬完出问题分不清
"搬错了"还是"本来就没跑通"（一次只动一个变量）。
而且 38 号落地后抽的成本更低（工厂已收成 2 参数）。

### 附加收益（常被忽略）
抽完之后 **`ai-multiagent` 变成纯业务模块** —— 每个文件都是"这个助手特有的"。
物理边界本身就有价值。
