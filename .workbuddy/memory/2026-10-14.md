### ★ 最硬的四条结论（写进 MEMORY.md 备查）

1. **成本**：Anthropic 原文 —— agent ≈ **4× chat** token，multi-agent ≈ **15× chat** token
   → **多智能体 ≈ 单 agent 的 3.75 倍**（倍数是我算的，原文只有那两个数）
2. **适合**：并行度高 + 信息超单窗口 + 多复杂工具。原文点名**不适合**"需要所有 agent 共享同一上下文"
   和"agent 间依赖多"的场景（举例：**多数编码任务**）
3. **★ 分歧的真正核心 = "子 agent 之间能不能看见彼此"**：
   - Cognition 两原则：① 共享**完整 agent trace**（不只是消息）② **动作携带隐含决策**，冲突的决策产生坏结果
   - 两条判据合起来才是可用的：**子任务需不需要"看见对方做了什么"才能做对？**
     不需要 → 并行成立（Anthropic）；需要 → 并行就是那个 Flappy Bird（画风不一致）
4. **★ 调和方式**：不是"要不要多智能体"，而是 **Anthropic 那套成立是因为子任务天然独立**，
   Cognition 那套反例失败是因为子任务**必须一致**。**判据在"一致性要求"上，不在"agent 数量"上。**

### ★ 诊断：`ai-graph` 的问题在**选型**，不在实现

**结论：这是一台造得很好的机器，装在了一个不需要它的工序上。**

### ★ 连带影响（必须一起处理）

**「正式模块」+「可中断可暂停可恢复」⇒ 暂停状态必须持久化。**
内存实现（`RunStateStore.InMemory`）**只够单机测试**：单实例、重启即丢、多实例不共享。
正式模块 ⇒ **必须提供 Redis 实现**（`spring-boot-starter-data-redis` 声明为 optional +
`@ConditionalOnClass/@ConditionalOnBean` 条件装配，照抄 `ai-memory` 的范式）。

**「图引擎待定」不阻塞开工 —— 这一点要写清楚：**
- "可中断 / 可暂停 / 可恢复" **不需要图引擎**：一个可序列化的 `RunState` + sealed `RunOutcome` 就够
- 图引擎真正提供的是「**任意拓扑 + 编译期图校验 + 可视化调试**」，不是"暂停"本身
- ⭐ **而且 `RunState` 恰好是将来上图的前提**（图引擎也需要一个可序列化 state）
  → **所以"待定"的正确处理是：把 `RunState` 的序列化契约做严**
  （无参构造 + setter + **不引用任何框架类型**），将来要换实现，state 能直接复用
- **触发条件**：需要"任意拓扑的中断 + 编译期图校验 + 可视化"时，再评估上图

### ★ 正式模块带来的另一个真问题：名字

`ai-new-multiagent` **是个临时代号** —— 几个月后没人知道 "new" 相对于什么。

其余 8 项它一项都不管；② 控制流是**一条主循环**，图的表达力用不上；
③ 框架本身有坑且**本项目已踩过一轮**（`InterruptibleAction` 拼写 / `node_async` 才做代理 /
子图中断不传播 / `invoke(Map)` 弃用，见 25/31/32 号）；④ 41 号诊断"为 routing 付了图引擎成本"。

**★ 三条之前漏算的成本（诚实补齐）**：

| # | 成本 | 处置 |
|---|---|---|
| **A** | ★ **"自己实现"正是本项目最擅长踩的坑**。静默失效清单已很长（少 `::` / checkpoint 命名空间 / `approvalDecided` 未重置 / listener 未挂）。自研 `RunStateStore` **新增一类静默失效面："暂停了但恢复不了"**，且只在用户点批准那一刻才暴露 | **用设计消解**：把 `RunStateStore` 的调用**收在 `Orchestrator` 内部**（run 自存 / resume 自取），调用方**拿不到"忘了存"的机会** → 从"人的纪律"变成"代码结构"（同 33 号 `SessionKey` 的手法） |
| **B** | ★ **`ai-graph` 会变孤儿**（已有一份基于 langgraph4j 的实现，编译通过、业务零残留）。新模块也不用图引擎 → 它没有使用者了 | **该在别处解决**：`ai-graph` 去留是独立决定。**为了救一个模块而选技术栈，是把两件事绑在一起** → 建议**删掉** `ai-graph` |
| **C** | **「框架替你存」vs「你得记得存」**：langgraph4j 的 checkpoint 是**自动的**（每 super-step 落盘），我的设计把持久化显式推给调用方 | 同 A 的处置 |

**结论：仍然建议不用。** "用的成本"（框架抽象层 / 调试绕一层 / 版本升级 / 图的表达限制）是**持续的**，

## 10:09 ★ 用户追问「这里怎么保证多轮对话」→ 暴露一个必须补的漏洞

**当前设计只有「长期记忆」（`RunContext.memoryText` = 用户是谁），没有「会话记忆」（这次对话刚才聊了什么）。**

具体后果：
```
第 1 轮  "查一下订单 12345 的状态"  → ✅ 正常
第 2 轮  "那它什么时候发货？"       → ❌ Planner/Worker 拿到的 request 就是这 7 个字，
                                      不知道"它"是什么 → 要么猜，要么反问
```
**这不是优化，是多轮对话的基本要求。**

### 修法：三层上下文分离

```
┌─ 会话历史（完整对话）──────────┐
│  只给 Planner + Synthesizer 看 │ ← ai-memory 的 ChatMemoryProvider
└────────────────────────────────┘
            ↓ 指代消解，写进 goal
┌─ 子任务私有上下文 ─────────────┐
│  只看 scope + 自己的 WorkerTurn│
│  执行者看不到对话历史（隔离）    │
└────────────────────────────────┘
```

**★ 关键设计：指代消解的责任放在【规划器】，不放执行者。**
规划器看到完整对话 → 把"那它什么时候发货"翻译成"查订单 12345 的预计发货时间"；
执行者只看到后者。**这就是"显式 scope"的真正价值** —— 把"理解对话"和"执行任务"分开，
也正是 Cognition 那条原则的落点：**共享的是浓缩后的决策（plan），不是原始轨迹**。

### 四处改动
1. `RunContext` 加 `conversationText`（渲染后的对话文本，最近 N 轮）
2. `Orchestrator` 注入 **`ConversationProvider`**（接缝，默认实现从 `ChatMemoryProvider` 取）
   —— ★ **不推给调用方**，避免"忘了传"（同 RunStateStore 收进 Orchestrator 的手法）
3. `Planner` / `Synthesizer` 提示词加 `{{conversation}}`；**`WorkerAgent` 不加**
4. `RunState` 存 `conversationText` —— 保证 `refine` / `resume` 时也看得到

### 成本核算
对话文本只进 Planner（每轮一次）+ Synthesizer（一次），**不进执行者** →
增长有界；而执行者是数量最多的调用（每子任务 × 每轮工具）→ **隔离把成本压住了**。

### 范围变 12 项（+1：会话历史接入）
**根因**：原清单只列了"长期记忆"，漏了"会话记忆" —— 而后者在 42 号矩阵里是 ✓ 已验证
（assistant-demo 用了 `SummarizingChatMemoryProvider` + Redis），**只是没接进新模块**。

## Lombok 化 + 修 3 个 Jackson 断点（用户要求"直接在 43 中改"）

用户指出 43 号大量手写 get/set 该用 Lombok。检查后发现**比 Lombok 严重得多的问题**：
"可暂停/可恢复"整条链路在运行期是断的，而编译全绿。

**三个断点（全部由 JacksonProbe2 探针实测抓出）**：
1. `Budget/RunState/TaskNode/Plan` 读方法是 record 风格（`runId()`）—— Jackson 不认：
   Budget 序列化直接抛 InvalidDefinitionException；RunState 序列化只剩 `{"lastDoneCount":0}`
2. `TaskNode.isDone()` / `TaskOutcome.isFailed()` 符合 Jackson is-getter 约定 →
   序列化多出 done/failed 字段 → 反序列化 UnrecognizedPropertyException
3. `RunEvent` 带 Instant，裸 mapper 缺 JavaTimeModule → InvalidDefinitionException

**修复**：
- 4 个 core 类 Lombok 化（@Getter/@Setter 标准命名）；调用点 ~60 处脚本批量替换，
  **编译兜底抓出 6 处误伤**（record 组件 `a.pending()`/`f.outcome()`/`p.pending()`、
  业务方法 `planner.plan()`、方法引用 `TaskNode::outcome` 没被正则匹配到）
- 两个 is-getter 加 @JsonIgnore（派生属性不序列化）
- **RedisRunStateStore 改专用 mapper**（显式注册 JavaTimeModule + 关 WRITE_DATES_AS_TIMESTAMPS），
  构造器去掉 ObjectMapper 参数 —— 跨请求恢复是独立序列化契约，不借用全局配置
- 框架 pom 加 jackson-datatype-jsr310（版本由 Boot parent 管）

**产物**：43/44 号代码块全部刷新（脚本拼装）；43 号加 0.5 节修订记录 + 14 节探针说明；
探针存 `docs/probes/JacksonProbe2.java`（与 SubGraphProbe 并列）

## Bug 修复：AiService 方法缺 @UserMessage（turn/synthesize 双杀）—— 已修并验证

**症状**（用户实测日志）：`IllegalConfigurationException: The method 'turn' does not have
a user message defined` + 同样的一句 for 'synthesize'。子任务失败、汇总降级。

**根因**：`WorkerAgent.turn` / `Synthesizer.synthesize` 的参数全是 `@V`，没有 `@UserMessage`。
对照组：`Planner.plan` 有 `@UserMessage String request` 所以正常。
★ 特点：**启动不报、构建代理不报，调用时才抛**。

**修法**：task → `@UserMessage("{{task}}")`（turn）；outcomes → `@UserMessage("{{outcomes}}")`（synthesize）。
写成 "{{xxx}}" 而非裸值：参数值要同时填 system 里的同名占位符。

**验证**：沙箱网络拦了 curl（`SERVER__PORT=65418` 环境变量 + 出站 AUTH 网关），
改用 JVM 内探针 `docs/probes/UserMessageProbe.java`（假端点 + 调一次方法 +
期望异常不是 IllegalConfigurationException）→ 两个方法均"过了配置校验" ★★★

**环境发现**：本沙箱 `SERVER__PORT` / `SERVER__HOST` 环境变量会覆盖 yml 的 server.port；
`HTTP_PROXY=127.0.0.1:65458` 会把 curl 拦成 AUTH_REQUIRED —— 以后在沙箱里验证 HTTP
端点要走 `--noproxy` 或直接 JVM 内探针，别被网络层的错干扰判断。
