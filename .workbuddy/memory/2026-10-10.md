## 目录结构分析（ai-common / ai-memory）—— 挖出两个真 bug

用户问「ai-common 和 ai-memory 的目录结构能怎么优化」。我读了两个模块全部 49 个源文件 +
装配清单 + 引用关系，结论写成 `docs/code-handouts/12-目录结构优化建议.md`。

**结论：结构本身没大毛病，但它掩盖了两个真 bug。先修 bug，别动 P2 风格问题。**

### 🔴 P0-1 `McpAutoConfiguration` 没进 `.imports` → MCP 整体失效

`ai-common` 有**三个** `@AutoConfiguration` 类，但 `.imports` 只列了两个：

```
com.best.ai_common.config.AiCommonAutoConfiguration
com.best.ai_common.metrics.TokenUsageDbAutoConfiguration
```

`mcp/McpAutoConfiguration`（条件 `@ConditionalOnProperty("ai.mcp.enabled")`）**不在清单里** →
**yml 里写 `ai.mcp.enabled: true` 也不生效**，因为那个类根本没被 Spring 读进来。
症状：注入 `McpToolProvider` 报 `NoSuchBeanDefinitionException`；用 `ObjectProvider` 兜着就静默没工具。

**根因是结构性的**：三个装配类散在 `config/` `metrics/` `mcp/` 三个包，`.imports` 就得跟着长，
而这个文件**纯文本、无编译检查**。

**修法**：抄 `ai-memory` 的模式 —— 1 个 `AiCommonAutoConfiguration` + 嵌套 static `@Configuration`
（`TokenUsageDbConfig` / `McpConfig`），`.imports` 从此永远 1 行。
⚠️ 陷阱：嵌套类失去类级 `after`，`@ConditionalOnBean(DataSource.class)` 会求值过早 →
必须给**外层**类加 `@AutoConfiguration(after = DataSourceAutoConfiguration.class)`。

### 🔴 P0-2 `StreamingChatModelRegister` 没挂 `TokenUsageListener` → 流式调用不计费

对比两个类：

| 类 | 构造器 | 挂 listener |
|---|---|---|
| `ChatModelRegister` | `(properties, serviceName, recorder)` | ✅ |
| `StreamingChatModelRegister` | `(properties)` | ❌ |

**而流式正是主场景**（`ChatStreamController` 走它）→ `ai_token_usage` 表里只有同步调用，
用户在页面聊天的 token 一条都不记。`OpenAiStreamingChatModel` 是支持 `.listeners(...)` 的
（04 里确认过），所以是漏了不是做不到。

**排查线索（值得养成习惯）**：同一个包里两个"平级"的实现，**形状不同就一定有漏**。

### P1（两处越界，5 分钟可改）

判据：**只被一个子包用，就住进那个子包。**
- `user/VectorCodec` → 只被 `user/db/FloatArrayTypeHandler` 用 → 下沉 `user/db/`
- `metrics/AiTokenUsageEntity` → 只被 `metrics/db/` 两个类用 → 下沉 `metrics/db/`
  （现状层级是反的：实体在父包、Mapper 在子包）

### P2（建议不动，共 6 条）

`AiUserContextInterceptor` 在 `config`（其实该在 `context/web`）、`memory_store`/`summary_store`
下划线命名、`session` 顶层混装契约与实现细节、`user` 顶层 9 个类、`McpProperties` 在 `properties`、
两类 Store 命名不对称。

**不动的理由**：包名是内部实现细节（使用方只 import 几个类）；只有一个使用者，
按既定纪律"先跑通再抽象"；且改包名有**三处字符串引用不会自动改**
（`@MapperScan` 注解值、mapper XML 的 `namespace` / `typeHandler` / `type`、
`resources/mapper/` 下镜像包名的目录）。

### 一个观察：两模块的包组织原则不同

- `ai-common` 按**技术角色**（properties / register / context / metrics）
- `ai-memory` 按**业务能力**（session / user）

不一定是问题（产出不同），但 `ai-common/mcp/` 是唯一按功能分包的地方，而它的 `McpProperties`
又回到 `properties/` —— **原则一旦有例外就说明它在这里不够用**。
彻底改法建议把 ai-common 改成 `config / model / metrics / mcp / context` 五包，
但**不建议现在做**（`properties` 与 `register` 分开有实际好处：配置定义 vs 实例工厂是两件事）。

### 🔴 P0-5（本轮最重要）流式调用的 token 台账，`user_id` 必然是 `anonymous`

`TokenUsageListener.onResponse` 用 `AiUserContext.get()`（ThreadLocal）取用户。而：

| 场景 | `onResponse` 在哪个线程 | 读得到吗 |
|---|---|---|
| 同步（`ask()`） | **调用线程** | ✅ |
| **流式（`TokenStream`，主场景）** | **模型自己的 I/O 线程**（OkHttp 回调线程） | ❌ 必为 null |

**决定性是"线程不同"，不是 `afterCompletion` 的时机** —— 即使 ThreadLocal 没清，
流式回调在 OkHttp 线程上执行也读不到。

**这个坑只在修好上一轮 P0-2（给流式挂 listener）之后才暴露**；而且如果先测**同步**调用，
台账 `user_id` 是对的，会误以为计量没问题。

**修法（推荐）**：删掉那句 `AiUserContext.get()`，`user_id` 一致写 anonymous，
在注释里写明"流式下 ThreadLocal 不可达，用户维度请查网关"。
**理由：一致地缺失好过随机地正确** —— 混合数据比全缺更糟，因为不知道该信哪些行。
（选项 A：`customHeaders` 带头让网关记；选项 C「给 ChatModel 套装饰器」**不可行**，
listener 回调在别的线程，任何 ThreadLocal 都传不过去，`ChatRequest` 也没有 attributes 通道。）

**顺带**：`AiUserContext.wrap/open` 是**死代码**（全项目零调用者）——说明作者想过跨线程问题，
但它只对"从当前线程 fork 的任务"有效，**救不了模型 I/O 线程**。

### ★ P0-5 的结论被推翻 —— 不需要网关，也不需要包装类

反编译本机 `langchain4j-core-1.20.0.jar` + `langchain4j-open-ai-1.20.0-sources.jar`，
拿到三条硬证据：

1. **`StreamingChatModel.chat(ChatRequest, handler)` 是接口的 default 方法**，字节码（`javap -c`）：
   ```
   53: new java/util/concurrent/ConcurrentHashMap      ← 创建 attributes
   67: new StreamingChatModel$1                        ← 包装 handler，传入 attributes
   96: invokestatic ChatModelListenerUtils.onRequest(...)  ← ★ 先触发 onRequest
   104: invokeinterface doChat(...)                    ← 再发起异步 HTTP
   ```
   → **onRequest 在【调用线程】执行**（业务调 `TokenStream.start()` 那一行），
   而 onResponse 的 HTTP 回调在**模型 I/O 线程**。
   → `OpenAiStreamingChatModel.doChat()` 里**完全不含 listener 触发**（grep 不到），
   全由接口 default 方法触发 —— **是框架保证，不是 provider 实现细节**。

2. `attributes` 是 `new ConcurrentHashMap<>(options.listenerAttributes())`，**跨线程安全**，
   同一实例在 onRequest/onResponse/onError 间传递。

3. **`OpenAiStreamingChatModel` 第 197 行已自动带 `.streamOptions(StreamOptions.builder().includeUsage(true).build())`**
   —— **1.20 已自动请求 usage**，修正了 04 号文档"流式需手动带 stream_options"的说法。

**正解**：`TokenUsageListener` 补 `onRequest`（在调用线程快照 userId 进 attributes），
`onResponse` 从 attributes 取。**1 个文件、~15 行，同时修好同步与流式两条路径。**

「包装 `StreamingChatModel`」也能 work（userId 闭包进匿名 handler），但要多写两个类
（`ChatModel` + `StreamingChatModel` 各一）并转发 6-7 个方法，**不划算**，已排除。

> 又踩一次 macOS BSD grep 的坑：BRE 不支持 `\|`，必须 `grep -E`。

### ✅ 用户改对的三处（其中一处是我漏的 bug）

**① `TokenUsageListener.onRequest` 的 null 兜底 —— 我漏掉的真 bug。**

```java

attributes.put(ATTR_USER_ID, userId == null || userId.isBlank() ? ANONYMOUS : userId);
```

**`attributes` 是 `ConcurrentHashMap`，不允许 null value，`put(k, null)` 抛 NPE。**
而这次调用发生在**框架的 `StreamingChatModel.chat()` 里**（字节码第 96 行

**② `UserMemoryRecorder.recordAsync` 用 `AiUserContext.open(userId)` 包异步任务。**

```java
taskExecutor.execute(() -> {
    try (AiUserContext.Scope ignored = AiUserContext.open(key.userId())) {

    } catch (Exception e) { ... }
});
```

**修正我第三轮的判断**：`AiUserContext.wrap/open` 不是纯粹的死代码 ——

## 鉴权边界的讨论 → `19-鉴权边界与userId可信性.md`，用户决定【暂缓】

用户提出"后期必须登录才能访问，是不是就不会有 anonymous 的问题了"。
**部分成立，但漏了要紧的一层**：

| # | 问题 | 「必须登录」能解决吗 |
|---|---|---|
| 1 | 未登录能访问 → anonymous → 互串记忆 | ✅ 能（前提：所有流量必经网关） |
| 2 | **登录后伪造 `X-User-Id` → 越权读他人记忆** | ❌ **不能** |

**问题 2 的答案在网关侧**：`X-User-Id` 是**覆写**（从 token 解析后覆盖）还是**透传**？
- 覆写 → 客户端伪造无效 ✓
- 透传 → 登录了也能读别人记忆，且**加 401 检查无用**（userId 看着合法）

**自测方法**（不必等网关）：带自己 token + 伪造 `X-User-Id: not-my-id` 打一次请求，查
`SELECT DISTINCT user_id FROM ai_token_usage ORDER BY id DESC LIMIT 5` ——
出现 `not-my-id` 就是透传。用台账查是因为它**每次都写**，比记忆快。

**风险窗口的代价**（回答"暂缓行不行"）：会话记忆串了**可逆**（Redis TTL 48h）；
**长期记忆串了不可逆** —— 永久保存且**事后无法区分归属**（脏数据和正常数据长得一样），
只能整条删让用户重说，而"发现异常"靠用户抱怨。

### 📌 用户的决定：暂缓，接真实鉴权时再说

**合理**（现在没有真实用户数据）。但我建议调整**形态**：不要让"暂缓"变成"代码里没有这个概念"，
否则它从"待办"变成"遗忘"。推荐的最小方案（19 号 §8）：

**不改拦截逻辑，加一个 `MemoryGuardStartupCheck`**（`@PostConstruct` 打一段 warn），
把待办放进**每次启动的日志**里 —— 20 行，不影响任何请求，也不阻塞本地开发。

**触发条件**：① 第一个真实用户接入之前；② 给团队外部的人访问之前；③ 内网开放访问之前。
判据：**除了你之外的人的数据有没有进过那两张表**。

**处理顺序不能反**：① 先确认网关覆写还是透传 → ② 再打开 `ai.memory.require-user-id`
→ ③ 删掉启动检查类。**反了的话**：require-user-id 只拦住没带头的请求，带伪造头的照样通过，
你会以为已处理但实际没有。

## 📌 用户提出的具体痛点：每建一个服务就复制一份 yml

产出 `docs/code-handouts/22-配置分层与共享实施.md`。

### 现状量化：62 / 64
`assistant-demo/application.yml` 共 **64 行**，**只有 2 行是服务私有的**
（`server.port` + `spring.application.name`），其余 **62 行 97% 会被原样复制**。

### 方案：模块自带 defaults + 服务侧 `spring.config.import`
```
ai-common/src/main/resources/ai-common-defaults.yml   ← 新建（模型/工具/web/datasource+redis 本地默认值）
ai-memory/src/main/resources/ai-memory-defaults.yml   ← 新建（ai.memory.*）
assistant-demo/src/main/resources/application.yml     ← 64 行 → ~15 行
```
服务侧只留 `server.port` + `spring.application.name` + `spring.config.import` 两行。

**为什么分两份 defaults 而不是一份**：谁的能力谁的默认值；ai-memory 独立部署时跟着走；
import 顺序决定优先级（后 import 的胜出，更具体的模块放后面）。

**新建服务的模板 = 复制 8 行，改 2 个值（port / name）。**

### ⭐ 三个关键论点
1. **用结构代替约定** —— 文件位置本身就固化分层（`xxx-defaults.yml` = 平台级，
   `application.yml` = 服务级），写错位置会立刻表现为"这个值没生效"，不靠纪律维持。
2. **不要靠"jar 里放 `application.yml`"** —— Spring Boot 确实会加载 classpath（含 jar）上的
   `application.yml`，但**优先级取决于 classpath 扫描顺序、不可控**；官方也不建议 starter 这么做。
   **用 `spring.config.import` 显式引入**，顺序确定、可被覆盖。
3. **它是通往 Nacos 的同一条路** —— 将来只把 `classpath:` 改成 `optional:nacos:` 一个字符串，
   服务侧其他一行都不用改。（静态 import 还有个 Nacos 没有的优点：**配置与代码版本绑定**，
   不会出现"代码新版、配置旧版"的错配。）

### 优先级（**行为性知识，必须实测一次再信**）
被 import 的配置**优先级低于**声明它的文件 → 平台级 = 默认值，服务级 = 覆盖。
多个 import 之间后声明的胜出。
```
ai-common-defaults.yml < ai-memory-defaults.yml < application.yml < application-{profile}.yml < 环境变量
```
验证法：在 application.yml 写 `ai.memory.user.min-score: 0.99`，确认记忆检索不到（覆盖生效）。

### 四个坑
1. **【安全】共享配置会被分发到每个服务 → 明文凭据绝不能进去。**
   现在 `ai.mcp.servers.mcp_gateway.headers.Authorization` 是**明文 token**
   （而 `ai.chat`/`ai.embed` 用占位符，同一文件两种做法不一致）→ 搬进 defaults 时必须改成
   `${MCP_GATEWAY_TOKEN}`。**⚠️ 且建议轮换那个已写进文件的 token**（项目还不是 git 仓库，
   没有历史包袱，是好时机）。通用纪律：**共享配置里的每一项都按"会被复制到 N 个地方"对待。**
2. **连接串严格说是"环境级"不是"平台级"** —— 但长期记忆必须跨助手共享同一份 schema，
   所以**同一环境内必须一致**。本地放 defaults 当默认值，**生产必须由环境变量/profile 覆盖**。
3. **不要放 `application.yml`**（见上）。文件名也别叫 `application-*.yml`（会被当 profile 配置）。
4. **import 不带 `optional:`** —— 平台配置缺失应**明确失败**而非静默缺配置。
   （接 Nacos 时反过来用 `optional:nacos:` —— 配置中心暂时不可用不该阻止启动。
   这个差别本身就说明静态配置与动态配置的定位不同。）

### 何时换 Nacos（不是现在）
信号：要"改配置不重启" / 服务数 5+ / 多环境统一管理 / 需要变更审计。
现在静态 import 已解决 97%，且**配置与代码版本绑定**是它的优点。

## 🔍 用户问：向量部分为什么不用 LangChain4j 的 `EmbeddingStore`？

产出 `docs/code-handouts/23-向量检索选型-为什么不用EmbeddingStore.md`。
这正好命中项目纪律第 1 条（自己写组件前必须回答"为什么不用现成的"）——
03 号文档里只顺带提过一句，不够正式，这次补上。

### 先厘清（重要，避免误伤）
"不用 LangChain4j 的向量 API"这个说法**不准确**。实际：
- **用了** `EmbeddingModel`（向量化）、**用了** `ContentRetriever`（`UserMemoryContentRetriever implements` 它）、
  **用了** MyBatis-Plus（持久化）
- **没用** `EmbeddingStore` + `EmbeddingStoreContentRetriever`

→ 问题精确化为："要不要把**向量存储 + 相似度检索**这一小段**换成 `EmbeddingStore`"。
**我们不反对用框架抽象，只是这一个的前提不成立。**

### 实测事实
- `EmbeddingStore<Embedded>`：`add` / `removeAll(Filter)` / `search(EmbeddingSearchRequest)`，
  后者支持 `maxResults` / `minScore` / `filter`（metadata 比较器齐全）
- **`InMemoryEmbeddingStore` 在【主包 `langchain4j`】里，不是 core**；
  **无索引结构、检索是线性扫描**（javap 验证：类中无 ANN 字段 + `search` 字节码里有余弦调用）。
  它支持 `serializeToJson()` / `fromJson()` → 理论上能持久化
- `EmbeddingStoreContentRetriever`（在 **core**）：`maxResults` / `minScore` / `dynamicFilter` 都有
- ⚠️ **本机 `~/.m2` 有 `langchain4j-pgvector-1.20.0-beta30`（2026-09-09 下载），
  但本项目从未引用** —— 是别的项目/探索留下的，别误会项目在用 pgvector

### 四条理由（按强度）
1. **【最硬】`EmbeddingStore` 不带业务过滤，候选集是全库。**
   `InMemoryEmbeddingStore` 的过滤和相似度计算在**同一次线性扫描**内，没有索引先缩小集合。
   我们的 SQL `where user_id = ?` **在算余弦之前**就把候选集降到单用户量级（≤500 条，恒定）。
   **数据库的 WHERE 替我们承担了"向量库索引"的职责** —— 这不是实现细节，是复杂度量级差异。
2. **`UserMemoryStore` 的 5 个操作里 4 个对不上**：只有 `insert`↔`add` 能对应；
   `findByUserId`（需 query 向量）/ `countByUserId` / `deleteOldest` / `deleteAll` 都没有。
   根因：**`EmbeddingStore` 是索引，我们的表同时是权威源** → 换它 = 双写（一致性成本）。
3. **两条业务规则表达不了**：① 时间倒序重排（一期不做 UPDATE/DELETE，冲突事实只能靠时间定序，
   相关度排序解决不了"住奥斯汀 vs 搬到西雅图"）；② 维度不一致**跳过**而非抛异常
   （`InMemoryEmbeddingStore` 会直接抛 → 一条脏数据让该用户所有检索全失败，**行为差异不是风格差异**）。
4. **外部向量库的代价换不来收益**：pgvector 要换掉 MySQL；Milvus/Qdrant/Chroma 要新中间件。
   收益是 ANN 索引，价值在**百万级向量**，我们在 500 条里找 top-5 —— 线性扫描是微秒级。

### 诚实的成本清单
自己写的只有两处：`CosineSimilarity`（~20 行）+ `MemoryRecallService.recall()` 的编排（~30 行）。
准确说法：**在一个 50 行的地方没用框架抽象，因为那个抽象解决的是"持有一批向量"，而我们不需要"持有"。**

### 触发条件（出现任一才重新评估）
单用户事实数 > 2000 / 需要**跨用户检索** / **已经因为知识库上了向量库**（最实际）。

### 最小切换路径
`UserMemoryStore` 是自定义接口，`MemoryRecallService` 和 `UserMemoryRecorder` 只依赖它
→ **换实现即可，上层一行不改**。推荐"只换存储实现"（保留时间定序与维度校验），
而不是连检索一起换（那要引入 `UserMemory` → `TextSegment` 的映射层）。

| 长期记忆·写 | `writeMemory` 节点（图出口） | ✅ 共享 —— 同一个 `UserMemoryRecorder` |
| 人在回路 | `approvalGate` 之前 | 新增，底座不涉及 |

## 追加：supervisor 路由改用枚举（用户建议，已落地）

用户说"supervisor 可以返回枚举类型，更准确"。核实后**成立，已改** ——
改动集中在 `SupervisorAgent`（加嵌套枚举 `Routing` + 换返回类型）和 `SupervisorNode`
（删掉脆弱的 `normalize()`，改成穷尽 switch 的 `edgeKeyOf()`）。

### 三条核实到的事实
| 结论 | 证据 |
|---|---|
| LangChain4j 原生支持枚举返回 | `DefaultOutputParserFactory.get()`：`if (rawClass.isEnum()) → EnumOutputParser` |
| `@Description` 会进提示词 | `EnumOutputParser.formatInstructions()` 输出常量名 + 描述；`Description` retention=**RUNTIME**（`javap -v` 确认） |
| **不引入网关风险** | `DefaultAiServices.supportsJsonSchema()` 看 `chatModel.supportedCapabilities()`；`OpenAiChatModel` 默认**空集** → 走提示词路径，请求体里没有 `response_format` |

### 枚举消掉的那个隐患（比"更准确"更具体）
原实现 `Set.of("expertA","expertB","FINISH") + raw.contains(candidate)`：
模型一次提到多个候选时（"可以先看 expertB，需要清理再走 expertA"），
命中哪个由 **`Set.of` 的遍历顺序**决定，而不是语义 —— 同一句回答可能被判成不同路由，
而且没有任何日志能解释。枚举让模型只能交一个值，答不出就是显式异常。

### 边界：枚举**不进** state
`addConditionalEdges(String, AsyncEdgeAction<S>, Map<String,String>)` 的映射表 key 被框架固定为 String，
且 state 要序列化进 Redis。所以 `state.next` 保持 String，枚举只活在
